# V3.19.S8: Policy Detail View (POLICY Function)

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V3.19: Tickoni Native Investment Terminal
**Labels:** `type/story`, `area/investing`

Render the POLICY function panel: the full policy check table with observed vs limit vs result, rejection reasons, and evidence references.

## Product Outcome

Operators can understand exactly why an investment decision was allowed or denied by inspecting every individual policy check, its observed value, the applicable limit, and the outcome — all within the POLICY function panel.

## User Story

As an investment user, I want to see every policy check that ran for a decision, with what was measured, what the limit is, and what the outcome was, so that I can understand the reason for the decision without reading raw policy code.

## Scope

- In scope: compact policy check table with rows for asset_class, market, venue, sector, instrument_denylist, notional_limit, daily_notional_limit, single_name_concentration, holding_period, round_trip, approval_required — each showing observed value, limit value, and result (PASS / FAIL / WAIVED); rejection reasons section (empty when all checks pass); evidence references (evidence ref, catalog version, taxonomy version) when available; `/show policy` command activating the POLICY function from another panel; color coding per row (green = PASS, red = FAIL, amber = WAIVED); single scrollable table, no expandable trees or nested sections; policy version and outcome visible in header.
- Out of scope: changing policy rules, adding new policy checks, recomputing policy outcomes in the UI, capability catalog administration, or modifying the tkpoly runtime decision logic.

## Preconditions And Assumptions

- Policy data comes from governed `tk_api` response fields or deterministic fixtures.
- The POLICY function panel renders inside the terminal shell from S1.
- Policy outcomes are display-only; the UI does not recompute or override tkpoly decisions.
- The POLICY panel is a deep-dive view. S2 (CASE workbench) shows a summary of the policy decision inline.

## Acceptance Criteria

- [ ] Given the USD 2,000 investment fixture, when the POLICY function renders, then the full policy check table shows each check with observed value, limit value, and result.
- [ ] Given a restricted instrument fixture, when the POLICY function renders, then the failing check (instrument_denylist) is shown in red with the exact reason, and the rejection reasons section is visible.
- [ ] Given an oversize notional fixture, when the POLICY function renders, then the failing check (notional_limit or per_order_notional) is shown in red with the observed value exceeding the limit.
- [ ] Given the `/show policy` command, when submitted, then the POLICY function is activated and scrolls into focus from another panel.

## Notes And Open Questions

- Should the policy check table show all checks for every case, or only the checks that are relevant to the current workflow (e.g., skip venue checks for non-trading workflows)?
- Are hash values displayed in full or truncated with a detail expand? (Truncated with expand is more terminal-appropriate for density.)
- Should the rejection reasons section be collapsible or always visible? (Always visible is more terminal-appropriate for audit transparency.)
