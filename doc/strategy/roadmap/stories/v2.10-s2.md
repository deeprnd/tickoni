# V2.10.S2: Build.zig module registry and walk-based discovery

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.10: Build System Consolidation And Qt Build Validation
**Labels:** `type/story`, `area/platform`

Refactor `build.zig` from its current ~1,766 lines into a <500-line declarative
build script with a module registry, walk-based test discovery, and utility
functions for import resolution and link helper application. No manual copy/paste
of per-file `b.createModule` + `b.addTest` blocks — a single registration loop
handles the pattern.

## Product Outcome

Developers can add a new Zig test file without touching `build.zig` (except for
the optional module registry entry). Adding a test file drops from 20+ lines of
manual boilerplate to a zero-line change if the file falls under a declared
discovery path. This removes a structural barrier to community contribution.

## User Story

As a developer adding a new Zig module with `test {}` blocks, I want
`build.zig` to auto-discover and register it, so that I don't need to read
existing entries, copy boilerplate, and carefully set imports and link helpers
for each of the three test lanes.

## Scope

- In scope: create a module registry at the top of `build.zig` declaring
  ~15–20 named modules (name → path + imports).
- In scope: implement a walk function that iterates over `src/tickoni/` paths
  with configurable include/exclude glob patterns, sorted alphabetically for
  determinism.
- in scope: implement import resolution from the module registry based on the
  file's containing directory.
- In scope: implement link helper application by path convention
  (e.g., `c_abi/*` → `linkTickoniCodec`, `tiles/*/mod.zig` importing c_abi →
  `linkTickoniFiredancer`).
- In scope: refactor the unit/cov test registration into a single walk loop;
  the cov lane reuses unit test artifacts with `installArtifact` instead of
  `runArtifact`.
- In scope: refactor the integration test lane into a separate walk loop that
  creates fresh module instances per lane.
- In scope: preserve `addPlainTestRun` for process-mode tests.
- In scope: preserve existing link helper functions unchanged.
- In scope: all existing tests (unit, integration, cov) pass after the refactor.
- Out of scope: changes to CI pipeline structure (`.github/workflows/`).
- Out of scope: changes to Firedancer C shim files or build.
- Out of scope: build-time caching or incremental build optimization.

## Preconditions And Assumptions

- The current `build.zig` at ~1,766 lines has ~1,400 lines (80%) of copy/paste

- The link helper functions (`linkTickoniCodec`, `linkTickoniFiredancer`,

## Post-Incident Recap: Duplicate ballet.c Symbols

**Date:** 2026-08-19
**Commit:** 2cef9972a — `build.zig: deduplicate ballet.c in test binaries via
dedicated investment_demo_test_mod`
**Symptom:** `zig build` system-test binaries (e.g. `portfolio_cash_demo_test`)
failed with 23 duplicate symbol errors from `ballet.o`.

**Root cause:** `investment_demo_mod` was both (a) the shared dependency imported
by system test binaries and (b) the root module for `investment_demo_test` in the
unit test lane. `linkTickoniCodec(b, investment_demo_test, fd_lib_dir)` added
`ballet.c` to `investment_demo_test.root_module` which IS `investment_demo_mod`.
`linkTickoniCodec(b, portfolio_cash_demo_test, fd_lib_dir)` also added `ballet.c`
to `portfolio_cash_demo_test.root_module`. When Zig compiled
`portfolio_cash_demo_test`, it compiled both the root module AND
`investment_demo_mod` as a dependency — both carried `ballet.c` → 23 duplicate
symbols.

**Resolution:** Created a dedicated `investment_demo_test_mod` (mirroring the
existing `model_test` pattern at line 1177 of `build.zig`) so that
`linkTickoniCodec` adds `ballet.c` only to the unit test's root module, not the
shared dependency module. System test binaries get their own `linkTickoniCodec`
calls on their root modules — no change to `investment_demo_mod`.

## Prevention Recommendations

**R1: Dedicated root modules per test lane — never share a module as both a root
test module and an imported dependency.**
Create separate `*_test_mod` instances for each test lane (unit, system, cov).
The module registry should distinguish "shared library module" from "test root
module". When `linkTickoniCodec`, `linkTickoniFiredancer`, or similar helpers
add C sources to a module, those C sources must not leak into dependency
compilation. Pattern:

```zig
// shared — no C sources, used as dependency by system tests
const investment_demo_mod = b.addModule("investment_demo", .{ .root_source = ... });

// unit test lane — dedicated root with C sources
const investment_demo_test_mod = b.addModule("investment_demo_test", .{
    .root_source = b.path("src/tickoni/test/integration/investment_demo.zig"),
    .imports = &.{ investment_demo_mod },
});
linkTickoniCodec(b, investment_demo_test_mod, fd_lib_dir);

// system test lane — its own root, imports investment_demo_mod
portfolio_cash_demo_test_mod = b.addModule(...);
portfolio_cash_demo_test_mod.addImport("investment_demo", investment_demo_mod);
linkTickoniCodec(b, portfolio_cash_demo_test_mod, fd_lib_dir);
```

**R2: Assert C source uniqueness before finalizing build steps — catch duplicates
at build-script time, not link time.**
After calling `linkTickoniCodec` or any helper that adds C sources, iterate the
module's C sources and assert no duplicate source file paths. A comptime check
in `linkTickoniCodec` or a post-walk assertion would convert 23 linker errors
into a clear build-script error with the offending file listed:

```zig
// In linkTickoniCodec or post-walk:
var seen = std.AutoHashMapOwned([]const u8).init(b.allocator);
errdefer seen.deinit();
for (step.root_module.c_sources.items) |cs| {
    const path = cs.files[0];
    try seen.put(path);
}
// If seen.count differs from c_sources.len, we have a duplicate.
```

**R3: Module registry entries must declare their role — shared, test_root, or
both.**
The module registry should carry a `role` field: `shared` (imported by others,
never a test root), `test_root` (root of a test binary, owns C sources), or
`both` (deprecated — should be split into separate instances). This makes the
intent explicit and prevents the shared-module-as-root-module anti-pattern at
registration time:

```zig
const ModuleRole = enum { shared, test_root };

const ModuleEntry = struct {
    name: []const u8,
    path: []const u8,
    imports: []const []const u8,
    role: ModuleRole,
    link_helper: ?*const fn (*std.Build, *std.Build.Step.Compile, []const u8) void = null,
};
```

A walk-based builder that uses the module registry (the goal of this story) can
enforce that no `shared` role module has a `link_helper`, and that each
`test_root` role has exactly one `link_helper` call.

- Module registry format: `{ "name", .{ .path = ..., .imports = ... } }` vs
  inline `addModule` calls. Spike the more readable option.
- Import resolution: per-directory nearest-module lookup vs per-file override
  map. Spike based on how many files need overrides.
- Link helper inference: path-based convention vs explicit metadata on module
  declarations. Spike for correctness guarantees.
- Cov lane: reuse unit artifacts with `installArtifact` wrapper or separate
  walk. Spike for build efficiency.
