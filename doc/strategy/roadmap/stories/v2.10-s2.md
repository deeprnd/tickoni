# V2.10.S2: Build.zig module registry and walk-based discovery

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.10: Build System Consolidation And Qt Build Validation
**Labels:** `type/story`, `area/platform`

Refactor `build.zig` from its current ~1,766 lines into a <500-line declarative
build script with a module registry, walk-based test discovery, and utility
functions for import resolution and link helper application. No manual copy/paste
of per-file `b.createModule` + `b.addTest` blocks — a single registration loop
handles the pattern.

## Product Outcome

Developers can add a new Zig test file without touching `build.zig` (except for
the optional module registry entry). Adding a test file drops from 20+ lines of
manual boilerplate to a zero-line change if the file falls under a declared
discovery path. This removes a structural barrier to community contribution.

## User Story

As a developer adding a new Zig module with `test {}` blocks, I want
`build.zig` to auto-discover and register it, so that I don't need to read
existing entries, copy boilerplate, and carefully set imports and link helpers
for each of the three test lanes.

## Scope

- In scope: create a module registry at the top of `build.zig` declaring
  ~15–20 named modules (name → path + imports).
- In scope: implement a walk function that iterates over `src/tickoni/` paths
  with configurable include/exclude glob patterns, sorted alphabetically for
  determinism.
- in scope: implement import resolution from the module registry based on the
  file's containing directory.
- In scope: implement link helper application by path convention
  (e.g., `c_abi/*` → `linkTickoniCodec`, `tiles/*/mod.zig` importing c_abi →
  `linkTickoniFiredancer`).
- In scope: refactor the unit/cov test registration into a single walk loop;
  the cov lane reuses unit test artifacts with `installArtifact` instead of
  `runArtifact`.
- In scope: refactor the integration test lane into a separate walk loop that
  creates fresh module instances per lane.
- In scope: preserve `addPlainTestRun` for process-mode tests.
- In scope: preserve existing link helper functions unchanged.
- In scope: all existing tests (unit, integration, cov) pass after the refactor.
- Out of scope: changes to CI pipeline structure (`.github/workflows/`).
- Out of scope: changes to Firedancer C shim files or build.
- Out of scope: build-time caching or incremental build optimization.

## Post-Incident Recap: Duplicate ballet.c Symbols

**Date:** 2026-08-19
**Commit:** 2cef9972a — `build.zig: deduplicate ballet.c in test binaries via
dedicated investment_demo_test_mod`
**Symptom:** `zig build` system-test binaries (e.g. `portfolio_cash_demo_test`)
failed with 23 duplicate symbol errors from `ballet.o`.

**Root cause:** `investment_demo_mod` was both (a) the shared dependency imported
by system test binaries and (b) the root module for `investment_demo_test` in the
unit test lane. `linkTickoniCodec(b, investment_demo_test, fd_lib_dir)` added
`ballet.c` to `investment_demo_test.root_module` which IS `investment_demo_mod`.
`linkTickoniCodec(b, portfolio_cash_demo_test, fd_lib_dir)` also added `ballet.c`
to `portfolio_cash_demo_test.root_module`. When Zig compiled
`portfolio_cash_demo_test`, it compiled both the root module AND
`investment_demo_mod` as a dependency — both carried `ballet.c` → 23 duplicate
symbols.

**Resolution:** Created a dedicated `investment_demo_test_mod` (mirroring the
existing `model_test` pattern at line 1177 of `build.zig`) so that
`linkTickoniCodec` adds `ballet.c` only to the unit test's root module, not the
shared dependency module. System test binaries get their own `linkTickoniCodec`
calls on their root modules — no change to `investment_demo_mod`.

## Prevention Recommendations

**R1: Dedicated root modules per test lane — never share a module as both a root
test module and an imported dependency.**
Create separate `*_test_mod` instances for each test lane (unit, system, cov).
The module registry should distinguish "shared library module" from "test root
module". When `linkTickoniCodec`, `linkTickoniFiredancer`, or similar helpers
add C sources to a module, those C sources must not leak into dependency
compilation. Pattern:

```zig
// shared — no C sources, used as dependency by system tests
const investment_demo_mod = b.addModule("investment_demo", .{ .root_source = ... });

// unit test lane — dedicated root with C sources
const investment_demo_test_mod = b.addModule("investment_demo_test", .{
    .root_source = b.path("src/tickoni/test/integration/investment_demo.zig"),
    .imports = &.{ investment_demo_mod },
});
linkTickoniCodec(b, investment_demo_test_mod, fd_lib_dir);

// system test lane — its own root, imports investment_demo_mod
portfolio_cash_demo_test_mod = b.addModule(...);
portfolio_cash_demo_test_mod.addImport("investment_demo", investment_demo_mod);
linkTickoniCodec(b, portfolio_cash_demo_test_mod, fd_lib_dir);
```

**R2: Assert C source uniqueness before finalizing build steps — catch duplicates
at build-script time, not link time.**
After calling `linkTickoniCodec` or any helper that adds C sources, iterate the
module's C sources and assert no duplicate source file paths. A comptime check
in `linkTickoniCodec` or a post-walk assertion would convert 23 linker errors
into a clear build-script error with the offending file listed:

```zig
// In linkTickoniCodec or post-walk:
var seen = std.AutoHashMapOwned([]const u8).init(b.allocator);
errdefer seen.deinit();
for (step.root_module.c_sources.items) |cs| {
    const path = cs.files[0];
    try seen.put(path);
}
// If seen.count differs from c_sources.len, we have a duplicate.
```

**R3: Module registry entries must declare their role — shared, test_root, or
both.**
The module registry should carry a `role` field: `shared` (imported by others,
never a test root), `test_root` (root of a test binary, owns C sources), or
`both` (deprecated — should be split into separate instances). This makes the
intent explicit and prevents the shared-module-as-root-module anti-pattern at
registration time:

```zig
const ModuleRole = enum { shared, test_root };

const ModuleEntry = struct {
    name: []const u8,
    path: []const u8,
    imports: []const []const u8,
    role: ModuleRole,
    link_helper: ?*const fn (*std.Build, *std.Build.Step.Compile, []const u8) void = null,
};
```

A walk-based builder that uses the module registry (the goal of this story) can
enforce that no `shared` role module has a `link_helper`, and that each
`test_root` role has exactly one `link_helper` call.

- Module registry format: `{ "name", .{ .path = ..., .imports = ... } }` vs
  inline `addModule` calls. Spike the more readable option.
- Import resolution: per-directory nearest-module lookup vs per-file override
  map. Spike based on how many files need overrides.
- Link helper inference: path-based convention vs explicit metadata on module
  declarations. Spike for correctness guarantees.
- Cov lane: reuse unit artifacts with `installArtifact` wrapper or separate
  walk. Spike for build efficiency.

## Zig 0.17 std.Build — Full Analysis for v2.10-S2

### Old (0.16) vs New (0.17) Architecture

**Before (single file, ~15,000+ lines):**
  std/build.zig        ← one massive file with Build, Step, Module all in it

**After (multi-file module):**
  std/Build.zig        ← entry point (re-exports from subdirectory)
  std/Build/
    Configuration.zig  ← 115 KB — serialized build config, step graph,
                         string table, path deps, lazy paths, system libs
    Cache.zig          ← 62 KB — build caching, manifest, hash pipeline
    Serialize.zig      ← 72 KB — build graph serialization for web UI / caching
    Module.zig         ← 21 KB — module creation, imports, C sources, link objects
    Step.zig           ← 5 KB — step base type, registry
    abi.zig            ← 18 KB — WebSocket protocol for web UI, fuzzer interface
    Step/
      Compile.zig      ← 28 KB — full compilation step
      Run.zig          ← 29 KB — subprocess execution step
      Options.zig      ← 15 KB — runtime options generation
      TranslateC.zig   ← 7 KB — .c to .zig translation
      InstallArtifact.zig, InstallDir.zig, InstallFile.zig
      ConfigHeader.zig, Fmt.zig, FindProgram.zig, CheckFile.zig
      Fail.zig, ObjCopy.zig, UpdateSourceFiles.zig, WriteFile.zig
    Cache/
      DepTokenizer.zig ← 38 KB — dependency tokenization for caching

This is roughly 360 KB of structured source code vs the old single file.

### Key Changes Relevant to Our Build.zig Refactoring

#### 1. Module Creation — addModule vs createModule

**0.16:** Two separate functions on `*std.Build`:
  // Separate public (importable by other packages) and private modules
  pub fn addModule(build: *Build, name: [:0]const u8, options: Module.CreateOptions) *Module
  fn createModule(build: *Build, options: Module.CreateOptions) *Module

**0.17:** Same two functions exist, but the Module type is now under `std.Build.Module`:
  // 0.17
  const Module = std.Build.Module;
  const m = b.addModule("my_module", .{ .root_source_file = b.path("src/main.zig") });

The API is compatible-ish but the internals changed — `createModule` at line 294 of
`Module.zig` now uses `graph.arena.create(Module)` instead of the old allocator pattern.

#### 2. LazyPath — New `dupe()` method

**0.17** adds `dupe(graph: *const Graph)` and `dupeList()` methods to `LazyPath` throughout
`Module.zig` for graph-copying. The `dupe` pattern propagates paths through the build
graph arena.

#### 3. Step/Compile — `expect_errors` Enhanced

New `ExpectedCompileErrors` union in `Step/Compile.zig` line 253:
  pub const ExpectedCompileErrors = union(enum) {
    contains: []const u8,
    exact: []const []const u8,
    starts_with: []const u8,
    stderr_contains: []const u8,
  };
Allows declaring "this compile step should fail with these errors" — useful for
testing error handling.

#### 4. Step/Compile — Generated Output Flags

**0.17** adds granular control over what artifacts to generate:
  emit_directory:       Configuration.OptionalGeneratedFileIndex
  generated_docs:       Configuration.OptionalGeneratedFileIndex
  generated_asm:        Configuration.OptionalGeneratedFileIndex
  generated_bin:        Configuration.OptionalGeneratedFileIndex
  generated_h:          Configuration.OptionalGeneratedFileIndex
  generated_implib:     Configuration.OptionalGeneratedFileIndex
  generated_llvm_bc:    Configuration.OptionalGeneratedFileIndex
  generated_llvm_ir:    Configuration.OptionalGeneratedFileIndex

Previously you just got `zig-out/bin/` artifacts. Now you can request headers, docs,
assembly, etc.

#### 5. Step/Compile — Build ID, LTO, Debug Compression

  build_id:        ?std.zig.BuildId          ← .fast, .uuid, .sha1, .md5, .hexstring
  lto:             ?std.zig.LtoMode          ← new in 0.17
  compress_debug_sections:                   ← .none, .zdebug, .zlib

#### 6. Step/Run — Enhanced Testing (HIGH IMPACT)

**0.17** adds:
  pub const StdIo = union(enum) {
    infer_from_args,
    inherit,
    check: std.ArrayList(Check),
    zig_test,
  };

  pub const Check = union(enum) {
    expect_stderr_exact: []const u8,
    expect_stderr_match: []const u8,
    expect_stdout_exact: []const u8,
    expect_stdout_match: []const u8,
    expect_term: process.Child.Term,
    expect_stderr_snapshot: std.Build.LazyPath,
    expect_stdout_snapshot: std.Build.LazyPath,
  };

This is a **huge** improvement for our integration tests. Instead of running `zig build`
and grepping output, we can assert on stdout/stderr patterns directly in `build.zig`.

#### 7. Configuration — Complete Serialization

**0.17** introduces `std.Build.Serialize` (72 KB) which serializes the entire build
graph:
  - Step graph traversal with module dependency resolution
  - C source file tracking per compile step
  - Lazy path resolution and deduplication
  - Module import mapping
  - System library configuration

This enables the build system web UI (`build-web` directory) to connect via WebSocket
and display the build graph in real-time. The `abi.zig` file defines the WebSocket
protocol.

#### 8. HashHelper — Enhanced Hashing (HIGH IMPACT)

**0.17** `Cache.zig` line 196 adds:
  pub const HashHelper = struct {
    pub fn addBytes(hh: *HashHelper, bytes: []const u8) void
    pub fn addListOfBytes(hh: *HashHelper, list_of_bytes: []const []const u8) void
    pub fn add(hh: *HashHelper, x: anytype) void        ← type-specific hashing
    pub fn peek(hh: HashHelper) [hex_digest_len]u8       ← non-mutating hash
    pub fn oneShot(bytes: []const u8) [hex_digest_len]u8 ← single-call hash
  };

Previously there was no public hash API — you had to manually track inputs. Now
`HashHelper.oneShot()` can hash a list of strings in one call.

#### 9. Step/Options — Runtime Options Generation

**0.17** adds `Step.Options` which generates Zig source files at build time containing
const declarations. This lets `build.zig` generate a `options.zig` that a Zig module can
`@import()` for compile-time configuration.

#### 10. System Lib `UsePkgConfig`

**0.17** `Module.SystemLib` adds `use_pkg_config`:
  pub const SystemLib = struct {
    use_pkg_config: UsePkgConfig,  ← enum { always, skip, required }
  };
This is a new control for pkg-config dependency resolution.

### What This Means for Our Build.zig Refactoring (v2.10-S2)

#### Directly Applicable Improvements

1. **`HashHelper.oneShot()`** — can replace manual hash accumulation for deduplication
   checks:
     const hash = std.Build.Cache.HashHelper.oneShot(strings_to_hash);

2. **`Step.Run.StdIo.check`** — can add build-time assertions for test behavior:
     const run = b.addRun("check-integration");
     run.stdio = .check;
     run.addCheck(.{ .expect_stdout_match = ".*expected.*" });

3. **`expect_errors` on Compile steps** — test error handling:
     const test = b.addTest(.{ .name = "test-errors" });
     test.expect_errors = .contains{ "error: expected type" };

4. **Granular `generated_*` flags** — no more manual copy of artifacts:
     compile.generated_h = .always;
     compile.generated_docs = .always;

5. **`link_z_common_page_size` / `link_z_max_page_size`** — control ELF page sizes
   (useful for our security posture).

#### Breaking Changes / Migration Effort

The biggest change is the module restructuring itself. The public API surface
(`addModule`, `createModule`, `addTest`, `addExecutable`, `Step.Compile` methods) is
largely preserved, but:
  - All internal types moved from `std.Build.X` to `std.Build.X` where `X` is now a
    file in `Build/` subdirectory
  - `std.Build.Configuration` is now a multi-file module (~115 KB)
  - Serialization/deserialization is now built-in via `std.Build.Serialize`
  - The `Graph` concept is more explicit (via `build.step.owner.graph`)
  - Arena allocation is more heavily used for path deduplication

The good news is that `std.Build.addModule`, `std.Build.createModule`,
`Step.Compile.addCSourceFiles`, `Step.Compile.addLibraryPath`, etc. still exist and work
the same way. The public API is preserved — it's just reorganized internally.

#### Recommendation for v2.10-S2

The story's goals (module registry, walk-based discovery, link helper application) map
directly to Zig 0.17's new capabilities:

1. **Module registry** → Now naturally fits with the `std.Build.Module` API +
   `addModule` / `createModule` distinction. Our R3 role field (`shared` vs
   `test_root`) aligns perfectly with `addModule` (public/shared) vs
   `createModule` (private/test).

2. **Walk-based discovery** → Can use `std.Build.LazyPath.dupe(graph)` and
   `std.Build.Module.addImport` with graph-aware dedup. The `dupe` pattern ensures
   paths are properly tracked in the build graph.

3. **Link helper application** → The new `expect_errors` and `Step.Run.check` make it
   easier to validate that link helpers worked correctly. We can add a check step that
   runs the test binary and verifies expected output.

4. **Build graph serialization** → Zig 0.17 now has this built-in, so our walk-based
   approach could integrate with `std.Build.Serialize` for reproducibility. If the module
   registry produces a deterministic graph, it can be serialized as an acceptance
   criterion.

The serialization layer (`Serialize.zig`) essentially provides a canonical build graph
representation — if our module registry produces a deterministic graph, it can be
serialized for reproducibility checks. This directly addresses R2 from the prevention
recommendations (catch duplicates at build-script time).
