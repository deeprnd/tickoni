# V2.10.S10: README Badge Automation — Shield.io URLs from PR Status

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.10: Build System Consolidation And Qt Build Validation
**Labels:** `type/story`, `area/operations`, `type/feature`

## Problem Statement

The README currently displays four static badge images whose URLs are hand-tuned but whose *state* is never updated automatically:

1. **Build** — should reflect whether all platform build jobs pass
2. **Unit Tests** — should reflect whether all unit test jobs pass
3. **Security** — should reflect whether security checks pass
4. **Coverage** (`cov-tk`) — currently always shows `unknown/lightgrey` because coverage jobs are **not wired into CI at all**

The existing badge URLs are hardcoded shield.io URLs that don't change. The `refresh-badges.py` script exists but runs manually, reads exit codes from local commands, and is not part of any automated pipeline. There is also no coverage badge workflow in CI, so the coverage badge can never reflect real data.

## Product Outcome

README badges on `main` reflect the **latest merged commit's** CI lane status via dynamic shield.io URLs. Every badge updates automatically after a PR merge or direct push to main. Coverage badges update when a separate coverage workflow runs.

The badges are **category aggregates**, not per-platform:

| Badge | Maps to CI jobs | Passes when |
|-------|----------------|-------------|
| **build** | `build` job in `ci.yml` (which runs `build-tk` + `build-fd` on all platforms) | All platform builds succeed |
| **unit** | `unit` job in `ci.yml` (unit tests on all platforms) | All platform unit tests succeed |
| **security** | `security-secrets` + `security-deep` jobs in `ci.yml` | Both security checks pass |
| **cov-tk** | New `coverage-badge` workflow (runs `test-cov-tk`) | Coverage job succeeds |

## Architecture

### Badge URL format (shield.io)

Shield.io's public badge API renders badges from URL-encoded query parameters:

```
https://img.shields.io/badge/<label>-<message>-<color>?style=flat-square
```

- `label`: badge text (e.g. "build", "unit tests", "security", "harness coverage")
- `message`: state (e.g. "passing", "failing", "unknown")
- `color`: hex or named color (e.g. "brightgreen", "red", "lightgrey")

The URLs are **dynamic** — no stored SVGs needed. Every page load fetches the badge from shield.io's CDN.

### Badge update mechanism

A standalone GitHub Actions workflow (`badge-update.yml`) triggers on:
- `push` to `main` (covers both direct pushes and PR merges)
- `workflow_run` completion of the `coverage-badge` workflow (for coverage badge only)

The workflow:
1. Checks out `main`
2. Reads the **latest commit's CI status** via the GitHub API (`GET /repos/{owner}/{repo}/commits/{sha}/check-runs`) or by fetching the commit's check suite statuses
3. For each badge category, resolves pass/fail/unknown from the relevant check-run names
4. Constructs the shield.io URL with the appropriate state
5. Uses `sed` to replace the `src` attribute between marker comments in `README.md`
6. Commits and pushes the updated README back to `main`

This approach works because:
- `push` triggers fire after all CI jobs for that commit complete
- The GitHub API gives us the check-run status for any commit
- We only need to read status, not write to PR branches (unlike the original story)

### Coverage workflow gap

Coverage is **not currently in CI**. This story adds:
1. A `coverage-badge.yml` workflow that runs `test-cov-tk` on push to `main`
2. A `ci-badge-update.yml` workflow that reads coverage results and updates the badge

### CI Job Aggregators (Consolidated)

The `ci.yml` already has the right structure: the `build`, `unit`, `security-secrets`, `security-deep`, and `dev-setup` jobs each run on a matrix of platforms and are aggregated by the `ci-required` job. The badges map to these existing aggregator jobs:

- **build badge** → `build` job (which runs `_ci-build.yml` on all platforms)
- **unit badge** → `unit` job (which runs `_ci-unit.yml` on all platforms)
- **security badge** → `security-secrets` + `security-deep` jobs (both must pass)
- **cov-tk badge** → NEW `coverage-badge` job/workflow

No additional intermediate placeholder workflows are needed — the existing `ci.yml` jobs already serve as the aggregation layer.

## Scope

- **In scope:** Design and implement `badge-update.yml` that triggers on `push` to `main` and updates README badge shield.io URLs based on the latest commit's CI check-run status
- **In scope:** Add coverage workflow (`coverage-badge.yml`) to CI — runs `test-cov-tk` on push to `main`, updates coverage badge after completion
- **In scope:** Wire coverage into `ci.yml` as a proper CI job (or keep as a separate workflow since coverage is heavy and doesn't block PRs)
- **In scope:** Map badge categories to CI job names: `build`, `unit`, `security` (secrets+deep), `cov-tk`
- **In scope:** Use marker comments `<!-- badge:name:start -->` / `<!-- badge:name:end -->` for insertion points
- **In scope:** Handle unknown state (badge shows `unknown/lightgrey` when no corresponding CI job has run yet)
- **In scope:** Update `doc/execution/build.md` and `doc/execution/development.md` to document the new badge-update mechanism
- **In scope:** Remove references to the manual `refresh-badges.py` as the primary update path (keep as local experiment tool)
- **Out of scope:** Switching from shield.io to a self-hosted badge server
- **Out of scope:** Adding new badge types beyond `build`, `unit`, `security`, `cov-tk`
- **Out of scope:** Changing badge colors, styles, or the marker comment format

## Acceptance Criteria

- [ ] Given a PR merge to `main` where build, unit, and security lanes pass, when the `push` to `main` completes, then `README.md` badge URLs for `build`, `unit`, `security` show `passing/brightgreen` via shield.io
- [ ] Given a PR merge to `main` where any lane fails, when CI completes, then the failed badge shows `failing/red`
- [ ] Given a commit where a badge type has no corresponding CI job (e.g. coverage before the workflow exists), then its badge shows `unknown/lightgrey`
- [ ] Given coverage data exists, the `cov-tk` badge shows a real coverage percentage (e.g. `72.3%/orange`) via shield.io
- [ ] Given a developer who runs `refresh-badges.py` locally, when they pass an exit code, then the badge updates locally but documentation states this is for experimentation
- [ ] Coverage workflow runs on push to `main` and updates the coverage badge after completion

## CI Workflow Additions

### New: `coverage-badge.yml`

Triggers on `push` to `main`. Runs `test-cov-tk` via `just`. After completion, triggers the badge-update workflow (or runs it inline).

### New: `badge-update.yml`

Triggers on `push` to `main`. Reads the latest commit's CI check-runs via GitHub API. For each badge category:
- `build` → check `build` job status
- `unit` → check `unit` job status
- `security` → check both `security-secrets` and `security-deep` statuses (AND logic)
- `cov-tk` → check `coverage-badge` workflow status (if it ran)

Updates `README.md` badge URLs between markers.

### CI Job Mapping

| Badge | ci.yml job(s) | Logic |
|-------|--------------|-------|
| build | `build` | ALL platform builds must pass (ci.yml already enforces this) |
| unit | `unit` | ALL platform unit tests must pass |
| security | `security-secrets` + `security-deep` | BOTH must pass |
| cov-tk | `coverage-badge` (new) | Workflow must succeed |
