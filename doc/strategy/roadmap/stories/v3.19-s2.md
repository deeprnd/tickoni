# V3.19.S2: Investment Safe-Action Workbench (CASE Function)

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V3.19: Tickoni Native Investment Terminal
**Labels:** `type/story`, `area/investing`

Render the V1.1/V1.11 investment safe-action flow in the CASE function: thesis
input, normalized intent, proposed basket, rejected candidates, ticket, policy
gate, paper state, and replay proof.

## Product Outcome

Investment users and operators can see how an investment thesis became a bounded
proposal, which instruments were rejected, which checks passed, and why the
final action is allowed, blocked, paper-only, or approval-required — all within
the CASE function panel.

## User Story

As an investment user, I want to inspect the policy-checked investment proposal
before any execution path, so that I understand the allowed consequence and the
denied alternatives.

## Scope

- In scope: normalized intent fields (amount, market, venues, asset classes,
  exclusions, concentration); basket table with ticker, role, allocation, price,
  and status; rejected candidates table with denial reason (e.g., restricted
  leveraged ETF, asset class violation); trade ticket preview (order type,
  quantity); policy decision panel showing individual check results (cash check,
  buying power, per-order notional, daily notional, market/venue scope,
  restricted instrument, same-day round trip, minimum holding period); proposal
  hash; paper state indicator; `/explain denial` command displaying the denied
  candidate's exact reason; `/show policy` command for POLICY function.
- Out of scope: new basket construction logic, new trading policy rules, live
  brokerage placement, direct market-data calls from the UI, or new financial
  capability definitions.

## Preconditions And Assumptions

- V1.1/V1.11 investment fixture or `tk_api` mock data exists for the USD 2,000
  AI-infrastructure scenario.
- Restricted `SOXL` and oversize USD 25,000 flows are represented as denied or
  blocked fixture states.
- Paper placement state, when shown, is produced by the governed runtime path.
- The workbench renders inside the CASE function panel from S1.

## Acceptance Criteria

- [ ] Given the USD 2,000 investment fixture, when the CASE function renders,
      then the normalized intent, allowed basket, ticket preview, and policy
      checks are visible in one workspace.
- [ ] Given a restricted instrument fixture, when the CASE function renders,
      then the candidate appears in the rejected table with the exact denied
      reason and no quote or paper-fill affordance.
- [ ] Given an oversize notional fixture, when the CASE function renders, then
      the policy gate shows the effective limit, decision, and disabled direct
      action controls.
- [ ] Given the `/explain denial` command, when submitted, then the denied
      candidate's reason (e.g., "restricted leveraged ETF", "asset class
      violation") is displayed prominently.

      does not recompute allow or deny.

**Audit and replay**

- [ ] Proposal hash, policy hash, and replay status link to the PROOF panel
      when present.

**Runtime topology and tile ownership**

- [ ] N/A - no topology changes.

**Model, tool, adapter, or execution boundary**

- [ ] Market, model, and adapter attribution is display-only and sourced from
      governed records.

**CaseOps API or UI**

- [ ] Workbench data is loadable from a deterministic fixture or documented
      `tk_api` read response.

**Storage role: Memory, Analytics, Ledger**

- [ ] N/A - workbench data is sourced from `tk_api` or fixtures; the UI does

**Metrics, diagnostics, and operations**

- [ ] N/A - no new metrics or diagnostic signals are introduced.

**Security and fail-closed behavior**

- [ ] Given unavailable or malformed investment data, when the CASE function

      inferred or defaulted values.
