# V3.23.S2: Installer — platform-specific install helpers with fail-closed host validation and per-user scoped paths

**Status:** Backlog
**Epic:** #[github-epic-issue] (V3.23)
**Parent roadmap item:** V3.23: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow
**Labels:** `type/story`, `area/platform`, `area/security`, `type/feature`

<!-- One sentence: the independently verifiable deliverable. -->

A user-scoped installer helper runs on Linux (shell script), macOS (shell helper),
and Windows (PowerShell script) to install `tickoni` and `tickoni-supervisor` into
`~/.tickoni/bin/` (Linux/macOS) or `%LOCALAPPDATA%\tickoni\` (Windows) without
requiring admin or elevated privileges. The installer validates the host OS and
architecture before installing, failing closed on unsupported platforms with an
explicit diagnostic.

## Product Outcome

A consumer-money user or developer-community evaluator on any supported platform
can run the installer once and have a working `tickoni` binary available without
admin credentials. The installer refuses to run on unsupported hosts and explains
why.

## User Story

As a macOS, Linux, or Windows user, I can download the Tickoni release tarball,
verify its checksum, run the installer script, and immediately use
`tickoni --version` and `tickoni doctor` without needing to modify PATH manually
or install as root/admin.

As a runtime owner, I want the installer to fail closed on unsupported hosts with
a clear diagnostic so that broken installs don't silently degrade.

## Scope

- In scope:
  - Linux installer: `install.sh` that extracts tarball to `$HOME/.tickoni/bin/`,
    creates `~/.tickoni/demos/` and `~/.tickoni/evidence/` subdirectories, and
    optionally writes a shell alias or symlink to `$HOME/.local/bin/` (if writable).
  - macOS installer: `install.sh` that extracts to `$HOME/.tickoni/bin/` and
    creates the standard directory structure.
  - Windows installer: `install.ps1` that extracts to
    `%LOCALAPPDATA%\tickoni\bin\`, creates subdirectories, and optionally
    updates `%PATH%` for the current user scope.
  - All installers validate the host OS and architecture against the release
    artifact's expected platform/arch before copying files.
  - Unsupported hosts receive a clear diagnostic message and the installer exits
    non-zero without installing any files.
  - No admin/sudo/root privileges are required on any platform.
  - No secrets, credentials, broker connections, or model calls are made during
    installation.
  - No outbound network calls are made during install.

- Out of scope:
  - macOS `.pkg` installer with GUI wizard.
  - Windows MSI installer.
  - Automatic PATH modification for all users (Windows only per-user PATH).
  - Docker container installation.
  - Homebrew tap or Linux distro package installation.
  - Code signing of installer scripts.

## Preconditions And Assumptions

- V3.23.S1 produces release tarballs with correct filenames and structure.
- `retail-runtime-support.md` documents the standard install layout:
  `$HOME/.tickoni/bin/`, `$HOME/.tickoni/demos/`, `$HOME/.tickoni/evidence/`.
- The runtime binaries (`tickoni`, `tickoni-supervisor`) already report version,
  OS, architecture, runtime tier, and isolation tier via `--version`.
- No elevated privileges are needed for the target install directory.

## Acceptance Criteria

- [ ] Given a Linux x86_64 release tarball, when a user runs `install.sh` as a
      non-root user, then `tickoni` and `tickoni-supervisor` are installed to
      `$HOME/.tickoni/bin/`, and `~/.tickoni/demos/` and `~/.tickoni/evidence/`
      are created.
- [ ] Given a macOS tarball, when a user runs `install.sh` as a non-root user,
      then the same directory structure is created under `$HOME/.tickoni/`.
- [ ] Given a Windows tarball, when a user runs `install.ps1` without admin
      privileges, then binaries are extracted to
      `%LOCALAPPDATA%\tickoni\bin\` without requiring elevation.
- [ ] Given an unsupported host (wrong OS or architecture), when a user runs
      the installer with a tarball from a different platform, then the installer
      prints a diagnostic and exits non-zero without installing any files.
- [ ] Given a successful install, when a user runs `tickoni --version`, then
      the output includes version, OS, architecture, runtime tier, and isolation
      tier.
- [ ] Given a successful install, when a user runs `tickoni doctor --plain`,
      then the doctor output matches the release metadata.
- [ ] Given the installed runtime, when a user runs `tickoni-supervisor demo
      investment --plain`, then the demo runs and produces deterministic
      paper/sandbox output with audit/replay evidence in `~/.tickoni/evidence/`.
- [ ] Given the installed runtime, when `tickoni --version` is run, then
      `~/.tickoni/bin/tickoni` is used (PATH is set or alias created).

host validation, tarball extraction to `%LOCALAPPDATA%\tickoni\bin\`, directory
creation, and optional per-user PATH update via `$env:Path`.

V3.23.S2.T4 — Host validation. Implement platform-specific host detection and
validation logic. Linux: check OS via `/etc/os-release` or `uname -s`. macOS:
check via `uname -s`. Windows: check via `uname -s` or environment variables.
Architecture: check via `uname -m`. Fail with diagnostic on unsupported combinations.
