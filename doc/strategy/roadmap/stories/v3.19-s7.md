# V3.19.S7: API Contracts, Fixtures, Screenshots, And Release Evidence

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V3.19: Tickoni Native Investment Terminal
**Labels:** `type/story`, `area/operations`

Define the minimum `tk_api` read/review contracts and evidence pack needed to
verify the terminal UI without weakening runtime boundaries. Document the
`InvestmentCaseView` aggregated view contract.

## Product Outcome

Implementers, reviewers, and partners can see exactly which API shapes,
fixtures, screenshots, and tests prove the terminal behavior and no-bypass
guarantees for all five functions: CASE, POLICY, IMPACT, PROOF, SYSTEM.

## User Story

As a developer or reviewer, I want the UI contracts and evidence pack
documented, so that implementation can proceed without inventing policy, storage,
adapter, or execution semantics inside the frontend.

## Scope

- In scope: minimum `InvestmentCaseView` aggregated read contract for `tk_api` over shared-memory channels with fields: case, environment, source, freshness, intent, account, proposal, ticket, rejected_candidates, policy_decision, policy_checks, impact_summary, action_state, audit_summary, replay_summary, runtime_summary; each major section carrying status, source, as_of, freshness, reason_unavailable; where policy applies: policy_version, outcome, reason_code, reason_text, observed_value, limit_value, scope; where audit/replay applies: event_hash, policy_hash, proposal_hash, evidence_refs, replay_capsule_id, replay_status, first_divergent_sequence, first_divergent_field, expected_hash, actual_hash; fixture file paths and schemas for all five function panels; screenshot checklist covering all panel types and states (allowed basket, restricted instrument denied, oversize notional blocked, replay match, tamper divergence, unavailable bus, fixture mode); bus-transport test contract (channel overflow, sequence gaps, resynchronization); blocked-flow examples; focused test commands; contract notes documenting that `tk_ui` communicates only through `tk_api` (shared-memory for local, `tk_gateway` for remote).
- Out of scope: implementing new runtime endpoints, changing public contracts
  beyond documented read/review needs, or adding live external dependencies.

## Preconditions And Assumptions

- If an endpoint does not exist, this story documents the required contract
  before implementation work begins on any downstream story.
- Contract examples must preserve architecture boundaries and source-of-truth
  roles: Memory is on-disk Markdown, Analytics is the analytics store, Ledger
  is the approved execution ledger.
- S7 is a documentation and fixture story; it is the dependency that unlocks
  the implementation stories (S1–S6). Other stories should not begin until S7
  has defined their required contract shapes.

## Acceptance Criteria

- [ ] Given this epic, when implementation starts, then every UI panel (CASE,
      POLICY, IMPACT, PROOF, SYSTEM) has a fixture or documented `tk_api` read
      response with source, freshness, and unavailable-state fields.
- [ ] Given a sensitive action affordance, when no approved runtime contract
      exists, then the UI contract marks the action disabled or proposal-only.
- [ ] Given release review, when evidence is collected, then screenshots,
      blocked-flow fixtures, and focused test commands are linked from this
      roadmap item.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Contract examples carry policy version, outcome, reason, and relevant
      scope fields where policy applies.

**Audit and replay**

- [ ] Contract examples carry hashes, evidence refs, replay capsule id, status,
      and divergence fields where audit/replay applies.

**Runtime topology and tile ownership**

- [ ] Contract examples for system availability identify runtime health sources
      (API, fixture) with clarity on which is active.

**Model, tool, adapter, or execution boundary**

- [ ] Contract examples include attribution and status only; no direct model,
      tool, adapter, or execution credentials appear in UI fixtures.

**CaseOps API or UI**

- [ ] `tk_api` is documented as the only UI boundary for case, evidence,
      proposal, approval, audit, replay, and health fanout.

**Storage role: Memory, Analytics, Ledger**

- [ ] Contract examples do not expose DuckDB (analytics store), TigerBeetle
      (approved execution ledger), or Markdown (memory) connection details;
      all data flows through `tk_api`.

**Metrics, diagnostics, and operations**

- [ ] N/A - this story documents contracts and fixtures; it does not introduce
      metrics or diagnostic signals.

**Security and fail-closed behavior**

- [ ] Contract examples for unavailable states include reason_unavailable and
      show how downstream panels should disable actions when data is stale or
      disconnected.

## Evidence Plan

- Demo or command: documentation review plus local fixture-driven terminal run
  across all five functions.
- Tests: schema/example validation and focused UI fixture tests.
- Fixtures or samples: investment (allowed, restricted, oversize), replay (match,
  tamper, stale capsule), system (available, unavailable, fixture mode) examples.
- Audit/replay evidence: clean replay, tamper, stale capsule, and missing
  evidence examples.
- Blocked-flow evidence: restricted instrument, out-of-scope instrument,
  degraded adapter, unknown command, unavailable impact, and unavailable API
  examples.

## Quality Gate

- [ ] Focused tests for changed behavior pass.
- [ ] `just test-unit-tk` passes when Tickoni runtime code changes.
- [ ] `just test-integration-tk` passes when cross-tile, API, replay, adapter,
      or fixture behavior changes.
- [ ] `just test-demo-tk` or the story-specific demo command prints the required
      scenario when this story changes a demoable product flow.
- [ ] Documentation and roadmap status are updated when user-visible scope,
      non-goals, or evidence gates change.
