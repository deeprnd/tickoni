# V3.19.S7: UI Tile, API Communication, Test Harnesses, And Release Evidence

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V3.19: Tickoni Native Investment Terminal
**Labels:** `type/story`, `area/platform`

Define the `tk_ui` tile architecture, `tk_api` ↔ `tk_ui` communication contracts, the test harness (unit + integration), and the evidence pack needed to verify the terminal UI without weakening runtime boundaries.

## Product Outcome

Implementers, reviewers, and partners can understand the `tk_ui` tile boundary, the shared-memory channel contract between `tk_api` and `tk_ui`, the full test harness with unit and integration tests, and the evidence pack (fixtures, screenshots, command tests) needed to verify all six function panels.

## User Story

As a developer or reviewer, I want the `tk_ui` tile boundary, `tk_api` ↔ `tk_ui` communication contracts, test harness, and evidence pack documented, so that implementation can proceed without inventing policy, storage, adapter, or execution semantics inside the frontend.

## Scope

- In scope: **`tk_ui` tile boundary** — definition of the composite edge tile wrapping the Qt application, owning local shared-memory channels, bus bridge, command admission, feature projection stores, presentation models, and collection models; **`tk_api` ↔ `tk_ui` communication contract** — shared-memory channel definitions (ui_cmd, ui_rsp, ui_evt, ui_lval, ui_bulk, ui_diag) with delivery semantics (ordered/preserve/no-coalescing for commands, ordered/preserve/reconcile for responses, ordered/preserve/resync-on-gap for events, coalesce-by-key for latest-values, bounded-outstanding-payload-ownership for bulk, sample-or-replace for diagnostics), sequence numbering, overflow policies (fail-closed vs. coalescing), gap detection and resynchronization, process generation validity, and bulk payload resolution; **`InvestmentCaseView` aggregated read contract** for `tk_api` with fields: case, environment, source, freshness, intent, account, proposal, ticket, rejected_candidates, policy_decision, policy_checks, impact_summary, action_state, audit_summary, replay_summary, runtime_summary — each major section carrying status, source, as_of, freshness, reason_unavailable; where policy applies: policy_version, outcome, reason_code, reason_text, observed_value, limit_value, scope; where audit/replay applies: event_hash, policy_hash, proposal_hash, evidence_refs, replay_capsule_id, replay_status, first_divergent_sequence, first_divergent_field, expected_hash, actual_hash; **unit test harness** — focused tests for changed behavior per story: shell tests (keyboard navigation, command parser, responsive rendering, empty/loaded states), CASE tests (thesis rendering, basket table, rejected candidates, policy summary, ticket preview), POLICY tests (check table rendering, PASS/FAIL/WAIVED results, rejection reasons), IMPACT tests (before/after cash, exposure deltas, alert display), PROOF tests (timeline rendering, hash display, replay status, tamper check), SYSTEM tests (freshness display, bus status, fixture mode), cross-story tests (function key navigation, command bar routing, status strip coherence); **integration test harness** — cross-tile and API tests: `tk_api` read contract validation against runtime fixtures, fixture-driven terminal run across all six functions, bus-transport tests (channel overflow, sequence gaps, resynchronization, saturated channel behavior), replay fixture validation (clean replay, tamper divergence, stale capsule, missing evidence), system availability fixture validation (available, unavailable API, degraded bus), blocked-flow tests (restricted instrument, out-of-scope instrument, degraded adapter, unknown command, unavailable impact, unavailable API), cross-platform launch evidence (same fixture produces same semantic terminal state on Linux, macOS, Windows); **fixture file paths and schemas** for all six function stories; **screenshot checklist** covering all panel types and states (allowed basket, restricted instrument denied, oversize notional blocked, replay match, tamper divergence, unavailable bus, fixture mode); **contract notes** documenting that `tk_ui` communicates only through `tk_api` (shared-memory for local, `tk_gateway` for remote).
- Out of scope: implementing new runtime endpoints, changing public contracts beyond documented read/review needs, adding live external dependencies, or modifying runtime tile ownership, topology, or link semantics.

## Preconditions And Assumptions

- If an endpoint does not exist, this story documents the required contract before implementation work begins on any downstream story.
- Contract examples must preserve architecture boundaries and source-of-truth roles: Memory is on-disk Markdown, Analytics is the analytics store, Ledger is the approved execution ledger.
- S7 is a documentation and fixture story; it defines the contracts that unlock the implementation stories (S1–S6, S8). Other stories should not begin until S7 has defined their required contract shapes.
- The `tk_ui` tile is a composite edge tile wrapping the Qt application, not a runtime tile. It owns presentation concerns only.

## Acceptance Criteria

- [ ] Given this epic, when implementation starts, then the `tk_ui` tile boundary, `tk_api` ↔ `tk_ui` communication contract, and `InvestmentCaseView` schema are documented.
- [ ] Given unit tests for all six function stories, when run, then every panel renders from fixtures without overlapping text at supported desktop widths.
- [ ] Given integration tests with bus-transport fixtures, when run, then channel overflow, sequence gaps, and resynchronization produce documented behavior (fail-closed or coalescing) without crashing.
- [ ] Given release review, when evidence is collected, then screenshots, blocked-flow fixtures, and focused test commands are linked from this roadmap item.
- [ ] Given a sensitive action affordance, when no approved runtime contract exists, then the UI contract marks the action disabled or proposal-only.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Contract examples carry policy version, outcome, reason, and relevant scope fields where policy applies.
- [ ] `tk_ui` does not recompute policy outcomes; all policy data flows through `tk_api`.

**Audit and replay**

- [ ] Contract examples carry hashes, evidence refs, replay capsule id, status, and divergence fields where audit/replay applies.
- [ ] Replay fixture validation tests verify MATCH, DIVERGE, and MISSING outcomes.

**Runtime topology and tile ownership**

- [ ] `tk_ui` tile boundary is documented; no topology changes from `tk_ui`.
- [ ] `tk_ui` does not own tile links, queues, workspaces, or runtime tile identities.

**Model, tool, adapter, or execution boundary**

- [ ] Contract examples include attribution and status only; no direct model, tool, adapter, or execution credentials appear in UI fixtures.
- [ ] `tk_ui` does not call LLM providers, financial APIs, or execution backends directly.

**CaseOps API or UI**

- [ ] `tk_api` is documented as the only UI boundary for case, evidence, proposal, approval, audit, replay, and health fanout.
- [ ] `tk_ui` communicates only through `tk_api` — shared-memory for local, `tk_gateway` for remote.
- [ ] All six function panels have a fixture or documented `tk_api` read response with source, freshness, and unavailable-state fields.

**Storage role: Memory, Analytics, Ledger**

- [ ] Contract examples do not expose DuckDB (analytics store), TigerBeetle (approved execution ledger), or Markdown (memory) connection details; all data flows through `tk_api`.
- [ ] `tk_ui` does not connect directly to DuckDB, TigerBeetle, or Markdown files.

**Metrics, diagnostics, and operations**

- [ ] N/A - this story documents contracts and fixtures; it does not introduce metrics or diagnostic signals in the runtime.

**Security and fail-closed behavior**

- [ ] Contract examples for unavailable states include reason_unavailable and show how downstream panels should disable actions when data is stale or disconnected.
- [ ] Given unavailable or malformed proof data, when the PROOF function renders, then the panel shows unavailable or evidence-required rather than inferred values.

## Evidence Plan

- Demo or command: documentation review of `tk_ui` tile boundary and communication contract, plus local fixture-driven terminal run across all six functions.
- Tests: unit tests per story (shell, CASE, POLICY, IMPACT, PROOF, SYSTEM), integration tests (bus-transport, cross-platform launch, blocked-flow), contract validation.
- Fixtures or samples: investment (allowed, restricted, oversize), replay (match, tamper, stale capsule), system (available, unavailable, fixture mode), bus (overflow, gap, resync, saturated) examples.
- Audit/replay evidence: clean replay, tamper, stale capsule, and missing evidence examples.
- Blocked-flow evidence: restricted instrument, out-of-scope instrument, degraded adapter, unknown command, unavailable impact, and unavailable API examples.
- Screenshots: all six function panels in all states (allowed basket, restricted instrument denied, oversize notional blocked, replay match, tamper divergence, unavailable bus, fixture mode).

## Quality Gate

- [ ] Focused tests for changed behavior pass.
- [ ] `just test-unit-tk` passes when Tickoni runtime code changes.
- [ ] `just test-integration-tk` passes when cross-tile, API, replay, adapter, or fixture behavior changes.
- [ ] `just test-demo-tk` or the story-specific demo command prints the required scenario when this story changes a demoable product flow.
- [ ] Documentation and roadmap status are updated when user-visible scope, non-goals, or evidence gates change.
