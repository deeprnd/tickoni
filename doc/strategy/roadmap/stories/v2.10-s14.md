# V2.10.S14: Migrate All Tickoni Tiles to Firedancer fd_stem Polling Loop

**Labels:** `type/story`, `area/platform`

**GitHub Issue:** TBD

<!-- One sentence: the independently verifiable deliverable. -->

A comprehensive migration that replaces all per-tile polling loops in Tickoni with Firedancer's universal `fd_stem` run loop. Each tile provides callbacks (`before_credit`, `during_frag`, `after_credit`, `metrics_write`, `should_shutdown`) instead of its own `while` loop body. A new C bridge file (`tk_stem.c`) includes `fd_stem.c` and registers per-tile callbacks in a global table — the tile logic stays in Zig, invoked through the C bridge. All 8 existing pipeline tiles (ingest, normalize, dedupe, policy, audit, replay, diag, metric) are migrated. On Linux the full `fd_stem` loop runs; on non-Linux targets the existing per-tile loops continue to work as a fallback.

## Product Outcome

Operators and developers get a unified tile lifecycle: every Tickoni tile follows the same `fd_stem`-based callback pattern, making new tile development predictable, cross-tile debugging consistent, and Firedancer infrastructure integration seamless. The bounded polling loop, multi-input fan-in with randomized round-robin, backpressure discipline, and credit-based `before_credit`/`after_credit` lifecycle hooks from `fd_stem` are available to every tile. The `fd_stem` code — 875 lines of C that runs P2P, verify, pack, RPC, and metric tiles in Firedancer — becomes the single run loop for Tickoni, eliminating 8 near-identical per-tile `while` loops.

## User Story

As a Tickoni developer, I want every tile to use the same `fd_stem`-based callback pattern so that I can understand any tile's lifecycle by reading one polling loop — no need to track whether a tile has its own `while` loop, a custom observer loop, or the metric tile's HTTP polling.

As a test author, I want all tiles to follow the same lifecycle (register callbacks → `stem_run` → callbacks fire → `should_shutdown` returns → heartbeat/halt-wait) so that integration tests can use a single harness for tile boot, work, and shutdown verification.

As a runtime owner, I want every tile to inherit Firedancer's bounded polling, backpressure, and multi-input fan-in from `fd_stem` so that no tile can spin-loop, overwhelm a consumer queue, or silently drop inputs without the stem's credit-based discipline.

## Scope

- In scope:
  - Create `src/tickoni/c_abi/shim/tk_stem.c` — a C bridge that includes `fd_stem.c` and defines a callback registry (`tk_stem_registry[FD_TOPO_MAX_TILES]`) with function pointers for `before_credit`, `during_frag`, `after_credit`, `metrics_write`, and `should_shutdown`.
  - Implement `tk_stem_run(tile_id, tile_ctx_ptr, callbacks...)` — registers the tile's callbacks in the global registry and calls `stem_run()` with the tile's context pointer. The stem loop calls back into the registered functions via the global table.
  - Wire `fd_stem` callbacks in `tk_stem.c` using the `STEM_CALLBACK_*` macro guards (matching how Firedancer generates `stem_run` via `#include "fd_stem.c"`):
    - `STEM_CALLBACK_BEFORE_CREDIT` → calls the tile's `before_credit_fn`
    - `STEM_CALLBACK_DURING_FRAG` → calls the tile's `during_frag_fn`
    - `STEM_CALLBACK_AFTER_CREDIT` → calls the tile's `after_credit_fn`
    - `STEM_CALLBACK_METRICS_WRITE` → calls the tile's `metrics_write_fn`
    - `STEM_CALLBACK_SHOULD_SHUTDOWN` → calls the tile's `should_shutdown_fn`
  - Migrate each of the 8 existing tiles from `while` loops to `fd_stem` callbacks in `src/tickoni/tiles/payment_pipeline/process.zig`:
    - `tkings` (0 in, 1 out): only `BEFORE_CREDIT` and `AFTER_CREDIT` fire, no `DURING_FRAG`
    - `tknorm` (1 in, 1 out): `DURING_FRAG` → process → `AFTER_CREDIT` → publish
    - `tkdedu` (1 in, 1 out): same pattern as norm
    - `tkpoly` (1 in, 1 out): same pattern as norm
    - `tkaudt` (1 in, 0 out): `DURING_FRAG` → audit, no `AFTER_CREDIT`
    - `tkrepl` (0 in, 0 out): `BEFORE_CREDIT` for file-based replay, `SHOULD_SHUTDOWN` for work-complete
    - `tkdiag` (0 in, 0 out): `BEFORE_CREDIT` for periodic snapshot
    - `tkmetr` (0 in, 0 out): `BEFORE_CREDIT` for HTTP server polling, `SHOULD_SHUTDOWN` for HALT
  - Modify `tile_process.zig` to register per-tile callback functions (`tile_before_credit`, `tile_during_frag`, `tile_after_credit`, `tile_metrics_write`, `tile_should_shutdown`) and call `tk_stem_run()` instead of the direct `work()` loop. After `stem_run` returns (when `should_shutdown` is true), the heartbeat/halt-wait loop continues.
  - Modify `tile_run.c` to use `tk_stem_run` instead of `tk_tile_run` for the `.run` callback in `TK_TILE_RUN`.
  - Platform handling: on Linux, `fd_stem` runs via `fd_topo_run_tile()`; on non-Linux, fall back to the existing per-tile loop (same code as before).
  - Migrate tiles in order from simplest to most complex: tkings, tkrepl, tkdiag, tkmetr, tkaudt, tknorm, tkdedu, tkpoly.
  - Update `tile-delivery-status.md` and `tile-topology.md` to reflect the new lifecycle.
  - Update integration tests for all migrated tiles.

- Out of scope:
  - Modifying Firedancer's `fd_stem.c`, `fd_stem.h`, or `fd_topo_run.c`.
  - Adding new tiles beyond the 8 existing ones.
  - Changing Firedancer's `fd_topo_run_tile` harness or callback signatures.
  - Removing `rt.link.Producer` and `rt.link.Consumer` until all tiles are migrated and verified.
  - Changes to the supervisor's spawn-and-track loop in `supervisor.zig`.
  - Changes to Firedancer's `fd_topo_run_tile_t` struct layout.
  - Changing the N-processes model — this story only changes the polling loop, not the process-per-tile architecture.

## Preconditions And Assumptions

- Firedancer's `fd_stem.c` is available under `src/disco/stem/fd_stem.c` and generates `stem_run()` via `#include` with `STEM_CALLBACK_*` macro guards.
- `fd_stem` supports tiles with any input/output link configuration: 0-in/1-out (tkings), 1-in/1-out (tknorm/tkd edu/tkpoly), 1-in/0-out (tkaudt), 0-in/0-out (tkrepl/tkdiag/tkmetr).
- The `STEM_CALLBACK_SHOULD_SHUTDOWN` callback is used by `fd_stem` to break the loop when a tile should stop.
- `fd_topo_run_tile()` (which calls the `.run` callback) is Linux-only on the upstream side. Tickoni already has non-Linux fallbacks via `tk_topo_run_tile()`.
- The existing per-tile `while` loops in `process.zig` follow the same pattern: `consume() → process() → publish()` for pipeline tiles, or just periodic work for observer tiles.
- Each tile has its state stored in a tile-local context that is passed through the callback `ctx` pointer.
- On Linux, Tickoni runs N-processes (not Firedancer's 1-process-N-threads). The `fd_stem` loop runs inside each process. The process model is unchanged.
- `tkmetr` uses `fd_http_server_poll` in its `BEFORE_CREDIT` callback (same pattern as Firedancer's `fd_metric_tile.c`).

## Notes And Open Questions

- `fd_stem.c` is 875 lines of C that `#include`s into each tile's compilation unit via `STEM_CALLBACK_*` macro guards. The `stem_run()` function is generated once per tile with that tile's specific `before_credit`/`during_frag`/`after_credit` callbacks baked in via the global registry.
- The `tk_stem_registry[FD_TOPO_MAX_TILES]` global table is safe because Tickoni runs one tile per process — each process registers exactly one entry and only accesses its own tile's slot.
- `fd_stem` supports 0-input tiles (polled_in_cnt=0): `DURING_FRAG` simply never fires. This is exactly how Firedancer's `fd_metric_tile.c` and `fd_genesi_tile.c` handle 0-input patterns.
- **Architecture note:** Firedancer runs 1-process-N-threads on Linux for P2P throughput, but Tickoni runs N-processes for crash isolation. This is a deliberate tradeoff — the `fd_stem` loop runs inside each process. The process model is unchanged by this migration.
- **Migration order:** simplest to most complex, easiest to verify — tkings (0 in, 1 out), tkrepl (0 in, 0 out), tkdiag (0 in, 0 out), tkmetr (0 in, 0 out), tkaudt (1 in, 0 out), tknorm (1 in, 1 out), tkdedu (1 in, 1 out), tkpoly (1 in, 1 out).
- Should `tkmetr` use `fd_stem` or keep its separate `TK_METRIC_RUN`? The plan proposes using `fd_stem` for `tkmetr` too (the overhead is minimal since `stem_run` just loops calling `BEFORE_CREDIT`), unifying all tiles under one pattern. But if the overhead is measurable, `tkmetr` can keep `TK_METRIC_RUN` as a special case.
- `rt.link.Producer` and `rt.link.Consumer` are used by the current `while` loops. They can be removed after all tiles are migrated and verified — not in this story's scope.
- The `SHOULD_SHUTDOWN` callback checks both the CNC HALT signal and per-tile "work complete" conditions (e.g., event count reached, replay file exhausted). This prevents the infinite `stem_run` loop from hanging when a tile has finished its work.
