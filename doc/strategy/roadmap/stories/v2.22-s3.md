# V2.22.S3: Version identity, doctor, and demo manifest preflight

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.22: Windows Retail Runtime Support
**Labels:** `story`, `operations`, `enhancement`

Define runtime version identity, host preflight, and demo compatibility checks
on Windows so user-facing flows fail closed before producing ambiguous evidence.

## Product Outcome

Every Windows retail run identifies exactly what was installed, what host it ran
on, which demo manifest was selected, and whether the host is allowed to
produce that demo's evidence.

## User Story

As a consumer-money user on Windows, I want Tickoni to check my platform and
demo version before running, so that I do not trust an artifact from an
unsupported or ambiguous runtime.

## Scope

- In scope: `tickoni --version` fields, `tickoni doctor` checks for Windows
  prerequisites, demo manifest schema, preflight failure rules, version
  metadata in audit/replay.
- Out of scope: installer design (S4), demo execution (S6), trust/audit
  closure (S7).

## Preconditions And Assumptions

- S1 defines tier language; S3 reports which tier is active.
- V2.14 defined the existing runtime; S3 adds version and preflight layers.
- Windows-specific prerequisites (WSL2 version, Docker Desktop, Windows Build
  number) must be checked in addition to generic preflight checks.

## Acceptance Criteria

- [ ] Given a built Tickoni binary, when the user runs `tickoni --version`,
      then the output includes Tickoni semver, build id, git revision or
      release digest, target OS/architecture, runtime tier, isolation tier,
      policy schema version, replay schema version, and demo manifest version.
- [ ] Given a Windows host, when the user runs `tickoni doctor`, then the
      output reports host OS version, architecture, CPU features, WSL2/Docker
      Desktop/VM/native prerequisites, local tool availability, fixture
      availability, model/mock mode, local storage paths, disabled live
      execution, and unsupported direct source builds.
- [ ] Given a demo manifest, when the installed Tickoni version, runtime tier,
      host capability, or fixture set does not satisfy the manifest, then the
      demo fails closed with an explicit error and produces no proposal or
      audit artifacts.
- [ ] Given a successful demo, when audit or replay metadata is produced, then
      version, platform tier, isolation tier, release digest, and demo manifest
      identity are included.

## Evidence Plan

- Demo or command: `tickoni --version` and `tickoni doctor` on a supported
  Windows host.
- Tests: preflight failure test on an unsupported host or stale manifest.
- Fixtures or samples: Demo manifest sample, version output sample.
- Audit/replay evidence: Audit JSONL sample with tier metadata.
- Blocked-flow evidence: Preflight failure on unsupported Windows host.

## Quality Gate

- [ ] Version, doctor, and demo-manifest behavior is specified before
      Windows installer or runtime implementation.
- [ ] Unsupported hosts, stale demos, and missing fixtures produce explicit
      failure messages and no proposal/audit artifacts on Windows.
- [ ] Documentation and roadmap status are updated when preflight behavior
      changes.
