# V2.21.S1: Platform support tier definitions

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.21: Cross-Platform Retail Runtime Support
**Labels:** `story`, `platform`, `enhancement`

Define official runtime support tiers and their scope before any macOS or
Windows implementation hardens Linux-only assumptions.

## Product Outcome

Users and developers know whether their host is supported, which runtime tier
they are using, and which guarantees are unavailable before they run a
money-adjacent demo.

## User Story

As a developer-community evaluator, I want Tickoni to name the supported
runtime tier for my Mac or Windows machine, so that I can run the right demo
path without assuming Linux-equivalent performance or isolation.

## Scope

- In scope: define tier language, map workflows to tiers, specify degraded-
  guarantee visibility rules.
- Out of scope: macOS/Windows implementation decisions (separate stories),
  Firedancer porting (S2), installer design (S4/S5).

## Preconditions And Assumptions

- V2.14 established the Linux full-runtime tier with Firedancer process and
  shared-memory topology.
- Linux remains the default high-throughput tier unless a separate decision
  approves native parity.

## Acceptance Criteria

- [ ] Given a host OS and architecture, when the user checks tier definitions,
      then the output identifies Linux full-runtime, macOS retail runtime,
      Windows retail runtime, container/WSL2/VM-assisted mode, or unsupported.
- [ ] Given a supported tier, when the user selects a workflow, then the tier
      explicitly states which workflows are supported (build-only,
      doctor-only, deterministic paper demo, CaseOps review, replay proof,
      sandbox adapter substitute, full Linux tile runtime) and which are not.
- [ ] Given degraded guarantees (performance, sandboxing, networking, shared
      memory, execution), when the runtime reports tier status, then the
      degradation is visible in CLI, CaseOps, audit, replay, and docs.
