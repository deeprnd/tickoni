# V3.19.S6: System Availability Panel (SYSTEM Function)

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V3.19: Tickoni Native Investment Terminal
**Labels:** `type/story`, `area/platform`

Show compact terminal/system availability in the SYSTEM function panel: source,
freshness, bus status, gateway availability, and fixture/runtime mode. Not a
full operations console.

## Product Outcome

Runtime owners and reviewers can distinguish unavailable data from a policy
denial by seeing a compact availability summary — sufficient to tell the
difference between a runtime gap and a finance decision.

## User Story

As a runtime owner, I want compact system availability indicators in the
terminal, so that I can distinguish a policy denial from an unavailable API,
stale data, or disconnected backend.

## Scope

- In scope: compact status indicators for CASE function data freshness (e.g.,
  "DATA 12s"), bus status ("BUS OK" / "BUS DEGRADED"), fixture/runtime mode
  indicator (fixture mode vs. live `tk_api`), bus connectivity state; status
  strip integration showing data freshness and bus status as persistent badges;
  SYSTEM function panel with a brief explanation of degraded state (e.g.,
  "fixture data — not live API", "API disconnected — showing stale payload",
  "backend unavailable — action disabled"); no capability catalog cards, no
  adapter ping tables, no approval path lists, no aggregate limit tables, no
  tile health grids, no queue depth displays, no full metrics dashboards, no
  diagnostic workbenches, no capability administration screens.
- Out of scope: capability catalog administration, adapter management,
  approval-path administration, aggregate limit management, tile health dashboards,
  queue depth and backpressure inspection, full metrics summaries, diagnostic
  workbenches, full operations console, capability definitions, adapter
  manifests, or sandbox policy.

## Preconditions And Assumptions

- Availability data is sourced from `tk_api` over shared-memory channels or deterministic
  fixtures.
- Firedancer reuse is limited to generic substrate patterns documented in
  architecture and tile-topology docs.
- The SYSTEM function panel renders inside the terminal shell from S1.
- Firedancer infrastructure is referenced generically (queues, topology,
  workspaces, metrics, diagnostics) — no Solana validator tile IDs, RPC
  schemas, or validator-specific concepts are exposed.

## Acceptance Criteria

- [ ] Given available system data, when the SYSTEM function renders, then data
      freshness, API status, and fixture/runtime mode are visible as compact
      indicators.
- [ ] Given unavailable API fixture data, when the SYSTEM function renders, then
      the panel clearly states the backend is unavailable and related action
      controls are disabled or unavailable.
- [ ] Given fixture mode, when the SYSTEM function renders, then the panel
      identifies that the terminal is running in fixture mode, not against live
      runtime.

### Conditional Acceptance

**Financial capability and policy**

- [ ] N/A - system panel does not display policy decisions; it shows availability
      status that contextualizes whether a policy denial is trustworthy.

**Audit and replay**

- [ ] N/A - system panel does not alter or display audit/replay records directly.

**Runtime topology and tile ownership**

- [ ] N/A - system panel does not display tile topology; it shows availability
      status only, not Tile IDs or link shapes.

**Model, tool, adapter, or execution boundary**

- [ ] Availability status is display-only; no direct provider or adapter calls
      are introduced by the system panel.

**CaseOps API or UI**

- [ ] System availability data is loaded from `tk_api` or deterministic fixtures,
      not from raw process scraping in UI code.

**Storage role: Memory, Analytics, Ledger**

- [ ] N/A - system panel does not touch storage roles.

**Metrics, diagnostics, and operations**

- [ ] N/A - system panel shows availability summary only; it does not render
      full metrics or diagnostic dashboards.

**Security and fail-closed behavior**

- [ ] Given a backend disconnect, when the SYSTEM function renders, then action
      state in other functions transitions to disabled or unavailable rather
      than showing stale data.

## Evidence Plan

- Demo or command: local UI flow using available, unavailable API, and fixture
  mode fixtures.
- Tests: render available, unavailable, and fixture mode states.
- Fixtures or samples: system availability summary, API disconnected, fixture
  mode indicators.
- Audit/replay evidence: N/A - system availability only.
- Blocked-flow evidence: unavailable API fixture showing disabled actions.
