# V6.31: Crypto And Stablecoin Guard

**Status:** Later
**Milestone:** M6
**Labels:** `epic`, `area/crypto`, `area/security`

V6.31 adds guardrails for crypto and stablecoin transfers. It checks wallet, network, asset, chain-risk, travel-rule, and amount scope before a transfer proposal is accepted, while keeping execution proposal-only — no crypto transfer executes autonomously.

## Product Intent

V6.31 checks crypto transfers. Trading authority stays separate from transfer authority. No crypto transfer executes autonomously. It gives crypto or stablecoin users and operators a pre-flight gate on wallet safety, network support, asset allowlist, chain-risk tier, travel-rule status, and amount limits.

## Users And Jobs

- [Crypto/stablecoin user]: Verify that a withdrawal, deposit, or portfolio move is safe before it touches a wallet, network, or custody account.
- [CaseOps operator]: Review crypto transfer proposals with wallet, network, asset, chain-risk, travel-rule, and amount controls surfaced in one view.
- [Compliance operator]: Enforce travel-rule status and chain-risk tier requirements on crypto transfers before approval.

## Success Metrics

- A stablecoin transfer proposal is fully scoped (wallet, network, asset, chain-risk, travel-rule, amount) before policy evaluation.
- Unsupported tokens, unsafe wallets, high-risk chains, and missing travel-rule evidence return `deny` or `require_approval` deterministically.
- All allowed proposals, blocked wallets, unsupported networks, and missing evidence produce audit and replay artifacts.
- No crypto transfer executes autonomously across paper, sandbox, or live paths.

## Demo Moment

- Command or flow: `just tktest crypto-transfer-proposal --fixture stablecoin_internal_transfer`
- Expected result: A `crypto_transfer.propose` policy decision of `allow` or `require_approval` with wallet, network, asset, chain-risk, travel-rule, and amount fields populated in audit output; no adapter call to any external system.

## Scope

### In Scope

- Crypto and stablecoin capability: `crypto_transfer.propose`.
- Asset allowlist: BTC, ETH, USDC, USDT, SOL, and approved test assets.
- Network allowlist: Bitcoin, Ethereum, Solana, stablecoin networks, L2.
- Wallet allowlist per asset and network.
- Custody account scope and counterparty/exchange account checks.
- Chain-risk tier classification.
- Travel-rule status checks where applicable.
- Per-transaction, per-day, per-month amount limits.
- Proposal modes: internal transfer, withdrawal, deposit reconciliation, stablecoin cash movement.
- Stablecoin cash-impact view alongside brokerage cash.
- Policy outcomes: `deny`, `require_approval`, `require_more_evidence`, `escalate`.
- Audit and replay artifacts for all proposal outcomes.

### Out Of Scope

- `crypto_transfer.initiate` — denied until approved sandbox/live execution.
- Trading authority or trading execution.
- On-chain transaction submission or signing.
- Real wallet or exchange connectivity; stub adapters only.
- Multi-chain bridge routing or cross-chain transfers.
- AML/KYC/sanctions screening beyond travel-rule status and chain-risk tier.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  - Check whether a crypto or stablecoin transfer proposal is safe — wallet, network, asset, chain-risk, travel-rule, and amount scope — before approval.
- What changed from the previous roadmap increment?
  - `crypto_transfer.propose` is a first-class capability with guard evaluation, replaceable by the existing payment/trading proposal surfaces.
- What is this epic's wow-effect?
  - An operator sees wallet allowlist status, chain-risk tier, travel-rule compliance, and amount limits for a crypto proposal in one view — the same deterministic checks that prevent execution.
- How does this epic progress Tickoni's unique value proposition?
  - Policy-gated action (fail-closed on unsupported tokens/unsafe wallets), forensic replay (all proposal outcomes audited and replayable), and consequence isolation (execution denied by default).
- Which demo command or CaseOps flow closes the epic?
  - `just tktest crypto-transfer-proposal` — deterministic local inputs, no external systems.
- Which account, wallet, network, asset, and amount checks are enforced?
  - Asset allowlist, network allowlist, wallet allowlist, custody account scope, chain-risk tier, travel-rule status, per-transaction/day/month limits.
- What happens when the requested action exceeds policy, scope, or evidence?
  - `deny` for unsupported tokens or unsafe wallets. `require_approval` or `require_more_evidence` for high-risk chains or missing travel-rule data. `escalate` for edge cases.
- Is execution paper-only, draft-only, sandbox, live, or disabled?
  - Disabled. `crypto_transfer.propose` only; `crypto_transfer.initiate` denied.
- Which fixtures, samples, audit records, replay capsules, or API examples prove the behavior?
  - Stablecoin internal transfer fixture, withdrawal fixture with unsupported wallet, high-risk chain fixture, missing travel-rule fixture.
- Can replay run without external side effects when replay applies?
  - Yes. Replay capsules substitute captured adapter outputs; no external systems called.
- What intentional blocked-flow or divergence example proves fail-closed behavior?
  - Transfer to an unallowlisted wallet address returns `deny`. Transfer on an unsupported network returns `deny`. Missing travel-rule evidence returns `require_more_evidence`.
