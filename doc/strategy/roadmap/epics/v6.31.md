# V6.31: The Crypto Transfer Checklist — Deterministic Safety Before Human Approval

**Labels:** `type/epic`, `area/crypto`, `area/security`
**GitHub Issue:** [26](https://github.com/deeprnd/tickoni/issues/26)

---

## The Why

We believe that in a financial system, the machine should earn trust through determinism, and the human should earn trust through judgment. They should never share the same risk.

Right now, a CaseOps operator staring at a crypto transfer request without a complete safety view is not approving anything. They are gambling. They are asked to verify wallet allowlists, network compatibility, asset validity, chain-risk tiers, travel-rule compliance, and amount limits — and then decide "yes" or "no" — without understanding blockchain internals, without deterministic evidence, and without a frame that tells them which dimension matters and which one is already solved.

That is not a human judgment problem. That is a machine verification problem. And when a machine asks a human to do the machine's job, both fail.

The operator doesn't need more checks. The operator needs a signal that turns six open questions into one clear answer: go, pause, or dead. The machine does the verification. The human makes the call. They never share the same risk.

This is the Circle of Safety for the financial operator. Inside it, the machine has already done the boring so the human can do the brave. Outside it, the operator is alone with uncertainty — and uncertainty is where trust dies.

---

## The Problem (As Engineers Frame It, And Why That Frame Is Wrong)

The logical problem is: "Operators don't have enough data to approve crypto transfers safely."

The logical fix is: "Build a better checklist." Add more fields. More data points. More verification steps.

But good analysis taught us the opposite of a good idea can also be a good idea. And the opposite of a checklist isn't no checklist — it's a perception layer so clean that the operator doesn't need to *think* about compliance at all.

Think of the Eurostar example: the engineering answer to "people find the London-Paris train too long" is to spend billions cutting journey time. The psycho-logic answer is to make the existing journey something people don't want to end. You'd have people asking for the train to be slower.

The crypto transfer checklist has the same dynamic. You don't fix operator anxiety by giving them more data. You fix it by making the data so deterministic and so visually legible that the operator never has to feel anxious in the first place.

Six green signals aren't "more checks." They're the *absence* of questions. And the absence of questions feels different from the presence of checks — even though they contain the same information.

**The problem isn't "people need more data." The problem is "people shouldn't need to understand blockchain internals to approve a transfer." The fix is psychological, not technical. The machine does the work. The operator sees the result.**

## The What

V6.31 makes `crypto_transfer.propose` a first-class capability with a deterministic six-dimension safety envelope. Every proposal arriving at a human operator is already scored, already scoped, and already backed by audit evidence.

The six dimensions:
1. **Wallet** — is the counterparty allowlisted?
2. **Network** — is this chain supported?
3. **Asset** — is this token valid on this network?
4. **Chain-Risk Tier** — what is the risk classification of this chain?
5. **Travel-Rule Status** — is compliance evidence present and complete?
6. **Amount Limits** — does this fit within per-transaction/day/month bounds?

Each dimension produces a signal: green (pass), amber (attention needed), or red (dead). No ambiguity. No default-allow. No "maybe check this yourself."

The operator sees a single proposal with six colored signals and a deterministic policy decision. They don't need to understand how the machine arrived at those signals. They need to trust that it did.

---

## The How

The mechanism is straightforward, but the framing matters. This isn't a checklist bolted on after the fact. It's the check *before* the question.

| Dimension | Input Source | Output | Policy Outcome |
|-----------|-------------|--------|----------------|
| Wallet allowlist | Stub adapter (read-only) | ✓ / ✗ | ✗ → deny |
| Network allowlist | Stub adapter (read-only) | ✓ / ✗ | ✗ → deny |
| Asset allowlist | Stub adapter (read-only) | ✓ / ✗ | ✗ → deny |
| Chain-risk tier | Analytics store / static mapping | L1-L4 | L3+ → require_approval |
| Travel-rule status | Evidence store | present / missing | missing → require_more_evidence |
| Amount limits | Capability scope | within / exceeded | exceeded → deny or require_approval |

The policy engine (`tkpoly`) evaluates all six dimensions *before* the proposal ever reaches a human. The outcome is one of: `allow`, `deny`, `require_approval`, `require_more_evidence`, or `escalate`. No soft failures. No default-allow.

Every outcome — allowed, blocked, escalated — produces append-only, hash-chained audit records. Replay capsules substitute all adapter outputs, so deterministic replay never calls external systems.

### What the Operator Actually Sees

This is where the psycho-logic matters most. The operator doesn't see a spreadsheet of checks. They see:

```
  Wallet allowlisted      [✓]
  Network supported       [✓]
  Asset confirmed         [✓]
  Chain-risk tier         L1  [✓]
  Travel-rule compliant   [✓]
  Amount within limits    [✓]
  
  Policy decision: allow
```

Or, with a blocked wallet:

```
  Wallet allowlisted      [✗]  ← UNAPPROVED ADDRESS
  Network supported       [✓]
  Asset confirmed         [✓]
  Chain-risk tier         L1  [✓]
  Travel-rule compliant   [✓]
  Amount within limits    [✓]
  
  Policy decision: deny
```

Six signals. One decision. No thinking required.

## Scope

### In Scope

- Crypto and stablecoin capability: `crypto_transfer.propose`.
- Six-dimension safety score: wallet allowlist, network allowlist, asset allowlist, chain-risk tier, travel-rule status, per-transaction/day/month amount limits.
- Custody account scope and counterparty/exchange account checks.
- Proposal modes: internal transfer, withdrawal, deposit reconciliation, stablecoin cash movement.
- Stablecoin cash-impact view alongside brokerage cash.
- Policy outcomes: `deny`, `require_approval`, `require_more_evidence`, `escalate`.
- Audit and replay artifacts for all proposal outcomes.
- Stub adapters for wallet, network, and asset data (read-only).

### Out Of Scope

- `crypto_transfer.initiate` — denied until approved sandbox/live execution.
- Trading authority or trading execution.
- On-chain transaction submission or signing.
- Real wallet or exchange connectivity; stub adapters only.
- Multi-chain bridge routing or cross-chain transfers.
- AML/KYC/sanctions screening beyond travel-rule status and chain-risk tier.

## Release / Evidence Gate

- **What can the user or operator do now that they could not before this epic?**
  See six deterministic safety signals for any crypto or stablecoin transfer before approval — wallet status, network support, asset validity, chain-risk tier, travel-rule compliance, and amount limits — instead of six open questions.

- **What changed from the previous roadmap increment?**
  `crypto_transfer.propose` becomes a first-class capability with a complete safety envelope, replacing the previous state where crypto proposals arrived at approval without systematic pre-flight checks.

- **What is this epic's wow-effect: the visible moment in this epic's demo or workflow that makes Tickoni feel unlike a generic agent harness?**
  The operator sees a single proposal with six colored signals — green, amber, or red — and a deterministic policy decision. The same view that prevents bad transfers from ever reaching approval. But the wow isn't the signals themselves. The wow is that the operator doesn't have to *think* to read them. Six green lights mean "go." No analysis. No doubt. That's the difference between a checklist and a trust signal.

- **How does this epic progress Tickoni's unique value proposition from doc/strategy/positioning.md: speed, isolation/control, spend governance, policy-gated action, and forensic replay?**
  Policy-gated action: every dimension verified before the human sees it. Forensic replay: every pass and block audited and reconstructable. Consequence isolation: execution denied by default, always.

- **Which demo command or CaseOps flow closes the epic?**
  `just tktest crypto-transfer-proposal` — deterministic local inputs, no external systems.

- **Which account, wallet, network, asset, and amount checks are enforced?**
  Asset allowlist, network allowlist, wallet allowlist, custody account scope, chain-risk tier, travel-rule status, per-transaction/day/month limits.

- **What happens when the requested action exceeds policy, scope, or evidence?**
  `deny` for unsupported tokens or unsafe wallets. `require_approval` or `require_more_evidence` for high-risk chains or missing travel-rule data. `escalate` for edge cases.

- **Is execution paper-only, draft-only, sandbox, live, or disabled?**
  Disabled. `crypto_transfer.propose` only; `crypto_transfer.initiate` denied.

- **Which fixtures, samples, audit records, replay capsules, or API examples prove the behavior?**
  Stablecoin internal transfer fixture, withdrawal fixture with unsupported wallet, high-risk chain fixture, missing travel-rule fixture.

- **Can replay run without external side effects when replay applies?**
  Yes. Replay capsules substitute captured adapter outputs; no external systems called.

- **What intentional blocked-flow or divergence example proves fail-closed behavior?**
  Transfer to an unallowlisted wallet address returns `deny`. Transfer on an unsupported network returns `deny`. Missing travel-rule evidence returns `require_more_evidence`.
