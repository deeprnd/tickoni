# V7.15: The Autopilot Envelope — Trust Through Bounds, Not Promises

**Status:** Later
**Milestone:** M7
**Labels:** `epic`, `area/agents`, `area/platform`, `type/feature`

Agents that can loop forever, drain tokens silently, or pretend to be someone else are not autonomous — they are liabilities. The question is not whether agents can work faster. The question is whether operators can trust them when they do. V7.15 answers that question by wrapping every agent run inside a deterministic envelope: step limits, retry caps, token budgets, and identity propagation — all enforced as auditable policy events, not runtime errors. The machine defines the boundaries. The operator sees the trail. Agents operate at speed because the bounds make speed safe.

## Product Intent

Current Tickoni V1.11 agents run inside governed tile boundaries with capability envelopes, but the run itself has no lifecycle. An agent could loop indefinitely, exhaust its token budget with no record, or present a different identity on a downstream request. Generic solutions add timeouts and hope. Tickoni does better: budget exhaustion, step limits, and identity drift become explicit policy events with audit records and deterministic terminal states. The operator never sees an agent panic. They see an agent finish — normally or by bounds — with a complete audit trail.

The product promise: **an agent run ends with an audit record, not an unhandled exception.** Whether the agent completed its work or hit a limit, the operator sees a deterministic outcome with context, not a crash dump.

## Users And Jobs

- [CaseOps operator]: Inspect every agent run's lifecycle — running, completed, or bounded — with explicit audit records showing what happened, why it stopped, and what the agent saw.
- [Compliance operator]: Know that no agent can loop indefinitely, silently drain a token budget, or impersonate another identity. Every boundary violation is captured, not suppressed.
- [Engineering operator]: Replay agent runs with envelope fields preserved, knowing that step counts, retry sequences, and budget consumption are deterministic artifacts, not implementation details.

## Success Metrics

- Every agent run transitions to an explicit terminal state (completed, step-limit-exceeded, retry-limit-exceeded, budget-exhausted, policy-denied, or error) with an audit record.
- Budget exhaustion, step-limit violation, and identity substitution attempts produce audit records with concrete counts, limits, and budget IDs — no ambiguity.
- A budget-exhausted run cannot issue further model requests, even when the model fixture would respond.
- Replay restores run-envelope fields deterministically; envelope fields are captured and restored during replay without external side effects.
- No agent run terminates via an unhandled panic or silent truncation.

## Demo Moment

- Command or flow: `just tktest run-envelope --fixture step_limit_exceeded`
- Expected result: An agent run drives to step-limit-exceeded, emits a deterministic audit record with step count and limit, and halts gracefully — no panic, no unhandled exception. A second command drives to budget-exhausted with the same pattern. A third shows normal completion. Three terminal states, three audit records, one consistent interface.
- Command or flow: `just tktest run-envelope --fixture identity_substitution`
- Expected result: An agent attempt to present a different identity or role on a downstream request is denied. The denial is captured as an audit record with the original envelope identity and the attempted substitution.

## Scope

### In Scope

- Agent run envelope: run id, agent identity, role, workflow, case or synthetic run id, policy version, capability envelope id, step limit, retry limit, token budget id, start time, and run state.
- Run state machine: running, completed, step-limit-exceeded, retry-limit-exceeded, budget-exhausted, policy-denied, error. Budget-exhausted and step-limit-exceeded are expected terminal states, not runtime errors.
- Step counter: each iteration of an agent reasoning loop increments the counter; limit hit transitions to step-limit-exceeded with audit record.
- Retry counter: agent-level retry counter independent of model-level retry; limit hit transitions to retry-limit-exceeded.
- Budget exhaustion: token budget tracked per run; exhaustion emits audit record with budget type, budget id, consumed tokens, and token limit before halting.
- Identity propagation: agents carry explicit role and identity from the run envelope on every model, tool, and adapter request; substitution is denied.
- Metrics export through `tkmetr`: completed runs, step-limit-exceeded runs, retry-limit-exceeded runs, budget-exhausted runs.
- Integration fixtures and audit JSONL samples for each terminal state.

### Out Of Scope

- New agent capabilities or tools.
- Changes to `tkmodl` dispatch, `tktool` dispatch, or replay substitution mechanics.
- Changes to capability envelopes, policy rules, or audit record schema.
- New approval paths or execution authority.
- External model-provider, API, or adapter connectivity changes.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  See every agent run's lifecycle as an auditable sequence — from running through to a terminal state — with explicit counts, limits, and budget context. Before this, exhausted budgets and step overruns were runtime errors; now they are policy events with audit records.

- What changed from the previous roadmap increment?
  V1.11 agents ran inside governed boundaries but had no formal lifecycle. V7.15 adds a run envelope with explicit step limits, retry caps, token budgets, and identity propagation — each boundary enforced as an auditable state transition, not an advisory guard.

- What is this epic's wow-effect: the visible moment in this epic's demo or workflow that makes Tickoni feel unlike a generic agent harness?
  An agent hits its step limit and the terminal shows a graceful halt with an audit record reading "step_limit_exceeded: 100/100 steps, budget: 42000/50000 tokens." No crash. No panic. No silence. The same pattern repeated for budget exhaustion and retry exhaustion. Three limits, three records, one interface.

- How does this epic progress Tickoni's unique value proposition from doc/strategy/positioning.md: speed, isolation/control, spend governance, policy-gated action, and forensic replay?
  Spend governance: every token spent is accounted against a per-run budget with an audit record. Isolation/control: agents cannot substitute identity or continue after budget exhaustion. Forensic replay: envelope fields captured and restored deterministically. Speed enabled by bounds: operators can trust agents because the envelope makes autonomy safe, not reckless.

- Which demo command or CaseOps flow closes the epic?
  `just tktest run-envelope` — deterministic local inputs, no external systems.

- Which checks are enforced?
  Step limit, retry limit, token budget, and identity propagation from envelope. All enforced at runtime with audit records on transition.

- What happens when a run exceeds its limits?
  Step limit: transitions to step-limit-exceeded, emits audit record, halts. Retry limit: transitions to retry-limit-exceeded. Budget exhausted: transitions to budget-exhausted, emits audit record, denies further model requests. Identity substitution: denied with audit record.

- Is execution paper-only, draft-only, sandbox, live, or disabled?
  Paper-only. Unchanged from V1.11.

- Which fixtures, samples, audit records, replay capsules, or API examples prove the behavior?
  Run envelope fixtures for step-limit-exceeded, retry-limit-exceeded, budget-exhausted, and completed states. Audit JSONL samples for each terminal state. Malformed envelope rejection tests. Fail-closed validation tests.

- Can replay run without external side effects when replay applies?
  Yes. Replay capsules capture and restore envelope fields; no external systems called.

- What intentional failure proves failure behavior?
  Budget-exhausted run that cannot issue a further model request even when the model fixture would respond. Identity substitution attempt that is denied with audit record. Zero-limit envelope that fails validation.
