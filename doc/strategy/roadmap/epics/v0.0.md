# V0.0: Proof Of Correctness

**Status: Done**
**Milestone: M0**
**Labels: `epic`, `area/platform`, `area/security`, `area/trust`, `area/audit`**

The AI-powered financial systems problem is not "can AI think?" — it is "can we trust what it did?"

Every day, financial operators and auditors face a binary: they either *believe* a system produced the right result, or they cannot verify it at all. Most systems live in the latter category. They produce output, and you take their word. In finance, "take their word" is not a strategy — it is a liability.

V0.0 gives Tickoni a property that almost no AI system can claim: it can prove it produces the same result, given the same input, every single time. The proof is not in a test report or a performance benchmark. It is in a replay you can run yourself, offline, with no network and no external systems, that walks you through the identical event path and tells you whether the result matches.

This is not a technical convenience. It is the only trust boundary that matters when AI touches money. Everything else in Tickoni — policy enforcement, audit trails, bounded agents, adapter gating — sits on top of this proof. Without it, every later claim of "safe" or "verified" or "governed" is just a demo with no way to verify.

---

## Product Intent

Tickoni solves the verification problem in agentic finance. Institutions cannot deploy AI systems that touch money unless those systems can be proven deterministic, auditable, and replayable. V0.0 delivers the runtime foundation that makes that proof possible: events enter, flow through deterministic processing, and leave behind a hash-chained audit trail that any operator or auditor can independently verify through replay.

V0.0 proves Tickoni can:
- Accept synthetic financial events with stable framing, source attribution, and backpressure control
- Normalize events to canonical facts with content-stable hashes that survive process restart
- Deduplicate by idempotency key and content hash — not timing or insertion order
- Evaluate capability envelopes with explicit allow/deny/require-approval outcomes
- Record append-only, hash-chained audit events that form a verifiable chain
- Replay a captured run with external effects completely disabled and detect divergence
- Report health and diagnostic state through Firedancer's metrics and diagnostics infrastructure

This is the trust foundation. Every later epic builds on the ability to say "watch the replay" — not "trust the system."

## Users And Jobs

- [Auditor/Compliance Officer]: Replay any run with external effects disabled and independently verify the audit chain matches, without relying on the system's word
- [Operator]: Feed financial events through the full pipeline and confirm deterministic, reproducible output before any human approval is required
- [Risk Manager]: Observe policy-enforced capability envelopes (allow/deny/require-approval) as explicit, auditable decisions, not implicit system behavior
- [Researcher/Analyst]: Run the same event sequence repeatedly in a sandbox and confirm zero divergence, enabling reliable experimentation with AI agents
- [Board/Investor]: See a deterministic replay demo that proves the system works the same way every time — the single visible moment that distinguishes Tickoni from every other AI harness

## Success Metrics

- Identical source event payloads produce identical canonical content hashes across process restarts
- The audit chain verify function passes on any journal produced by a normal run
- Replay of an unmodified captured run reports zero divergences every time
- Replay never calls a network endpoint, database, or external system
- Metric counters expose accept/normalize/dedup/policy outcomes/audit/repaly check/match/divergence gauges
- Crash records are structured and queryable through tkdiag
- No tile accepts unvalidated input — all malformed events are dropped with counter exposure

## Demo Moment

One offline command, no network, no external systems:

- Command or flow:
  1. Feed a synthetic financial event through the full pipeline (tkings → tknorm → tkdedu → tkpoly → tkaudt)
  2. Produce an audit record with a complete hash chain
  3. Run the replay against the captured event sequence with external effects disabled
  4. Verify the replay reports zero divergence and the audit chain hashes match
- Expected result: The operator can stand in front of a board and say "here is the replay, here is the chain, it produces the same result every time" — and have it be true.

### How Many Stories

Eight stories cover the full pipeline: ingest → normalize → dedupe → policy → audit → replay → metrics. Each story delivers one capability and can be verified independently, though the complete proof requires all eight in sequence.

### Decomposition Rules

1. **Independent delivery**: each story produces a verifiable capability (ingest, normalize, dedupe, etc.)
2. **One capability per story**: no story mixes ingestion with normalization or policy with audit
3. **Split by capability lifecycle**: S1 = orchestration, S2–S7 = pipeline stages, S8 = observability
4. **Closure story**: each story's child tasks (T10) handle evidence, demo, and quality gates
5. **Domain boundaries**: each pipeline stage is a separate story; telemetry is its own story

### Bad Splits (Avoid)

- Combining two pipeline stages (e.g., "ingest and normalize") into one story — they have distinct ownership and failure modes.
- Putting the policy evaluation inside the audit story — tkpoly and tkaudt are separate trust boundaries.
- Merging metrics into any pipeline stage — observability is orthogonal to the event path.

## Dependencies And Decisions

- V0.0 has no prerequisite epics — it is the foundation.
- Decision: V0.0 uses Firedancer infrastructure (tango queues, workspace discipline, metrics, diagnostics) as the transport layer, but does not introduce Solana validator semantics, RPC, or validator tile identities as Tickoni concepts.
- Decision: Synthetic events replace live data for the entire V0.0 phase. Live integration is deferred until capability is proven structurally.
- Decision: Replay substitution replaces model, adapter, and execution calls — no LLM server, trading API, payment API, or tkexec is reachable during replay.
