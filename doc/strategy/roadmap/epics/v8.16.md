# V8.16: Tool Broker Boundary — One Path to Every Adapter

**Labels:** `type/epic`, `area/agents`, `area/platform`, `area/security`, `area/trust`
**GitHub Issue:** [35](https://github.com/deeprnd/tickoni/issues/35)

Every tool call that an agent or model makes enters Tickoni through a door. Right now that door has two different shapes — model-native function calls and MCP-style requests — and they take different routes through the system. A third route exists too: any caller that knows the adapter interface can bypass the door entirely. V8.16 closes those backdoors by making every tool request pass through `tktool` as a single, normalized, registry-validated, adapter-dispatched call. After this epic, the path from a model's function call to a financial adapter is identical regardless of how the request arrived.

Extracted from V1.11.S8.

---

## Product Intent

V1.11 established the rule: all tool calls must go through `tktool`. But the enforcement mechanism was stub-backed — a call carried a capability envelope in theory, the tool request schema existed on paper, and the allowed tool registry was a placeholder. Model-native function calls and MCP-style requests traveled different normalization paths, and the direct-adapter bypass (agent → adapter, no `tktool`) was untested.

V8.16 builds the enforcement layer. It normalizes every invocation protocol into a single tool request record, validates every call against the live allowed tool registry, dispatches exclusively through `tkadpt`, and records every decision — allow, reject, substitute — in the audit trail. The constraint that all tool calls look the same at the boundary is not a limitation; it is the trust signal. When every path converges, every path is governable.

## Users And Jobs

- **Governed agent**: I issue tool requests whether as model-native function calls or MCP-style requests, so I never accidentally bypass the tool broker and every request carries a verified capability envelope.
- **CaseOps operator**: I inspect audit output that identifies the invocation protocol, see unknown-tool and missing-envelope rejections, and confirm the direct-adapter bypass is closed.
- **Compliance reviewer**: I can replay tool dispatches with external effects disabled, and the replay capsule contains the normalized request, the registry lookup result, and the adapter substitution.
- **Runtime engineer**: I verify that no path from model output or agent action reaches `tkadpt` except through `tktool`, confirmed by automated regression tests.

## Success Metrics

- Model-native function calls and MCP-style requests for the same tool produce byte-identical normalized tool requests at the `tktool` boundary.
- Unknown tool names are rejected before adapter dispatch; rejection records are visible in audit output.
- Tool requests with missing or empty capability envelopes are rejected before adapter dispatch.
- Direct adapter calls that bypass `tktool` are denied; confirmed by regression test.
- Replay substitution replaces adapter results without calling live adapters; audit output shows replay substitution ID.
- `just test-unit-tk` and `just test-integration-tk` pass with tool broker tests included.

## Demo Moment

- Command: `just test-integration-tk` with the tool broker test suite
- Expected result: A single deterministic run shows model-native and MCP-style calls producing identical normalized requests, an unknown-tool rejection, a missing-envelope rejection, and a direct-adapter bypass denial — all visible in audit JSONL output.

## Scope

### In Scope

- Tool request schema at the `tktool` boundary with invocation protocol field
- Normalization of model-native function calls and MCP-style requests into identical records
- Validation against the configured allowed tool registry
- Dispatch exclusively through `tkadpt`
- Audit fields for tool requests: request id, tool name, invocation protocol, adapter id, input/output hashes, latency, result status, replay substitution id
- Direct adapter call rejection path (no bypass from agent or model output to `tkadpt`)
- Replay substitution for captured adapter results
- Integration test suite covering normalization, rejection, and bypass paths
- Tool broker metrics exported through `tkmetr`

### Out Of Scope

- New adapter implementations
- New tools or capabilities added to the registry
- Changes to `tkmodl` dispatch or agent run governance
- New provider configuration surfaces
- External ingestion or partner review endpoints
