# V8.16: Tool Broker And MCP-Compatible Dispatch

**Status: Planned · Milestone: M7**

**Epic:** #TBD · **Issue:** #TBD
**Labels:** `epic`, `area/agents`, `area/platform`

Build the full `tktool` boundary: normalize model-native function calls and
MCP-style requests into a single tool request schema, validate against the
allowed tool registry, and dispatch exclusively through `tkadpt`. V1.11 routes
tool calls through a stub-backed `tktool`; this increment closes the bypass
path and makes model-native and MCP-style calls indistinguishable at the
adapter boundary.

Extracted from V1.11.S8.

---

## Product Intent

V1.11 establishes that tool calls must go through `tktool`. The dispatch
mechanism is stub-backed: calls carry a capability envelope but the tool
request schema, invocation protocol normalization, and registry validation are
not yet built. V8.16 adds the enforcement layer so that a model-native function
call and an MCP-style request for the same tool produce the same normalized
request, and so that unknown tools, missing envelopes, or direct adapter calls
fail closed before any adapter dispatch.

## User Story

As a governed agent, I can issue tool requests through `tktool`, whether as
model-native function calls or MCP-style requests, so that adapters are never
reached directly and every tool dispatch carries a verified capability envelope
and a stable normalized request.

## What The Operator Sees

- normalized tool requests in audit output with invocation protocol field
  distinguishing model-native function calls from MCP-style requests
- unknown-tool rejection records with tool name and capability envelope id
- missing-capability-envelope rejection records
- direct-adapter-call rejection records confirming the bypass path is closed
- replay substitution id in tool request audit output when a captured adapter
  result is used

## Success Demo

- [ ] A model-native function call and an MCP-style request for the same tool
  produce byte-identical normalized tool requests at the `tktool` boundary.
- [ ] An unknown tool name is rejected before adapter dispatch; the rejection is
  visible in audit output.
- [ ] A tool request with a missing capability envelope is rejected before
  adapter dispatch.
- [ ] A direct adapter call that bypasses `tktool` is denied.
- [ ] Replay substitution replaces the adapter result without calling the live
  adapter.

## Release Gate

- `just test-unit-tk` passes with no unexpected skips
- `just test-integration-tk` passes offline against local mocks
- model-native and MCP-style calls for the same tool produce identical
  normalized requests
- unknown tool name and missing envelope each fail closed before adapter dispatch
- no path from agent or model output reaches `tkadpt` directly

## Non-Goals

- no new adapter implementations
- no new tools or capabilities added to the registry
- no changes to `tkmodl` dispatch or agent run governance

## WBS

### V8.16.S1: Normalized tool request and registry validation

**Issue:** #TBD

**Description:** Define tool request schema with invocation protocol field, normalize model-native function calls and MCP-style requests into identical records, validate against allowed tool registry, dispatch only through tkadpt, emit audit fields.

Tasks:

- V8.16.S1.T1: Define a tool request schema at the `tktool` boundary: tool
  request id, tool name, invocation protocol, actor id, role, workflow, case or
  synthetic run id, policy version, capability envelope id, and input hash.
- V8.16.S1.T2: Define invocation protocol as an enum: model-native-function-call
  and mcp-tool-call. Model-native function calls from a model response are
  normalized into the same tool request schema as MCP-style requests before any
  adapter dispatch.
- V8.16.S1.T3: Validate the tool request at the `tktool` boundary: tool name
  must be in the configured allowed tool registry, invocation protocol must be
  recognized, and capability envelope must be present and non-empty. Invalid
  requests fail closed before any adapter dispatch.
- V8.16.S1.T4: Dispatch normalized tool requests to `tkadpt` only. Agents and
  model output must not reach `tkadpt` directly; `tktool` is the only permitted
  dispatch path.
- V8.16.S1.T5: Emit tool request audit fields: request id, tool name,
  invocation protocol, adapter id, input hash, output hash, latency, result
  status, and replay substitution id when applicable.
- V8.16.S1.T6: Add tests for model-native function call normalization, MCP-style
  request normalization, unknown tool name rejection, missing capability envelope
  rejection, direct adapter call rejection, and replay substitution.

Acceptance:

- A model-native function call and an MCP-style request for the same tool
  produce identical normalized tool requests at the `tktool` boundary.
- An unknown tool name or missing capability envelope is rejected before any
  adapter dispatch.
- Agents and model output cannot reach `tkadpt` except through `tktool`.
