# V2.21: macOS Retail Runtime Support

**Status:** Done
**Milestone:** M2
**Labels:** `epic`, `area/platform`, `area/operations`, `area/security`, `area/trust`, `type/enhancement`

<!-- One paragraph: what complete feature this epic delivers and why now. -->

Build on v2.14's Firedancer process and shared-memory topology work so Tickoni
runs on consumer macOS hardware. Linux remains the high-throughput Firedancer
tile runtime, but now a consumer user with a MacBook or Mac desktop can run the
same policy-gated demos, audit output, and replay proofs that engineers run on
Linux. The same trust surface, the same financial boundaries, on consumer
hardware. No Linux workstation required. No enterprise toolchain.

Consumer users, reviewers, and developer-community evaluators on macOS should
not need a tuned Linux workstation before they can inspect a policy-gated money
proposal, audit trail, or replay proof. V2.21 turns platform support into part
of the trust surface: every build, installer, demo, and audit artifact must
say which Tickoni version, host OS, architecture, runtime tier, and isolation
guarantees produced it.

This continues v2.14 by deciding how the Linux process/shared-memory topology
is exposed to retail Mac users without forcing unsafe portability shortcuts
into Firedancer substrate. Minimal adaptation of Firedancer tiles and code is
a constraint: reuse or wrap generic substrate deliberately, exclude Solana
validator semantics from distributed artifacts, and keep platform-specific
substitutes behind Tickoni-owned support-tier decisions.

## Users And Jobs

- Consumer-money user: run a local Tickoni demo on a MacBook or Mac desktop
  and see policy decisions, proposal hashes, audit output, and replay proof
  before any live money path exists.
- Developer-community evaluator: build and run the supported retail runtime on
  consumer Mac hardware with clear preflight failures instead of
  reverse-engineering Linux-only Firedancer assumptions.
- CaseOps operator or partner reviewer: know exactly which platform tier and
  Tickoni version produced a proposal or replay artifact on macOS.
- Runtime owner: preserve the high-throughput Linux Firedancer engine while
  making portable runtime limits, sandbox gaps, and unsupported features
  visible and fail-closed on macOS.
- Security reviewer: verify installers, checksums or signatures, no-secrets
  defaults, per-user install locations, disabled live execution, and no hidden
  privilege escalation on macOS.

## Success Metrics

- A supported macOS retail path can build or install Tickoni and run the
  selected deterministic paper/sandbox demo on consumer hardware.
- `tickoni --version`, `tickoni doctor`, and demo preflight output identify
  Tickoni version, build id, git revision or release digest, OS, architecture,
  runtime tier, isolation tier, demo compatibility, and live-execution status.
- Deterministic fixture flows produce equivalent normalized event hashes,
  policy outcomes, proposal hashes, audit records, and replay results across
  Linux full-runtime mode and supported macOS retail mode.
- Unsupported host capabilities, stale demo manifests, unsupported CPU/OS
  combinations, and attempted live execution fail closed with actionable
  diagnostics on macOS.
- macOS packages include only Tickoni-owned code and the Firedancer substrate
  Tickoni actually reuses; Solana validator tiles, RPC schemas, and unrelated
  source are excluded.
- Install and update paths provide a manual verification route with checksums,
  signatures, or attestations, and do not request broker, payment, crypto,
  approved execution ledger, or live model-provider credentials.

## Demo Moment

- Command or flow: install or build Tickoni on a supported macOS machine, run
  `tickoni doctor`, then run the selected retail demo manifest for a
  deterministic paper investment or money-movement proposal.
- Expected result: the user sees the platform tier, disabled live execution,
  policy-checked proposal, audit JSONL, replay match, version/provenance
  metadata, and a blocked-flow example when the host or demo version is
  unsupported.

## Scope

### In Scope

- Define official support tiers for Linux full-runtime, macOS retail runtime,
  container/WSL2/VM-assisted modes, and unsupported hosts.
- Decide the first macOS support path: native portable mode, Linux container
  (Colima), VM packaging, or a documented hybrid.
- Inventory Linux-only Firedancer and Tickoni assumptions that affect consumer
  build/run support, isolation, determinism, packaging, or conformance.
- Limit build, test, and coverage to only the Firedancer modules Tickoni
  actually reuses for macOS retail modes — macOS must not try to port what
  it does not need.
- Decide target-specific Tickoni C ABI bridge behavior: Linux may link real
  Firedancer libraries, while macOS retail mode must either link only
  proven-portable Firedancer subsets or use Tickoni-owned substitutes.
- Preserve the high-throughput Firedancer engine as the Linux full-runtime tier
  while allowing consumer Mac hardware to run supported proof/demo flows.
- Add version, build metadata, release digest, platform tier, isolation tier,
  and demo-manifest compatibility requirements to the product plan.
- Plan official install, update, uninstall, checksum/signature, and manual
  verification paths for macOS.
- Make platform mode and degraded guarantees visible in CLI, CaseOps, audit,
  replay, metrics, diagnostics, and documentation where they affect trust.
- Define cross-platform conformance evidence for deterministic fixture flows
  between Linux full-runtime and macOS retail mode.
- Define package inclusion rules so only reused Firedancer substrate ships in
  consumer artifacts.

### Out Of Scope

- No silent port of the full Firedancer hot path to macOS before measured
  evidence.
- No throughput-parity claim for macOS before measured evidence.
- No weakening of capability envelopes, audit hash chaining, replay
  substitution, adapter boundaries, sandbox expectations, or fail-closed
  behavior for portability.
- No live trading, payments, crypto transfers, ledger posting, writes, or privileged execution on consumer macOS mode.
- No production financial credentials during install, preflight, first run, or
  demo on macOS.
- No replacement of the Tickoni tile architecture with a generic
  cross-platform service backend.
- No direct import of Solana validator tile identities, RPC schemas, or
  validator runtime assumptions into Tickoni platform support.
- No assumption that `libfd_tango.a`, `libfd_util.a`, or `libfd_ballet.a`
  compile, link, or export the same symbols natively on macOS. Runtime
  `if supported` checks are not sufficient when the compiler or linker cannot
  resolve the Firedancer symbol in the first place.
- Windows retail runtime implementation (scoped to V2.22 epic).

## Dependencies And Decisions

- V2.21.S2 shipped the build-scope filter and Firedancer reuse inventory that
  keep macOS retail support limited to the substrate Tickoni actually reuses.
- V2.22 (Windows) reuses the tier/preflight/conformance/trust framework but is
  not part of this epic's shipped support claim.
- First macOS support path decision: native retail path with user-scoped build /
  install surfaces; container/Colima/VM flows are not required for the official
  V2.21 support path.
- Installer and distribution: Deferred to V3.23 (Separate epic: "Distribute a
  Runnable Tickoni Package with Installation, Verification, and Update Flow").
  V2.21 proved the runtime compiles and runs on macOS; no binary package is
  shipped. The `retail-runtime-support.md` documents the planned install layout
  (`~/.tickoni/bin/`, `~/.tickoni/demos/`, `~/.tickoni/evidence/`) but the
  installer was not implemented.
- CaseOps platform-tier/degraded-guarantee display is explicitly deferred beyond
  V2.21; the shipped trust surface is CLI + audit/replay/demo evidence.
