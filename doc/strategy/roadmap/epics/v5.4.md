# V5.4: Target Exposure And Rebalance Suggestions

**Labels:** `type/epic`, `area/investing`, `area/platform`
**GitHub Issue:** [24](https://github.com/deeprnd/tickoni/issues/24)

> **The problem this solves:** Investors don't need rebalancing. They need certainty that their portfolio isn't quietly drifting toward risk they never asked for. The logical fix is a spreadsheet that tells you you're wrong — the psycho-logic fix is a system that shows you the drift before you feel it and proposes a correction that carries the same policy discipline as every other financial action.
>
> People don't pay for exposure computation. They pay for the absence of anxiety about it. V5.4 builds the surface that turns raw drift into a controlled, auditable proposal — the same frame that makes a payment proposal feel governable rather than surprising.

Target exposure management and deterministic rebalance suggestion generation:
users set target allocations by sector or asset class, and the system computes
exposure drift against targets to produce `portfolio.rebalance.propose`
envelopes with explicit scope dimensions. Rebalance suggestions are
computation-drafted (deterministic exposure diff), not agent-drafted, so they
are replay-stable. V5.4 owns the rebalance proposal surface; exposure
computation is V5.29, watchlist is V5.5, and model governance is V5.2.

Extracted from the M5 backlog proposal.

## Product Intent

Tickoni can compute exposure (V5.29) but has no rebalance surface. V5.4 adds
target exposure management and deterministic rebalance suggestions: users set
target allocations, the system computes drift (current minus target), and
produces `portfolio.rebalance.propose` capability envelopes for any drift that
exceeds configured thresholds. Rebalance suggestions are proposals only — no
execution path. They carry the same policy discipline as trading proposals:
actor, role, workflow, case/run id, scope, policy version, and explicit
concentration limit checks via `tkpoly`.

### The Why

Generic portfolio tools show drift as a number on a dashboard. That's the
engineering answer: compute `current − target`, display the delta, and hope the
user acts on it. The problem with that approach is that a number is not an
action — it's a source of anxiety.

V5.4 reframes drift from "a statistic you ignore" into "a controlled proposal
you can review, policy-check, and approve or deny." The surface is not a chart;
it is a `portfolio.rebalance.propose` envelope that enters Tickoni's full policy
and audit pipeline. The same mechanism that governs a trading proposal also
governs a rebalance proposal. That's the differentiator: the user doesn't need
to learn a new "advisory" mental model because there isn't one. Every suggestion
is a financial consequence proposal, and every proposal is governed.

### The Psycho-Logic

A faster drift calculation is expensive and already solved. The unexploited
opportunity is the proposal surface itself. When drift appears as a capability
envelope — with actor, scope, concentration limits, and a policy decision —
the user doesn't feel like they're looking at a portfolio tool. They feel like
they're operating a financial control system. The computation is the same; the
framing changes the experience of the output entirely.

## Users And Jobs

- Consumer investor: set target allocations by sector or asset class, see
  current drift against targets, receive rebalance suggestions when drift
  exceeds thresholds.
- Risk reviewer: inspect rebalance envelopes for policy compliance, verify
  that suggestions are computation-drafted (deterministic), confirm that
  concentration limits are enforced by `tkpoly`.
- CaseOps operator: review rebalance proposals with full capability scope,
  policy decision, and replay capsule.

## Success Metrics

- Target exposure can be set and persisted per portfolio.
- Rebalance suggestions are computed deterministically from exposure drift,
  producing `portfolio.rebalance.propose` envelopes with explicit scope
  dimensions.
- Concentration limits (per-name and per-sector) are checked by `tkpoly` on
  every rebalance proposal.
- No live model, broker, payment, trading, crypto, approved execution ledger, or execution
  side effects occur unless this epic explicitly enables an approved sandbox path.

## Scope

### In Scope

- Target exposure management: set and persist target allocations by sector
  or asset class per portfolio.
- Drift computation: deterministic difference between current and target
  exposure.
- Rebalance suggestion generation: computation-drafted (deterministic)
  `portfolio.rebalance.propose` envelopes with explicit scope dimensions.
- Concentration limits: per-name cap and per-sector cap checked by `tkpoly`.
- Policy outcomes: `allow`, `deny`, `require_approval`, `require_more_evidence`,
  or `escalate` on every rebalance proposal.

### Out Of Scope

- Exposure computation (V5.29).
- Watchlist management (V5.5).
- Automatic valuation queue (V5.5).
- Model tier selection (V5.2).
- Portfolio optimization (Markowitz, Black-Litterman).
- Factor models or alpha generation.
- Agent-drafted rebalance suggestions (computation-drafted only for
  determinism).
- Live order placement or any execution path.

### How Many Stories

V5.4 is a mid-range epic (target management + drift/rebalance proposals + visibility + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: target exposure storage + drift computation
   in S1+S2 respectively — the target management and proposal generation are
   distinct capabilities (storage vs computation + policy), each independently
   testable.
3. **Split by capability lifecycle**:
   - S1: Core capability — target exposure management: set and persist target
     allocations with validation, stored in the analytics store.
   - S2: Core capability — drift computation and rebalance proposal generation:
     deterministic exposure diff producing `portfolio.rebalance.propose` envelopes
     with `tkpoly` concentration limit checks.
   - S3: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces rebalance proposals with full capability scope, policy decision,
     and replay capsule.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: target storage (S1), drift/rebalance computation
   (S2), and CaseOps surface (S3) are separate stories, not features within one.

### Bad Splits (Avoid)

- Target exposure storage + "drift" as two stories. Drift is part of the rebalance
  computation contract, but target management is a separate capability (storage
  vs computation).
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.
