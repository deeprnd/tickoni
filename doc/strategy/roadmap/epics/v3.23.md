# V3.23: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow

**Status:** Backlog
**Milestone:** M3
**Labels:** `epic`, `area/operations`, `area/platform`, `area/security`, `area/trust`, `type/enhancement`

<!-- One paragraph: what complete feature this epic delivers and why now. -->

V2.21 and V2.22 proved the runtime compiles and runs natively on macOS and
Windows. Now V3.23 ships the first distributable package — downloadable,
verifiable by SHA256 checksum, installable without admin, uninstallable with
evidence preserved. The runtime works, but V3.23 makes it accessible. This is
the point where Tickoni leaves the lab and becomes a product.

V3.23 ships user-scoped installer artifacts, a manual verification harness
(checksums and optional signatures), update and uninstall flows, and a platform-
aware release pipeline that produces the same Tickoni binary for Linux full-
runtime, Windows retail, and macOS retail. The trust surface (version, tier,
evidence) is now shipped, not just documented.

## Product Intent

A consumer user on any supported platform can install Tickoni without admin
privileges, verify the package against published checksums, run `tickoni doctor`
and a deterministic paper demo, update safely, and uninstall cleanly. Every
installed artifact carries version, OS, architecture, runtime tier, and isolation
tier metadata.

This is a trust signal that most financial products cannot make: download,
verify, install, and walk away — without admin rights, without embedded hooks,
without live financial credentials. The installer refuses to run on unsupported
hosts, never requests broker or model credentials, and disables live execution
by default.

## Users And Jobs

- Consumer-money user: install Tickoni on a consumer laptop/desktop, run a
  paper demo, see policy-checked proposals and replay proofs without any admin
  credentials or Linux-only toolchain.
- Partner reviewer / auditor: download a release artifact, verify its checksum
  against published hashes, inspect audit/replay evidence locally, and uninstall
  without losing evidence unless explicitly requested.
- Developer-community evaluator: install a pre-built Tickoni package for their
  platform and architecture, run doctor and demo, compare conformance results
  against Linux full-runtime, and update when a new version ships.
- Runtime owner: maintain a release pipeline that produces per-platform, per-
  architecture binary packages with checksums, manages the update lifecycle,
  and documents the uninstall path.

## Success Metrics

- A supported platform user can install Tickoni without sudo/admin, run
  `tickoni --version` and `tickoni doctor`, and execute a deterministic paper
  demo on first install.
- Every release artifact includes published SHA256 checksums (and optional
  signatures when the signing infrastructure is available). A user can verify
  checksums before running the installer.
- `tickoni update` or a documented reinstall path preserves `~/.tickoni/evidence/`
  and `~/.tickoni/demos/` while replacing only the runtime binaries and configs.
- `tickoni uninstall` (or documented manual removal) removes binaries and runtime
  files without deleting audit/replay evidence unless the user explicitly requests
  a full reset.
- The installer reports the installed Tickoni version, OS, architecture, runtime
  tier, and isolation tier; the installed `tickoni doctor` output matches the
  release metadata.
- Unsupported hosts fail closed with an explicit diagnostic instead of silently
  installing an unsupported binary.

## Demo Moment

- Command or flow: download the release artifact for the user's platform, verify
  SHA256 against published checksums, run the installer (per-user, no admin), then
  execute:

  ```bash
  ~/.tickoni/bin/tickoni --version
  ~/.tickoni/bin/tickoni doctor --plain
  ~/.tickoni/bin/tickoni-supervisor demo investment --plain \
    --manifest ~/.tickoni/demos/demo.manifest.json
  ```

- Expected result: version output shows Tickoni version, git revision, OS,
  architecture, runtime tier, isolation tier; doctor reports the support path
  (native Linux full-runtime, Windows retail, macOS retail); demo produces
  deterministic policy-checked proposal, audit JSONL, and replay match; live
  execution is disabled; all evidence artifacts are local.

## Scope

### In Scope

- Define per-platform installer targets:
  - Linux: tarball (`.tar.gz`) with post-install script or shell alias; winget
    package (`.yaml`) for Windows; no .deb/.rpm at this stage.
  - macOS: tarball (`.tar.gz`) with post-install helper; .pkg is out of scope
    but the tarball path supports manual verification.
  - Windows: tarball (`.tar.gz`) with PowerShell install helper; winget manifest
    (`.yaml`) for per-user install.
- Produce per-platform, per-architecture release binaries:
  - `tickoni` (CLI — version/doctor)
  - `tickoni-supervisor` (demo/audit/replay)
- Publish SHA256 checksums for each release artifact alongside a signed manifest
  or checksum list. If signature infrastructure is not yet available, publish
  checksums only and document the manual verification path.
- Document and implement the update path: download, verify checksum, replace
  binaries, preserve `~/.tickoni/evidence/` and `~/.tickoni/demos/`.
- Document and implement the uninstall path: remove binaries, leave evidence
  intact by default, allow full reset if user opts in.
- Ensure no admin or elevated privileges are required for install, update, or
  uninstall. User-scoped paths (`~/.tickoni/`, `%LOCALAPPDATA%\tickoni\`) are
  the default on all platforms.
- Ensure the installer fails closed on unsupported hosts (wrong OS, wrong
  architecture, too-old Windows) with an explicit diagnostic.
- Ensure installer telemetry is disabled by default; no outbound calls during
  install.
- Ensure the installer does not request broker, payment, crypto, approved execution ledger, or
  live model-provider credentials.

### Out Of Scope

- Signed release artifacts / code-signing infrastructure (key management,
  Sigstore, GPG, minisign). Documented as a follow-on decision.
- App-store distribution (Microsoft Store, Homebrew tap, Linux distro repos).
- Automatic background self-update. Update requires user action (download +
  install or `tickoni update`).
- Cross-platform unified binary. Each platform ships its own build.
- Windows MSI installer or macOS `.pkg` at this stage. `.tar.gz` + helper
  scripts are the default.
- CaseOps integration for release management.
- Multi-architecture single binary (e.g., macOS Universal Binary). Separate
  artifacts per architecture.

## Dependencies And Decisions

- V2.21 (macOS) and V2.22 (Windows) must produce buildable binaries before this
  epic can package them. The release pipeline consumes `zig-out/bin/tickoni` and
  `zig-out/bin/tickoni-supervisor` artifacts.
- `doc/execution/retail-runtime-support.md` already documents the planned install
  layout (`~/.tickoni/bin/`, `~/.tickoni/demos/`, `~/.tickoni/evidence/`), manual
  verification path, update path, uninstall path, and privacy defaults. This epic
  implements what those docs prescribe.
- The support tier model is defined in V2.21.S1/V2.22.S1 (`platform-tiers.md` +
  `tier.zig`). Installers must respect the tier (Linux full, macOS retail, Windows
  retail).
- A signing infrastructure decision (Sigstore, GPG, minisign, platform-native)
  is needed separately. Checksums only are sufficient for V3.23; signing is
  out of scope but documented as a follow-on.
- Distribution channel decisions (winget, Homebrew, Linux distro repos) are
  deferred. V3.23 provides tarballs + winget for Windows as the minimum viable
  distribution surface.
- Minimum version manifest for demos (already defined in S3 of V2.22) must be
  respected by the installed runtime.
