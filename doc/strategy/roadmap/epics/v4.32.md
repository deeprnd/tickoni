# V4.32: The Valuation That Proves Itself — Every Assumption Visible, Every Result Defensible

**Labels:** `type/epic`, `area/investing`, `area/platform`
**GitHub Issue:** [19](https://github.com/deeprnd/tickoni/issues/19)

> In finance, the number itself is not the product. The trust behind the number is. A valuation that can't be questioned is not a valuation — it's a guess wearing a spreadsheet. V4.32 gives the Tickoni runtime the one thing no generic tool can: a computation where every assumption is visible, every step is hashable, and every result is replayable from first principles. The real benefit isn't that it computes DCF math. The benefit is that it makes assumptions auditable — so any analyst, auditor, or operator can verify the result and be certain.

This epic does not ingest data, run Monte Carlo, produce per-share conclusions, or integrate with policy — it establishes the pure math engine that other epics consume. It is the foundation of institutional trust in Tickoni's valuation layer.

## The Why

Every institution has a moment where a number stops being a number and becomes a liability.

A portfolio manager shows a committee a DCF output. The committee asks one question: "walk me through the assumptions." The spreadsheet is six months old, built by a former analyst, and every input is buried in merged cells with no source. The number was probably right. But the institution can't defend it — and in finance, a number you can't defend is worth less than no number at all.

Generic valuation tools solve the wrong problem. They compete on speed, interface polish, and feature breadth. They produce point estimates with opaque assumptions — hidden ERP, implicit beta, unmodeled country risk — and the user is expected to trust the black box. Trust is the competitive advantage in finance. A black box that hides its assumptions is an anti-feature.

The real problem is not that institutions lack valuation tools. It's that institutions lack valuation *trust*. A DCF with transparent inputs and hash-chained outputs beats a black-box model every time — not because the math is different, but because you can prove it.

This is what V4.32 solves. It doesn't make the computation faster. It makes the computation *defensible*.

## The Reframe

**Rename:** This is not an "audit-grade valuation engine." An audit-grade tool is something you use *after* the damage is done. V4.32 is a *trust engine* — something that proves its own correctness before anyone has reason to doubt it. The name signals prevention, not documentation.

**Re-anchor the comparison:** The competitive question isn't "which tool computes DCF fastest?" It's "which tool produces a valuation an auditor can verify from scratch, given only the inputs?" Speed is a table-stakes feature. Defensibility is the differentiator.

**Reframe the context:** Generic tools frame valuation as "compute a number from financial data." V4.32 reframes it as "prove a number from first principles." The user doesn't need another calculator. They need a computation they can show a committee and say "verify it yourself."

The product promise:

**Every valuation assumption is visible. Every computation is replayable. Every result is provable.**

## Product Intent

Institutional valuation requires academic discipline: explicit equity risk premium, explicit beta, explicit term structure, explicit country risk premium. These assumptions are not nice-to-haves — they are the difference between a number you can act on and a number you can't defend. Aswath Damodaran's methodology at NYU Stern demonstrates that transparent, reproducible valuation is not just academic rigor — it's operational trust.

Generic valuation tools produce point estimates with hidden assumptions. Academic valuation discipline — explicit ERP, explicit beta, explicit term structure, explicit country risk, explicit scenario trees — makes assumptions auditable and replayable. V4.32 brings that discipline into the Tickoni runtime as a native `tkval` tile, producing enterprise value from canonical financial facts with deterministic, seed-stable computation.

Every cost-of-equity component is broken out: risk-free rate, equity risk premium, beta, country risk premium. Every FCFF projection year is traceable to its growth rate input. Every terminal value is computed by two independent methods (Gordon Growth and exit-multiple cross-check), with divergence reported — because in valuation, agreement between methods is signal, and disagreement is the signal.

Same inputs, same output, always. Not a spreadsheet. Not a black box. A computation you can audit.

## Users And Jobs

- Portfolio analyst: run a DCF on canonical financial facts and get a base-case enterprise value with cost-of-equity breakdown and terminal value components — and verify every number from input assumptions. The "wow" is closing the laptop and knowing the number is defensible.
- Risk reviewer: audit which assumptions (WACC, growth rate, terminal value method) drove the valuation, with full traceability from output to input. The "wow" is finding a hidden sensitivity in five seconds that would take an hour of spreadsheet spelunking.
- CaseOps operator: see a valuation result card showing inputs, method, and enterprise value range from the base and cross-check models — and trust that the result is what it claims to be.
- Engine builder: compose higher-level valuation stories (Monte Carlo, scenario, conclusion) on top of `tkval` without re-implementing DCF math. The "wow" is that every layer inherits the trust property from the foundation.

## Success Metrics

- Given canonical FCFF facts and policy inputs, the system produces a base-case enterprise value with cost-of-equity breakdown (risk-free rate, equity risk premium, beta, country risk premium) and terminal value via Gordon Growth.
- Same inputs produce byte-identical output under replay with external effects disabled — the same DCF always yields the same result, every time.
- An exit-multiple terminal value cross-check runs alongside Gordon Growth and reports divergence percentage, giving the operator a second lens on terminal value reasonableness.
- The `tkval` tile wires into the Firedancer topology with explicit links from `tknorm` (input facts) and to `tkmetr` (output counters).
- All numerical outputs are traceable to input assumption fields in a canonical struct; no hardcoded constants bypass audit.

## Story Breakdown

### How Many Stories

Five stories covering tile scaffold, per-metric computation, and orchestration with audit/replay closure. Each metric gets its own story so the math can be tested, verified, and reasoned about in isolation before wiring into the full DCF pipeline.

### Decomposition Rules

1. Independent delivery: each story produces a testable `tkval` slice.
2. One metric per story: WACC, FCFF, terminal value each have distinct input schemas, computation logic, and test fixtures.
3. Split by capability domain: topology, per-metric math, DCF orchestration, audit/replay are separate stories.
4. Closure via T10 child tasks in the final story.
5. Story dependencies flow forward: S1 enables S2–S4, S2–S4 feed S5.

### Bad Splits (Avoid)

- Splitting WACC into sub-stories (risk-free rate, beta, ERP separately) — WACC is one computed value with multiple input dimensions, same story.
- Splitting FCFF into yearly projections — the 5-year projection is one function, same story.
- Adding scenario analysis, Monte Carlo, or per-share valuation — out of scope (V4.24, V4.25).

### Good Split Example


#### V4.32.S2: WACC computation — risk-free rate, ERP, beta, country risk premium, cost of equity, cost of debt

T10:
1. Implement `tk_val_compute_wacc()` in `backend.zig`: receives
   `TkValDCFInput`, returns WACC components (risk-free rate, ERP, beta,
   country risk premium, cost of equity)
2. Implement cost of equity: `r_e = r_f + beta × (ERP + CRP)`
3. Implement cost of debt: `r_d = r_f + credit_spread` (credit spread derived
   from country rating or assumed from input)
4. Implement weighted average: `WACC = (E/V) × r_e + (D/V) × r_d × (1 - tax_rate)`
   where E/V and D/V come from input struct market-cap / debt ratio
5. Add bounds-checking: cost of equity > risk-free rate; WACC positive; beta
   within declared bounds; ERP non-negative
6. Handle edge case: debt ratio not provided — default to equity-only WACC
   (D/V = 0)
7. Write unit tests:
   a. Happy path: AAPL FY2023-like inputs produce expected WACC (~9–11%)
   b. Zero debt: equity-only computation matches cost of equity
   c. Negative ERP: validation fails, returns error
   d. Beta > 3: validation fails, returns error
   e. Negative growth rate: validation fails, returns error
8. Update metrics counters: wacc_computed, validation_failure (in S1 stubs)
9. Ensure deterministic output: same inputs → same floating-point result (no
   thread-local state, no randomness)
10. Write unit test for WACC edge cases (all inputs at boundary: beta=0,
    beta=3, ERP=0, tax_rate=0, tax_rate=1)

Inputs: `TkValDCFInput` (populated by S1 fixture)
Outputs: `TkValDCFOutput.wacc`, `TkValDCFOutput.cost_of_equity`,
  `TkValDCFOutput.cost_of_debt`, `TkValDCFOutput.cost_of_equity_breakdown`
Test: unit tests a–e pass. WACC for AAPL FY2023-like fixture is within
  expected range (9–11%).
Verification: WACC breakdown fields show each component (r_f, beta, ERP, CRP).

#### V4.32.S3: FCFF projection engine — 5-year projection with explicit growth rate, margin, and capex inputs

T10:
1. Implement `tk_val_project_fcff()` in `backend.zig`: receives
   `TkValDCFInput` with base FCFF and growth assumptions, returns 5-year
   FCFF projection array
2. Implement explicit growth phase: each year `FCFF_t = FCFF_{t-1} × (1 + g_t)`
   where `g_t` comes from input struct (explicit yearly growth rates)
3. Handle margin-based projection: if revenue and margin inputs present,
   compute `EBIT_t = revenue_t × margin_t`, then `NOPAT_t = EBIT_t × (1 - tax_rate)`,
   then `FCFF_t = NOPAT_t + DDA_t - capex_t - working_capital_change`
4. Implement capex as percentage of revenue or explicit capex input
5. Add validation: growth rates bounded (0–50% per year), revenue not negative,
   FCFF negative is allowed (investing company)
6. Handle flat-growth shortcut: if explicit yearly rates not provided, use
   single growth rate for all 5 years
7. Write unit tests:
   a. Happy path: AAPL FY2023 base FCFF, 5 explicit growth rates produces
      projected FCFF array
   b. Flat-growth mode: single growth rate applied to all 5 years
   c. Negative FCFF: allowed, projection continues
   d. Zero revenue: validation fails
   e. Growth rate > 50%: validation fails
8. Update metrics counters: fcff_projected, fcff_projection_year
9. Ensure deterministic output: same inputs → same FCFF projection (no
   randomness, no thread-local state)
10. Write unit test for capex-driven projection: revenue, margin, capex % all
    present → FCFF computed from NOPAT + DDA - capex - WC change

Inputs: `TkValDCFInput` with base FCFF, explicit growth rates (or flat rate),
  optional revenue/margin/capex fields
Outputs: `TkValDCFOutput.fcff_projections[5]`, `TkValDCFOutput.growth_rate_used`
Test: unit tests a–e pass. Projection matches hand-calculated values for
  simple case (single growth rate, constant FCFF base).
Verification: `TkValDCFOutput` contains all 5 projected FCFF values with
  corresponding growth rates.

#### V4.32.S4: Terminal value — Gordon Growth method, exit-multiple cross-check, divergence calculation

T10:
1. Implement `tk_val_gordon_growth()` in `backend.zig`: receives last-year FCFF,
   terminal growth rate, WACC → returns terminal value
2. Implement Gordon Growth formula: `TV = FCFF_n × (1 + g_term) / (WACC - g_term)`
3. Implement exit-multiple method: `TV = FCFF_n × exit_multiple`
4. Implement divergence calculation: `divergence = |TV_gordon - TV_multiple| / TV_gordon`
5. Add validation: terminal growth rate < WACC (required for Gordon Growth
   convergence); exit multiple positive; terminal growth rate reasonable
   (< long-term GDP growth, typically < 5%)
6. Handle edge case: WACC <= terminal growth rate → error (Gordon Growth
   undefined)
7. Update metrics counters: terminal_value_computed, terminal_value_method,
   divergence_reported
8. Write unit tests:
   a. Happy path: Gordon Growth TV matches hand calculation
   b. Exit multiple TV matches hand calculation
   c. Divergence calculation correct when both methods applied
   d. WACC <= terminal growth: validation fails
   e. Negative terminal growth: allowed, projection continues
   f. Exit multiple = 0: validation fails
9. Ensure deterministic output: same inputs → same terminal values
10. Write unit test for WACC exactly equal to terminal growth (boundary case
    — should fail validation, not divide to infinity)

Inputs: `TkValDCFOutput.wacc`, `TkValDCFOutput.fcff_projections[4]` (last year),
  terminal growth rate, exit multiple
Outputs: `TkValDCFOutput.terminal_value_gordon`,
  `TkValDCFOutput.terminal_value_multiple`,
  `TkValDCFOutput.terminal_value_divergence_pct`
Test: unit tests a–f pass. Divergence is 0 when both methods produce same
  input (sanity check).
Verification: `TkValDCFOutput` contains both terminal value methods and the
  divergence percentage between them.

#### V4.32.S5: DCF orchestration, audit, and demo — enterprise value assembly, deterministic output, audit trail, replay, fixtures, demo closure
