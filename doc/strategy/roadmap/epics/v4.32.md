# V4.32: DCF Valuation Engine

**Status:** Backlog
**Milestone:** M4
**Labels:** `epic`, `area/investing`, `area/platform`

Add the core DCF valuation computation pipeline: a `tkval` tile
that accepts canonical financial facts and produces base-case enterprise value
through WACC, FCFF projection, and Gordon Growth terminal value, with an
exit-multiple cross-check. The tile exposes a deterministic, replay-stable
computation boundary within the Tickoni runtime.

This epic does not ingest data, run Monte Carlo, produce per-share conclusions,
or integrate with policy — it establishes the pure math engine that other
epics consume.

## Product Intent

This engine implements the academic valuation methodology published by Aswath Damodaran, using his freely available NYU Stern datasets (ERP, country risk premiums, industry betas) and his public framework for explicit ERP, beta, and term structure assumptions. The engine implements the methodology and computes the math — it is not a branded product. The name "Damodaran" references the data source and philosophy, not a commercial offering.

Generic valuation tools produce point estimates with opaque assumptions.
Academic valuation discipline — explicit ERP, explicit beta, explicit term
structure, explicit country risk, explicit scenario trees — makes assumptions
auditable and replayable. V4.32 brings that discipline into the Tickoni runtime
as a native `tkval` tile, producing enterprise value from canonical financial
facts with deterministic, seed-stable computation.

## Users And Jobs

- Quant researcher: run a DCF on canonical financial facts and get a
  base-case enterprise value with cost-of-equity breakdown and terminal value
  components.
- Risk reviewer: audit which assumptions (WACC, growth rate, terminal value
  method) drove the valuation.
- CaseOps operator: see a valuation result card showing inputs, method, and
  enterprise value range from the base and cross-check models.
- Engine builder: compose higher-level valuation stories (Monte Carlo, scenario,
  conclusion) on top of `tkval` without re-implementing DCF math.

## Success Metrics

- Given canonical FCFF facts and policy inputs, the system produces a
  base-case enterprise value with cost-of-equity breakdown (risk-free rate,
  equity risk premium, beta, country risk premium) and terminal value via
  Gordon Growth.
- The same inputs produce byte-identical output under replay with external
  effects disabled.
- An exit-multiple terminal value cross-check runs alongside Gordon Growth and
  reports divergence percentage.
- The `tkval` tile wires into the Firedancer topology with explicit links from
  `tknorm` (input facts) and to `tkmetr` (output counters).
- All numerical outputs are traceable to input assumption fields in a canonical
  struct; no hardcoded constants bypass audit.

## Demo Moment

- Command or flow: `just val-core-demo` runs a deterministic demo with an
  AAPL FY2023 fixture, loads WACC inputs from a fixture struct, runs the
  DCF engine, and prints enterprise value, cost-of-equity breakdown, and
  terminal value cross-check divergence.
- Expected result: reproducible enterprise value output with all cost-of-equity
  components, Gordon Growth terminal value, exit-multiple cross-check, and
  divergence percentage.

## Scope

- Model provider integration (LLMs) for valuation.
- Market data feeds or live pricing.

## Story Breakdown

### How Many Stories

Small scoped epic — 4 stories covering tile scaffold, core DCF math,
terminal value cross-check, and audit/replay closure.

### Decomposition Rules

1. Independent delivery: each story produces a testable `tkval` slice.
2. One capability per story: core computation, terminal value, audit.
3. Split by capability lifecycle, not layer.
4. Closure via T10 child tasks in the final story.
5. Domain boundaries: topology, computation, audit are separate stories.

### Bad Splits (Avoid)

- "WACC" and "FCFF" as two stories — both are core DCF math, same story.
- "Gordon Growth" and "exit multiple" as two stories — terminal value is one
  capability with two methods, same story.
- Tile scaffold and core computation split — scaffold is scaffolding, not
  independently deliverable.

### Good Split Example

```
V4.32.S1: tkval tile scaffold and core DCF engine — WACC, FCFF, Gordon Growth,
          topology links, and deterministic computation.
V4.32.S2: Terminal value cross-check — exit-multiple method and divergence
          reporting against Gordon Growth.
V4.32.S3: Plugin architecture support — extensible input and output plugins
          for ERP/EDGAR/XBRL and external data sources.
V4.32.S4: Audit trail, replay, and demo closure — evidence, fixtures,
          deterministic demo, and quality gates.
```

## Dependencies And Decisions

- Varanus project availability, licensing, and Zig API surface must be
  confirmed before story implementation begins.
- Decision: DCF computation precision — fixed-point vs floating-point.
  Fixed-point is safer for financial determinism; floating-point is simpler
  and fast enough for analysis-only.
- Decision: whether beta estimation is included (regression against market
  returns) or assumed as input. This epic assumes input-only.
- Depends on V4.34.S4 (market data collection) for live beta/ERP input
  availability; works with fixture input for demo.
- Depends on V4.25.S3 (capability envelope) for policy integration after
  computation.
