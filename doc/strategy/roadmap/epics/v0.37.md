# V0.37: Firedancer Integration Hardening

**Labels:** `type/epic`, `area/platform`, `area/security`
**GitHub Issue:** TBD

Tickoni builds on Firedancer infrastructure — shared-memory queues, topology
builder, workspace discipline, lifecycle, metrics, and diagnostics — but the
repository still carries Agave-specific gating, Solana-specific tile names, and
a build pipeline that entangles the Firedancer validator C build with the
Tickoni Zig supervisor build. This epic hardens the integration: it separates
the build paths so Tickoni builds without Agave, removes Solana/Agave references
from Tickoni-owned code, makes the Firedancer C lib build standalone, adds
testing for the integration boundary, and establishes a clean product topology
that excludes all validator tiles while keeping the infrastructure substrate.

## Product Intent

Operators and CI need a build pipeline that compiles Tickoni without pulling in
Agave, Solana schemas, or validator tile code. The Firedancer C libraries
(tango, util, ballet, disco, waltz) are infrastructure that Tickoni reuses; the
Solana protocol layer (flamenco, frankendancer, validator tiles) is not a
dependency and must not gate Tickoni builds, tests, or CI lanes. This epic
delivers that separation end-to-end: build, test, and topology.

## Users And Jobs

- [CI Operator]: Run Tickoni builds and tests without Agave installed and without
  the Solana validator binary on the path
- [Developer]: Add a new Tickoni tile without accidentally pulling in Solana
  schemas, validator tile names, or flamenco dependencies
- [Reviewer]: Read Tickoni-owned code and verify zero Solana/Agave references
- [Auditor]: Confirm that the product topology excludes all validator tiles and
  the Firedancer C libraries are built in a clean, auditable state

## Success Metrics

- `just build-tk` completes without Agave or any Solana-specific build
  dependencies
- `just test-unit-tk` and `just test-integration-tk` pass with Tickoni built
  standalone (no Frankendancer, no flamenco, no validator tiles)
- `grep -ri 'agave\|flamenco\|solana'` over `src/app/tickoni/` and
  `src/tickoni/` finds zero substantive references (comments mentioning Solana
  as a comparison are acceptable)
- `just build-fd` can be run in isolation to build only the Firedancer C
  infrastructure libraries without requiring the full validator binary
- The product topology in `src/app/tickoni/topologies.zig` registers only
  Tickoni tile IDs; no Firedancer validator tile names appear
- `zig build test`, `zig build integration-test`, and `zig build system-test`
  all pass on Linux without Frankendancer or Agave on the system

## Demo Moment

One machine, no Agave, no Solana tooling installed:

- Command or flow:
  1. `just build-fd` — builds only the Firedancer C infrastructure libs
  2. `just build-tk` — builds the Tickoni Zig supervisor against those libs
  3. `just test-unit-tk && just test-integration-tk` — runs all Tickoni test
     lanes
  4. `grep -ri 'agave\|flamenco' src/app/tickoni/ src/tickoni/` — confirms
     zero references
- Expected result: All steps complete successfully; Tickoni is fully
  independent of Agave and Solana-specific build paths

## Scope

### In Scope

- Remove Agave gating from `build.zig` and Tickoni build helpers
- Remove Agave/Flamenco/Solana references from Tickoni-owned .zig, .c, and .h files
- Make the Firedancer C lib build (`build-fd`) standalone — no validator binary
  required, no Agave required
- Establish Tickoni test lanes that verify the Firedancer integration boundary
  (topology construction, workspace join/leave, link validation, tile lifecycle)
- Clean up the product topology: no validator tiles registered, only Tickoni
  tile IDs
- Update `justfile` build/test recipes to reflect the separated build paths
- Update tile-topology.md and architecture.md to document the clean boundary

### Out Of Scope

- Any changes to Firedancer upstream (no PRs to firedancer-io/firedancer)
- Adding new Tickoni tiles (tile additions belong in a separate epic)
- CaseOps UI, `tkapi`, or HTTP/WebSocket handler changes
- Model gateway (`tkmodl`), tool broker (`tktool`), adapter (`tkadpt`), or
  execution (`tkexec`) implementation
- Agent runtime (`tkdisp`, `tkagnt`) changes
- Frankendancer path removal (that is a separate cleanup effort; this epic
  only removes Agave gating from the Tickoni path)
- Windows build changes beyond ensuring Tickoni tests can run in the Windows
  CI lane

### How Many Stories

Five stories cover the full scope: build isolation, code cleanup, integration
testing, topology hardening, and documentation/closure. Each story delivers an
independently verifiable outcome — you can verify build isolation without the
test suite, and you can verify the test suite without the docs.

### Decomposition Rules

1. **Independent delivery**: each story must be independently verifiable via
   `zig build test`, `just test-*`, or grep-based checks.
2. **One capability per story**: build isolation is one capability (the build
   path), code cleanup is another (the references), integration tests are a
   third (the test boundary), topology is a fourth (the product registry).
3. **Split by capability lifecycle**: S1 = build path, S2 = code cleanliness,
   S3 = runtime integration tests, S4 = product registry, S5 = docs and closure.
4. **Closure story**: S5 handles evidence, demo, documentation, and quality
   gates.
5. **Domain boundaries**: build system and code cleanup are separate from
   runtime topology and tests; each has its own verification method.

### Bad Splits (Avoid)

- Merging build isolation and code cleanup into one story — they have different
  verification methods (build success vs. grep checks).
- Putting integration tests inside the topology story — test coverage and
  topology correctness are separate concerns.
- Combining documentation into any implementation story — docs/closure must
  come last and cover all stories.

## Dependencies And Decisions

- V0.0 is a prerequisite for understanding the baseline Tickoni runtime; V0.37
  refines how it integrates with Firedancer infrastructure.
- Decision: The Firedancer C infrastructure libraries (tango, util, ballet,
  disco, waltz) remain buildable and linkable by Tickoni; only the Solana
  protocol layer (flamenco, validator tiles, frankendancer) is excluded from
  the Tickoni build path.
- Decision: `just build-fd` builds only the Firedancer C infrastructure libs;
  the full Firedancer validator binary is a separate, non-Tickoni build.
- Decision: No changes to Firedancer upstream; all changes are Tickoni-owned
  in `build.zig`, `justfile`, `src/app/tickoni/`, `src/tickoni/`, and docs.
- Decision: Comments in Tickoni-owned code that reference Solana for
  comparison/context (e.g., "unlike a Solana validator tile") are acceptable
  and do not need removal; only substantive code references (imports,
  struct fields, function calls, identifiers) must be cleaned.
