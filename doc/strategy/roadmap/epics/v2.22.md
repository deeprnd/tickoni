# V2.22: Portable Financial-Trust Runtime

**Labels:** `type/epic`, `area/platform`, `area/operations`, `area/security`, `area/trust`, `type/enhancement`
**GitHub Issue:** [14](https://github.com/deeprnd/tickoni/issues/14)

<!-- One paragraph: what complete feature this epic delivers and why now. -->

Financial-trust controls — policy decisions, audit trails, replay proofs — were built on Linux infrastructure, which meant the end-users who should be able to verify institutional-grade finance tools couldn't: they sit on Windows laptops and desktops. V2.22 changes the implicit assumption that trust requires a specific operating system. The Tickoni runtime now carries the same policy gates, the same hash-chained audit, and the same replay discipline to consumer Windows hardware. The trust surface is portable: same financial boundaries, same crash isolation, same audit chain, on Windows. No Linux workstation required. No WSL2. No containers. No enterprise toolchain.

Every institutional-grade financial tool requires enterprise infrastructure. V2.22 changes that assumption. Windows users — native execution, no WSL2, no containers — run the same deterministic paper demos, policy-gated decisions, audit output, and replay proofs that engineers run on Linux. The trust surface is portable: same financial boundaries, same crash isolation, same audit chain, on Windows.

## Product Intent

**Why:** Financial-trust controls should not be platform-gated. When the only way to verify institutional-grade policy decisions, audit trails, and replay proofs is a Linux workstation, the people who most need to trust the system — end-users, small operators, auditors reviewing from consumer machines — are excluded by architecture, not by design.

**What:** Tickoni's retail runtime path now runs on Windows consumer hardware — deterministic paper demos, policy-checked proposals, audit JSONL output, and replay proof — with the same capability envelopes, hash-chained audit records, and fail-closed guarantees as the Linux full-runtime tier.

**Product Promise:** A Windows user installs Tickoni without admin rights, runs `tickoni doctor`, executes a deterministic paper investment demo, and sees policy-checked proposal, audit JSONL, and replay match — with the exact same trust guarantees as the Linux engineering tier.

## Users And Jobs

- Consumer-money user: run a local Tickoni demo on a Windows laptop or desktop
  and see policy decisions, proposal hashes, audit output, and replay proof
  before any live money path exists.
- Developer-community evaluator: build and run the supported retail runtime on
  consumer Windows hardware with clear preflight failures instead of
  reverse-engineering Linux-only Firedancer assumptions.
- CaseOps operator or partner reviewer: know exactly which platform tier and
  Tickoni version produced a proposal or replay artifact on Windows.
- Runtime owner: preserve the high-throughput Linux Firedancer engine while
  making portable runtime limits, sandbox gaps, and unsupported features
  visible and fail-closed on Windows.
- Security reviewer: verify installers, checksums or signatures, no-secrets
  defaults, per-user install locations, disabled live execution, and no hidden
  privilege escalation on Windows.

## Success Metrics

- A supported Windows retail path can build or install Tickoni and run the
  selected deterministic paper/sandbox demo on consumer hardware.
- `tickoni --version`, `tickoni doctor`, and demo preflight output identify
  Tickoni version, build id, git revision or release digest, OS, architecture,
  runtime tier, isolation tier, demo compatibility, and live-execution status.
- Deterministic fixture flows produce equivalent normalized event hashes,
  policy outcomes, proposal hashes, audit records, and replay results across
  Linux full-runtime mode and supported Windows retail mode.
- Unsupported host capabilities, stale demo manifests, unsupported CPU/OS
  combinations, and attempted live execution fail closed with actionable
  diagnostics on Windows.
- Windows packages include only Tickoni-owned code and the Firedancer substrate
  Tickoni actually reuses; Solana validator tiles, RPC schemas, and unrelated
  source are excluded.
- Install and update paths provide a manual verification route with checksums,
  signatures, or attestations, and do not request broker, payment, crypto,
  approved execution ledger, or live model-provider credentials.

## Demo Moment

- Command or flow: install or build Tickoni on a supported Windows machine, run
  `tickoni doctor`, then run the selected retail demo manifest for a
  deterministic paper investment or money-movement proposal.
- Expected result: the user sees the platform tier, disabled live execution,
  policy-checked proposal, audit JSONL, replay match, version/provenance
  metadata, and a blocked-flow example when the host or demo version is
  unsupported.

## Scope

### In Scope

- Define official support tiers for Linux full-runtime, Windows retail runtime,
  container/WSL2/VM-assisted modes, and unsupported hosts.
|- Decide the first Windows support path: **Resolved — native portable Tickoni on Windows (S4.T5).**
  Windows retail runtime implementation is complete per this decision.
- Inventory Linux-only Firedancer and Tickoni assumptions that affect consumer
  build/run support, isolation, determinism, packaging, or conformance on
  Windows.
- Limit build, test, and coverage to only the Firedancer modules Tickoni
  actually reuses for Windows retail modes — Windows must not try to port
  what it does not need.
- Decide target-specific Tickoni C ABI bridge behavior: Linux may link real
  Firedancer libraries, while Windows retail mode must either link only
  proven-portable Firedancer subsets or use Tickoni-owned substitutes.
- Preserve the high-throughput Firedancer engine as the Linux full-runtime tier
  while allowing consumer Windows hardware to run supported proof/demo flows.
- Add version, build metadata, release digest, platform tier, isolation tier,
  and demo-manifest compatibility requirements to the product plan.
- Plan official install, update, uninstall, checksum/signature, and manual
  verification paths for Windows (PowerShell, winget, per-user scope).
- Make platform mode and degraded guarantees visible in CLI, CaseOps, audit,
  replay, metrics, diagnostics, and documentation where they affect trust.
- Define cross-platform conformance evidence for deterministic fixture flows
  between Linux full-runtime and Windows retail mode.
- Define package inclusion rules so only reused Firedancer substrate ships in
  consumer artifacts.

### Out Of Scope

- No silent port of the full Firedancer hot path to Windows before measured
  evidence.
- No throughput-parity claim for Windows before measured evidence.
- No weakening of capability envelopes, audit hash chaining, replay
  substitution, adapter boundaries, sandbox expectations, or fail-closed
  behavior for portability.
- No live trading, payments, crypto transfers, ledger posting, writes, or privileged execution on consumer Windows mode.
- No production financial credentials during install, preflight, first run, or
  demo on Windows.
- No replacement of the Tickoni tile architecture with a generic
  cross-platform service backend.
- No direct import of Solana validator tile identities, RPC schemas, or
  validator runtime assumptions into Tickoni platform support.
- No assumption that `libfd_tango.a`, `libfd_util.a`, or `libfd_ballet.a`
  compile, link, or export the same symbols natively on Windows. Runtime
  `if supported` checks are not sufficient when the compiler or linker cannot
  resolve the Firedancer symbol in the first place.
|- macOS retail runtime implementation (scoped to V2.21 epic).
|- E2E system tests (`just test-e2e-all`) and live LLM tests (`just test-system-tk`) — deferred to V2.10 epic. V2.22 focuses on deterministic fixture-backed demo conformance and cross-platform evidence comparison.

## Dependencies And Decisions

- V2.21.S2 (Done) provides the build-scope filter and Firedancer reuse
  inventory that V2.22 depends on.
- V2.21 (macOS) establishes the pattern for tier definitions, preflight,
  conformance, and trust/docs that V2.22 adapts for Windows.
| Windows support path decision (S4.T5): **Native portable Tickoni on Windows.**
  No WSL2, Docker Desktop, or VM. CI runs directly on Windows 2025 and
  Windows 11 ARM64 runners.
- Installer and distribution: Deferred to V3.23 (Separate epic: "Distribute a
  Runnable Tickoni Package with Installation, Verification, and Update Flow").
  V2.22 proved the runtime compiles and runs; no binary package is shipped.
- Minimum Windows version (S4.T5): **Windows 10 2004+ for x86_64, Windows 11
  for ARM64** (native ARM64 Zig requires Win11).
