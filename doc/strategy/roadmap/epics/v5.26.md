# V5.26: The Audit-Chain Portfolio — Where Every Position Carries Its Own Proof

**Status:** Backlog
**Milestone:** M5
**Labels:** `epic`, `area/investing`, `area/platform`

> **Why this matters:** A portfolio should not be a black box that only exists inside a database session. The belief is simple: when someone puts money behind an idea — buying AAPL, allocating cash, adjusting weights — that decision deserves the same forensic integrity as a payment, a trade, or a ledger entry. Every position should carry its own tamper-evident history, replayable at any point, reconstructable from the audit chain. This is not spreadsheet tracking. This is portfolio-state integrity as a first-class property.
>
> **The psychological truth:** People trust what they can see the full story of. A portfolio is only as trustworthy as its history. By making the entire mutation chain — every add, edit, and deletion — visible, deterministic, and replayable, we don't just build a state machine. We build a *trust asset*. The constraint (audit-chain-only source of truth) is reframed as a signal: you're not storing data, you're preserving intent.

Extracted from the M5 backlog proposal.

## Product Intent

The problem is not that investors cannot track positions — spreadsheet apps do that fine. The problem is that every other portfolio tool treats state as an opaque blob: you see *what* you own, but not *why*, *when*, or *by whose authority* it changed. Tickoni flips this. V5.26 delivers a portfolio state machine where every mutation is a deterministic financial event with a stable payload hash, flowing through the governed event path (`tkings` → `tknorm` → `tkdedu` → `tkaudt`) so that portfolio state is always reconstructable from the audit chain — never from an opaque database session.

This is the foundation for everything else in M5: exposure computation (V5.29), rebalance suggestions (V5.4), watchlist and valuation (V5.5), and model governance (V5.2) all consume portfolio state, but only V5.26 creates and owns it. It is the first place where portfolio ownership becomes an auditable, replayable fact — not a best-effort summary.

We start with the belief that investment intent deserves audit-grade integrity. The "what" (portfolio CRUD) and the "how" (audit-chain reconstruction) follow naturally from that "why."

## Users And Jobs

- Consumer investor: create a portfolio with a base currency, add holdings (shares or notional), adjust quantities, and delete holdings or portfolios — while knowing that every change is preserved with a stable hash and reconstructable at any point. The job is not "manage positions" but "maintain a portfolio whose complete history is self-evident."
- Risk reviewer: audit every portfolio mutation, verify that holdings are valid instruments with positive quantities, and reconstruct portfolio state from the audit chain at any point in time. The job is trust verification without guesswork.
- CaseOps operator: see the full portfolio lifecycle — creation, every edit, deletion — with stable event IDs, hashes, and capability envelopes for each mutation. The job is operational clarity over opaque state changes.

## Success Metrics

- A user can create a portfolio with holdings and cash, edit it (add/adjust/delete holdings), and delete it — each mutation flows through the governed event path and is reconstructable from the audit chain.
- Portfolio mutations are deterministic: the same input always produces the same event hash and audit record.
- Invalid holding records (negative shares, zero quantity, unknown instrument) are rejected by normalization before they reach audit or policy.
- No live model, broker, payment, trading, crypto, approved execution ledger, or execution side effects occur unless this epic explicitly enables an approved sandbox path.
- A risk reviewer can reconstruct portfolio state at any point in time solely from the audit chain, without consulting a secondary data store.

## Demo Moment

- Command or flow: Create a portfolio with base currency USD, add AAPL (50 shares), MSFT (30 shares), TSLA (10 shares), NVDA (20 shares), and USD 5,000 cash. Edit: reduce AAPL to 40 shares. Delete: remove TSLA. Delete portfolio.
- Expected result: deterministic demo output showing portfolio creation event, four audit records for holdings, one edit record, one deletion record, one portfolio deletion record — all reconstructable from the audit chain with stable hashes. The operator can replay from raw events and arrive at the exact same portfolio state.

## Scope

### In Scope

- Portfolio CRUD: create, edit (add/adjust/delete holdings with shares or notional), delete. Base currency support. State reconstructable from audit chain.
- Holding validation: reject negative shares, zero quantity, unknown instruments, and malformed payloads at normalization.
- Stable event hashing: every portfolio mutation produces a deterministic payload hash stored in the audit chain.
- Capability envelope for portfolio mutations: `portfolio.create`, `portfolio.edit`, `portfolio.delete` with actor, role, workflow, case/run id, scope, and policy version.

### Out Of Scope

- Exposure computation and pie chart rendering (V5.29).
- Target exposure management and rebalance suggestion generation (V5.4).
- Watchlist management (V5.5).
- Automatic valuation queue (V5.5).
- Model tier selection and budget enforcement (V5.2).
- Live order placement or any execution path.
- Portfolio optimization, factor models, or performance ranking.
- Tax-lot accounting or harvest-loss tracking.
- Multi-currency portfolio reconciliation (single base currency per portfolio).

### How Many Stories

V5.26 is a mid-range epic (CRUD + visibility + replay + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: CRUD + validation in S1; validation is part of
   the CRUD contract, not a separate story.
3. **Split by capability lifecycle**:
   - S1: Core capability — create/edit/delete with validation, capability
     envelopes, audit trail.
   - S2: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces portfolio state.
   - S3: State lifecycle — replay and state management dependent on S1 being
     stable.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: portfolio CRUD and CaseOps surface are separate stories
   (S1, S2), not features within one story.

### Bad Splits (Avoid)

- CRUD + "validation" as two stories. Validation is part of the CRUD contract.
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.
