# v2.14: Firedancer Process And Shared-Memory Topology

**Status: Done · Milestone: M2**

**Epic:** #TBD · **Issue:** #TBD

V1.11 established a governed tile topology with audit, replay, and no-bypass.
The tile boundaries were logical: tiles shared a process, communicating over
heap-backed queues. v2.14 converts every tile into a real Firedancer-style
runtime unit — a supervisor-managed OS process with its own address space,
communicating over Firedancer Tango `mcache`/`dcache` shared-memory links.

> **The promise:** "Tiles don't talk to each other" is a rule.
> **The guarantee:** "Tiles can't corrupt each other" is physics.

Before this, a crashing tile could silently corrupt its sibling. After v2.14,
each tile runs as a supervisor-managed OS process. A crash is contained,
reported, and isolated. This is the foundation that makes every boundary in
Tickoni trust-worthy rather than theoretical.

> **Why it matters:** Institutions don't audit rules — they audit guarantees.
> Physical crash containment is the signal that makes the entire architecture
> legible to risk teams.

---

## Product Intent

The problem isn't that tiles talk to each other. The problem is that they
*can* — in a shared process, a crash in one tile is indistinguishable from
corruption in another. Every trust boundary built on top of that shared
address space is a promise, not a guarantee.

V2.14 makes Tickoni tile boundaries real. Each tile gets its own OS process,
its own address space, and Firedancer Tango shared-memory links for reliable
inter-tile communication. A crashing tile reports its identity, leaves its
siblings untouched, and triggers the declared crash-only shutdown or restart
path.

The comparison isn't "shared-memory vs heap queues." It's "theoretical
boundaries vs physical guarantees." Every audit, policy decision, and replay
record on top of this foundation becomes verifiable because the substrate
itself prevents the corruption no amount of software logic could fully guard
against.

Tickoni must not inherit a hard "one tile per exclusive core" requirement from
Firedancer validator deployment assumptions. The Linux full-runtime path should
support exclusive affinity where available and explicit shared-core placement
where multiple tiles intentionally reuse the same CPU. That reusable-core model
keeps ordinary developer and consumer hardware viable and leaves room for the
cross-platform retail runtime decisions in V1.21 without weakening the
high-throughput Linux tier.

## Users And Jobs

- **[Operator]:** Start and monitor tile processes, see one entry per tile,
  verify CPU placement, and trust that a tile crash doesn't cascade.
- **[Developer]:** Add a new tile without reverse-engineering topology — one
  source of truth for tile identity, link cardinality, and harness callbacks.
- **[Auditor]:** Inspect supervisor and tile OS identity, link health metrics,
  and crash reports that name the failing tile without ambiguity.
- **[Compliance reviewer]:** Validate that process isolation is structural,
  not procedural — the system enforces containment whether humans are watching.

## Success Metrics

- One OS process per configured tile, verified by supervisor PID + distinct
  child PIDs (not threads in the same address space).
- Zero heap-backed correctness queues in production process mode.
- Crash containment: a forced tile crash leaves sibling state readable and
  uncorrupted, with the supervisor reporting the exact failing tile identity.
- Byte-identical demo and replay output across exclusive-core and shared-core
  CPU configs.
- Zero Firedancer type references outside the `c_abi/` adapter boundary.
- Tile registry is the single source of truth — four independent identity
  mappings collapsed into one.
- Per-tile link arrays (no last-match-wins loss on multi-link tiles).
- Stuck-tile detection: a tile blocked mid-wait is flagged by staleness,
  not masked as healthy quiet.

## Demo Moment

Run `tickoni-supervisor start-process <run-dir>` and watch the supervisor
launch eight distinct processes (one per tile). Crash one by setting
`crash_after_heartbeats`. The supervisor reports the tile identity, siblings
continue processing, and the audit log shows the exact failure chain — no
data corruption, no cascading failure, no ambiguity about which tile failed.

The operator sees: eight PIDs, eight link health metrics, one crash report.
The auditor sees: identical output on exclusive-core and shared-core configs.
The compliance reviewer sees: containment that doesn't depend on a human
reading the logs.

## Scope

### In Scope

- Replace in-process tile threads with supervisor-managed processes for every
  configured tile.
- Back correctness-bearing inter-tile links with Firedancer Tango shared-memory
  (`mcache`/`dcache`); remove heap-backed queues from production.
- Define reliable flow control through `fseq`/`fctl`; backpressure replaces
  drops on correctness links.
- Define workspace lifecycle, link properties (owner, mapping, depth, MTU,
  reliability, restart, shutdown, health metrics) per link.
- Single tile registry as source of truth — collapse four independent identity
  mappings into one.
- Per-tile input/output link arrays replacing single-link fields.
- Real harness reuse: call `fd_topo_run_tile` through a narrow `c_abi` shim
  instead of a hand-rolled Tickoni mirror.
- Stuck-tile defense: heartbeat emission inside work loops + supervisor-side
  staleness detection.
- Sandbox entry via `tk_sandbox_enter` with generated per-tile seccomp-BPF
  policies (wired; namespace elevation deferred to V1.21).
- CPU placement with `exclusive`, `shared`, and `floating` modes; fail closed
  for unavailable or malformed CPU IDs.
- Source-tree normalization: rename ambiguous files, consolidate contracts,
  separate scenarios from runtime tiles, standardize test naming.

### Out Of Scope

- New tile capabilities or policy rules
- Changes to capability envelopes, audit records, or replay capsule shape
- Changes to the investment demo product path
- Changes to upstream Firedancer validator tile semantics, Solana schemas, or
  validator topology ownership
- Hard requirement that every tile must own an exclusive CPU core
- Financial policy, approval, adapter authority, audit schema, or replay
  semantic changes as part of the source-tree migration
- macOS/Windows retail runtime (owned by V1.21)
- The planned `investmentWorkflow()` topology

### How Many Stories

Eight stories cover the full scope: process isolation and shared-memory
integration (S1–S2), source-tree normalization across five stories (S3–S7),
and harness-reuse orchestration (S8). The source-tree work is five parallel
refactors that each deliver visible improvements — renaming, consolidating,
separating, normalizing, and standardizing. They can be done in any order
relative to each other, but S3–S7 must complete before S1–S2's integration
testing is trustworthy because the test and fixture paths must be clean for
isolation verification.

### Decomposition Rules

1. Each story delivers independently verifiable value.
2. One capability per story: runtime isolation, evidence, naming, contracts,
   demo separation, ownership roots, naming standards, harness reuse.
3. Lifecycle split: implementation stories (S1, S3–S8) separate from closure
   story (S2).
4. Domain boundaries respected: financial correctness untouched, platform work
   isolated from product logic.

### Bad Splits (Avoid)

- Splitting process isolation into separate stories for processes vs. links —
  they are the same boundary, just different angles.
- Merging source-tree normalization into a single "reorganize everything" story
  — five parallel refactorings each justify their own delivery and review.
- Treating harness reuse as part of S1 — S8 is a distinct architectural
  migration with its own risk surface and audit trail.

## Release / Evidence Gate

- What can the user or operator do now that they could not before? Monitor
  tiles as isolated processes, receive crash identity reports, validate CPU
  placement across exclusive and shared-core layouts, and trust that a
  tile crash does not cascade to siblings.
- What is the wow-effect? A forced tile crash leaves siblings running, the
  supervisor names the failed tile, and the audit log confirms zero corruption.
  The trust boundary is no longer paper-only.
- What changed from V1.11? Heap-backed queues → Tango shared-memory links;
  tile threads → supervisor-managed OS processes; four identity mappings →
  one tile registry.
- Which checks are enforced? CPU affinity and workspace assignment fail closed
  for malformed or unavailable configuration.
- What happens on a tile crash? Supervisor reports the failing tile; sibling
  tiles continue; no data corruption; fail-closed enforcement prevents
  corrupted tiles from rejoining the topology.
- Is execution paper-only, draft-only, sandbox, live, or disabled? Unchanged
  from V1.11 — paper-only.
- Which artifacts are needed for partner trust? Supervisor configuration
  sample, link health metrics, crash isolation integration test output.
- Which command closes the increment? `just test-integration-tk` with
  process-isolation suite passing.
- Which fixtures are used? Existing payment-pipeline process-mode fixtures;
  new multi-inbound-link topology fixture for S8.
- Are policy and limit decisions visible in audit output? Unchanged from V1.11.
- Can replay run without side effects? Yes; replay output must match under
  both exclusive-core and shared-core configs.
- What intentional failure proves failure behavior? Crashing one tile process
  confirms sibling isolation and crash-only supervisor behavior.

## Dependencies And Decisions

- **Prerequisite:** M1 — V1.11 governed tile topology with audit, replay,
  and no-bypass (logical boundaries established).
- **Dependency:** M3 — tile-specific harness integration (S8 calls into the
  harness built here).
- **Decision:** Process isolation is the trust baseline, not namespace
  confinement. Sandbox entry is wired but namespace elevation is deferred to
  V1.21 because consumer-tier hosts may not grant the required privileges.
  Process isolation without `CLONE_NEWUSER` is sufficient for crash containment.
- **Decision:** Firedancer's parent-side spawn path stays Tickoni-owned.
  fdctl coupling (TILES[], PID namespace, shared-memory stacks) blocks reuse;
  Tickoni's self-exec model (execve + wait) is the correct shape.
- **Decision:** `fd_stem.c` multiplexer is not imported. It is designed for
  Solana's multi-input tiles; Tickoni's single-input financial pipeline stages
  use the SHOULD_SHUTDOWN check directly in each tile's work loop.
