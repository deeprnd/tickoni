# v2.14: Firedancer Process And Shared-Memory Topology

**Status: Done · Milestone: M2**

**Epic:** #TBD · **Issue:** #TBD

V2.14 is where Tickoni's tile boundaries become real. Before this, tiles shared
a process — logical boundaries on paper, shared memory in reality. After V2.14,
each tile runs as a supervisor-managed OS process. A crashing tile cannot
corrupt its sibling. This is the foundation that makes every boundary in Tickoni
trust-worthy rather than theoretical.

Extracted from V1.11.S6.

---

## Product Intent

V1.11 established a governed tile topology with audit, replay, and no-bypass.
The tile boundaries are logical: tiles share a process and communicate over
heap-backed queues. v2.14 converts every tile into a real Firedancer-style
runtime unit — a supervisor-managed OS process with its own address space,
communicating over Firedancer Tango `mcache`/`dcache` shared-memory links.
Demo and replay output must be identical across both exclusive-core and
shared-core CPU configs.

The goal is physical crash containment, not just logical separation. A tile
that crashes cannot corrupt its sibling's state. The supervisor reports the
failing tile by identity and follows the declared crash-only shutdown or
restart path. This is the difference between "tiles don't talk to each other"
(a rule) and "tiles can't corrupt each other" (a guarantee).

Tickoni must not inherit a hard "one tile per exclusive core" requirement from
Firedancer validator deployment assumptions. The Linux full-runtime path should
support exclusive affinity where available and explicit shared-core placement
where multiple tiles intentionally reuse the same CPU. That reusable-core model
keeps ordinary developer and consumer hardware viable and leaves room for the
cross-platform retail runtime decisions in V1.21 without weakening the
high-throughput Linux tier.

v2.14 should make Tickoni tiles real Firedancer-style runtime units, not merely
Zig worker processes named "tiles." The integration target is:

- use `src/tango/mcache` and `src/tango/dcache` for inter-process fragments;
- use `src/tango/fseq` or `src/tango/fctl` for reliable consumer progress and
  backpressure;
- use `src/tango/cnc` or an equivalent narrow wrapper for tile boot, heartbeat,
  halt, and fail state;
- use Firedancer workspace and shared-memory mechanics, plus the relevant
  `src/disco/topo` workspace, link, object, join-mode, and process-start
  patterns;
- use `src/util/sandbox` for seccomp/Landlock/process isolation where the
  Linux full-runtime tier can support it.

Do not add Tickoni product fields or financial semantics to upstream-hot
Firedancer topology structs. Keep Tickoni policy, placement, tile IDs, and
financial contracts in Tickoni-owned Zig/C ABI wrappers under `src/tickoni/`.

## User Story

As a Tickoni operator, I can run each tile as an isolated supervisor-managed
process over Firedancer shared-memory links, so that tile crashes are contained,
CPU placement is validated, and tile boundaries are real rather than logical.

## What The Operator Sees

- process list with one entry per tile, each managed by the supervisor
- shared-memory workspace identifiers per inter-tile link
- CPU placement assignments per tile, including exclusive-core and intentional
  shared-core/reusable-core layouts
- link health metrics per link: depth, backpressure or overrun for reliable
  correctness links, and counted drops only for explicitly lossy telemetry links
- crash report with the identity of the failing tile and the supervisor's
  crash-only shutdown or restart decision

## Success Demo

- [ ] Supervisor starts each tile as a separate process; `ps` shows one process per tile.
- [ ] Events cross tile boundaries through Tango shared-memory links; no heap queue is present.
- [ ] CPU placement fails closed when a configured CPU id is unavailable, while
      valid shared-core configs may intentionally assign multiple tiles to one CPU.
- [ ] A crashing tile is reported by identity, does not corrupt sibling state,
      and triggers the declared supervisor crash-only shutdown or restart path.
- [ ] Demo and replay output match under exclusive-core and shared-core configs.

## Release Gate

- `just test-unit-tk` passes with no unexpected skips
- `just test-integration-tk` passes offline against local mocks
- integration test shows tiles as isolated processes over shared-memory links
- CPU placement fails closed for malformed or unavailable CPU ids and accepts
  explicit shared-core/reusable-core assignments
- demo and replay results are byte-identical under both core configs
- source-tree migration stories preserve existing V1.1/V1.3 behavior while
  separating runtime, contracts, codecs, scenarios, fixtures, and test support

## Non-Goals

- no new tile capabilities or policy rules
- no changes to capability envelopes, audit records, or replay capsule shape
- no changes to the investment demo product path
- no changes to upstream Firedancer validator tile semantics, Solana schemas,
  or validator topology ownership
- no hard requirement that every tile must own an exclusive CPU core
- no financial policy, approval, adapter authority, audit schema, or replay
  semantic changes as part of the source-tree migration

## Testing Model

For v2.14 acceptance, "process isolation" means separate OS processes in the
Linux process topology, not merely separate Zig or pthread threads in one
address space. A dev/test thread mode may remain useful for fast unit tests,
but it does not satisfy the S1/S2 process-isolation acceptance criteria.

Process-mode tests should record supervisor and tile OS identity:

- supervisor PID;
- one child PID per configured tile;
- tile name, kind/id, configured CPU placement mode, and assigned CPU when
  pinned;
- OS thread group id or equivalent evidence that each tile has its own process
  address space;
- parent/child relationship or launch record tying every tile process to the
  supervisor.

Shared-core placement does not mean shared process. Multiple tile processes may
intentionally share one CPU only when the config declares the CPU placement mode
as `shared`; otherwise duplicate CPU assignment fails closed.

Negative memory and workspace tests are in scope when they prove fail-closed
runtime boundaries:

- malformed, missing, stale, or duplicate workspace identifiers;
- missing `mcache`, `dcache`, `fseq` or `fctl`, or `cnc` objects;
- link MTU or fragment-size mismatches;
- dcache fragment bounds errors or invalid chunk references;
- reliable consumer progress not advancing and producer backpressure engaging;
- process mode accidentally selecting heap-backed correctness queues;
- forced tile crash while shared-memory state remains readable and
  non-corrupted for diagnostics or deterministic shutdown.

"Workspace join with the wrong mode" and link depth/burst mismatches are
deliberately not test cases in this story's actual implementation: no wrapped
Firedancer join call takes a read/write mode argument, `Producer`/`Consumer`
have no overlapping methods so using one as the other is a Zig compile error,
`depth` is read once from a single shared `LinkHandles` by both sides so it
cannot mismatch by construction, and Tickoni's channel model has no separate
`burst` parameter at all. See v2.14.S1.T14 for the same finding recorded
against the task list.

Out of scope for v2.14 negative testing: proving resistance to arbitrary kernel
memory attacks, fuzzing all Firedancer workspace internals, cross-platform
portable queue substitutes, production throughput saturation, and hostile
in-process memory corruption. Those require separate security, fuzzing,
platform, or performance stories.

## Product Outcome

Developers can inspect `src/tickoni` and immediately tell whether a file owns
runtime substrate, canonical contracts, codec boundaries, deterministic demo
orchestration, or test-only data. This reduces accidental ownership drift before
process isolation and shared-memory topology work expands the tree.

## User Story

As a Tickoni developer/operator, I want source paths to encode ownership, so
that future tile, schema, codec, demo, and fixture work can be reviewed without
guessing which layer owns financial correctness.

## Scope

- In scope: move Zig codec bindings from `src/tickoni/c_abi` to
  `src/tickoni/codec`; move protobuf files under `src/tickoni/schema/proto`;
  move V1 money-decision Zig contracts under `src/tickoni/schema/consumer_money`;
  replace ambiguous `src/tickoni/scenarios` with `src/tickoni/demo`.
- In scope: update `build.zig`, imports, proto contract tests, docs, and test
  paths so the repository remains buildable.
- Out of scope: changing tile IDs, link semantics, policy outcomes, audit
  schema, replay capsule shape, model/tool/adapter authority, or financial
  product semantics.

## Preconditions And Assumptions

- Existing V1.1 and V1.3 investment, replay, audit, model, adapter, and
  decision-card behavior is the compatibility baseline.
- `src/tickoni/c_abi` remains only for narrow Zig declarations and wrappers
  around retained Firedancer substrate such as queues and sandboxing.
- The current consumer-money schema namespace is a path cleanup only; domain
  strings such as `investment.intent` and `trading_order.propose` are not
  renamed.

### v2.14.S8: Full Firedancer harness reuse for Linux tile orchestration (Option 3)

**Status:** Backlog
**Epic:** #TBD
**Parent roadmap item:** v2.14: Firedancer Process And Shared-Memory Topology
**Labels:** `story`, `area/platform`

Complete the Linux full-runtime side of the option 3 decision in
[`firedancer-orchestration-reuse.md`](../../../knowledge/rant/firedancer-orchestration-reuse.md)
and the adapter contract in
[`tile-orchestration.md`](../../../knowledge/tile-orchestration.md): stop
maintaining Tickoni-side copies of what Firedancer's harness already solves
— per-tile lifecycle, link discovery, sandbox entry, and stuck-tile
detection — and drive them from the real Firedancer hooks/guards wherever
that is genuinely possible, with every remaining Tickoni-owned piece
justified by a documented, Solana-coupling finding rather than left as an
assumed exception.

This story implements the corrected, final "honest assessment" from the
original ADR (now `doc/strategy/roadmap/backlog/audits/adr_wip.md`), not that
document's earlier Phase 1-5 draft. That draft proposed building Tickoni-owned analogues of
several things Firedancer's harness already provides for free (its own
topology struct, its own stem-loop-equivalent, its own tempo/fctl shims as
prerequisites); the document's own closing analysis concludes that plan is
over-engineered and that the right shape is thin Tickoni structs embedding
the Solana-free subset of Firedancer's topology/tile/run types, calling the
real harness entrypoints directly. This story follows that corrected shape.

## Product Outcome

Three real, currently-open problems get fixed by reuse instead of by
building more Tickoni-owned parallel machinery:

1. **Tile identity is one source of truth.** Today tile id → behavior is
   independently computed in four places — `supervisor.zig`'s thread-mode
   spawn (index-based), `supervisor.zig`'s `snapshotProcessMetrics`
   (string-matched), `tile_main.zig`'s process dispatch (string-matched
   if/else), and `process.zig`'s counter indices (positionally assumed).
   After this story, one tile registry is the single answer for a tile's
   run/process callback, counter schema, and expected link cardinality, all
   four call sites read from it, and Firedancer's own `TILES[]` +
   one-dispatcher pattern is the reference shape.
2. **Links are arrays, not one field each way.** `LaunchSpec` today carries
   exactly one `input_link`/`output_link`, and `supervisor.zig`'s
   channel-selection loop is last-match-wins — a topology where a tile has
   two inbound links (e.g. an audit tile fed by both an ingest path and a
   policy path) would silently lose all but the last-matched one today.
   `tile-orchestration.md` already documents the target shape as per-tile
   `in_cnt`/`in_link_id[]`/`out_cnt`/`out_link_id[]` arrays; this story
   builds that shape as a thin wrapper around what `fd_topo_tile_t` and
   `fd_topo_fill_tile` already provide, instead of a second bespoke Tickoni
   array format.
3. **A blocked tile is not indistinguishable from a dead one.** Tile work
   loops (`tiles/payment_pipeline/process.zig`) today check halt and emit
   heartbeat only between pipeline iterations; a stage blocked inside a
   single `consume()`/`publish()` wait is invisible to the supervisor until
   its next iteration boundary. This is a documented known gap in that file.
   The Linux full-runtime tile lifecycle also does not enter a sandbox at
   all today — `tk_sandbox_enter` is declared but never called from Zig, and
   no tile has a generated seccomp-BPF policy.

After this story, the Linux full-runtime tier calls the real
`fd_topo_run_tile` harness (workspace join, privileged init, sandbox entry
with a real generated per-tile seccomp policy, link fill from the topology's
own arrays, metrics registration, unprivileged init, run, shutdown
enforcement) instead of a hand-rolled Zig mirror of that shape, heartbeat and
shutdown checks happen inside each tile's own work loop instead of only
between iterations, and the parent-side supervisor spawn/crash-tracking path
has been evaluated against Firedancer's own `run.c`/`run1.c`/`fd_boot.c`
conventions and reuses what is genuinely Solana-free. Firedancer's Solana-shaped
pieces — `fd_topob.c`'s topology builder, `fd_cfg_stage_*` config stages,
`tile_kind`/`kind_id`/`is_agave` fields, and the `fd_stem.c` multiplexer built
for Solana's multi-input tiles — stay out of Tickoni product code; Tickoni's
own tile run loops keep the SHOULD_SHUTDOWN-style check directly, since
`adr_wip.md`'s audit already found `fd_stem.c` is the wrong abstraction for
Tickoni's single-input financial pipeline stages.

## User Story

As a Tickoni runtime owner, I want Linux tile orchestration — lifecycle,
links, tile identity, sandboxing, and stuck-tile detection — to reuse
Firedancer's actual harness and hooks wherever that is genuinely possible,
instead of Tickoni maintaining a second, less-proven version of the same
mechanics, so that every documented harness guard actually protects Tickoni
tiles and any piece that stays Tickoni-owned does so for a stated, specific
reason.

      **Architectural context — the two-phase model.** `fd_topo_run_tile`
      (src/disco/topo/fd_topo_run.c lines 48–140) executes tiles in two
      phases:

      Phase 1 — Launch/Lifecycle: joins workspaces, calls
      `privileged_init(topo, tile)`, populates seccomp/allow_fds, enters
      sandbox, calls `fd_topo_fill_tile(topo, tile)` to join mcache/dcache/
      fseq, registers metrics/events, calls `unprivileged_init(topo, tile)`.
      Then enters Phase 2.

      Phase 2 — Run Loop: calls `tile_run->run(topo, tile)`. For Firedancer
      Stem tiles this is `fd_stem_run1()` — a tight bounded-polling loop
      that checks SHOULD_SHUTDOWN every iteration, receives/returns credits
      via fseq, and triggers housekeeping at randomized-interval ticks
      computed by tempo functions. Tickoni's equivalent is
      `tile_process.zig`'s `tk_tile_run()` callback: runs `work()` once to
      completion, then enters a heartbeat/halt-wait loop that queries the
      tile's cnc for HALT signals between iterations.

      **What `fd_tempo` actually provides** (src/tango/tempo/fd_tempo.h/c):
      NOT a "new/join/query" object. It is a set of clock-calibration
      utilities that map a fast tickcounter (`fd_tickcount()`) to
      nanoseconds so Firedancer can schedule randomized-interval housekeeping
      without relying on the wallclock in tight loops.

      - `fd_tempo_tick_per_ns(opt_sigma)` — first call in a thread group
        takes ~0.5s to sample the tickcounter-to-wallclock rate; caches it.
        Returns the rate in GHz. Used inside `fd_tempo_async_min()` to convert
        nanosecond intervals into tick counts.
      - `fd_tempo_lazy_default(cr_max)` — returns a conservative lower bound
        on the housekeeping interval in ns: ~2.25× max credits.
      - `fd_tempo_async_min(lazy, event_cnt, tick_per_ns)` — computes the
        minimum interval (ticks, integer power of 2 in [1,2^31]) between
        randomized housekeeping events.
      - `fd_tempo_async_reload(rng, async_min)` — returns a random interval
        in the range async_min to 2×async_min ticks. Used to reload the housekeeping
        timer after each cycle to avoid auto-synchronization anomalies.
      - `fd_tempo_wallclock_model(opt_tau)` / `fd_tempo_tickcount_model()` —
        calibrate the cost model of `fd_log_wallclock()` and `fd_tickcount()`
        calls (shifted exponential with minimum t0 and jitter tau). First
        call slow, subsequent fast.
      - `fd_tempo_observe_pair(opt_now, opt_tic)` — precision timing
        calibration; alternates wallclock/tickcount reads to find the best
        estimate of their simultaneous values.

      These functions are used INSIDE the stem loop's housekeeping scheduler
      (lines 368, 383, 510 of fd_stem.c) to compute `lazy`, then `async_min`,
      then `then = now + async_reload()`. They are NOT called by the supervisor.
      Tickoni's tile run loops should use them the same way: call
      `fd_tempo_tick_per_ns()` once at boot to get the conversion rate, then
      use `lazy_default`/`async_min`/`async_reload` to size and randomize
      housekeeping intervals inside the tile's own work loop.

      **What `fd_fctl` actually provides** (src/tango/fctl/fd_fctl.h/c):
      NOT a "consume_credit/produce_credit" API. It is a credit-based flow
      control object that manages backpressure for a transmitter with zero or
      more reliable receivers.

      - `fd_fctl_new(shmem, rx_max)` — formats memory as a fctl object.
      - `fd_fctl_join()` / `fd_fctl_leave()` / `fd_fctl_delete()` — attach/
        detach from shared memory.
      - `fd_fctl_cfg_rx_add(fctl, cr_max, seq_laddr, slow_laddr)` — register
        a receiver. `seq_laddr` is the location where this receiver writes its
        current sequence position (monotonically non-decreasing).
      - `fd_fctl_cfg_done(fctl, cr_burst, cr_max, cr_resume, cr_refill)` —
        finalize configuration. Zeros for cr_{max,resume,refill} pick
        reasonable defaults.
      - `fd_fctl_cr_query(fctl, tx_seq, _rx_idx_slow)` — returns a lower bound
        of credits available to the transmitter at sequence `tx_seq`. Involves
        inter-thread communication; should be called during housekeeping, not
        in the critical path.
      - `fd_fctl_rx_cr_return(rx_seq, rx_seq)` — called by a receiver to tell
        the transmitter its current position (used as a compiler memory fence).
      - Accessors: `fd_fctl_cr_burst()`, `fd_fctl_cr_max()`,
        `fd_fctl_cr_resume()`, `fd_fctl_cr_refill()`, `fd_fctl_rx_cnt()`,
        `fd_fctl_rx_cr_max()`.

      The pattern (from fd_fctl.h lines 438–501 TL;DR):
      - Receiver: periodically writes `*_rx_seq = rx_seq` (can be aggressive,
        typically L1 cache hit).
      - Transmitter: calls `fd_fctl_cr_query()` during housekeeping to refresh
        credit count. If `cr_avail < cr_burst`, skip sending and wait.
        When receivers are keeping up, fctl rarely does inter-thread
        communication (roughly every ~2/3 cr_max sequence numbers).

  `firedancer-orchestration-reuse.md`, not a silent fallback to a bespoke Zig
  reimplementation.
- T7 is resolved: Firedancer's parent-side spawn path is tightly coupled to
  fdctl (TILES[]), PID namespace (clone), and shared-memory stacks.
  Tickoni keeps its self-exec model (execve+waitProcess). See T7 task above.
- T5 is deferred to V1.21, not a silent scope drop: real sandbox entry
  needs `unshare(CLONE_NEWUSER)`, which failed closed (`EPERM`) under this
  implementation session's own AppArmor confinement even with the kernel
  allowing unprivileged user namespaces — a concrete instance of exactly
  the "consumer-tier host may not have this privilege" case v2.14.S1 and
  V1.21 already anticipated. Process isolation (supervisor-managed OS
  processes, crash-only teardown, audited boundaries) does not require
  namespace confinement to hold; sandboxing stays an optional hardening
  layer, wired in by a future V1.21 support-tier story once that story
  defines the fallback/capability model for hosts that can't create user
  namespaces. See T5 task above.
- `fd_topo_run_tile` lifecycle ordering (lines 49–140: join workspaces →
  privileged_init → seccomp → sandbox → fill links → register
  metrics/events → unprivileged_init → run → enforce shutdown) is the
  reusable piece exercised through the T3/T4 shim. Only Tickoni-owned
  fields (name, cpu_idx, allow_shutdown, metrics) are read; Solana union
  fields are zeroed by fd_topob_new()'s memset and never touched in the
  per-process path.
- `fd_stem.c` multiplexer reuse is intentionally not required:
  `adr_wip.md`'s audit concluded it is the wrong abstraction for Tickoni's
  single-input pipeline stages (designed for Solana's multi-input
  multiplexer); the SHOULD_SHUTDOWN-style check is implemented directly in
  each tile's own run loop instead.
