# V5.29: Exposure Computation

**Status:** Backlog
**Milestone:** M5
**Labels:** `epic`, `area/investing`, `area/platform`

Deterministic exposure computation from auditable holding records: sector,
industry, and asset-class breakdown rendered from the same state that powers
policy checks. Exposure data is a deterministic function of the portfolio state
produced by V5.26, computed without model or adapter calls, and surfaced
through CaseOps for the pie charts that M5's demo requires. V5.29 owns the
computation and its data surface; target exposure and rebalance suggestions
are V5.4, watchlist is V5.5, and model governance is V5.2.

Extracted from the M5 backlog proposal.

## Product Intent

Tickoni has portfolio state (V5.26) but no way to visualize it. V5.29 computes
exposure from holding records as a deterministic, replay-stable function —
no models, no adapters, no external inputs. The computation maps each holding
to its sector, industry, and asset class, aggregates quantities or notionals
by dimension, and produces the data structure that CaseOps renders as pie
charts. This is pure computation on auditable state, so the output is
identical across runs with the same event stream.

## Users And Jobs

- Consumer investor: view sector and industry exposure as pie charts rendered
  from auditable holdings, understand portfolio concentration.
- Risk reviewer: verify that exposure data is a deterministic function of the
  audit chain, compare exposure snapshots across time, confirm exposure
  computation respects the same data that powers policy checks.
- CaseOps operator: see exposure breakdown in the portfolio view, confirm
  that exposure data matches the portfolio's holding records.

## Success Metrics

- Exposure computation is deterministic: the same portfolio state produces
  identical sector/industry/asset-class breakdown across runs.
- Pie chart data renders correctly from auditable holding records for sector,
  industry, and asset-class breakdown.
- Exposure data is a deterministic function of the same state that powers
  policy checks in `tkpoly`.
- No live model, broker, payment, trading, crypto, approved execution ledger, or execution
  side effects occur unless this epic explicitly enables an approved sandbox path.

## Demo Moment

- Command or flow: Use the fixture portfolio (AAPL 50 shares, MSFT 30 shares,
  TSLA 10 shares, NVDA 20 shares, USD 5,000 cash). Compute exposure to show
  Technology 82% of portfolio value (drift +42% from target).
- Expected result: deterministic demo output showing Technology sector at 82%,
  correct sector/industry/asset-class breakdown, and pie chart data
  reconstructable from the fixture portfolio state.

## Scope

### In Scope

- Exposure computation from auditable holding records: sector, industry, and
  asset-class breakdown.
- Deterministic aggregation: same state always produces the same breakdown.
- No model or adapter calls — pure computation on V5.26 portfolio state.
- Data surface for CaseOps pie chart rendering.
- Target allocation reference data (default 60/40 stock/bond or customizable).

### Out Of Scope

- Target exposure management and rebalance suggestion generation (V5.4).
- Watchlist management (V5.5).
- Automatic valuation queue (V5.5).
- Model tier selection (V5.2).
- Portfolio optimization (Markowitz, Black-Litterman).
- Factor models, alpha generation, or performance ranking.
- Multi-currency exposure (single base currency per portfolio).
- Real-time market data or quote-based exposure (computed from holding
  cost basis or quantity, not live prices).

### How Many Stories

V5.29 is a mid-range epic (computation + visibility + replay + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: exposure computation + deterministic aggregation
   in S1; these are part of the computation contract, not separate stories.
3. **Split by capability lifecycle**:
   - S1: Core capability — deterministic exposure computation: sector/industry/
     asset-class aggregation from auditable holding records.
   - S2: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces exposure data for pie chart rendering.
   - S3: State lifecycle — replay and audit for exposure computation, dependent
     on S1 being stable.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: exposure computation and CaseOps surface are separate
   stories (S1, S2), not features within one story.

### Bad Splits (Avoid)

- Exposure computation + "aggregation" as two stories. Aggregation is part of
  the computation contract.
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.
