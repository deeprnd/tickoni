# V5.29: Visible Exposure Engine

**Status:** Backlog
**Milestone:** M5
**Labels:** `type/epic`, `area/investing`, `area/platform`

> You can't govern what you can't see. Before V5.29, Tickoni tracks portfolios but hides them — holding records exist in the audit chain, yet an operator has no single view of what a portfolio actually *is* in aggregate. V5.29 transforms Tickoni from a system that records positions to one that reveals them. Sector, industry, and asset-class exposure render as deterministic, auditable charts derived from the same state that powers policy checks. No market data, no model calls, no adapters. Just pure computation on what the portfolio already owns — the same data, visible.

## Product Intent

Institutions cannot govern risk they cannot see. Before this epic, Tickoni's portfolio state (V5.26) is accurate but invisible: holdings exist in the audit chain, but no surface tells an operator whether a portfolio is 82% Technology or diversified across sectors.

This epic makes portfolio state visible. A deterministic exposure engine maps each holding to its sector, industry, and asset class, aggregates quantities into sector/industry/asset-class breakdowns, and surfaces the result through CaseOps for pie chart rendering. The computation reads only from auditable holding records — no live prices, no model calls, no adapters. It is a pure function of portfolio state.

The counterintuitive insight: exposure doesn't need market data to be useful. What an operator needs to see first is *concentration*, not *valuation*. Knowing the portfolio is 82% Information Technology is actionable even before market prices are fetched — it tells you where the risk lives. Cost-basis or quantity-based exposure surfaces the structural truth of the portfolio; market-price valuation is the refinement, not the foundation.

The output is a deterministic function of the same state that powers `tkpoly` policy checks, so what the operator sees is what the policy engine reasons over. Trust comes from the fact that anyone who reconstructs the computation from the audit chain gets the identical breakdown.

## Scope

### In Scope

- Exposure computation from auditable holding records: sector, industry, and
  asset-class breakdown.
- Deterministic aggregation: same state always produces the same breakdown.
- No model or adapter calls — pure computation on V5.26 portfolio state.
- Data surface for CaseOps pie chart rendering.
- Target allocation reference data (default 60/40 stock/bond or customizable).

### Out Of Scope

- Target exposure management and rebalance suggestion generation (V5.4).
- Watchlist management (V5.5).
- Automatic valuation queue (V5.5).
- Model tier selection (V5.2).
- Portfolio optimization (Markowitz, Black-Litterman).
- Factor models, alpha generation, or performance ranking.
- Multi-currency exposure (single base currency per portfolio).
- Real-time market data or quote-based exposure (computed from holding
  cost basis or quantity, not live prices).

### How Many Stories

V5.29 is a mid-range epic (computation + visibility + replay + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: exposure computation + deterministic aggregation
   in S1; these are part of the computation contract, not separate stories.
3. **Split by capability lifecycle**:
   - S1: Core capability — deterministic exposure computation: sector/industry/
     asset-class aggregation from auditable holding records.
   - S2: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces exposure data for pie chart rendering.
   - S3: State lifecycle — replay and audit for exposure computation, dependent
     on S1 being stable.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: exposure computation and CaseOps surface are separate
   stories (S1, S2), not features within one story.

### Bad Splits (Avoid)

- Exposure computation + "aggregation" as two stories. Aggregation is part of
  the computation contract.
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.
