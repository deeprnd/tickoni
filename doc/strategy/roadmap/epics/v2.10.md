# V2.10: Build System Consolidation And Qt Build Validation

**Status:** Backlog
**Milestone:** M2
**Labels:** `epic`, `area/platform`, `area/operations`, `type/enhancement`, `type/documentation`

<!-- One paragraph: what complete feature this epic delivers and why now. -->

Consolidate the scattered build, test, quality, and security tooling into a
single `just`-driven surface with cross-platform `contrib/platform.sh` detection,
refactor `build.zig` from its current ~1,766 lines into a <500-line declarative
build script with walk-based test discovery, and validate a Qt 6 CMake-based
build path so the V3.19 native investment terminal has a proven build foundation
before full terminal development.

This epic exists because every new platform lane requires a human to update N
separate `case "$(uname -s)"` blocks scattered across `justfile` and `contrib/`,
`build.zig` at 1,766 lines is the largest single file in the codebase and a
significant gate for community contribution, and V3.19 plans a Qt desktop app
but has no validated build integration path yet.

## Product Intent

Developers, CI, and reviewer-hardware should have a single, documented entry
point for every build, test, quality, and security action. No contributor, CI
workflow, or script should invoke `gcc`, `zig`, `gmake`, or a `contrib/*.sh`
directly. Platform detection must live in one script. The Zig build script must
be refactorable without touching CI, Firedancer C build, or Tickoni runtime
behavior. And Qt must be demonstrably buildable through the repo before terminal
development starts.

## Users And Jobs

- Developer-operator: run `just build-all` and `just test-unit-all` locally on
  any supported platform without memorizing OS-specific flags or script paths.
- CI workflow author: call fully-qualified recipes (`just test-unit-tk-linux-x86`)
  with zero ambiguity about which OS/arch/compiler triple is in effect.
- New contributor: run `just setup` once and proceed with any `just` recipe
  without consulting multiple scattered install guides.
- Terminal developer: build the Qt investment terminal scaffolding through a
  validated CMake integration before V3.19 UI and QML work begins.
- Security reviewer: run `just security-check-all` and `just quality-lint-check-fd`
  with deterministic output regardless of the host.

## Success Metrics

- `contrib/platform.sh` replaces all inline `uname -s`/`uname -m` parsing in
  `justfile`, `zigw.sh`, `fd-build-windows.sh`, and `detect-windows-arch.sh`.
- `detect-windows-arch.sh`, `fd-build-linux.sh`, `fd-build-windows.ps1`, and
  `install-zig-bootstrap.py` are deleted (or confirmed orphaned and deleted).
- `build.zig` refactored to <500 lines with walk-based discovery for unit,
  integration, and cov lanes passing all existing tests.
- `just setup-{os}-{arch}[-{compiler}]` recipes install everything a build/test
  lane needs; a fresh checkout goes from zero to green via `just setup && just
  build-all && just test-unit-all` plus the one documented manual prerequisite
  (install `just`).
- CI workflows call fully-qualified recipe names for all scheduled jobs.
- Qt 6 CMake build path builds the terminal scaffolding (`main.cpp`,
  `ApplicationController`, `ApiTypes`, QML stub) on at least Linux x86.

## Demo Moment

- Command or flow: on a clean checkout, run `just setup`, `just build-all`,
  `just test-unit-tk`, `just test-integration-tk`, then `just build-tkni` (Qt
  build) and confirm the terminal binary launches with the QML shell rendering.
- Expected result: all lanes pass; `tickoni-terminal` launches, shows the dark
  shell, and connects to a local fixture mode without requiring any manual
  platform-specific flags.

## Scope

### In Scope

- `contrib/platform.sh`: single cross-platform OS/arch detection script.
- `justfile` cleanup: consolidate inline OS detection, introduce fully-qualified
  recipe names, keep bare dispatchers as auto-routing conveniences.
- Delete orphaned/redundant scripts: `detect-windows-arch.sh`,
  `fd-build-linux.sh`, `fd-build-windows.ps1`, `install-zig-bootstrap.py`.
- `build.zig` refactor: module registry + walk-based test discovery (<500 lines).
- Qt build POC: CMakeLists.txt, minimal Qt 6 scaffolding (C++ app, API types,
  command registry stub, QML shell), buildable on Linux x86 at minimum.
- CI workflow cutover: update all 7 workflow files to use fully-qualified recipe
  names; no new scheduled lanes.
- `setup-*` recipes: one per platform lane, install everything needed.
- Documentation updates: `doc/execution/build.md`, `development.md`, `ci.md`,
  `testing-tickoni.md`, `contribution/tickoni.md`.

### Out Of Scope

- New CI lanes or CI schedule changes beyond wiring existing recipes to
  fully-qualified names (D5).
- Full Firedancer unit-test coverage on macOS/Windows (spike in S3).
- Qt terminal beyond the build POC — no QML pages, no real API client, no
  investment flow implementation (V3.19 owns that).
- Changes to Firedancer C build, upstream Makefiles, or Firedancer tile semantics.
- Changes to Tickoni runtime tile behavior, capability envelopes, audit schema,
  or replay logic.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  A single `just setup && just build-all && just test-unit-all` flow on any
  supported platform, a Qt build path ready for V3.19, and a `build.zig` that
  a contributor can extend without reading 1,766 lines of boilerplate.
- What changed from the previous roadmap increment?
  Consolidated build surface, reduced `build.zig` complexity, validated Qt
  build foundation.
- What is this epic's wow-effect?
  A new developer clones the repo, runs two commands, gets green tests on
  their platform, and can add a new Zig test file with zero changes to
  `build.zig`.
- How does this epic progress Tickoni's unique value proposition?
  Removes a structural contribution barrier, making the codebase safer for
  community extension without weakening financial boundaries.
- Which demo command or CaseOps flow closes the epic?
  `just setup && just build-all && just test-unit-all && just test-integration-tk && just build-tkni`.
- Is execution paper-only, draft-only, sandbox, live, or disabled?
  Build/test only; no live side effects.

## Dependencies And Decisions

- S1 (platform script + cleanup) must ship before S4 (justfile renames) because
  the dispatcher recipes call `platform.sh`.
- S2 (build.zig refactor) is independent of S1, S4, S5; can ship in any order.
- S3 (Qt POC) is independent but should be done before V3.19 full development.
- S6 (CI cutover) should follow S1 and S4 so CI calls fully-qualified recipes.
- S7 (evidence/docs) is the closure story, depends on all others.
- S10 (badge updates) depends on S6 (CI cutover) because PR check-runs must
  exist before badge state can be determined from workflow completion events.
