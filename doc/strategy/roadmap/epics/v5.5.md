# V5.5: Watchlist Management And Valuation Queue

**Status:** Backlog
**Milestone:** M5
**Labels:** `epic`, `area/investing`, `area/platform`

Watchlist CRUD: add/remove tickers with optional notes. Watchlist tickers
enter the V4.32 DCF valuation queue automatically, producing
`valuation.analysis.propose` capability envelopes with capability checks
(`valuation_market_data.read`, `valuation_financials.read`,
`valuation_analysis.analyze`). Every valuation run is captured as a replay
capsule substituting model and adapter outputs. V5.5 owns the watchlist and
valuation queue; portfolio state is V5.26, exposure is V5.29, rebalance is
V5.4, and model governance is V5.2.

Extracted from the M5 backlog proposal.

## Product Intent

Tickoni has portfolio state (V5.26), computed exposure (V5.29), rebalance
suggestions (V5.4), and model governance (V5.2), but no way to track
companies outside the portfolio and get them valued. V5.5 delivers the
watchlist surface: users add tickers to watch, those tickers automatically
enter the V4.32 valuation queue, and every valuation run produces a
replay capsule with full capability checks and deterministic substitution.
This closes the M5 demo loop: watchlist ticker enters valuation queue,
completes DCF valuation with intrinsic value range and Monte Carlo CI,
and is replayable from captured inputs.

## Users And Jobs

- Consumer investor: add tickers to a watchlist with optional notes, remove
  tickers, see watchlist valuation status.
- Portfolio analyst: get automatic DCF-style valuation on every company
  that appears in any portfolio or watchlist, receive proposal-grade valuation
  records with evidence.
- Risk reviewer: audit watchlist mutations, inspect valuation assumptions,
  verify capability envelope compliance for every valuation queue entry.
- CaseOps operator: review watchlist entries, valuation evidence cards,
  replay capsules, and the full audit trail from watchlist entry to
  valuation completion.

## Success Metrics

- A user can add and remove tickers from a watchlist with optional notes.
- Watchlist tickers automatically enter the V4.32 valuation queue with full
  capability checks.
- Every valuation run produces a replay capsule substituting model and adapter
  outputs without calling external services.
- Valuation evidence cards show intrinsic value range and Monte Carlo CI.
- No live model, broker, payment, trading, crypto, approved execution ledger, or execution
  side effects occur unless this epic explicitly enables an approved sandbox path.

## Demo Moment

- Command or flow: Add AMZN to the watchlist with note "evaluate for portfolio
  inclusion". Show AMZN entering the V4.32 DCF valuation queue with
  capability checks (`valuation_market_data.read`, `valuation_financials.read`,
  `valuation_analysis.analyze`). Show completed valuation with intrinsic value
  range and Monte Carlo CI. Replay the valuation with substituted outputs.
- Expected result: deterministic demo output showing watchlist entry, valuation
  queue entry with capability checks, completed valuation record, replay
  capsule substituting model and adapter outputs.

## Scope

### In Scope

- Watchlist CRUD: add/remove tickers with optional notes.
- Automatic valuation queue: watchlist tickers queued for DCF valuation
  with V4.32 capability checks.
- Valuation record production: intrinsic value range, Monte Carlo CI,
  valuation evidence cards.
- Replay capsule: every valuation run captured as replay capsule substituting
  model and adapter outputs.
- Valuation queue depth and status metrics via `tkmetr`.

### Out Of Scope

- Portfolio CRUD (V5.26).
- Exposure computation (V5.29).
- Target exposure and rebalance suggestions (V5.4).
- Model tier selection (V5.2).
- Live market data ingestion (assumed provided as input/fixture per V4.32).
- Push notifications or device push.
- Social/clone/copy portfolio features (deferred to M7).

### How Many Stories

V5.5 is a mid-range epic (watchlist CRUD + valuation queue + visibility + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: watchlist CRUD in S1, valuation queue in S2 —
   these are distinct capabilities (ticker management vs valuation execution),
   each independently testable.
3. **Split by capability lifecycle**:
   - S1: Core capability — watchlist management: CRUD for tickers with notes,
     validation, stored in the analytics store.
   - S2: Core capability — automatic valuation queue: watchlist tickers enter
     DCF valuation with capability checks, produce valuation records.
   - S3: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces watchlist entries, valuation evidence cards, and replay status.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: watchlist CRUD (S1), valuation queue (S2), and CaseOps
   surface (S3) are separate stories, not features within one story.

### Bad Splits (Avoid)

- Watchlist CRUD + "ticker validation" as two stories. Validation is part of
  the CRUD contract.
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.
