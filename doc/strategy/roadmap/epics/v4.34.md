# V4.34: Institutional-Grade Data Foundation

**Status:** Backlog
**Milestone:** M4
**Labels:** `type/epic`, `area/investing`, `area/platform`

Institutions don't lose weeks because their valuation models are weak. They lose because the data entering those models is unreliable, untraceable, and manually assembled. V4.34 stops treating financial data ingestion as a plumbing problem. It turns SEC filings, XBRL, Excel financials, and market data into validated, traceable canonical facts with full source attribution — so the valuation engine (V4.32) never has to guess what it's computing on.

This epic does not run valuation math, Monte Carlo, or produce conclusions — it delivers validated, canonical input data.

## Product Intent

Valuation is only as defensible as the data feeding it. V4.34 builds the data foundation: SEC EDGAR filings become canonical FCFF inputs without manual entry. XBRL tag-to-fact mapping eliminates spreadsheet transcription. Excel-based ERP financials parse and validate against known constraints. Market data (price, beta, cap) produces validated canonical facts. Every datum carries source attribution, version, and validation pass status. Validation catches missing fields, impossible values, and inconsistent entries before they reach the computation layer. The output is not raw data — it's auditable, replay-stable, canonical facts that `tkval` consumes with confidence.

## Users And Jobs

- Portfolio analyst: load AAPL financials from an Excel file, get canonical
  FCFF-ready facts with validated growth rates, margins, and capex.
- Quant researcher: fetch EDGAR SEC filings, parse XBRL, and get market data
  (beta, price, cap) normalized into canonical facts for `tkval`.
- Risk reviewer: audit which data source, version, and validation checks
  produced the financial facts.
- Data engineer: maintain the plugin architecture for adding new data sources
  (ERP systems, EDGAR filings, XBRL) without code changes.

## Story Breakdown

### How Many Stories

Mid-range epic — 5 stories covering each major data source plugin, validation,
and audit/replay closure.

### Decomposition Rules

1. Independent delivery: each story delivers a testable data slice.
2. One capability per story: one data source per story.
3. Split by domain: ERP, EDGAR, XBRL, market data, validation are distinct.
4. Closure via T10 child tasks in the final story.
5. Domain boundaries: each plugin is its own story.

### Bad Splits (Avoid)

- "Excel parsing" and "Excel validation" as two stories — validation belongs
  in the same story as parsing.
- "EDGAR" and "XBRL" as separate stories — EDGAR retrieval produces XBRL
  data; XBRL loading is the next step, but they serve different purposes
  (retrieval vs parsing) and are separate sources.
- "Market data" split by field (price vs beta vs cap) — all market data
  feeds the same canonical fact struct, one story.

### Good Split Example

```
V4.34.S1: ERP data plugin implementation — FreeXL-based Excel parsing via V4.36 plugin framework, storing, refresh.
V4.34.S2: EDGAR data plugin implementation — Edgartools-based SEC filing retrieval via V4.36 plugin framework, storing, refresh.
V4.34.S3: XBRL data plugin implementation — Arelle-based XBRL loading and tag-to-fact mapping via V4.36 plugin framework.
V4.34.S4: Market data collection — price, beta, market cap, share count via V4.36 plugin framework.
V4.34.S5: Financial statement ingestion and validation — missing fields, impossible values, inconsistent entries, audit trail.
```
