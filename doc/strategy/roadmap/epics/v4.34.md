# V4.34: Valuation Data Layer

**Status:** Backlog
**Milestone:** M4
**Labels:** `epic`, `area/investing`, `area/platform`, `type/enhancement`

V4.32 does the math, but the numbers have to come from somewhere. V4.34 ingests
financial data from real sources — Excel financials, SEC EDGAR filings, XBRL
data, market prices — and normalizes them into canonical facts with full source
attribution and validation. SEC filings become canonical FCFF inputs. XBRL
tag-to-fact mapping replaces manual data entry. Validation catches missing
fields, impossible values, and inconsistent entries before they reach the
computation layer. The output is not raw data. It's validated, traceable
financial facts that feed the engine.

This epic does not run valuation math, Monte Carlo, or produce conclusions —
it delivers validated, canonical input data.

## Product Intent

V4.32 produces enterprise value from canonical financial facts, but those facts
must come from somewhere. V4.34 builds the data layer: parsing Excel-based
financials (FreeXL), retrieving SEC filings (Edgartools), loading XBRL data
(Arelle), collecting market data (price, beta, cap), and validating financial
statements against known constraints. SEC filings become canonical FCFF inputs.
XBRL tag-to-fact mapping replaces manual data entry. Validation catches missing
fields, impossible values, and inconsistent entries before they reach the
computation layer. The output is not raw data — it's validated, traceable
canonical facts that `tkval` consumes.

## Users And Jobs

- Portfolio analyst: load AAPL financials from an Excel file, get canonical
  FCFF-ready facts with validated growth rates, margins, and capex.
- Quant researcher: fetch EDGAR SEC filings, parse XBRL, and get market data
  (beta, price, cap) normalized into canonical facts for `tkval`.
- Risk reviewer: audit which data source, version, and validation checks
  produced the financial facts.
- Data engineer: maintain the plugin architecture for adding new data sources
  (ERP systems, EDGAR filings, XBRL) without code changes.

## Success Metrics

- ERP data (Excel) can be loaded, parsed, and validated without code changes.
- EDGAR data can be retrieved, stored, and refreshed without code changes.
- XBRL data can be loaded from SEC filings with tag-to-fact mapping.
- Market data collection (price, beta, market cap, share count) produces
  validated canonical facts.
- Financial statement validation catches missing fields, impossible values,
  and inconsistent accounting entries.
- All ingested data flows through `tknorm` and `tkdedu` before reaching `tkval`.

## Story Breakdown

### How Many Stories

Mid-range epic — 5 stories covering each major data source plugin, validation,
and audit/replay closure.

### Decomposition Rules

1. Independent delivery: each story delivers a testable data slice.
2. One capability per story: one data source per story.
3. Split by domain: ERP, EDGAR, XBRL, market data, validation are distinct.
4. Closure via T10 child tasks in the final story.
5. Domain boundaries: each plugin is its own story.

### Bad Splits (Avoid)

- "Excel parsing" and "Excel validation" as two stories — validation belongs
  in the same story as parsing.
- "EDGAR" and "XBRL" as separate stories — EDGAR retrieval produces XBRL
  data; XBRL loading is the next step, but they serve different purposes
  (retrieval vs parsing) and are separate sources.
- "Market data" split by field (price vs beta vs cap) — all market data
  feeds the same canonical fact struct, one story.

### Good Split Example

```
V4.34.S1: ERP data plugin — FreeXL-based Excel parsing, storing, refresh.
V4.34.S2: EDGAR data plugin — Edgartools-based SEC filing retrieval, storing, refresh.
V4.34.S3: XBRL data plugin — Arelle-based XBRL loading and tag-to-fact mapping.
V4.34.S4: Market data collection — price, beta, market cap, share count.
V4.34.S5: Financial statement ingestion and validation — missing fields,
           impossible values, inconsistent entries, audit trail.
```
