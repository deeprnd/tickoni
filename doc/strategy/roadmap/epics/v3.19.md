# V3.19: Tickoni Native Investment Terminal

**Status:** Backlog
**Milestone:** M3
**UI Platform:** Qt 6 desktop application
**Supported Platforms:** Linux, macOS, Windows
**Labels:** `epic`, `area/trust`, `area/audit`, `area/investing`, `area/platform`, `type/enhancement`

Build Tickoni's first native professional financial terminal: a dense,
keyboard-first Qt desktop application that turns investment intent into a
policy-checked, explainable, and replayable proposal.

The terminal adopts the seriousness, speed, information density, and
function-driven workflow of professional financial terminals. Tickoni's
primary object is the governed financial consequence rather than price
movement, PnL, rank, or trading activity.

The application is a presentation and operator-control surface over `tk_api`.
Financial correctness, policy decisions, proposal identity, audit records,
replay results, model and adapter governance, and execution authority remain
owned by the Tickoni runtime.

V3.19 deliberately proves one complete workflow before expanding into a broad
operations suite:

```text
investment intent
-> normalized mandate
-> basket and ticket
-> policy decision
-> before/after impact
-> proposal or governed paper action
-> audit and replay proof
```

## Product Intent

Tickoni's existing increments prove deterministic investment flows, governed
runtime boundaries, portfolio consequence, audit, replay, and cross-platform
build support. V3.19 turns those capabilities into the first visible product
surface suitable for repeated operator use.

The first terminal release must answer five questions without requiring the
operator to read fixture output, audit JSONL, replay logs, or diagnostic files:

1. What did the user ask Tickoni to do?
2. What proposal did Tickoni produce?
3. Which policy checks allowed, denied, or resized it?
4. What changes in cash, buying power, and exposure if the proposal proceeds?
5. Can the decision and its evidence be reproduced and verified?

The product line for this increment is:

```text
Tickoni turns investment intent into policy-checked, replayable financial proposals.
```

## Strategic UI Direction

V3.19 is a native desktop terminal, not a browser dashboard made to resemble
one.

The product should borrow these professional-terminal qualities:

- persistent desktop application state;
- keyboard-first navigation;
- command-driven function access;
- high-density tables with stable alignment;
- multiple windows for parallel case inspection;
- visible source, freshness, environment, and policy context;
- immediate movement between summary and exact evidence;
- minimal animation and no decorative dashboard behavior.

The product must not imitate Terminal-specific branding, proprietary function
codes, data products, or visual assets. Terminal is a reference for workflow
discipline and information density, not a design template to copy.

## Users And Jobs

- Investment user: enter or inspect an investment thesis and understand the
  bounded proposal before any action.
- CaseOps operator: move quickly between investment cases, policy reasons,
  consequence, and proof.
- Compliance or risk reviewer: inspect exact policy gates, hashes, evidence
  references, and replay outcome.
- Product reviewer: run deterministic allowed, denied, oversized, replay, and
  tamper scenarios from one native application.
- Runtime owner: see a compact terminal/API availability summary sufficient to
  distinguish unavailable data from a policy denial. Full operations
  administration is deferred.

## Success Metrics

- One native Qt application builds and launches on Linux, macOS, and Windows.
- The USD 2,000 V1.1/V1.11 AI-infrastructure scenario renders normalized
  intent, account state, basket, rejected candidates, ticket, policy outcome,
  impact, proposal identity, and replay status.
- The restricted `SOXL` scenario shows the exact denied reason and exposes no
  quote or paper-action affordance for the rejected instrument.
- The USD 25,000 scenario shows the effective maximum or blocking limit and
  disables the direct action.
- Missing, stale, malformed, disconnected, or unavailable state never renders
  as allowed.
- Navigation and local command dispatch respond without perceptible delay;
  high-volume updates respect the 60/120 fps GUI frame budget.
- The minimum supported viewport preserves mode, freshness, policy decision,
  exact reason, consequence, and action state.
- No UI path bypasses `tk_ui`, `tk_api`, `tkpoly`, `tkaudt`, `tkrepl`,
  `tkmodl`, `tktool`, `tkadpt`, or future `tkexec` boundaries.
- Channel overflow, sequence gaps, and resynchronization follow defined
  overflow policies without crashing the UI.
- The same fixture produces the same semantic terminal state on all supported
  platforms.

## Demo Moment

Run the native Tickoni terminal against deterministic local fixture data.

The operator opens the AI-infrastructure case and sees:

- the original thesis and normalized mandate;
- account cash and buying power;
- an allowed basket and paper ticket;
- restricted `SOXL` in the rejected-instruments table;

## Architecture And Ownership

The terminal remains outside the deterministic financial runtime:

```text
+-----------------------------+
|| Tickoni Qt Terminal         |
|| tk_ui tile sandbox          |
|| QML views + C++ models      |
+-------------+---------------+
              |
              | shared-memory command channel
              | shared-memory event/value channels
              v
+-----------------------------+
|| tk_api                      |
|| Semantic API tile           |
+-------------+---------------+
              |
  +-----------+-----------+----------------+----------------+
  |                       |                |                |
  v                       v                v                v
 tkpoly                  tkaudt           tkrepl           tkmetr/tkdiag
 policy authority        audit truth      replay truth     availability only


Remote path:
  tk_ui -> local bus -> tk_gateway_client -> external protocol
                                         -> remote tk_gateway -> remote tk_api
```

- `tk_ui` is a composite edge tile wrapping the Qt application. `tk_ui` owns
  the local shared-memory channels, bus bridge, command admission, feature
  projection stores, presentation models, and collection models.
- `tk_api` is the semantic API tile. It is not defined by HTTP. It owns
  capability negotiation, subscriptions, request validation, expected-revision
  validation, governed command routing, query and command response semantics,
  state revisions and freshness, and event projection contracts.
- A separate `tk_gateway` tile owns external network protocols (HTTP,
  WebSocket, QUIC) and translates them to typed internal tk_api messages for
  remote clients.
- `tkpoly` remains the only authority for finance-native policy outcomes.
- `tkaudt` remains the source of material event history and audit identities.
- `tkrepl` remains the source of replay match, divergence, capsule, and tamper
  state.
- `tkmodl`, `tktool`, and `tkadpt` remain hard boundaries for model, tool, and
  adapter access.
- Future `tkexec` remains disabled unless a separate approved-execution epic
  explicitly enables a sandbox or live path.
- The terminal may cache presentation data, but cache contents are never a
  source of financial truth.
- A shared-memory channel overflow, sequence gap, resynchronization failure, or
  bus disconnect must transition action state to unavailable or resynchronizing.

## Qt Technical Foundation

Use:

```text
Qt 6
+-- Qt Quick / QML              terminal shell and visual composition
+-- Qt Quick Controls           controls with a custom Tickoni style
+-- C++                         application state, bus bridge, commands
+-- Presentation models         focused view models (CaseViewModel, etc.)
+-- Feature stores              read-optimized projection stores
+-- QAbstractItemModel          basket, policy, impact, evidence tables
+-- Shared-memory channels      tk_api tile link (ui_cmd, ui_rsp, ui_evt, ui_lval)
+-- CMake                       desktop build and packaging integration
```

### Required Separation

- QML owns layout, binding, focus, transitions, and presentation only.
- Presentation models own typed Q_PROPERTY values, local presentation state,
  command submission through application use cases, and stale/unavailable states.
- Feature stores own validated snapshots, event application, revision tracking,
  and produce immutable ModelPatches for GUI-thread model updates.
- The bus bridge owns shared-memory workspace attachment, channel cursors,
  message schema validation, sequence gap detection, process-generation checks,
  bulk payload resolution, and handoff to stores. It is not exposed to QML.
- Application use cases own command validation, request ID allocation,
  idempotency, and command enqueueing. They do not contain QML types or
  shared-memory offsets.
- Collection models use QAbstractItemModel subclasses for large collections.
  All model mutations occur on the GUI thread.
- QML must not call shared-memory descriptors, network protocols, tile links,
  model providers, adapters, files, shell commands, or execution systems
  directly.
- QML must not publish directly to tile links or global event buses. A QML
  control calls only a typed method on its focused presentation model.
- Financial policy must not be recomputed in QML or C++ terminal code.
- Display models may derive presentation-only values such as formatted text,
  column widths, and style roles from governed semantic state.
- Runtime semantic values must not be inferred from colors, labels, or icon
  state.

## Terminal View Contract

V3.19 should not require the frontend to assemble the main case view from many
loosely synchronized calls. Define one aggregated read model for the first
release, with optional detail reads for expanded proof or evidence.

Suggested conceptual response:

```text
InvestmentCaseView
+-- case
+-- environment
+-- source
+-- freshness
+-- intent
+-- account
+-- proposal
+-- ticket
+-- rejected_candidates
+-- policy_decision
+-- policy_checks
+-- impact_summary
+-- action_state
+-- audit_summary
+-- replay_summary
+-- runtime_summary
```

Each major section must carry or inherit:

```text
status
source
as_of
freshness
reason_unavailable
```

Where policy applies, the response must include:

```text
policy_version
outcome
reason_code
reason_text
observed_value
limit_value
scope
```

Where audit or replay applies, the response must include fields already owned
by the runtime, such as:

```text
event_hash
policy_hash
proposal_hash
evidence_refs
replay_capsule_id
replay_status
first_divergent_sequence
first_divergent_field
expected_hash
actual_hash
```

The exact wire schema remains owned by `tk_api` over shared-memory channels;
this section defines the minimum UI view requirements, not a second policy or
audit schema.

## Visual Identity: Midnight Oni

The terminal should feel disciplined, technical, and premium rather than
colorful or decorative.

The visual concept is:

```text
cold machine surfaces
+ blue Tickoni intelligence
+ restrained amber terminal interaction
+ rare vermilion brand seal
+ strict semantic state colors
```

### Color Responsibilities

Brand color and operational state must remain separate.

| Role | Purpose | Suggested value |
| --- | --- | --- |
| Carbon black | Main workspace | `#070A0E` |
| Midnight navy | Standard panel | `#0B1119` |
| Steel navy | Raised or selected surface | `#101923` |
| Dark slate | Subtle divider | `#192431` |
| Blue-gray | Strong divider | `#263445` |
| Cool white | Primary text | `#E7EDF4` |
| Muted steel | Secondary text | `#8D9AAA` |
| Disabled gray | Unavailable text | `#566270` |
| Oni blue | Tickoni identity and active navigation | `#3478D4` |
| Active blue | Focus, selected step, link | `#4A9EFF` |
| Terminal amber | Prompt, function cue, shortcut | `#E8A83E` |
| Wealth vermilion | Rare brand seal or oni detail | `#A9343D` |
| Pass green | Allowed, pass, replay match | `#47A66A` |
| Signal red | Denied, failed, divergence | `#E0525E` |
| Warning amber | Approval, evidence, stale, near limit | `#D69A32` |

### Color Rules

- Blue identifies Tickoni, current focus, selected function, active case,
  evidence navigation, and the current workflow step.
- Terminal amber identifies the command prompt, function mnemonic, keyboard
  shortcut, timestamp emphasis, and small operator cues.
- Wealth vermilion is a rare brand element only: oni eye, horn, seal, premium
  report mark, or equivalent identity detail.
- Wealth vermilion must not mean allowed, profitable, successful, selected, or
  safe.
- Signal red is reserved for operational denial, failure, tamper, divergence,
  and destructive confirmation.
- Green is reserved for allowed, pass, healthy, replay match, and clean proof.
- Warning amber is reserved for approval required, evidence missing, stale
  state, near-limit, or degraded availability.
- Gray means pending, disabled, unavailable, inactive, or not applicable.
- Color is never the only carrier of meaning. Every state also requires text,
  a code, or a distinct symbol.

### Color Proportion

The default workspace should remain predominantly neutral:

```text
80% black, navy, and gray surfaces
15% white and muted information text
 4% Tickoni blue focus and navigation
 1% amber, vermilion, and semantic state accents combined
```

This is a discipline target rather than a pixel-level test. Large saturated
panel fills, rainbow tables, multi-color gradients, glowing borders, and
colored drop shadows are prohibited.

### Status Treatment

Prefer:

- a thin colored left rule;
- compact text status;
- a small square or dot;
- one-pixel underline;
- restrained badge outline;
- direct table-cell state.

Avoid large filled status cards.

Example:

```text
|| ALLOWED      green rule + green text
|| DENIED       signal-red rule + signal-red text
|| APPROVAL     warning-amber rule + amber text
|| UNAVAILABLE  gray rule + gray text
```

### Typography

- Use a compact sans-serif for labels and navigation.
- Use a monospace or tabular-number face for values, commands, hashes, IDs, and
  dense tables.
- Align decimals and currency units.
- Use no more than three primary text sizes in the default workspace.
- Use uppercase for short function names and statuses, not for paragraphs.
- Fonts must have redistributable licensing appropriate to the selected Qt
  distribution model; no font file is committed without license review.

### Borders, Shape, And Motion

- Thin gray-blue dividers.
- Sharp rectangles or minimal radius.
- No consumer-dashboard card shadows.
- Motion is limited to focus transition, command completion, connection state,
  replay progress, and critical state change.
- No celebratory animation.
- Hidden or background panels must not continuously animate or redraw.

## Information Architecture

Use five top-level functions in V3.19:

```text
CASE
POLICY
IMPACT
PROOF
SYSTEM
```

- `CASE`: default investment workbench.
- `POLICY`: exact checks, limits, observed values, and denied reasons.
- `IMPACT`: cash, buying power, exposure, and concentration before/after.
- `PROOF`: audit identity, evidence, replay, tamper, and divergence summary.
- `SYSTEM`: compact source, freshness, bus status, gateway availability,
  fixture/runtime mode. It is not a full operations console.

Deferred top-level areas include `PAYMENTS`, `CASEOPS`, `CAPABILITIES`,
`ADAPTERS`, `HEALTH`, and a full `AUDIT` explorer.

## Story Breakdown

Six stories implement the V3.19 terminal, each mapping to one of the five
information-architecture functions plus one documentation/closure story:

- **V3.19.S1 — Terminal Shell, Navigation, And Command Bar**
  Terminal frame, Midnight Oni visual system, keyboard navigation, command bar,
  five-function navigation bar (CASE, POLICY, IMPACT, PROOF, SYSTEM), status
  strip, responsive panel grid. Story 1.

- **V3.19.S2 — Investment Safe-Action Workbench (CASE Function)**
  Normalized intent, allowed basket, rejected candidates, ticket preview,
  policy check display, proposal hash, paper state indicator, restricted
  instrument handling (SOXL scenario), oversize notional blocking (USD 25,000
  scenario). Story 2.

- **V3.19.S3 — removed.** Payment guard workspace is out of scope: the epic
  explicitly excludes payment, payout, retry, transfer, or beneficiary
  workflows. Story removed.

- **V3.19.S4 — Before/After Impact View (IMPACT Function)**
  Cash, buying power, sector exposure, ETF exposure, single-name concentration,
  compact alerts. Investment-only impact (no combined payment obligation
  workspace). Story 4.

- **V3.19.S5 — Proof Black Box (PROOF Function)**
  9-step audit timeline, hash fields, evidence refs, model route, adapter
  attribution, approval state, replay status (MATCH/DIVERGE/MISSING),
  tamper check (CLEAN/TAMPERED), proof export, divergence details. Story 5.

- **V3.19.S6 — System Availability Panel (SYSTEM Function)**
  Compact data freshness, local bus status (connected, resynchronizing,
  overflow), sequence gap detection, process generation validity, gateway
  availability (remote mode), fixture/runtime mode indicator. Not a full
  operations console. Story 6.

- **V3.19.S7 — API Contracts, Fixtures, Screenshots, And Release Evidence**
  `InvestmentCaseView` aggregated read contract for `tk_api` over shared-memory
  channels, fixture file paths and schemas for all five functions, bus-transport
  test contract (channel overflow, sequence gaps, resynchronization), screenshot
  checklist, blocked-flow examples, documentation that `tk_ui` communicates only
  through `tk_api` (shared-memory for local, `tk_gateway` for remote). Story 7.
