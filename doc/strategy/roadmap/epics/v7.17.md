# V7.17: The Invisible Ceiling

**Status: Planned · Milestone: M7**

**Epic:** #TBD · **Issue:** #TBD
**Labels:** `type/epic`, `area/agents`, `area/security`, `area/audit`, `area/trust`

When V1.11 established `tkmodl`, it proved the system could say "no" to any unknown model or disabled provider. But saying no to the wrong model is easy. The harder trust problem comes when the system says "yes" too many times — when a role exhausts its token budget mid-run, or a misbehaving case keeps calling until the model collapses. V7.17 makes those limits visible, auditable, and structurally enforced. Not because we think agents will abuse the system — because we know auditors will ask about it.

The logical fix for "users worry about model cost" is to add more controls. The psychological fix is to make the limits *visible, deterministic, and impossible to cheat* — and then show them in a single replayable demo. Every limit hit tells the same story as every approval: the rules applied. In finance, that's not a side effect. It's the product.

**The infinite-game lens:** V1.11 proved we could enter the game with governed model access. V7.17 proves the governance survives when the pressure is on — when a role wants one more call, when a budget runs dry mid-analysis. Trust is maintained by what you refuse to allow, even when allowing it would be convenient.

**The psycho-logic lens:** The obvious answer to model-cost anxiety is "just limit it." The counterintuitive insight is that *the limit itself is the trust signal*. A system without limits sounds powerful. A system with visible, auditable limits that fire before anyone can reach them sounds *safe*. And in finance, safe is what sells.

## Product Intent

V1.11 `tkmodl` validates every model request and fails closed on unknown or disabled providers. What it does not enforce is how many times a given role or case may call a model, or what happens when a token budget runs out mid-run. V7.17 adds these limits as auditable policy-relevant events: call-limit-exceeded and budget-exhausted are expected terminal states with explicit audit records, not panics or silent truncations. A per-role limit halts only that role's model access, not the entire run.

This epic does not change `tkmodl`'s request validation or provider dispatch logic. It adds an enforcement layer: counters that track, limits that fire, and audit records that prove every enforcement action was deterministic and non-bypassable.

---

## Users And Jobs

- [Compliance operator]: Configure per-role, per-case, and per-run model-call limits and token budgets, and inspect every limit-exceeded or budget-exhausted event with full audit context (limit type, consumed count, budget id, policy version).
- [Runtime operator]: Verify that one role hitting its call limit does not affect other roles in the same run — containment is the feature, not collateral damage.
- [Auditor]: Replay a run where limits fired and confirm the audit trail shows every enforcement event in the correct order, with no missing or reordered records.
- [Risk reviewer]: Confirm that budget exhaustion is a documented, expected terminal state — not a crash, not a silent fallback, but a policy decision with a recorded hash.

---

## Success Metrics

- Every call-limit-exceeded event produces an audit record with budget id, limit type (run, role, or case), consumed count, configured limit, run id, and policy version
- Budget exhaustion produces a budget-exhausted audit record with budget id, consumed tokens, token limit, run id, and policy version; no further model requests are possible afterward
- Per-role limit containment: one role reaching its limit does not affect another role's call counter or model access
- Replay substitutions do not count against live call limits; replay remains fully deterministic
- Call-limit and budget counters are exported through `tkmetr` as observable gauges

## Demo Moment

- Expected result: the test output shows a per-role call-limit-exceeded audit record, other roles continuing uninterrupted, a budget-exhausted audit record halting further model requests, and a replay that substitutes captured outputs without touching live limits

## Scope

### In Scope

- Per-run, per-role, and per-case model-call limit counters in `TkModlConfig`
- Call-limit-exceeded as an auditable terminal state with required audit fields (budget id, limit type, consumed count, configured limit, run id, policy version)
- Budget-exhaustion as an expected terminal state with required audit fields (budget id, consumed tokens, token limit, run id, policy version)
- Per-role limit containment: halting one role's model access without affecting other roles or run state
- Call-limit and budget counters exported through `tkmetr`
- Integration tests for per-role, per-case, and per-run limit enforcement with audit record verification
- Deterministic `TkModlConfig` fixtures for at-limit, over-limit, and within-limit scenarios
- Audit JSONL samples for all three limit types and budget-exhausted
- Malformed `TkModlConfig` rejection tests (negative limits, zero budget, missing budget id)
- Fail-closed validation for invalid limit combinations at startup

### Out Of Scope

- No changes to `tkmodl` request validation or provider dispatch logic
- No changes to model allowlist, endpoint mapping, or replay substitution
- No changes to agent run envelope or tool broker
- No MCP-compatible tool dispatch normalization
- No content-addressed evidence store or replay capsule integrity hashes
- No live model provider integration

### How Many Stories

Two stories: S1 owns the enforcement mechanism (counters, limits, terminal states, audit records), S2 owns the evidence layer (tests, fixtures, metrics export, JSONL samples). This is a tight, focused epic — two stories is correct.

### Decomposition Rules

1. **Independent delivery**: S1 delivers the enforcement layer (counters + limits + audit); S2 delivers verification (tests + fixtures + metrics)
2. **One capability per story**: S1 = enforcement, S2 = evidence — no mixing
3. **Closure story**: S2 handles evidence, demo, documentation, and quality gates via its child tasks (T10)
4. **Domain boundaries**: enforcement and evidence are cleanly separated

### Bad Splits (Avoid)

- Splitting per-role, per-case, and per-run into three separate stories — they are variants of the same enforcement mechanism.
- Making audit records a separate story from the counters that trigger them — the audit record is the enforcement output, not a separate capability.
- Splitting tests from the feature they verify — deterministic tests belong with the story they validate.
