# V7.8: The Capability Ledger — What Agents Can (and Can't) Do, Explained In Your Language

**Labels:** `type/epic`, `area/security`, `area/trust`, `area/platform`
**GitHub Issue:** [33](https://github.com/deeprnd/tickoni/issues/33)

When a fintech, brokerage, or compliance team plugs into Tickoni, the first question is never "what features does it have?" It's "what can it actually do with my money, and what is it absolutely forbidden from doing?" Right now, that answer lives inside a black box — policy decisions computed by `tkpoly` and rendered as raw logs that only engineers understand. V7.8 turns that black box inside out. It gives partners a complete, programmatically accessible ledger of every financial action class Tickoni supports, every policy gate that governs it, and every boundary that agents cannot cross — all expressed in finance-native language, not internal engine vocabulary.

**An agent framework that keeps money safe is only as trustworthy as the people reviewing it can understand it.** If the policy surface is only visible to engineers reading tile logs, you have the same situation as a slot machine with the glass painted black: the machine is still running, but nobody can verify whether it's fair. V7.8 paints the glass clear. Every partner gets a front-row view of the rules that govern every agent recommendation, proposal, denial, and execution path. They don't need to know what a capability envelope is. They need to know, in plain finance language, which actions are allowed, which require approval, which are dead, and why.

Perception shapes behavior even when the underlying mechanics don't change. The same capability catalog hidden inside tile logs feels like a black-box engine. The same catalog rendered as a structured, queryable surface in the language of payments, trading, crypto, and compliance *is* governance. You didn't add more controls — you made the existing controls visible. And visibility is the cheapest form of trust.

The Product Promise: **Partners can read every rule Tickoni enforces on agent actions — in finance language, not engine vocabulary. See it. Query it. Trust it.**

## Scope

### In Scope

- **Capability catalog:** finance-native representation of all action classes (`observe`, `analyze`, `draft`, `recommend`, `propose`, `prepare`, `execute`, `override`, `administer`) and policy outcomes (`allow`, `deny`, `require_approval`, `require_more_evidence`, `escalate`).
- **Scope dimension viewer:** account, customer, merchant, legal entity, beneficiary, IBAN, wallet, custody account, rail, currency, country, market, venue, sector, instrument, order type, amount, exposure, frequency, holding period, risk tier, jurisdiction, and environment.
- **Evidence prerequisites:** which evidence fields are required for each proposal-capability combination.
- **Aggregate limit viewer:** per-case, per-customer, per-account, per-beneficiary, per-wallet, per-instrument, and per-time-window limits.
- **Approval-path viewer:** approver roles, expiry windows, revocation rules, and maker-checker requirements.
- **Denied-by-default execution list:** money movement, ledger posting, payout approval, account freezing, risk-rule override, policy modification, and unsupported trading/crypto actions — explicitly enumerated.
- **Programmatic catalog endpoint:** `GET /v1/capabilities` via `tkapi`, returning the full catalog structured by action class, policy outcome, scope dimension, evidence prerequisite, aggregate limit, and approval path. The response mirrors the UI surface.
- **Partner read endpoint integration:** V1.7 operator review surface (capability catalog, case evidence, policy decision, model usage, adapter behavior, approval state, replay status) is accessible through the same authenticated API surface. Access is scoped to the authenticated actor's capability envelope.
- **Tests:** agents cannot edit policy, expand capabilities, administer allowlists, or execute outside signed adapter and privileged executor paths.

### Out Of Scope

- Writing or editing capability policies — this epic exposes and queries them; policy authoring is a separate concern.
- TigerBeetle ledger execution or approved execution (`tkexec`) — execution is denied by default; this epic surfaces the denial, not the execution.
- Direct model/provider calls or financial API connectivity — governed through `tkmodl` and `tkadpt`.
- Operator UI component changes — API surface is the deliverable; CaseOps rendering is a follow-up concern.
- Story-level implementation tasks — scoped at story creation time.

### How Many Stories

5 stories. This epic spans three concerns: the catalog surface itself (S1), the programmatic API (S2), the partner integration (S3), plus verification (S4) and closure (S5). The catalog surface and API are tightly coupled and should be designed together; the partner integration story brings it all together for end users.

### Decomposition Rules

- One capability per story: catalog surface → API endpoint → partner integration → isolation tests → closure.
- Lifecycle split: define the data model first, then the endpoint, then the access control, then the tests.
- Closure story last: S5 ties all API and test work together.

### Bad Splits (Avoid)

- Splitting the catalog surface into "action class view" and "policy outcome view" — these are interdependent and must ship together for the partner to make sense of the rules.
- Creating a standalone story for "write docs" — documentation is part of the closure evidence, not a standalone story.
- Splitting S2 and S3 — the API endpoint and partner read integration share the same access control and evidence model; separating them fragments the delivery.

No raw logs. No engineer translation.

- What changed from the previous roadmap increment?
  V7.7 established the trust export — audit timelines, replay capsules, and hash-chain verification. V7.8 goes one step further: it doesn't just prove that decisions were made correctly; it shows the partner *what the rules are* that governed those decisions. Transparency before proof.

- What is this epic's wow-effect: the visible moment that makes Tickoni feel unlike a generic agent harness?
  A compliance officer types `GET /v1/capabilities?outcome=deny` and gets back a structured, finance-language list of every action Tickoni refuses to execute autonomously — money movement, ledger posting, account freezing, policy modification — with the exact policy reason for each denial. No raw logs. No internal vocabulary. Just the rules, laid bare. That moment shifts the conversation from "trust us" to "here are the rules — verify them yourself."

- How does this epic progress Tickoni's unique value proposition from `doc/strategy/positioning.md`?
  Policy-gated action: every boundary is visible, not hidden. Forensic replay: the catalog is deterministic and reconstructable. Consequence isolation: denied-by-default actions are enumerated explicitly. Trust is not claimed; it is displayed.

- Which demo command or CaseOps flow closes the epic?
  `GET /v1/capabilities` with various filters (`action_class`, `outcome`, `scope_dimension`) + `just tktest capability-isolation` for automated agent-boundary verification.

Aggregate limits by case, customer, account, beneficiary, wallet, instrument, and time window. Approver roles, expiry, revocation, and maker-checker requirements displayed per approval path.

- What happens when the requested action exceeds policy, scope, or evidence?

Denied-by-default actions (money movement, ledger posting, payout approval, account freezing, risk-rule override, policy modification, unsupported trading/crypto) are explicitly listed and never executed autonomously.

  Catalog query examples for each action class and policy outcome. Denied-by-default enumeration fixture. Agent isolation test vectors proving no self-elevation. Replay capsule demonstrating deterministic catalog queries.

  Yes. Catalog queries and policy decisions are deterministic and replay-stable. No model, adapter, or execution calls are made.

- What intentional blocked-flow or divergence example proves fail-closed behavior?
  An agent attempting to edit policy or expand its own capabilities returns a clear `deny` recorded in audit. A query scoped to one partner's capability envelope returns no data belonging to another partner.

## Dependencies And Decisions

- Depends on: `tkpoly` capability envelope evaluation and policy outcome machinery (`allow`, `deny`, `require_approval`, `require_more_evidence`, `escalate`).
- Depends on: `tkaudt` append-only, hash-chained audit records for all capability decisions.
- Depends on: `tkapi` HTTP endpoint scaffolding for `GET /v1/capabilities` and partner read endpoints.
- Depends on: `tkrepl` replay capability for deterministic catalog queries.
- Decision: the capability catalog is the single source of truth for what agents can and cannot do; it must be consistent between the programmatic API and the operator UI surface.
- Decision: partner-scoped access control uses the same capability envelope model that governs financial events; no separate auth schema.
- Story-level task scoping deferred to story creation time.
