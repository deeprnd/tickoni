# V4.24: Valuation with Uncertainty Bands

**Labels:** `type/epic`, `area/investing`, `area/platform`
**GitHub Issue:** [17](https://github.com/deeprnd/tickoni/issues/17)

> Every valuation is wrong. The competitive advantage comes from knowing *how* wrong — before you bet on it. V4.24 transforms Tickoni's DCF engine from a single-number calculator into an institution-grade uncertainty analysis tool. Perturb beta, ERP, growth rate, and terminal value inputs through 100,000 iterations natively in the runtime. Produces base/bull/bear cases with uncertainty bands, cross-check divergences, and sensitivity tables — deterministic, replay-stable, no Python dependency. The wow is not that it runs fast. The wow is that a portfolio manager can point at a distribution and say "the true range is 30% to 170% of this number" instead of a spreadsheet cell that lies to them.

This epic does not ingest data (V4.34) or produce investment conclusions (V4.25) — it makes every assumption's uncertainty visible, auditable, and replay-stable.

## Product Intent

A single DCF number is a lie told confidently. Every equity research report, every model output, every investment memo produces a point estimate — and the investor's brain fills in the false confidence gap. The real decision isn't "what is this company worth?" It's "what range could this reasonably fall into, and which assumptions are actually moving the needle?"

Tickoni's DCF engine already produces a number. V4.24 answers the question no other tool in the governed runtime does: what happens when every input is wrong by a realistic amount?

The outcome is not more columns in a table. The outcome is an investor who can show a committee "here's where 90% of outcomes land, here's which assumption drives the widest range, and here's where my cross-checks disagree with my primary model" — and have every number be traceable, hash-chained, and replay-stable.

## Users And Jobs

- Portfolio analyst: run Monte Carlo on a DCF, see where the value really lives as a distribution, identify which assumptions drive the widest range, and explain it to a committee without opening Excel.
- Risk reviewer: audit which assumption perturbations caused the most valuation divergence, compare cross-check disagreement to the primary model's output, and verify the methodology's transparency.
- CaseOps operator: review a valuation analysis card showing Monte Carlo distribution, scenario probabilities, sensitivity tables, and cross-check divergences — not a single cell with a hidden story.
- Quant researcher: run deterministic sensitivity experiments (beta, ERP, growth perturbations) and compare results byte-identically on replay — because the same inputs must always produce the same distribution.

## Success Metrics

- Native Monte Carlo simulation (no Python/R dependency) runs at least 100,000 iterations in under 30 seconds on a single core for a standard 5-year DCF parameter set.
- Monte Carlo produces base/bull/bear cases with uncertainty bands (percentiles) that a non-technical stakeholder can read in under 30 seconds.
- Cross-check suite (reverse DCF, peer multiples, sum-of-the-parts) runs alongside primary DCF and reports divergences that are themselves auditable.
- Two-dimensional sensitivity tables show valuation impact of paired assumption perturbations — the "which knob turns the needle" view.
- Methodology self-audit reports transparency metrics: assumption count, data quality score, model limitations.
- All statistical outputs are traceable to input perturbations and seed; deterministic under replay.

## Demo Moment

- Command or flow: `just val-mc-demo` runs Monte Carlo with 10,000 iterations on an AAPL FY2023 fixture, prints base/bull/bear cases with uncertainty bands, runs cross-checks, generates sensitivity tables, and reports methodology transparency score.
- Expected result: an operator watches a distribution emerge from a single input set, identifies the highest-leverage assumption in real time, and sees cross-check divergences surface — all natively, no external tool. The boardroom moment: the operator closes the laptop and says "we don't have a number. We have a range, and here's what matters most about it."

## Story Breakdown

### How Many Stories

Mid-range epic — 4 stories covering Monte Carlo engine, cross-checks, sensitivity analysis, and methodology audit/closure.

### Decomposition Rules

1. Independent delivery: each story produces a testable analysis slice.
2. One capability per story: Monte Carlo, cross-checks, sensitivity, audit.
3. Split by domain: each analysis method is its own story.
4. Closure via T10 child tasks in the final story.
5. Domain boundaries: Monte Carlo and cross-checks are separate stories.

### Bad Splits (Avoid)

- "Monte Carlo engine" and "Monte Carlo scenarios" as two stories — scenarios are part of the Monte Carlo capability, same story.
- "Reverse DCF" and "peer multiples" as two stories — both are cross-checks, same story.
- "Sensitivity table" and "sensitivity visualization" as two stories — output format does not define a separate capability.

## Dependencies And Decisions

- Varanus library must be integrated and tested before Monte Carlo stories begin (depends on V4.32).
- Decision: Monte Carlo random number generation — Mersenne Twister vs PCG vs Xoshiro family. Determinism vs speed trade-off. PCG recommended for deterministic replay with good statistical properties.
- Decision: perturbation distribution shapes — normal, uniform, triangular, or custom. Normal distribution is the default for financial parameters.
- Decision: number of iterations for default demo (10,000 vs 100,000). 10,000 for demo speed; 100,000 available via flag.
- Depends on V4.32 (core DCF engine) for base computation input.
- Depends on V4.34 (data layer) for canonical fact input availability.
