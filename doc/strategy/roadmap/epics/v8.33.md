# V8.33: Financial Telemetry, Audit, And Observability Governance

**Status:** Backlog
**Milestone:** M8
**Labels:** `epic`, `area/operations`, `area/audit`, `area/security`, `area/trust`, `area/platform`, `type/enhancement`

Turn telemetry from scattered runtime snapshots and future UI assumptions into a first-class Tickoni product surface: privacy-preserving by default, enterprise-exportable when configured, tamper-evident for financial review, and useful for operators who need to prove why an AI-assisted financial output was allowed, blocked, approved, or changed.

This epic is the missing owner for the large telemetry obligations currently referenced by V7.12 hook telemetry, V2.14 link/process health, V2.19 health panels, and `doc/execution/telemetry.md`. It does not replace those stories. It defines the telemetry product, privacy, audit, export, retention, and analytics foundation they should plug into.

## Product Intent

Generic agent tools can show that an agent called a model or tool. Tickoni must prove something stronger for finance: which evidence supported a financial answer, what data left the environment, which policy allowed or blocked the request, whether human approval was required, who approved it, and whether the final output changed after approval.

The product posture should combine:

- Hermes-style local-first privacy defaults: no outbound telemetry in local-only mode, local encrypted logs, and no raw prompt or response export by default.
- OpenClaw and Claude Code-style enterprise observability: OpenTelemetry export for metrics, traces, and logs to a customer-owned collector when enabled.
- Finance-grade audit controls: append-only, hash-chained, signed, retained, redacted-by-default, and replay-aware evidence for money-adjacent workflows.

Tickoni should not copy a generic agent analytics model blindly. Finance users need operational visibility, cost control, and analytics, but they also handle PII, account data, trading intent, portfolio holdings, restricted research, client mandates, regulated communications, secrets, and prompt-injection risk. Raw content capture must be opt-in, scoped, time-limited, admin-approved, and audited.

## Users And Jobs

- Runtime owner: see whether tiles, links, queues, models, tools, adapters, policy, audit, replay, and export paths are healthy without scraping raw process state.
- Compliance or risk reviewer: prove which evidence, assumptions, market data, citations, policy decisions, approvals, and output hashes supported a financial answer or proposal.
- Security reviewer: verify that secrets, PII, trading-sensitive content, client data, prompt text, tool inputs, and model responses are redacted or retained only under explicit policy.
- Enterprise administrator: choose local-only, customer-owned observability, or managed Tickoni Cloud telemetry mode with region, retention, tenant isolation, BYOK/KMS, and content-capture controls.
- Finance team lead: understand AI use, model spend, error rates, stale-data rates, policy-intervention rates, approval rates, and client-delivery risk.
- CaseOps operator: distinguish policy denial from adapter degradation, stale data, queue backpressure, model budget exhaustion, replay divergence, or diagnostic failure.

## Success Metrics

- Tickoni has an explicit telemetry mode setting with local-only, enterprise observability, and managed cloud modes documented and enforced fail-closed.
- No raw prompts, model responses, tool inputs or outputs, secrets, account identifiers, portfolio data, or client data are exported by default.
- `tkmetr` and `tkdiag` own production metrics and diagnostics surfaces instead of leaving feature stories to invent their own telemetry path.
- Operational logs, cost/usage logs, security logs, and financial audit trails have separate schemas, retention policy, access policy, and evidence rules.
- Financial audit events are append-only, hash-chained, batch-signable, and replay-aware, with content hashes and metadata preserved when raw content is redacted.
- OpenTelemetry export supports customer-owned collectors with Tickoni financial semantic attributes and bounded, low-cardinality labels.
- Policy blocks, prompt-injection detections, data-exfiltration attempts, approval decisions, stale-data warnings, uncited outputs, and client-delivery markers are visible in metrics, diagnostics, audit, and CaseOps where applicable.
- Dashboards answer operational, security, cost, and finance-risk questions without requiring raw content capture.

## Demo Moment

- Command or flow: run a deterministic CaseOps or CLI demo in local-only mode, then rerun with enterprise OpenTelemetry export pointed at a local fixture collector.
- Expected result: local-only mode emits encrypted local logs, redacted financial audit JSONL, `tkmetr` metrics, and `tkdiag` diagnostics with no outbound telemetry; enterprise mode exports only configured redacted metrics, traces, and logs with Tickoni semantic attributes; raw content remains absent unless an admin-approved content-capture policy is explicitly enabled.

## Scope

### In Scope

- First-class telemetry modes: local-only, enterprise observability, and managed Tickoni Cloud mode.
- Redacted-by-default prompt, response, tool, adapter, model, approval, and financial-output telemetry policy.
- Separate operational logs, cost/usage logs, security logs, and financial audit trails.
- Production ownership model for `tkmetr` metrics and `tkdiag` diagnostics.
- OpenTelemetry export for metrics, traces, and logs to customer-owned collectors when enabled.
- Tickoni financial semantic attributes for use case, actor role, policy decision, approval state, data classification, model risk tier, output type, citation coverage, and evidence quality.
- Tamper-evident financial audit trail with append-only events, hash chaining, signed batches, WORM/object-lock export planning, retention policy, and legal hold planning.
- Finance-specific redaction and data classification for PII, account numbers, IBAN/routing/card data, secrets, portfolio holdings, trading intent, unreleased research, client mandates, and regulated communications.
- Prompt-injection, data-exfiltration, stale-data, uncited-output, and restricted-data telemetry and blocked-flow evidence.
- Human approval telemetry for risky actions and regulated outputs.
- Enterprise admin controls for telemetry policy, content capture, retention, region pinning, BYOK/KMS, SSO/SAML/OIDC, SCIM, RBAC/ABAC, SIEM export, and audit export API.
- Analytics dashboards for usage, spend, model quality, policy blocks, stale-data rate, uncited-claim rate, assumption-change rate, policy-intervention rate, human-override rate, and client-delivery exposure.

### Out Of Scope

- No direct live trading, payment, crypto, broker, approved execution ledger, or execution authority is added by telemetry.
- No raw prompt, response, tool I/O, account data, portfolio data, client data, or restricted research export by default.
- No generic third-party analytics SDK embedded in the deterministic financial event path.
- No duplicate metrics registry, tracing bootstrap, or background telemetry daemon outside the `tkmetr` and `tkdiag` ownership model.
- No high-cardinality metric labels such as event IDs, account IDs, case IDs, wallet addresses, raw prompts, raw errors, stack traces, or client names.
- No UI-only policy, approval, redaction, retention, or telemetry enforcement.
- No managed Tickoni Cloud data processing without explicit data-processing, regional storage, tenant isolation, retention, and customer-key decisions.

## Competitive And Regulatory Lessons

- Hermes demonstrates the value of local-first defaults, local logs, and no external analytics collection as the privacy baseline.
- OpenClaw demonstrates a useful split between local gateway logs and optional OpenTelemetry export when diagnostics and the export plugin are enabled.
- Claude Code demonstrates the need to separate vendor operational telemetry from customer-owned OpenTelemetry export, and to keep raw prompts, responses, tool parameters, and API bodies redacted unless explicitly enabled.
- OWASP GenAI guidance treats prompt injection and sensitive-information disclosure as first-order LLM application risks. Tickoni telemetry must expose attempted injection, unauthorized tool use, and data exfiltration without exporting sensitive content by default.
- EU AI Act-style lifecycle event logging expectations and financial-sector retention duties mean Tickoni should make retention configurable policy, not a hard-coded period.
- NIST AI RMF and financial-sector AI risk-management expectations imply that telemetry fields should map to governance, risk, monitoring, and evidence controls rather than generic agent activity only.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  They can choose telemetry mode, prove no raw-content export by default, export redacted OTel telemetry to a customer collector, verify tamper-evident audit trails, and inspect financial-risk analytics.
- What changed from the previous roadmap increment?
  Telemetry becomes a first-class governance surface rather than a collection of scattered snapshots, feature-specific counters, and future UI assumptions.
- What is this epic's wow-effect?
  Tickoni can prove why a financial answer or action was allowed, which evidence supported it, who approved it, what changed after approval, and what data left the environment.
- How does this epic progress Tickoni's unique value proposition?
  It turns observability into finance-grade control: speed and agent workflows become reviewable through policy, audit, replay, redaction, and governed evidence rather than opaque transcripts.
- Which demo command or CaseOps flow closes the epic?
  A deterministic CaseOps or CLI flow that runs local-only and enterprise OTel-export variants, then verifies redaction, audit hash chain, replay, and blocked raw-content export.
- Which account, beneficiary, IBAN, wallet, rail, currency, market, venue, asset class, instrument, notional, amount, exposure, and frequency checks are enforced, if any?
  Existing workflow policy dimensions remain owned by their capability stories. This epic adds telemetry for policy decisions, approval state, evidence quality, data classification, and export scope; it does not invent new financial authority.
- What happens when the requested action exceeds policy, scope, or evidence?
  The owning policy path fails closed, while telemetry records the redacted policy outcome, denied reason category, evidence state, and replay-safe audit reference.
- Is execution paper-only, draft-only, sandbox, live, or disabled?
  Telemetry does not enable execution. Execution remains whatever the owning workflow allows; this epic observes, audits, and exports only governed evidence.
- Which fixtures, samples, audit records, replay capsules, screenshots, or API examples prove the behavior?
  Local-only config, enterprise collector config, managed-cloud blocked config, redaction fixtures, `tkmetr` samples, `tkdiag` samples, OTel envelopes, audit JSONL, signed batch metadata, replay capsules, dashboard fixtures, SIEM export samples, and blocked raw-content export samples.
- Can replay run without external side effects when replay applies?
  Yes. Replay disables or substitutes collector export, model calls, adapter calls, proposal results, approval results, and execution results.
- What intentional blocked-flow or divergence example proves fail-closed behavior?
  Malformed telemetry mode, missing collector, managed-cloud prerequisites absent, raw content capture without admin approval, forbidden high-cardinality label, prompt-injection tool request, data-exfiltration attempt, stale-data output, uncited client-delivery output, tampered audit event, and altered replay evidence.
