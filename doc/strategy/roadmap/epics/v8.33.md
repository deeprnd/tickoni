# V8.33: The Financial Audit Trail — Proof Before Approval

**Status:** Backlog
**Milestone:** M8
**Labels:** `epic`, `area/audit`, `area/security`, `area/trust`, `area/operations`, `area/platform`

Every financial output carries a question nobody can answer at scale: why was this allowed, why was this blocked, who approved it, what evidence supported it, what data left the environment, and does the audit trail hold up under review? Generic observability tools can show that an agent called a model or a tool. They cannot prove that a financial answer was built on the right evidence, scoped by the right policy, and is reconstructable from source data. A compliance reviewer staring at scattered metrics, raw logs, and unchained audit records is auditing by hope, not by design. V8.33 gives every financial output a deterministic, tamper-evident trail — every policy decision, every evidence reference, every redaction gate, and every export path chained, scored, and verifiable before the first question is asked. An operator doesn't need to know how to build an OpenTelemetry pipeline or hash a JSON batch. They need to know, in one view, that the trail is complete, untampered, and exportable to the auditor's tool of choice. Like a pilot's pre-flight checklist, the machine verifies; the human reviews.

## Product Intent

Generic observability bolts on metrics after the fact and hopes the auditor is satisfied. Tickoni puts the trail *before* the question. V8.33 makes every financial output a first-class governance surface with deterministic pre-flight across three layers — telemetry modes (local-only, enterprise, managed cloud), redaction by default, and tamper-evident audit chaining — so that every output arriving at a human reviewer or external auditor is already scoped, already redacted, and already backed by verifiable hashes.

The product promise: **an operator sees one verified audit trail instead of seven open questions.** The verification is done by the machine. The review is made by the human. They never share the same risk.

## Users And Jobs

- [CaseOps operator]: Prove why a financial output was allowed, blocked, approved, or changed — which evidence supported it, what data left the environment, which policy applied, and whether anything changed after approval — without reconstructing the trail from scattered logs.
- [Compliance or risk reviewer]: Inspect a complete, hash-chained, append-only audit trail with content hashes preserved even when raw content is redacted, and export it in a format an auditor's tool can verify.
- [Security reviewer]: Verify that secrets, PII, trading-sensitive content, raw prompts, tool inputs, and model responses are redacted or retained only under explicit policy — no raw content export by default.
- [Enterprise administrator]: Choose local-only, customer-owned observability, or managed Tickoni Cloud telemetry mode with region pinning, retention, tenant isolation, BYOK/KMS, and content-capture controls.
- [Finance team lead]: See model spend, error rates, stale-data rates, policy-intervention rates, approval rates, and client-delivery exposure on dashboards that answer questions without requiring raw content capture.
- [CaseOps operator]: Distinguish policy denial from adapter degradation, stale data, queue backpressure, model budget exhaustion, replay divergence, or diagnostic failure in a single operational view.

## Success Metrics

- Every financial output carries a complete governance surface — telemetry mode, redaction policy, audit hash chain, evidence references, data classification, and export scope — before it reaches a human reviewer or external system.
- No raw prompts, model responses, tool inputs or outputs, secrets, account identifiers, portfolio data, or client data are exported by default — only redacted, bounded, low-cardinality signals.
- Financial audit events are append-only, hash-chained, batch-signable, retention-aware, and verifiable with tamper fixtures — content hashes and metadata preserved when raw content is redacted.
- `tkmetr` and `tkdiag` own production metrics and diagnostics surfaces instead of leaving feature stories to invent their own telemetry path.
- Operational logs, cost/usage logs, security logs, and financial audit trails have separate schemas, retention policy, access policy, and evidence rules.
- OpenTelemetry export supports customer-owned collectors with Tickoni financial semantic attributes and bounded, low-cardinality labels — disabled and substituted during replay.
- Dashboards answer operational, security, cost, and finance-risk questions without requiring raw content capture.
- Policy blocks, prompt-injection detections, data-exfiltration attempts, approval decisions, stale-data warnings, uncited outputs, and client-delivery markers are visible in metrics, diagnostics, audit, and CaseOps where applicable.

## Demo Moment

- Command or flow: `just tktest audit-trail --fixture redacted_financial_output` (local-only mode), then `just tktest audit-trail --fixture enterprise_export --collector local` (enterprise export mode).
- Expected result: Local-only mode emits encrypted local logs, redacted financial audit JSONL, `tkmetr` metrics, and `tkdiag` diagnostics with zero outbound telemetry. Enterprise mode exports only configured redacted metrics, traces, and logs with Tickoni semantic attributes. A tamper fixture proves the hash chain is broken when a single event is altered. No adapter call to any external system. Raw content remains absent unless an admin-approved content-capture policy is explicitly enabled.

## Scope

### In Scope

- First-class telemetry modes: local-only, enterprise observability, and managed Tickoni Cloud mode — documented and enforced fail-closed.
- Redacted-by-default prompt, response, tool, adapter, model, approval, and financial-output telemetry policy.
- Separate operational logs, cost/usage logs, security logs, and financial audit trails with distinct schemas and retention policies.
- Production ownership model for `tkmetr` metrics and `tkdiag` diagnostics, including V2.14 link/process health.
- OpenTelemetry export for metrics, traces, and logs to customer-owned collectors when explicitly enabled — disabled or substituted during replay.
- Tickoni financial semantic attributes for use case, actor role, policy decision, approval state, data classification, model risk tier, output type, citation coverage, and evidence quality.
- Tamper-evident financial audit trail: append-only events, hash chaining, signed batches, WORM/object-lock export planning, retention policy, and legal hold planning.
- Finance-specific redaction and data classification for PII, account numbers, IBAN/routing/card data, secrets, portfolio holdings, trading intent, unreleased research, client mandates, and regulated communications.
- Prompt-injection, data-exfiltration, stale-data, uncited-output, and restricted-data telemetry and blocked-flow evidence.
- Human approval telemetry for risky actions and regulated outputs.
- Enterprise admin controls for telemetry policy, content capture, retention, region pinning, BYOK/KMS, SSO/SAML/OIDC, SCIM, RBAC/ABAC, SIEM export, and audit export API.
- Analytics dashboards for usage, spend, model quality, policy blocks, stale-data rate, uncited-claim rate, assumption-change rate, policy-intervention rate, human-override rate, and client-delivery exposure.

### Out Of Scope

- No direct live trading, payment, crypto, broker, approved execution ledger, or execution authority is added by telemetry.
- No raw prompt, response, tool I/O, account data, portfolio data, client data, or restricted research export by default.
- No generic third-party analytics SDK embedded in the deterministic financial event path.
- No duplicate metrics registry, tracing bootstrap, or background telemetry daemon outside the `tkmetr` and `tkdiag` ownership model.
- No high-cardinality metric labels such as event IDs, account IDs, case IDs, wallet addresses, raw prompts, raw errors, stack traces, or client names.
- No UI-only policy, approval, redaction, retention, or telemetry enforcement.
- No managed Tickoni Cloud data processing without explicit data-processing, regional storage, tenant isolation, retention, and customer-key decisions.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  They can choose telemetry mode, prove no raw-content export by default, export redacted OTel telemetry to a customer collector, verify tamper-evident audit trails, and inspect financial-risk analytics — all without reconstructing the trail from scattered logs or raw data.
- What changed from the previous roadmap increment?
  Telemetry becomes a first-class governance surface rather than a collection of scattered snapshots, feature-specific counters, and future UI assumptions.
- What is this epic's wow-effect: the visible moment in this epic's demo or workflow that makes Tickoni feel unlike a generic agent harness?
  An operator views one financial output and sees a single, verified trail — policy decision, evidence references, redaction state, hash chain, export scope — instead of opening seven different logs, dashboards, or audit files to piece together the story. The same trail that prevents blind approvals from ever reaching a human.
- How does this epic progress Tickoni's unique value proposition from doc/strategy/positioning.md: speed, isolation/control, spend governance, policy-gated action, and forensic replay?
  Forensic replay: every policy decision, evidence reference, redaction gate, and export path chained and verifiable. Consequence isolation: telemetry does not enable execution — it observes, audits, and exports governed evidence only. Policy-gated action: every dimension verified and redacted before export. Spend governance: model spend, error rates, and stale-data rates visible on dashboards without raw content capture.
- Which demo command or CaseOps flow closes the epic?
  `just tktest audit-trail --fixture redacted_financial_output` — deterministic local inputs, no external systems.
- Which account, beneficiary, IBAN, wallet, rail, currency, market, venue, asset class, instrument, notional, amount, exposure, and frequency checks are enforced, if any?
  Existing workflow policy dimensions remain owned by their capability stories. This epic adds telemetry for policy decisions, approval state, evidence quality, data classification, and export scope; it does not invent new financial authority.
- What happens when the requested action exceeds policy, scope, or evidence?
  The owning policy path fails closed, while telemetry records the redacted policy outcome, denied reason category, evidence state, and replay-safe audit reference.
- Is execution paper-only, draft-only, sandbox, live, or disabled?
  Telemetry does not enable execution. Execution remains whatever the owning workflow allows; this epic observes, audits, and exports only governed evidence.
- Which fixtures, samples, audit records, replay capsules, or API examples prove the behavior?
  Local-only config, enterprise collector config, managed-cloud blocked config, redaction fixtures, `tkmetr` samples, `tkdiag` samples, OTel envelopes, audit JSONL, signed batch metadata, replay capsules, dashboard fixtures, SIEM export samples, and blocked raw-content export samples.
- Can replay run without external side effects when replay applies?
  Yes. Replay disables or substitutes collector export, model calls, adapter calls, proposal results, approval results, and execution results.
- What intentional blocked-flow or divergence example proves fail-closed behavior?
  Malformed telemetry mode, missing collector, managed-cloud prerequisites absent, raw content capture without admin approval, forbidden high-cardinality label, prompt-injection tool request, data-exfiltration attempt, stale-data output, uncited client-delivery output, tampered audit event, and altered replay evidence.
