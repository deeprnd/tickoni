# V7.12: Runtime Hooks

**Status: Planned · Milestone: M7**
**Labels:** `epic`, `area/platform`, `area/audit`, `area/agents`

Add a canonical hook envelope and type registry so every model call, tool use,
and action proposal has a consistent, observable checkpoint that feeds audit,
replay divergence detection, and operator decision timelines.

---

## Product Intent

V1.11 established governed tile boundaries with audit, replay, and bypass
enforcement. V7.12 adds the checkpoint layer that makes every transition *within*
those boundaries observable at a fine-grained level. Without hooks, audit records
capture tile-level outcomes. With hooks, audit captures the exact moment before
and after a model call, tool use, or proposal decision, so operators and partners
can answer "why did this get allowed, blocked, resized, or changed?" with field-
level precision.

Hooks are not visible to consumers as hooks. They power the annotated decision
timeline that operators and partners inspect in the trust layer.

## User Story

As an operator or regulated partner, I can inspect an annotated timeline that
shows every model call, tool use, action proposal, approval, and replay event
in a governed money-decision flow, with exact before/after state, so I can
understand why each step was allowed, blocked, resized, or changed without
reading raw tile logs.

## What The Operator Sees

- annotated checkpoint timeline per case or synthetic run
- pre/post model call records with request hash, response hash, token usage,
  latency, and budget state
- pre/post tool use records with tool name, invocation protocol, adapter id,
  input hash, and output hash
- pre-action-proposal records with proposal hash, capability envelope id, and
  policy outcome before execution
- approval checkpoint records for broker and live modes
- replay divergence report showing first divergent hook type, sequence number,
  and field

## Non-Goals

- no hooks visible in the consumer investing or payment UI
- no hook-based policy enforcement (policy stays in `tkpoly`)
- no hook-based routing decisions
- no unbounded hook chains or recursive hook invocation
- no hook access to raw model prompts or responses outside audit paths

## WBS

### V7.12.S1: Hook envelope and type registry

**Description:** Define canonical hook envelope with id, type, tile, sequence, and payload hash fields, register hook types as comptime enum, enforce bounded link capacity with drop counters, validate envelope fields at construction.

Tasks:

- V7.12.S6.T1: Define a canonical hook envelope with hook id, hook type,
  tile id, event sequence number, nanosecond timestamp, case or synthetic run
  id, actor id, role, workflow, policy version, capability envelope id, and
  payload hash.
- V7.12.S6.T2: Define hook type as a comptime-resolved enum or tagged union
  covering `PreModelCall`, `PostModelCall`, `PreToolUse`, `PostToolUse`,
  `PreActionProposal`, `PreApproval`, `PostApproval`, `ReplayCheckpoint`, and
  `FirstDivergence`.
- V7.12.S6.T3: Define a bounded hook link capacity per hook type. A hook link
  that is full drops the hook event and records a drop counter; it does not
  block the owning tile.
- V7.12.S6.T4: Validate hook envelope fields at construction: required ids
  non-empty, timestamp monotonically increasing within a run, hook type in the
  registry, payload hash non-zero.
- V7.12.S6.T5: Add tests for malformed envelope rejection, unknown hook type
  rejection, drop counter increment on full link, and timestamp monotonicity.

Acceptance:

- A malformed or unknown-type hook envelope is rejected at construction and
  never reaches the audit path.
- A full hook link drops the event, increments a counter, and does not stall
  the owning tile.

### V7.12.S2: Pre and post model call hooks

**Description:** Emit PreModelCall before provider dispatch and PostModelCall after every terminal outcome, add replay substitution tracking, verify timing guarantees for success, error, retry, and budget-exhaustion paths.

Tasks:

- V7.12.S2.T1: Emit `PreModelCall` from `tkmodl` after validating the
  `TkModlRequest` but before dispatching to a provider. Include request id,
  model identifier, budget id, context token count, max output tokens, retry
  limit, capability envelope id, and request hash.
- V7.12.S2.T2: Emit `PostModelCall` from `tkmodl` after receiving a provider
  response or reaching a terminal error. Include request id, model identifier,
  backend category, prompt token count, completion token count, retry count,
  latency, response hash, policy decision id, and replay substitution id if
  applicable.
- V7.12.S2.T3: Add replay substitution id to `PostModelCall` when the call was
  satisfied by a captured fixture rather than a live provider.
- V7.12.S2.T4: Verify `PreModelCall` fires before any provider network call;
  verify `PostModelCall` fires after every terminal outcome including error and
  budget exhaustion.
- V7.12.S2.T5: Add tests for live allow, replay substitution, budget exhaustion,
  provider error, and unknown model id across both hook events.

Acceptance:

- Every `tkmodl` dispatch produces exactly one `PreModelCall` and one
  `PostModelCall` regardless of success, error, retry count, or replay mode.
- A budget-exhaustion stop state produces a `PostModelCall` with an explicit
  budget-exhausted outcome, not a missing hook.

### V7.12.S3: Pre and post tool use hooks

**Description:** Emit PreToolUse before tktool dispatch to adapter and PostToolUse after every terminal outcome, capture invocation protocol for audit, verify timing for allowed, denied, timeout, and replay paths.

Tasks:

- V7.12.S3.T1: Emit `PreToolUse` from `tktool` after normalizing a model-native
  function call or MCP-style request into a finance-native tool request, but
  before dispatching to `tkadpt`. Include tool request id, tool name, invocation
  protocol, adapter id, capability envelope id, and input hash.
- V7.12.S3.T2: Emit `PostToolUse` from `tktool` after receiving the adapter
  result or reaching a terminal error. Include tool request id, adapter id,
  output hash, latency, result status, and replay substitution id if applicable.
- V7.12.S3.T3: Capture invocation protocol field to distinguish model-native
  function calls from MCP-style requests in audit output.
- V7.12.S3.T4: Verify `PreToolUse` fires before any adapter call and
  `PostToolUse` fires after every terminal adapter outcome including timeout and
  denied scope.
- V7.12.S3.T5: Add tests for allowed adapter call, denied scope, adapter
  timeout, and replay substitution across both hook events.

Acceptance:

- Every `tktool` dispatch produces exactly one `PreToolUse` and one
  `PostToolUse` regardless of adapter outcome or replay mode.
- A denied-scope adapter call produces a `PostToolUse` with an explicit deny
  outcome, not a missing hook.

### V7.12.S4: Action proposal hooks

**Description:** Emit PreActionProposal before policy outcome for propose-class capabilities with proposal hash for replay verification, only fire for propose and above, verify hash matches audit record.

Tasks:

- V7.12.S4.T1: Emit `PreActionProposal` immediately before `tkpoly` emits its
  final outcome for a proposal-class capability: `trading_order.propose`,
  `payment_retry.propose`, `bank_transfer.propose`, and
  `crypto_transfer.propose`. Include proposal id, capability name, actor id,
  role, workflow, case or run id, policy version, capability envelope id,
  proposal hash, and the pending policy outcome.
- V7.12.S4.T2: The `PreActionProposal` hook must carry the proposal hash before
  any downstream execution or audit write, so a replay can verify the proposal
  was not modified between policy evaluation and action.
- V7.12.S4.T3: `PreActionProposal` does not fire for observe, analyze, draft,
  or recommend capabilities; it fires only for propose-class and above.
- V7.12.S4.T4: Add tests for allowed proposal, denied proposal, require-approval
  proposal, and require-more-evidence proposal across all four proposal
  capabilities.

Acceptance:

- Every propose-class capability evaluation produces exactly one
  `PreActionProposal` hook before the policy outcome is written to audit.
- The proposal hash in the hook matches the proposal hash in the audit record.

### V7.12.S5: Approval hooks

**Description:** Emit PreApproval and PostApproval around approval state changes, handle approval, rejection, revocation, and expiry outcomes, verify distinguishable outcomes.

Tasks:

- V7.12.S5.T1: Emit `PreApproval` when an operator or maker-checker approval
  action arrives for a pending proposal. Include approval id, proposal id,
  proposal hash at approval time, approver actor id, approver role, policy
  version, expiry, and environment.
- V7.12.S5.T2: Emit `PostApproval` after the approval state is recorded.
  Include approval id, proposal id, outcome (approved or rejected), approver
  actor id, and resulting approval state.
- V7.12.S5.T3: Emit `PreApproval` and `PostApproval` for revocation events as
  well, with outcome field set to `revoked`.
- V7.12.S5.T4: Verify that a stale or expired approval attempt produces a
  `PostApproval` with an explicit expired outcome rather than a missing hook.
- V7.12.S5.T5: Add tests for approval, rejection, revocation, and expired
  approval across `PreApproval` and `PostApproval`.

Acceptance:

- Every approval state change produces exactly one `PreApproval` and one
  `PostApproval` hook.
- A stale approval rejection and a revocation are distinguishable by the
  `PostApproval` outcome field.

### V7.12.S6: Replay hooks and first-divergence reporting

**Description:** Define ReplayCheckpoint hooks to compare captured and replay payload hashes at every boundary, emit FirstDivergence on first mismatch with field details, disable external effects during replay.

Tasks:

- V7.12.S6.T1: Define `ReplayCheckpoint` hook that fires at every hook
  boundary during a replay run. It carries the original captured hook id, the
  original captured payload hash, and the current replay payload hash.
- V7.12.S6.T2: Compare payload hashes at each `ReplayCheckpoint`. When the
  first mismatch is found, emit a `FirstDivergence` hook with divergent hook
  type, sequence number, original hash, replay hash, and the first differing
  field name when determinable.
- V7.12.S6.T3: Replay runs with external effects disabled: `PostModelCall`
  hooks in replay mode carry a replay substitution id, never a live provider
  response. `PostToolUse` hooks in replay mode carry a captured adapter
  substitution id.
- V7.12.S6.T4: `FirstDivergence` stops further replay checkpoint comparison and
  is written to the replay capsule divergence record.
- V7.12.S6.T5: Add tests for replay match, first-divergence on model output
  hash, first-divergence on proposal hash, and deliberate tamper of a captured
  fixture.

Acceptance:

- A replay run with no changes produces `ReplayCheckpoint` hooks with matching
  hashes at every boundary and no `FirstDivergence`.
- A tampered captured fixture produces a `FirstDivergence` at the correct hook
  sequence number with the correct differing field.
- Replay hooks fire no live model, adapter, broker, market, payment, or
  execution calls.

### V7.12.S7: Hook telemetry and diagnostics

**Description:** Export per-hook-type counters and latency histograms through tkmetr, expose registry state and drop counts through tkdiag, isolate hook failures from tile operations.

Tasks:

- V7.12.S7.T1: Export per-hook-type counters through `tkmetr`: total fired,
  total dropped (full link), total malformed rejected, and total replay
  checkpoints.
- V7.12.S7.T2: Export per-hook-type latency histograms for `PreModelCall` to
  `PostModelCall` and `PreToolUse` to `PostToolUse` pairs.
- V7.12.S7.T3: Export hook registry state through `tkdiag`: registered hook
  types, link capacity per type, current drop counts, and last fired sequence
  per type.
- V7.12.S7.T4: A hook construction or emission failure must not propagate an
  error to the owning tile. Hook failures are counted and exported through
  telemetry; they do not close or stall the tile.
- V7.12.S7.T5: Add tests for counter increment on fire and drop, histogram
  update on paired hooks, and tile isolation from hook emission failures.

Acceptance:

- Hook metrics are present in `tkmetr` output for every registered hook type
  that has fired at least once.
- A simulated hook emission failure increments the failure counter and does not
  affect tile operation or audit output.

## Evidence Gate

- Every `tkmodl` dispatch produces exactly one `PreModelCall` and one
  `PostModelCall` in the hook timeline, including replay substitution and budget
  exhaustion paths.
- Every `tktool` dispatch produces exactly one `PreToolUse` and one
  `PostToolUse`, including denied-scope and replay substitution paths.
- Every propose-class capability produces a `PreActionProposal` whose proposal
  hash matches the audit record.
- A replay run reproduces the hook sequence from captured inputs with no live
  effects, and a tampered fixture produces a `FirstDivergence` at the correct
  sequence number.
- Hook emission failures are counted in metrics and do not affect tile operation.
