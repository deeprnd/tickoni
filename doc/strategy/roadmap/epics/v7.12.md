# V7.12: Runtime Hooks — The Decision Timeline

**Status: Planned · Milestone: M7**
**Labels:** `epic`, `area/platform`, `area/audit`, `area/agents`

Every financial AI system has the same fundamental problem: nobody can tell *why* a decision was made. Not because the data is missing — because it's buried in tile-level outcomes that read like a ledger, not a story.

V7.12 adds the checkpoint layer that makes every transition *within* tile boundaries visible as a chronology of decisions, not a table of hashes. Without hooks, audit records capture the before and after of a model call, tool use, or proposal — but not the decision point between them. Operators can see what happened. They cannot see why it happened.

Hooks are not visible to consumers. They power the annotated decision timeline that operators and regulated partners inspect in the trust layer — where the invisible becomes visible, and accountability becomes narrative.

---

## Why This Matters

Start with the why, not the hook type.

Financial institutions don't need more data about model calls. They need **confidence that they can inspect any decision and explain it to a regulator in minutes, not days**. Right now, the gap between "the system decided X" and "here's why the system decided X" requires an engineer to read tile-level logs. That gap is the single biggest barrier to trust in autonomous financial systems.

The hook system closes that gap by capturing the exact moment — the before, the decision logic, and the after — for every model call, tool invocation, and action proposal. Operators don't read logs. They read a timeline.

**This is not an engineering problem. It's a trust problem.** And trust is built by making the invisible visible.

## What The Operator Sees

A clean, annotated timeline per case or synthetic run — not a scatter of hashes, but a chronological narrative:

- checkpoint timeline showing every model call, tool use, action proposal, approval, and replay event in order
- pre/post model call records with request/response hashes, token usage, latency, and budget state
- pre/post tool use records with tool name, invocation protocol, adapter id, input/output hashes
- pre-action-proposal records with proposal hash, capability envelope id, and the pending policy outcome
- approval checkpoint records showing the before/after of every broker and live-mode approval
- replay divergence report identifying the first hook-level mismatch with sequence number and field name

## What The Operator Does Not See

- hooks are not exposed in the consumer investing or payment UI
- hooks do not replace policy enforcement (policy stays in `tkpoly`)
- hooks do not drive routing decisions
- hooks cannot chain recursively or create unbounded execution chains
- hooks do not expose raw model prompts or responses outside audit paths

## WBS

### V7.12.S1: Hook envelope and type registry

**Description:** Define the canonical hook envelope — id, type, tile, sequence, payload hash — and register all hook types as a comptime enum. Enforce bounded link capacity with drop counters and validate all envelope fields at construction.

**Tasks:**

- V7.12.S1.T1: Define the canonical hook envelope with id, type, tile, sequence, and payload hash fields.
- V7.12.S1.T2: Register hook types as comptime enum; enforce bounded link capacity with drop counters.
- V7.12.S1.T3: Validate envelope fields at construction: non-empty required ids, monotonic timestamps, registered types, non-zero payload hashes.
- V7.12.S1.T4: Add tests for malformed rejection, unknown type rejection, drop counter on full link, and timestamp monotonicity.

**Acceptance:**

- Malformed or unknown-type envelopes are rejected at construction and never reach audit.
- Full links drop events, increment counters, and never stall the owning tile.

### V7.12.S2: Pre and post model call hooks

**Description:** Emit PreModelCall before provider dispatch and PostModelCall after every terminal outcome. Track replay substitutions. Verify timing for success, error, retry, and budget-exhaustion paths.

**Tasks:**

- V7.12.S2.T1: Emit PreModelCall from tkmodl after validating the request but before provider dispatch, including request id, model id, budget id, token counts, and capability envelope id.
- V7.12.S2.T2: Emit PostModelCall from tkmodl after provider response or terminal error, including token counts, retry count, latency, response hash, and replay substitution id.
- V7.12.S2.T3: Track replay substitution id on PostModelCall when satisfied by captured fixture.
- V7.12.S2.T4: Verify PreModelCall fires before any provider network call; PostModelCall fires after every terminal outcome including error and budget exhaustion.
- V7.12.S2.T5: Add tests for live allow, replay substitution, budget exhaustion, provider error, and unknown model id.

**Acceptance:**

- Every tkmodl dispatch produces exactly one PreModelCall and one PostModelCall across all outcomes.
- Budget-exhaustion stops produce a PostModelCall with explicit budget-exhausted outcome, not a missing hook.

### V7.12.S3: Pre and post tool use hooks

**Description:** Emit PreToolUse before tktool dispatch and PostToolUse after every terminal outcome. Capture invocation protocol for audit. Verify timing for allowed, denied, timeout, and replay paths.

**Tasks:**

- V7.12.S3.T1: Emit PreToolUse from tktool after normalizing model-native or MCP-style requests into finance-native tool requests, before dispatching to tkadpt.
- V7.12.S3.T2: Emit PostToolUse from tktool after adapter result or terminal error, including output hash, latency, result status, and replay substitution id.
- V7.12.S3.T3: Capture invocation protocol to distinguish model-native function calls from MCP-style requests.
- V7.12.S3.T4: Verify PreToolUse fires before any adapter call; PostToolUse fires after every terminal outcome including timeout and denied scope.
- V7.12.S3.T5: Add tests for allowed, denied scope, adapter timeout, and replay substitution.

**Acceptance:**

- Every tktool dispatch produces exactly one PreToolUse and one PostToolUse across all outcomes.
- Denied-scope calls produce a PostToolUse with explicit deny outcome, not a missing hook.

### V7.12.S4: Action proposal hooks

**Description:** Emit PreActionProposal before policy outcome for propose-class capabilities. Verify proposal hash matches audit record. Only fire for propose and above.

**Tasks:**

- V7.12.S4.T1: Emit PreActionProposal before tkpoly's final outcome for trading_order.propose, payment_retry.propose, bank_transfer.propose, and crypto_transfer.propose.
- V7.12.S4.T2: Carry proposal hash before any downstream execution or audit write, so replay can verify the proposal was not modified.
- V7.12.S4.T3: PreActionProposal does not fire for observe, analyze, draft, or recommend capabilities.
- V7.12.S4.T4: Add tests for allowed, denied, require-approval, and require-more-evidence proposals across all four proposal capabilities.

**Acceptance:**

- Every propose-class capability evaluation produces exactly one PreActionProposal before the policy outcome is written to audit.
- The proposal hash in the hook matches the audit record.

### V7.12.S5: Approval hooks

**Description:** Emit PreApproval and PostApproval around approval state changes. Handle approval, rejection, revocation, and expiry. Distinguishable outcomes.

**Tasks:**

- V7.12.S5.T1: Emit PreApproval when operator or maker-checker approval action arrives, including proposal hash at approval time, approver identity, expiry, and environment.
- V7.12.S5.T2: Emit PostApproval after approval state is recorded, including outcome and resulting state.
- V7.12.S5.T3: Emit PreApproval and PostApproval for revocation with outcome set to revoked.
- V7.12.S5.T4: Stale or expired approval attempts produce PostApproval with explicit expired outcome.
- V7.12.S5.T5: Add tests for approval, rejection, revocation, and expired approval.

**Acceptance:**

- Every approval state change produces exactly one PreApproval and one PostApproval.
- Stale approval rejection and revocation are distinguishable by outcome field.

### V7.12.S6: Replay hooks and first-divergence reporting

**Description:** Define ReplayCheckpoint hooks to compare captured and replay payload hashes at every boundary. Emit FirstDivergence on first mismatch. Disable external effects during replay.

**Tasks:**

- V7.12.S6.T1: Define ReplayCheckpoint hook firing at every hook boundary during replay with original and replay payload hashes.
- V7.12.S6.T2: Compare hashes at each ReplayCheckpoint; emit FirstDivergence on first mismatch with hook type, sequence number, both hashes, and first differing field.
- V7.12.S6.T3: Replay runs with external effects disabled; PostModelCall carries replay substitution id; PostToolUse carries captured adapter substitution id.
- V7.12.S6.T4: FirstDivergence stops further checkpoint comparison and writes to replay capsule divergence record.
- V7.12.S6.T5: Add tests for replay match, first-divergence on model and proposal hashes, and deliberate fixture tamper.

**Acceptance:**

- Replay with no changes produces matching ReplayCheckpoint hashes at every boundary and no FirstDivergence.
- Tampered fixtures produce FirstDivergence at the correct sequence number with the correct field.
- Replay hooks fire no live calls to model, adapter, broker, market, payment, or execution systems.

### V7.12.S7: Hook telemetry and diagnostics

**Description:** Export per-hook-type counters and latency histograms through tkmetr. Expose registry state and drop counts through tkdiag. Isolate hook failures from tile operations.

**Tasks:**

- V7.12.S7.T1: Export per-hook-type counters through tkmetr: total fired, total dropped, total malformed rejected, total replay checkpoints.
- V7.12.S7.T2: Export per-hook-type latency histograms for PreModelCall to PostModelCall and PreToolUse to PostToolUse pairs.
- V7.12.S7.T3: Expose registry state through tkdiag: registered types, link capacities, drop counts, last fired sequence.
- V7.12.S7.T4: Hook failures must not propagate to the owning tile — counted and exported through metrics only.
- V7.12.S7.T5: Add tests for counter increments, histogram updates, and tile isolation from hook failures.

**Acceptance:**

- Metrics are present for every registered hook type that has fired.
- Simulated hook failure increments counter and does not affect tile operation or audit.

## Evidence Gate

- Every tkmodl dispatch produces exactly one PreModelCall and one PostModelCall, including replay substitution and budget exhaustion.
- Every tktool dispatch produces exactly one PreToolUse and one PostToolUse, including denied-scope and replay substitution.
- Every propose-class capability produces a PreActionProposal whose hash matches the audit record.
- Replay reproduces the hook sequence from captured inputs with no live effects; tampered fixtures produce FirstDivergence at the correct sequence.
- Hook emission failures are counted in metrics and do not affect tile operation.
