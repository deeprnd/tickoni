# V5.2: Model Selection And Governance

**Status:** Backlog
**Milestone:** M5
**Labels:** `epic`, `area/investing`, `area/platform`, `area/security`

**Summary:** V5.2 is where Tickoni proves that governing AI access is not a productivity tax — it is a trust signal. Before V5.2, LLM models are interchangeable inference engines inside the runtime, and every agent can call them without constraint. After V5.2, every model call is policy-gated, budget-bounded, attributed, audited, and replayable. The counterintuitive insight: restricting *which* models an agent can use and *how much* it can spend per case makes Tickoni viable for financial operations in ways that generic agent harnesses never will be. A generic harness asks "can this agent call an LLM?" Tickoni asks "can this agent use this model, for this case, within this budget, under this policy, and prove it afterward?"

Extracted from the M5 backlog proposal.

## Product Intent

V5.2 delivers the `tkmodl` model gateway surface. Users assign a model tier per portfolio, and `tkmodl` enforces the governance contract — allowlist, context limit, retry limit, token budget, attribution, and replay substitution for every model call.

The constraint is the feature. Generic harnesses treat model access as an open resource: more models, broader provider coverage, fewer limits. Tickoni takes the opposite path. Per-portfolio model tiers, hard budgets, and mandatory audit are not limitations — they are the trust signal that makes a financial AI harness credible. Without V5.2, the bounded investigations in V5.26–V5.5, rebalance suggestions in V5.4, and valuation queue in V5.5 have no governed model access. This epic is the gate between unconstrained inference and governed financial operations.

## Users And Jobs

- Consumer investor: choose a model tier for each portfolio (or leave the
  default), understand which model is being used, and see model usage in the
  audit trail.
- Risk reviewer: inspect model attribution (which model, which provider,
  which investigation), verify budget enforcement and retry limits, confirm
  that replay substitutes captured model outputs.
- CaseOps operator: see model selection, usage counters, and replay substitution
  status for every investigation.

## Success Metrics

- A user can set a model tier per portfolio, and `tkmodl` enforces the allowlist,
  context limit, retry limit, and token budget for every call.
- Every model call is attributed to the correct portfolio, investigation, and
  tier, and stored in the audit chain.
- Replay substitutes captured model outputs without calling the LLM server or
  cloud provider.
- No live model, broker, payment, trading, crypto, approved execution ledger, or execution
  side effects occur unless this epic explicitly enables an approved sandbox path.

## Demo Moment

- Command or flow: Set portfolio "Demo" to use the `stub` model tier.
  Run a bounded investigation that queries portfolio holdings (V5.26 state).
  Verify `tkmodl` attributes the call to portfolio "Demo", enforces retry
  limits, and records the call in audit. Then replay the investigation and
  confirm `tkmodl` substitutes the captured output without calling any
  external service.
- Expected result: deterministic demo output showing model selection, audit
  record with attribution, replay capsule substituting the model output, and
  no external calls during replay.

## Scope

### In Scope

- Model tier selection stored as `tkmodl` capability scope per portfolio.
- Model allowlist enforcement: only configured tiers are callable.
- Token budget enforcement: context limit, retry limit, token accounting.
- Attribution: every model call records actor, portfolio, investigation,
  model id, provider category, and policy version.
- Append-only audit of model requests and responses.
- Replay substitution: `tkmodl` substitutes captured model outputs during
  replay, never calls LLM servers or cloud providers.
- Model selection distribution metrics via `tkmetr`.

### Out Of Scope

- Portfolio CRUD (V5.26).
- Exposure computation (V5.29).
- Rebalance suggestions (V5.4).
- Watchlist and valuation queue (V5.5).
- Model training, fine-tuning, or provider-specific prompts.
- Multi-modal models or non-text model outputs.
- Dynamic model pricing or cost-per-token accounting.
- Model performance ranking or A/B testing.

### How Many Stories

V5.2 is a mid-range epic (governance + visibility + replay + closure): 4 stories.

### Decomposition Rules

1. **Independent delivery**: each story produces an operator-visible outcome
   without waiting for every other story.
2. **One capability per story**: model tier selection + allowlist + budget
   enforcement in S1; these are part of the governance contract, not separate
   stories.
3. **Split by capability lifecycle**:
   - S1: Core capability — model tier selection, allowlist, budget enforcement,
     attribution, stored as `tkmodl` capability scope.
   - S2: Read / query / visibility — the operator-facing surface (CaseOps) that
     surfaces model selection and usage counters.
   - S3: State lifecycle — replay and audit for model calls, dependent on S1
     being stable.
   - S4: Closure story — evidence, demo, documentation, and quality gates via
     child tasks (T10), not a standalone epic-level story.
4. **Closure story**: S4 handles evidence, demo, documentation, and quality
   gates via child tasks (T10) per the story template convention, not as a
   separate story line.
5. **Domain boundaries**: model governance and CaseOps surface are separate
   stories (S1, S2), not features within one story.

### Bad Splits (Avoid)

- Model allowlist + "budget" as two stories. Budget enforcement is part of the
  governance contract.
- "Backend" + "frontend" as two stories. Both should be independently testable
  outcomes.
- "Database" + "API" as two stories. Same reason.
- Anything that requires ALL other stories to complete before one acceptance
  criterion can be tested. That is not independent delivery.

- What can the user or operator do now that they could not before this epic?
  Assign a model tier per portfolio and have every bounded investigation governed
  by `tkmodl` — with budget enforcement, attribution, and replay substitution.
  The user no longer has to wonder which model powered an agent's analysis or
  whether inference spend ran unbounded. They set the tier, and the system enforces it.
- What changed from the previous roadmap increment?
  M4 delivered the governed runtime and V4.32 valuation engine. V5.2 adds the
  model gateway that governs how agents and bounded investigations access LLMs.
- What is this epic's wow-effect?
  Set a model tier, see bounded investigations run through the governed gateway,
  and replay with the exact same outputs — no external calls, fully deterministic.
  It's the moment where "governed AI" stops being an abstract concept and becomes
  something you can verify by replaying a case.
- How does this epic progress Tickoni's unique value proposition from
  doc/strategy/positioning.md?
  Model access is policy-gated and auditable — the same discipline as payments
  and trading, applied to AI models. Tickoni doesn't just make agents work faster;
  it makes AI inference governable at the same level as financial actions.

  Deterministic demo: set tier, run bounded investigation, verify attribution,
  replay with substitution.

  Deterministic demo: model selection audit record with attribution, replay
  capsule substituting the captured model output, no external calls during

  Yes — `tkmodl` substitutes captured model outputs.

  Disallowed model tier rejected by `tkmodl` allowlist; malformed model request
  (context exceeding limit) rejected before call.

## Dependencies And Decisions

- V4.32 DCF valuation engine must be available; V5.2 governs the model
  calls that V4.32 and V5.26–V5.5 consume.
- `tkmodl` must integrate with existing model providers (deterministic stubs,
  local OpenAI-compatible server, OpenAI, Anthropic) — V5.2 adds governance
  on top of existing provider wiring.
- Decision: Model tier granularity — per-portfolio vs per-investigation.
  **Decision: per-portfolio stored as `tkmodl` capability scope; investigations
  inherit the portfolio's tier.**
