# M10: Broker And Crypto Platform Sync

## Description

M10 establishes read-only synchronization with external broker and crypto platforms
so Tickoni can ingest a user's existing holdings and portfolio composition as
canonical financial events. The sync feeds real portfolio state into the investment
workflow, closing the gap between Tickoni's portfolio model and what the user
actually holds.

Every sync event flows through tkings -> tknorm -> tkdedu -> tkpoly -> tkaudt,
producing deterministic, audit-grade financial facts. All adapter calls are
paper/sandbox only -- no live trading authority.

```text
broker credentials -> sync -> normalize -> audit -> portfolio state
```

## Included Epics

Product increments:

- `V10.1`: Credential Management For Broker And Crypto Platforms -- governed credential storage behind tkadpt, scoped tokens, fail-closed when credentials are missing or expired, separate paths for broker platforms (OAuth/credentials) and crypto exchanges (API keys)
- `V10.2`: Broker Adapter And Holdings Ingestion -- sandbox stub for broker platforms (eToro, Interactive Brokers, SnapTrade, Robinhood) that pulls holdings snapshots and returns deterministic fixtures
- `V10.3`: Crypto Exchange Adapter And Holdings Ingestion -- sandbox stub for crypto exchanges that pulls holdings snapshots and returns deterministic fixtures
- `V10.4`: Canonical Portfolio Event Schema -- normalized event schema covering instrument, quantity, price, currency, market, venue, asset class, and notional; versioned schema to support historical replay
- `V10.5`: Broker And Crypto Read Capabilities -- broker_read and crypto_read capability scopes in tkpoly with allow/deny outcomes, read-only enforcement, and scope dimensions (broker_account_id, asset_class, market, venue, instrument, currency, notional, exposure, sync_interval)
- `V10.6`: Sync Orchestration And Deduplication -- sync scheduler, source-offset tracking, idempotency key generation, deduplication against prior snapshots, rejection handling for unparseable holdings
- `V10.7`: Audit Recording For Sync Events -- append-only, hash-chained audit trail for sync start, each holding record, and sync completion in tkaudt; divergence between broker-reported and Tickoni-ingested values logged
- `V10.8`: the analytics store Portfolio Persistence -- portfolio table population and updates from normalized sync data; versioned schema to support historical replay
- `V10.9`: CaseOps Broker-Sync Display -- sync status, last-sync timestamp, held-instrument count, new vs. updated positions, normalization rejections, and full audit trail
- `V10.10`: Evidence, Demo, And Release Closure -- fixtures, demo flow, quality gates, documentation

## Why This Is A Milestone

M8 establishes sandbox execution for broker actions. M9 establishes external-source
research ingestion. M10 establishes the portfolio-state ingestion that makes both
of them grounded in reality.

It deserves milestone status because it closes the loop where Tickoni's portfolio
model stops being a blank slate and starts reflecting actual user positions:

- The investment workflow goes from research-only (M9) to research-grounded: an
  agent investigating a user can now see real holdings, not hypothetical ones.
- A new capability boundary class (broker_read/crypto_read) is introduced,
  proven to enforce read-only boundaries across two different external-source
  models (broker platforms and crypto exchanges).
- The normalized portfolio event schema becomes the template for all future
  external-source ingestion. Every new source (news feeds, regulatory filings,
  other aggregators) will reuse the same canonical event shape, the same
  capability-envelope model, and the same audit-replay patterns.
- Tickoni becomes a complete consumer-money product: invest -> pay -> move -> hold
  -> prove. "Hold" was the missing link. Broker and crypto sync provides the
  factual baseline of user holdings so that downstream policy checks, rebalance
  proposals, and risk calculations are anchored to real positions rather than
  blank-state assumptions.

M9 proved that external-source ingestion can be governed by capability envelopes
and replay substitution. M10 proves that the same governance model applies when
the external source carries financial consequence (actual holdings) rather than
purely informational content (video summaries).

## Completion Signal

A user can enable a broker platform (eToro, Interactive Brokers, SnapTrade, or Robinhood) or a
crypto exchange, trigger a portfolio sync, and verify that the holdings appear
in the analytics store as normalized financial events in the portfolio table. CaseOps displays
the sync result: instruments found, new vs. updated positions, any normalization
rejections, last sync timestamp, and source system. Every sync event is visible
as a hash-chained audit trail in tkaudt.

The same sync replays deterministically from a captured broker adapter fixture
without calling the live platform, producing identical portfolio state and audit
records. A compliance operator can inspect the evidence trail and verify that
every holding record carries source attribution, capability envelope scope
(broker_account_id, asset_class, market, venue, instrument, currency, notional,
exposure), and that no write or trading scope was permitted by the broker_read
or crypto_read capability gates.

## Summary

Tickoni's portfolio model was a blank slate until M10. Now it reflects what the
user *actually* holds. Read-only sync with brokers and crypto exchanges feeds
real holdings into Tickoni's governed event pipeline — normalize, dedupe,
policy-check, audit. The investment workflow goes from research-grounded (M9)
to reality-grounded: an agent investigating a user sees real positions, not
hypothetical ones. "Hold" was the missing link. After M10, the consumer-money
product is complete: invest → pay → move → hold → prove.
