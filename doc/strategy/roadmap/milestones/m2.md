# M2: Enforced Boundaries

## Description

M2 is where Tickoni earns the right to touch financial decisions.

Before M2, Tickoni was a proof-of-concept — all in-process, no boundaries, and Linux-only. After M2, every action is bounded, crash-isolated, auditable, and replayable on any supported platform. Not because we distrust the agents, but because ambition without enforceable limits is just risk wearing a different name.

Four changes make this real. First, tiles move from shared threads to supervisor-managed processes over Firedancer shared-memory links — one OS process per tile, one address space per tile. A crashing tile cannot corrupt its sibling. Second, Tickoni runs on consumer Mac and Windows hardware with the same policy-gated demos, audit output, and replay proofs that Linux engineers run internally. The high-throughput Firedancer engine remains on Linux; consumer hardware gets a supported retail runtime path that doesn't weaken financial boundaries for portability. Third, the build system (1,766 lines, the single largest file in the codebase) collapses to under 500 lines with walk-based test discovery, so a new developer can clone the repo, run two commands, and get green tests on their platform. Fourth, agent lifecycle, tool dispatch, and model-call limits become enforceable policy events rather than advisory counters.

These boundaries don't limit ambition — they enable trust. A crashing tile leaves its siblings running. An agent that exhausts its step limit halts gracefully with an audit record, not a panic or a loop. Every tool call — whether it arrives as a function name, an MCP request, or any other format — hits the same normalized gate. Tickoni works the same on a MacBook Air, a Windows laptop, and a Linux workstation. That's the difference between an experiment and a product.

## Why This Is A Milestone

M1 showed Tickoni could make a proposal on the right tile boundaries. M2 makes those boundaries real, portable, and accessible.

The milestone isn't "we moved from threads to processes" or "we ported to Mac and Windows." The milestone is "we moved from 'can it work?' to 'can we trust it?' — and can we trust it everywhere?"

Four changes, one goal:

- **Process isolation** (V2.14): Each tile runs as a supervisor-managed OS process over Firedancer shared-memory links. Crash containment, CPU placement, and flow control become real, not logical.
- **Portable runtime** (V2.21, V2.22): Tickoni runs on consumer Mac and Windows hardware — the same policy-gated demos, the same audit output, the same replay proofs. Linux remains the high-throughput tier; consumer platforms get a supported retail runtime path that preserves all financial boundaries. The trust surface is portable, not Linux-dependent.
- **Build system accessibility** (V2.10): The largest file in the codebase becomes a declarative under-500-line system with walk-based discovery. A new developer adds a test file, runs the suite, gets green results — without reading boilerplate. That's how you grow a community without weakening boundaries.
- **Enforced limits** (all): Agent step limits, token budgets, tool bypass closure, and per-role model-call caps produce audit records, not panics. The limits are real, not advisory.

Those boundaries are what separate an experiment from an institution. They are prerequisites for the proof and trust surfaces in M4.

## Completion Signal

M2 is complete when:

- A crashing tile leaves its siblings running and their audit trails intact.
- An agent that exhausts its step limit or token budget halts with an audit record — not a panic, not a loop.
- A tool bypass attempt is denied, regardless of how the request was formatted.
- Per-role model-call limits halt that role without affecting others.
- A consumer Mac or Windows user runs the same deterministic paper investment demo, policy outcomes, audit output, and replay proofs as the Linux full-runtime build — on native hardware, not through WSL2 or a container.
- A new contributor can add a Zig test file and run the full test suite without modifying the build system.

### The Problem With Paper Boundaries

Before M2, Tickoni's boundaries existed as rules on paper — logical separation within a single process, Linux-only by necessity, a build system that demanded deep plumbing knowledge just to compile. The product could make proposals, but it could not yet earn the trust required to act on them. Saying a tile must not corrupt its sibling is a promise; making it structurally impossible is a guarantee. M2 is the difference between the two.

### Crash Containment as a Psychological Signal

M2 makes those boundaries physically real. Every tile runs as an independent supervisor-managed OS process over Firedancer shared-memory links with built-in flow control and backpressure. A crashing tile is reported by identity, its siblings continue unperturbed, and the supervisor follows a declared crash-or-restart path.

An agent that exhausts its step limit halts gracefully with an audit record instead of spiraling into a loop. Every tool call — whether it arrives as a function name, an MCP request, or any other format — hits the same normalized gate. Tickoni works the same on a MacBook Air, a Windows laptop, and a Linux workstation. That's the difference between an experiment and a product. This is a psychological signal that does what engineering specs cannot: it shows the user that failure has consequences, and those consequences are bounded by design, not hope.

### Trust That Travels

Those same guarantees travel beyond Linux. Tickoni now runs on consumer macOS and Windows hardware as a supported retail runtime — the same deterministic paper investment demos, the same policy-gated proposals, the same audit JSONL output, the same replay proofs. No enterprise Linux workstation. No WSL2. No containers. A MacBook Air or Windows laptop is enough to inspect a policy-checked investment proposal, trace its audit trail, and replay the decisions end to end.

The system telling a non-technical reviewer *"I can show you the proposal, but I will never execute live money on this machine"* is more valuable than any marketing copy assuring them of the same.

### Removing The Hidden Barrier

M2 also tackles the hidden cost of complexity. The build system — 1,766 lines — collapses to under 500 through walk-based test discovery and a unified `just` surface. A new developer clones, runs two commands, gets green tests. Adding a test requires no build edits. A complex build system is a trust barrier — it says *"you need to read my internals before you can verify my outputs."*

### What This Unlocks

The trust surface Tickoni builds here — crash containment, enforceable limits, cross-platform portability, build accessibility — is what separates an experiment from a product. Every boundary that holds on three platforms, every limit that produces an audit record instead of a panic — these are the properties that let Tickoni earn the right to touch financial decisions. They are the prerequisites for the proof surfaces that come next.
