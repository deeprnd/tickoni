# M0: The Trust Foundation

## Description

M0 establishes Tickoni's first verifiable property: a system that can prove
it works the same way every time.

```text
synthetic event -> full pipeline -> hash-chained audit -> replay verification
```

Before M0, Tickoni is code. After M0, it is a system that can demonstrate
structural correctness — accepting events, normalizing them to stable facts,
deduplicating deterministically, enforcing policy, recording an auditable
chain, and replaying without external effects to prove the output is identical.

This is the trust foundation. Every user-facing increment that follows depends
on it. Without M0, M1's "safe to try" is a demo with no way to verify it.

## Included Epics

Product increments:

- `V0.0`: Proof Of Correctness (supervisor, ingestion, normalization,
  deduplication, policy, audit, replay, metrics, diagnostics)

## Why This Is A Milestone

M0 crosses the threshold from implementation to verifiable product.

Before M0: the system is code that happens to process events. No one can
independently verify that it works the same way on a different run, a different
machine, or after a code review.

After M0: the system can replay a captured run with external effects disabled
and prove zero divergence. The audit chain can be verified by anyone. The
normalization and deduplication logic is content-stable — identical inputs
produce identical outputs regardless of timing or insertion order.

M1's "safe to try" depends on this property. A user can't be confident they're
testing an investment idea in a reliable environment unless the underlying
runtime has been proven correct first.

## Completion Signal

One offline command feeds a synthetic event through the full pipeline, produces
a hash-chained audit record, replays the event sequence with external effects
disabled, and reports zero divergence.

Internal completion checks:

- Identical source event payloads produce identical canonical content hashes
  across process runs.
- verifyChain passes on any journal produced by a normal run.
- Replay reports zero divergences for unmodified captured runs.
- Replay performs no external system calls.

## Summary

> **The question wasn't "what can Tickoni do?" — it was "can Firedancer's tile model even work here?"** M0 answers that with code, not a deck. It was a proof of concept: adapt Firedancer's tile topology — supervisor, shared-memory links, process isolation — into a runtime that processes financial events and prove it works every time it runs.

### The Starting Point

Tickoni needed a runtime before it needed a product. The Firedancer tile model was a proven pattern for ultra-TPS event processing, but no one had verified it could serve as Tickoni's foundation. The question was practical: would Firedancer's supervisor, workspace discipline, shared-memory queues, and process isolation actually hold up when mapped to financial event ingestion, normalization, deduplication, policy checking, and audit? M0 exists to find out.

### What M0 Delivered

The first delivery was a complete event pipeline wired through Firedancer infrastructure — not a toy, not a benchmark, but a working implementation of every architectural decision:

* **Tile topology.** Firedancer's supervisor manages OS-process tiles, each running in its own address space. Ingestion, normalization, deduplication, policy, audit, and replay are each a tile, linked by Firedancer shared-memory queues with backpressure and flow control. The topology mirrors Firedancer's own architecture, not a convenience abstraction. Every tile has a workspace, a bounded lifecycle, and a defined link shape — the same discipline Firedancer enforces on its own validator tiles.
* **Event pipeline.** Synthetic events enter the ingestion tile, are canonicalized by the normalization tile, deduplicated by the dedup tile, checked against policy by the policy tile, recorded by the audit tile, and replayable through the replay tile. This is Firedancer, not a simulation of Firedancer. It is the same infrastructure, the same process model, wired to Tickoni's financial event domain.
* **Replay and metrics.** The replay tile replays captured inputs with external effects disabled. Metrics and diagnostics tiles expose health signals. This is how you validate that the tile topology didn't just look good on paper — it produced consistent, verifiable results across runs, with zero divergence between the original and the replay.

### Why It Matters

M0 didn't deliver a product. It delivered a working prototype that answered the single question worth answering at that stage: does the Firedancer tile model scale to Tickoni's event pipeline without losing correctness or performance? The pipeline processes synthetic events, maintains stable canonical facts, deduplicates deterministically, enforces policy, records an auditable chain, and replays to the same output. Zero divergence, no black boxes, no claims — just a working tile system wired through Firedancer infrastructure.

The proof matters because every downstream milestone builds on this foundation. M1's consumer investment loop depends on a runtime that produces consistent results. M2's process isolation and cross-platform boundaries depend on the tile topology being structurally sound. M3's terminal and installer depend on the pipeline being correct before you put a UI in front of it. M0 is the floor, not the ceiling.
