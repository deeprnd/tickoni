# V2.10.S4 — Fully-Qualified `just` Recipes Implementation Plan

> **For Hermes:** Use the `software-development:implementation-audit` and
> `software-development:writing-plans` skills when executing this plan.

**Goal:** Make the `justfile` naming grid canonical: fully-qualified build and
test recipes perform the work, bare recipes only route to the host's qualified
recipe, and quality/security aliases expose the same naming convention without
expanding their Linux/x86-only scope.

**Architecture:** Reuse the platform taxonomy already exposed by
`contrib/platform.sh` and the top-level `os`/`arch` variables in `justfile`.
Move existing recipe bodies into explicit `{command}-{os}-{arch}[-{compiler}]`
recipes, then reduce bare recipes to one-line routers. Native Firedancer C
unit-test recipes remain distinct from Tickoni Zig unit tests; non-Linux FD
unit-test variants must not inherit Linux-only linker flags.

**Tech Stack:** `just`, Bash, `contrib/platform.sh`, Firedancer GNU Make
recipes, Zig/Tickoni build recipes, existing CI and quality/security scripts.

## Audit Summary

Audit performed against the current working tree on 2026-08-28.

### Present

- `contrib/platform.sh` exists and its live smoke test returns `linux`, `x86`,
  and `linux-x86` on this host.
- `justfile` computes `os`, `arch`, `tk_os`, `tk_arch`, and `tk_platform` from
  `contrib/platform.sh` at lines 52–65.
- S1 cleanup is present: `detect-windows-arch.sh`, `fd-build-linux.sh`,
  `fd-build-windows.ps1`, and `install-zig-bootstrap.py` are absent.
- `contrib/build/zigw.sh` and `contrib/build/fd-build-windows.sh` use the repository-root
  `contrib/platform.sh`.
- The existing bare recipes are present: `build-fd`, `build-tk`,
  `test-unit-fd`, `test-unit-tk`, and `test-integration-tk`.
- Existing aggregate recipes already invoke bare dispatchers:
  `test-unit-all` invokes `test-unit-tk` and `test-unit-fd`; the integration
  aggregate invokes `test-integration-fd` and `test-integration-tk`.
- Existing platform-specific Windows Tickoni test recipes and existing
  platform-specific Firedancer build recipes provide reusable bodies.
- S5 setup recipes are present and the parent epic records S1 and S5 as
  complete.

### Missing or incomplete

1. **No canonical qualified grid.** The current `just --list` has no
   `build-fd-linux-x86-gcc`, `build-tk-linux-x86`,
   `test-unit-fd-macos-arm`, `test-unit-tk-linux-x86`, or
   `test-integration-tk-linux-x86` recipes. A dry-run probe confirms these
   names are absent.
2. **`build-fd` is not a pure router.** Its body still contains platform
   dispatch and a direct Linux build invocation (justfile lines 183–208).
3. **`test-unit-fd` has the wrong cross-platform meaning.** macOS and Windows
   currently build FD libraries and run Tickoni Zig tests instead of native FD
   C unit-test binaries (lines 278–301). This conflicts directly with D3 and
   the story acceptance criteria.
4. **`test-unit-fd` still uses Linux-only behavior globally.** The native path
   uses `nproc` and `-Wl,-z,shstk` (lines 313–316). These must be confined to
   Linux qualified recipes; portable core-count selection is required for
   non-Linux variants.
5. **`test-unit-tk` and `test-integration-tk` are not qualified recipes.**
   Their current bodies contain Windows routing and generic build logic rather
   than being split into platform-qualified implementations.
6. **Quality/security qualified aliases are absent.** The current justfile has
   only bare Linux/x86-oriented quality and security recipes; aliases such as
   `quality-lint-check-fd-linux-x86` are missing.
7. **CI still uses bare and legacy names.** Current workflows call recipes such
   as `just test-unit-fd`, `just test-unit-tk`, `just build-fd-gcc`, and
   `just build-fd-macos-x86_64`. CI cutover is explicitly S6 scope, so S4 must
   preserve compatibility and document this handoff rather than edit workflow
   files.
8. **There are two platform implementations.** `contrib/setup/platform.sh`
   duplicates the repository-root detector and has different fallback behavior.
   S1's intended single-source invariant is therefore not fully true. This is
   a scope/dependency finding for S1/S5 follow-up; S4 should source or invoke
   the root detector and must not add another detector.
9. **Documentation still describes the old command surface.**
   `doc/execution/ci.md`, `development.md`, and `testing-tickoni.md` contain
   bare/legacy recipe examples. Broad documentation reconciliation belongs to
   S7, but the S4 plan must provide the final recipe matrix and handoff notes.

### Scope and dependency decisions

- Do not add Qt recipes or touch the Qt POC. The current story explicitly marks
  Qt-related commands and S3 out of scope.
- Do not edit `.github/workflows/**` in S4. S6 owns CI cutover; S4 exposes the
  names that S6 will call and verifies them locally with dry-runs/static checks.
- Do not force quality/security work onto macOS or Windows. Add only the
  qualified Linux/x86 aliases required by the story, mapping to the existing
  recipes.
- Do not silently preserve the current non-Linux `test-unit-fd` fallback. If a
  native platform spike hits the documented macOS x86 vendor blocker, retain
  the qualified recipe and record the blocker against the vendor source rather
  than running a different test family.

## Target Recipe Contract

The following names are the implementation target. Existing legacy names remain
as compatibility aliases until S6 and documentation have migrated all callers.

| Family | Bare dispatcher | Canonical qualified recipes |
|---|---|---|
| FD build | `build-fd` | `build-fd-linux-x86-gcc`, `build-fd-linux-x86-clang`, `build-fd-linux-arm-gcc`, `build-fd-macos-x86`, `build-fd-macos-arm`, `build-fd-windows-x86`, `build-fd-windows-arm` |
| TK build | `build-tk` | `build-tk-linux-x86`, `build-tk-linux-arm`, `build-tk-macos-x86`, `build-tk-macos-arm`, `build-tk-windows-x86`, `build-tk-windows-arm` |
| FD native unit tests | `test-unit-fd` | `test-unit-fd-linux-x86-gcc`, `test-unit-fd-macos-x86`, `test-unit-fd-macos-arm`, `test-unit-fd-windows-x86`, `test-unit-fd-windows-arm` |
| TK unit tests | `test-unit-tk` | `test-unit-tk-linux-x86`, `test-unit-tk-linux-arm`, `test-unit-tk-macos-x86`, `test-unit-tk-macos-arm`, `test-unit-tk-windows-x86`, `test-unit-tk-windows-arm` |
| TK integration tests | `test-integration-tk` | `test-integration-tk-linux-x86`, `test-integration-tk-linux-arm`, `test-integration-tk-macos-x86`, `test-integration-tk-macos-arm`, `test-integration-tk-windows-x86`, `test-integration-tk-windows-arm` |
| Quality/security | unchanged bare recipes | Linux/x86 aliases only, e.g. `quality-lint-check-fd-linux-x86` → `quality-lint-check-fd` |

The exact supported compiler suffixes must follow the current build matrix:
Linux FD builds use `gcc`, `clang`, and ARM GCC variants; macOS and Windows use
the existing unsuffixed native clang recipes. Do not introduce version-specific
recipe names.

## Completion Criteria

S4 is ready for review when:

- Every target build/test family has canonical qualified recipes.
- Bare build/test recipes are pure platform routers.
- Legacy names are thin compatibility aliases, not duplicate implementations.
- Native FD C unit tests are used by every `test-unit-fd-*` target; any
  unavailable platform is documented with its exact blocker.
- Non-Linux FD unit recipes omit `-Wl,-z,shstk` and use portable core counts.
- Quality/security aliases map to existing Linux/x86-only recipes without
  expanding their support claim.
- Aggregates still call bare dispatchers.
- The recipe-grid checker passes and all available qualified lanes have real
  execution evidence or an explicit environment blocker.
- S6 has an explicit CI cutover list, while no S6 workflow changes were made in
  this plan's implementation.
- S4 story evidence, status, and documentation handoff are updated only after
  verification.

## Known blockers and risks

- The current host is Linux/x86; macOS and Windows native spikes cannot be
  honestly claimed from this environment.
- The roadmap proposal documents a pre-existing macOS x86 vendor-source risk in
  `blst`, `zstd`, and `lz4`. Treat that as a tracked blocked flow, not a reason
  to change recipe semantics.
- `contrib/setup/platform.sh` duplicates the root detector. Resolve that
  source-of-truth discrepancy separately or explicitly mark it as a follow-up;
  do not make S4 depend on the duplicate implementation.
- The story is currently `Backlog`, while the parent epic marks S1 and S5 done.
  Story status must remain unchanged until this plan's acceptance evidence is
  actually produced.
