# Plan: v2.10-s10 — README Badge Automation — Shield.io URLs from PR Status

**Goal:** Auto-update README badge URLs after CI completes on PR merge to main.

**Architecture:** Two GitHub Actions workflows — `coverage` job in `ci.yml` (runs coverage after unit tests, parallel with security-deep) and `badge-update.yml` (runs on ci.yml completion via `workflow_run`, reads CI check-run statuses via GitHub REST API, constructs dynamic shield.io URLs, and rewrites README.md between marker comments). All triggers use `workflow_run` only — no direct `push` to main.

**Tech Stack:** GitHub Actions (workflow_run triggers), GitHub REST API, Python for badge logic, shield.io CDN (no stored SVGs).

## Target State — What Gets Built

### New CI job: coverage

A `coverage` job is added to `ci.yml` (`.github/workflows/_ci-coverage.yml` reusable workflow). It runs after unit tests (same `needs` as `security-deep`) and is **parallel** with `security-deep`. This is the right placement because:
- Coverage needs a build artifact (produced by the `build` job), which is already available after `unit`
- Coverage is heavy (kcov scan) but independent of security-deep's work
- Both can run in parallel to reduce total CI time

### Badge update mechanism

`badge-update.yml` triggers via `workflow_run` (no `push` trigger — all changes go through PR):

**Single trigger — ci.yml completion:**
1. Checkout main with `token: ${{ secrets.GITHUB_TOKEN }}`
2. Get SHA: `${{ github.event.workflow_run.head_sha }}`
3. Fetch check-run statuses via GitHub API (`GET /repos/{owner}/{repo}/commits/{sha}/check-runs`)
4. For each badge, resolve pass/fail/unknown from check-run names:
   - `build` → `build` job must exist and have status `success`
   - `unit` → `unit` job must exist and have status `success`
   - `security` → both `security-secrets` AND `security-deep` must exist and have status `success`
   - `cov-tk` → `coverage` job must exist and have status `success`; read `build/coverage/tk/coverage-summary.json` for percentage
5. Construct dynamic shield.io URLs
6. Commit and push updated README to main

Shield.io URLs are dynamic — no stored SVGs needed. The Python script constructs URLs from badge state and rewrites the `src` attribute between marker comments in `README.md`.

### Trigger chain

```
PR merge to main
  → ci.yml runs (build, unit, security-secrets, security-deep, coverage, etc.)
    → coverage runs (parallel with security-deep) ← produces coverage-summary.json
    → security-deep runs (parallel with coverage)
  → ci.yml completes (all jobs done)
    → badge-update.yml runs ← resolves all badge statuses and updates README
```

All badges update in a single `badge-update.yml` run after ci.yml finishes. No separate coverage-badge workflow. No separate cov-tk trigger.

No `push` triggers exist anywhere in this design. Direct pushes to main are not allowed per repo policy. All workflow execution flows through the PR merge path.

### Phase 1: Add `coverage` CI job to `ci.yml`

**File:** `.github/workflows/_ci-coverage.yml` (NEW) + `ci.yml` (MODIFY)

**Trigger (internal):** Part of ci.yml DAG — runs after `build` and `unit`, parallel with `security-deep`.

**Purpose:** Run coverage for Tickoni harness as part of CI. Produces `build/coverage/tk/coverage-summary.json`.

**Reusable workflow `_ci-coverage.yml`:**

```yaml
name: Coverage Stage

on:
  workflow_call:

jobs:
  coverage:
    name: Tests / Coverage
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    steps:
      - name: Checkout
        uses: actions/checkout@v7
        with:
          fetch-depth: 0

      - name: Install just
        uses: taiki-e/install-action@just

      - name: Setup build toolchain for coverage
        run: just setup-build-linux-x86-gcc

      - name: Download build artifact (build job output)
        uses: actions/download-artifact@v5
        with:
          name: tickoni-build
          path: build/

      - name: Run coverage test
        run: just test-cov-tk

      - name: Generate coverage summary JSON
        run: |
          python3 contrib/tool/readme/coverage_report.py coverage-tk \
            build/coverage/tk \
            build/coverage/tk/coverage-summary.json \
            --config contrib/test/coverage-tk.json
```

**ci.yml changes:**
1. Add `coverage` job with `needs: [plan, build, unit]` and `if` matching `security-deep` pattern
2. Add `coverage` to `ci-required` job's `needs` list
3. Add `coverage` to `dev-setup` job's `needs` list (since dev-setup depends on everything)
4. Update the loop in `ci-required` to include `coverage` in the job list

**Note:** The coverage job downloads the build artifact from the `build` job so `just build-tk` doesn't need to recompile. If no artifact mechanism exists, it builds directly (simpler but slower).

**Verification:** Merge a PR to main and verify `build/coverage/tk/coverage-summary.json` appears in the repo after the CI completes.

### Phase 2: `badge-update.yml` — Badge update workflow

**File:** `.github/workflows/badge-update.yml` (NEW)

**Trigger:**
- `workflow_run` with `workflows: ["CI"]`, `types: [completed]`, `branch: [main]` — triggers after ci.yml completes (all badge types)

**Purpose:** Read CI statuses and update README badge URLs.

**Steps:**

1. Checkout main with `token: ${{ secrets.GITHUB_TOKEN }}` (needed for API reads and push)
2. Get SHA: `${{ github.event.workflow_run.head_sha }}` (resolved from workflow_run payload)
3. Run a Python script to:
   a. Call GitHub API to get check-run statuses for that commit
   b. Resolve each badge status:
      - `build` → `build` job must exist and have status `success`
      - `unit` → `unit` job must exist and have status `success`
      - `security` → both `security-secrets` AND `security-deep` must exist and have status `success`
      - `cov-tk` → `coverage` job must exist and have status `success`; read `build/coverage/tk/coverage-summary.json` for percentage
   c. Construct dynamic shield.io URLs using shield.io's public badge API
   d. Rewrite README.md between `<!-- badge:X:start -->` / `<!-- badge:X:end -->` markers
   e. Commit and push the updated README

**Implementation approach:** A single Python script at `contrib/tool/readme/badge_updater.py` that:
- Accepts commit SHA as argument (from `github.event.workflow_run.head_sha`)
- Calls `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` (list check runs for a commit)
- Parses check run names to badge statuses:
  - `build` → check name contains "Build" (ci.yml job name is "Build")
  - `unit` → check name contains "Unit" (ci.yml job name is "Tests / Unit")
  - `security` → check names contain "Security / Secrets" AND "Security / Deep" (AND logic)
  - `cov-tk` → check name contains "Coverage" (ci.yml job name is "Tests / Coverage")
- Reads `build/coverage/tk/coverage-summary.json` for cov-tk percentage
- Calls `replace_badge_block()` from existing `refresh-badges.py` to update README.md
- Commits with `git add README.md && git commit -m "ci: update badges for {sha}" && git push origin main`

**Security:** The GitHub API token has `contents: read` scope by default, which is sufficient for reading check runs. Pushing to main requires `contents: write` scope.

**No commit loop:** badge-update.yml uses `workflow_run` triggers (not `push` triggers), so the badge-update commit itself never re-triggers the workflow. This eliminates the infinite commit loop risk entirely.

**Verification:** Merge a PR that changes CI status (e.g. a doc-only PR that skips build) and verify the build badge shows `unknown/lightgrey`.

## Risks

- **GitHub API rate limits:** Unauthenticated reads are 60 req/hr; authenticated are 5000/hr. The workflow runs once per PR merge to main, so rate limits are not a concern. Use `GITHUB_TOKEN` with `contents: read` scope.
- **No commit loop:** badge-update.yml uses `workflow_run` triggers (not `push` triggers), so the badge-update commit itself never re-triggers the workflow. This eliminates the infinite commit loop risk entirely — no need to exclude bot commits.
- **No race condition:** `workflow_run` triggers fire only after the upstream workflow completes, so ci.yml finishes all jobs (build, unit, security-deep, coverage, etc.) before badge-update runs. No race condition possible.
- **Coverage is heavy:** kcov coverage scan takes significant time. Running it in the main CI pipeline adds ~5–10 minutes. However, it runs parallel with security-deep, so it doesn't extend total CI time. This is preferable to a separate workflow because all badge statuses resolve from one trigger.
- **Coverage needs build artifacts:** The coverage job needs the compiled binaries to run `just test-cov-tk`. Either the coverage job downloads the build artifact from the `build` job, or it runs `just build-tk` itself. The former is faster; the latter is simpler.
- **workflow_run branch filter:** The `workflow_run` trigger filters on `branch: [main]` to ensure badge-update.yml only runs after PR merges to main, not on PR branches or forks. GitHub's `workflow_run` `branch` filter restricts to the branch that triggered the original workflow.
