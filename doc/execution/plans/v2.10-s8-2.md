# Refactor: Separate `contrib/setup/` (install) from `contrib/build/` (compile)

**Status:** Plan
**Created:** 2025-08-29
**Scope:** `contrib/setup/` = INSTALL only · `contrib/build/` = COMPILE only
**Goal:** Clear ownership — setup installs 3rd-party tools and system packages, build compiles and links Firedancer and Tickoni source.

---

## Problem Statement

`contrib/setup/` and `contrib/build/` have blurry boundaries. The current plan merges build into setup, which inverts the responsibility:

- `contrib/setup/` should be **INSTALL ONLY** — installs system packages, 3rd-party dependencies (OpenSSL, RocksDB, Snappy), dev toolchains (Zig, compilers), and dev tooling.
- `contrib/build/` should be **BUILD ONLY** — compiles, links, and produces Firedancer libs and Tickoni Zig binaries. No 3rd-party building.
- Third-party tools (OpenSSL, RocksDB, Snappy, Zig) are installed once by setup; build never builds them.

The key principle: **third-party builds don't belong in the build folder.** They can always be swapped with a package-manager install. The build folder is for Firedancer and Tickoni source only.

### No files move between folders

The key decision: **no files migrate between setup and build**. Both folders already own the right scripts. The refactor is:

1. Delete unused files (`build.sh`, `deps-bundle.sh`, `ci-run-build-tk.sh`)
2. Clean up justfile references to deleted files
3. Ensure justfile recipes route through the correct folder
4. Update CI path filters

## What Goes Away

- `contrib/build/build.sh` — Firedancer matrix orchestrator. Never called by Tickoni justfile or CI.
- `contrib/build/deps-bundle.sh` — Firedancer redistributable bundle. Not used by Tickoni.
- `contrib/build/ci-run-build-tk.sh` — Thin wrapper. Direct `just build-tk` is simpler.

- `fd-tk-libs.sh` — FD source dirs, lib names, fd_build_fd(), fd_compute_mks(), fd_nproc()

- `fd-build-windows.sh` — Windows build wrapper (clang discovery, space-in-path workaround, libuuid_stub)
- `fd-write-zig-link-manifests.sh` — Windows Zig link manifest writer
- `zigw.sh` — Zig wrapper with Windows ARM target auto-discovery
- `make-j` — CPU-isolated make wrapper
- `run-test-series.sh` — Test runner utility

## Justfile Recipe Routing

### Current state (already correct routing)

Setup recipes already use `contrib/setup/` scripts:
```
setup-linux-x86-gcc → contrib/setup/linux-x86-essential.sh
setup-macos-arm     → contrib/setup/macos-arm-essential.sh
setup-windows-x86   → contrib/setup/windows-x86.ps1
```

Build recipes already use `contrib/build/` scripts:
```
build-fd-linux-x86-gcc → contrib/build/fd-build-lib.sh
build-fd-windows-x86   → contrib/build/fd-build-windows.sh
build-tk-linux-x86     → contrib/build/zigw.sh
```

FD deps setup currently references `contrib/build/deps.sh`:
```
setup-fd-deps-linux-x86-gcc → contrib/build/deps.sh check
```

### Needed change: deps.sh reference path

`deps.sh` stays in `contrib/setup/helpers/` (it's an install script), but the justfile recipes call it via `contrib/build/deps.sh`. The justfile references need to be updated to `contrib/setup/helpers/deps.sh`.

Alternatively, keep `contrib/build/deps.sh` as a thin wrapper that delegates to `contrib/setup/helpers/deps.sh`, but that adds an unnecessary indirection. Just update the references.

## Risks and Mitigations

1. **Firedancer's standalone build needs deps.sh.** If Firedancer's own build process calls `contrib/build/deps.sh` externally, keep a thin wrapper at that path that delegates to `contrib/setup/helpers/deps.sh`. Otherwise, update the reference.

2. **CI runs `contrib/build/deps.sh` directly.** CI workflows that hardcode the path must be updated. This is a simple find-and-replace across workflow YAML files.

3. **Justfile `setup-fd-deps-*` recipes.** These are the only justfile references to deps.sh. Five recipe updates, all identical pattern change.
