# Plan: v2.10-s8-1-3 — Genericize download/verify strategies

## Problem

Three problems in the install strategy layer:

1. `llama_cpp_download.py` hard-codes the version (`'b10760'`) as a fallback
   instead of reading it from `contrib/setup/tool-versions.json`. It reads
   artifact metadata from `build/build-config.json` which is a different file
   in a different directory.

2. `llama_cpp_download.py` implements SHA256 download-and-verify inline
   instead of reusing the shared helpers already present in
   `contrib/setup/install/strategies/download.py`.

3. `zig.py` implements minisign download-and-verify inline — the generic
   "download with signature verification" logic is not abstracted.

## Design Goals

- One version-of-record for tool versions: `tool-versions.json` (read via
  `config.resolve_version`).
- `download.py` becomes the single home for: SHA256 verification, archive
  extraction, generic download flow, and minisign verification.
- `llama_cpp_download.py` and `zig.py` become thin: they resolve the URL
  and pass it to the shared pipeline.

## Changes

### 1. Add `llama-cpp` to `tool-versions.json` ✅ DONE

Added `"llama-cpp": "b10760"` under `versions:`.

### 2. Add `zig` minisign to `tool-versions.json` ✅ DONE

Added `zig-minisign` entry:
```json
"zig-minisign": {
  "key": "RWSGOq2NVecA2UPNdBUZykf1CCb147pkmdtYxgb3Ti+JO/wCYvhbAb/U"
}
```

Added `version_ref_sig: "zig-minisign"` to the zig tool entry.

### 3. Generalize `download.py` ✅ DONE

Added these functions to `download.py`:

**a. `_verify_minisign(archive_path: Path, sig_path: Path, pubkey: str) -> None`** ✅

- Runs `minisign -V -P <pubkey> -x <sig> -m <archive>`.
- Dev-build warning for `-dev.` in the name.
- Graceful degradation if no minisign binary, empty/missing sig.

**b. `_download_and_verify(...)` Template Method ✅**

Downloads archive with optional SHA256 + minisign verification chain.

**c. `resolve_version_from_config(...)` ✅**

Thin re-export of `config.resolve_version`.

### 4. Refactor `llama_cpp_download.py` ✅ DONE

- Version resolved from `tool-versions.json` via `resolve_version(config, 'llama-cpp')` — no more hard-coded `'b10760'`.
- Download/verify uses shared `_download_and_verify()` pipeline.
- `_download_file`, `_verify_sha256`, `_extract_archive`, `_expand_home`, `_is_windows` imported from `.download`.

### 5. Refactor `zig.py` ✅ DONE

- Removed inline `_ZigMinisigVerifier` class — now uses shared `_download_and_verify()` + `_verify_minisign()`.
- Minisign public key resolved from `tool-versions.json` via `version_ref_sig` parameter.
- `_download_file` and `_download_and_verify` imported from `.download`.

### 6. Responsibility Split ✅ DONE

| File | Responsibility |
|------|---------------|
| `download.py` | `_download_file`, `_verify_sha256`, `_verify_minisign`, `_extract_archive`, `_download_and_verify`, `_expand_home`, `_is_windows`, `resolve_version_from_config` |
| `llama_cpp_download.py` | URL resolution from `build-config.json` (platform-specific artifact map, filename, server binary name, extract_dir). No download/verify logic. |
| `zig.py` | URL resolution from `ziglang.org/index.json` (dev build vs release, target mapping), PATH handling (Windows user-path, GITHUB_PATH), extraction (unzip fallback for Windows). No download/verify logic. |
| `config.py` | `load_config()`, `resolve_version()` — unchanged. |

## Verification

After implementation:
- `just setup-env` installs zig and llama.cpp successfully on Linux-x86.
- `just setup-env` installs zig and llama.cpp successfully on macOS-arm.
- Zig minisign verification passes on a release build.
- Zig dev-build minisign failure produces a warning (not a crash).
- llama.cpp SHA256 verification passes.
- Both tools are idempotent (running twice skips install).
