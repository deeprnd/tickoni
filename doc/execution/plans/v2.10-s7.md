# Plan: v2.10-s13 — Reduce Windows CI Time and Add Build Caching

**Goal:** Cut Windows CI stage time from ~25 minutes to ~12 minutes by eliminating redundant MSVC installs, and add toolchain caching across all platforms to save cumulative CI minutes.

---

## Problem Statement

| Platform | Build time | Test time | Total | Root cause of overhead |
|----------|-----------|-----------|-------|------------------------|
| Linux x86  | ~12 min   | ~12 min   | ~24 min | gcc-12 pre-installed on GitHub runners |
| Windows x86 | ~12 min   | ~13 min   | ~25 min | MSVC Build Tools (~5 GB download) on EVERY runner |

Windows CI takes ~25 minutes because:
1. Every `setup-fd-windows-x86` call runs `orchestrator.py build,mvsc,zig,ssl`
2. `mvsc` installs Visual Studio Build Tools (~5 GB, ~5-8 min) on every ephemeral runner
3. OpenSSL installation on Windows is slower than apt on Linux
4. No `actions/cache` is used anywhere — toolchains are installed from scratch each time

Linux benefits because gcc-12 is pre-installed on `ubuntu-24.04` runners. GitHub does not pre-install MSVC.

---

## Analysis

### Current Windows CI flow (per _ci-unit.yml, _ci-integration.yml, _ci-system.yml, _ci-demo.yml):

```
1. Checkout (actions/checkout@v7)
2. Install just (taiki-e/install-action@just)
3. Setup toolchain: just setup-build-windows-x86
   → orchestrator.py build,mvsc,zig,ssl --platform windows-x86
   → Downloads and installs MSVC Build Tools (~5 GB, ~8 min)
4. Setup Firedancer deps: just setup-fd-deps-windows-x86
   → orchestrator.py fd --platform windows-x86
   → Downloads/compiles snappy, rockdb (~3 min)
5. Build FD libs: just build-fd-windows-x86
   → orchestrator.py --platform windows-x86 build-fd fd-tickoni-fd libs clang --arch x86_64
   → Compiles Firedancer (~4 min)
6. Run tests: just test-unit-tk-windows-x86
   → zig build test + zig build run-tests (~3 min)
```

### Where the 25 minutes is spent:
- MSVC install: ~8 min (on first run, every runner)
- OpenSSL install: ~2 min
- Firedancer deps (snappy, rockdb): ~3 min
- Firedancer build: ~4 min
- Tickoni zig build + tests: ~3 min
- Setup overhead (just install, etc.): ~1 min
- **Total: ~21 min, plus CI runner queue time ≈ 25 min total**

### Key finding: `orchestrator.py` already has idempotency checks

The orchestrator checks if a tool is already installed via `build_check(tool)`. If MSVC is cached and the check succeeds, `mvsc` installs in ~0 seconds. The same for OpenSSL. The problem is GitHub runners are ephemeral — cache must be explicit via `actions/cache`.

## Plan

### Phase 1: Add `actions/cache` for MSVC, Zig, and OpenSSL (Windows)

**Files:** All Windows CI workflow files:
- `_ci-build.yml`
- `_ci-unit.yml`
- `_ci-integration.yml`
- `_ci-system.yml`
- `_ci-demo.yml`

**Change:** Add a cache step before setup steps in each Windows matrix entry.

```yaml
# Before any setup step, add:
- name: Cache MSVC Build Tools
  uses: actions/cache@v4
  with:
    path: |
      C:\Program Files\Microsoft Visual Studio\2022\Enterprise\VC
      C:\Program Files (x86)\Microsoft Visual Studio\2022\Enterprise\VC
    key: msvc-${{ runner.os }}-x86-2022
    restore-keys: |
      msvc-${{ runner.os }}-x86-

- name: Cache Zig SDK
  uses: actions/cache@v4
  with:
    path: C:\Users\runneradmin\scoop\apps\zig\*
    key: zig-${{ runner.os }}-x86
    restore-keys: |
      zig-${{ runner.os }}-

- name: Cache OpenSSL
  uses: actions/cache@v4
  with:
    path: C:\Users\runneradmin\scoop\apps\openssl\*
    key: openssl-${{ runner.os }}-x86
    restore-keys: |
      openssl-${{ runner.os }}-
```

**Expected impact:** After the first run populates the cache, subsequent runs skip MSVC install entirely (~8 min saved). OpenSSL and Zig caches provide ~2 min additional savings.

**Total Windows time after Phase 1:** ~12-14 minutes (on cache hit).

### Phase 2: Add `actions/cache` for Linux toolchains (gcc, clang, zig)

**Files:** All Linux CI workflow files.

```yaml
- name: Cache Zig SDK
  uses: actions/cache@v4
  with:
    path: ~/.local/zig
    key: zig-${{ matrix.runner }}-${{ hashFiles('contrib/setup/install-zig.py') }}
    restore-keys: zig-${{ matrix.runner }}-

- name: Cache Firedancer deps (snappy, rockdb, openssl)
  uses: actions/cache@v4
  with:
    path: build/fd-deps
    key: fd-deps-${{ matrix.platform }}-${{ matrix.compiler }}-${{ hashFiles('contrib/setup/tool-versions.json') }}
    restore-keys: fd-deps-${{ matrix.platform }}-
```

**Expected impact:** ~3-5 min per Linux job. Cumulative savings across 8 Linux matrix entries = ~25-40 min per PR.

### Phase 3: Check if gcc is available on Windows runners (MSVC replacement)

**Investigation:** GitHub's `windows-2025` runners may have gcc pre-installed via MSYS2 or Chocolatey. If so, we can drop the `mvsc` category entirely:

```yaml
- name: Check for gcc
  shell: bash
  run: gcc --version 2>&1 || echo "NO_GCC"
```

**If gcc is available:**
- Remove `mvsc` from all Windows setup calls
- Remove `setup-fd-windows-x86`'s `mvsc` dependency from `common.just`
- Windows setup becomes: `orchestrator.py build,zig,ssl --platform windows-x86`
- No MSVC download needed → saves the full 8 min

**If gcc is NOT available:**
- Phase 1 (cache) is the fix. MSVC is needed.

### Phase 4: Fix skipped FD unit tests on Windows (exit code 1 → 0)

**Files:** `just/build/windows.just`, all Windows matrix entries in CI workflows.

**Problem:** The justfile recipes `test-unit-fd-windows-x86` and `test-unit-fd-windows-arm` print "SKIPPED" and `exit 1`. The CI workflows call these recipes. Even though they're "skipped," the exit code 1 marks the job as failed, which is confusing and wastes CI time.

**Fix:**
```makefile
# Change from:
test-unit-fd-windows-x86:
    @echo "SKIPPED: ..." >&2; exit 1

# To:
test-unit-fd-windows-x86:
    @echo "SKIPPED: test-unit-fd-windows-x86 — Strawberry Perl access violation" >&2
```

And in CI workflows, add `continue-on-error: true` for the FD test step on Windows, since we know these tests are disabled.

**Expected impact:** Cleaner CI output, no false failures.

### Phase 5: Consolidate redundant setup calls in CI workflows

**Files:** `_ci-unit.yml`, `_ci-integration.yml`, `_ci-system.yml`, `_ci-demo.yml`.

**Problem:** Each workflow calls setup steps independently. Unit test workflow downloads MSVC, integration test workflow downloads MSVC, etc. With caching this is just wasted cache bandwidth, but without it it's 8 minutes wasted per workflow.

**Fix:** The build stage already uploads build artifacts. Test stages download them and should NOT rebuild. Currently they DO rebuild FD libs locally (`just build-fd-windows-x86` in each workflow). This is the biggest time waste on Windows.

**Proposed change:** Test workflows should download the build artifact from the Build stage instead of rebuilding:

```yaml
# In _ci-unit.yml, replace:
#   - name: Build Firedancer libs
#     run: just ${{ matrix.build-recipe }}
# With:
- name: Download build artifact
  uses: actions/download-artifact@v8
  with:
    name: build-windows-x86_64
    path: .
```

Then the test step only needs `zig build test` (no FD rebuild). This is already the pattern in `_ci-coverage.yml` (downloads artifact).

**Expected impact:** ~4 min saved per test workflow on Windows. ~4 workflows × 4 min = 16 min saved per PR on Windows alone.

## Execution Order

1. **Phase 3** (check gcc availability) — 5 min investigation, determines if Phase 1 is needed
2. **Phase 4** (fix skipped exit code) — 1 line change, zero risk, immediate benefit
3. **Phase 5** (use build artifacts in test workflows) — removes redundant FD rebuilds, biggest single-time saver
4. **Phase 1** (MSVC/Zig/OpenSSL cache for Windows) — if Phase 3 finds no gcc, this is critical
5. **Phase 2** (Linux caching) — cumulative savings, lower urgency

---

## Risk Assessment

| Phase | Risk | Mitigation |
|-------|------|-----------|
| Phase 1 | Stale cache after MSVC update | Cache key includes runner.os; MSVC updates are rare. Add `cache-miss` check in setup step to detect and invalidate if needed. |
| Phase 3 | gcc not available | Falls back to Phase 1. Zero risk. |
| Phase 4 | Exit code 0 masks real failure | Only applies to FD tests which are already known to be broken. Tickoni FD tests are separate. |
| Phase 5 | Test runs on build artifact compiled with different flags | Build and test stages already use the same runner (ubuntu-24.04 or windows-2025). Same ISA. No mismatch risk. |
| Phase 2 | Cache key collisions across compilers | Key includes compiler name (gcc-12 vs clang-18). Already accounted for. |

## Notes

- The existing `orchestrator.py` idempotency check (`build_check(tool)`) already does the right thing — it detects installed tools and skips. It just needs the cache to persist across jobs/stages.
- The `ZIG_LOCAL_CACHE_DIR` and `ZIG_GLOBAL_CACHE_DIR` variables in `common.just` already redirect Zig caches to `build/.zig-cache` and `build/.zig-global-cache`. These are covered by the build artifact upload/download, so no additional Zig cache handling is needed.
- The `build/` directory is already part of the artifact upload path in `_ci-build.yml` (line 163-167: `build/`, `target/`, `zig-out/`). The test workflows that download this artifact already get the Zig caches.
