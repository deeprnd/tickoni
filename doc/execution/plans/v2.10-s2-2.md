# Plan: Make Dev Setup Validation Cross-Platform

**Story:** v2.10-s2-2
**Status:** PLANNED
**Created:** 2026-09-04

## Background

The `tests-dev-setup.yml` workflow (now standalone, running weekly on Mondays + on-demand) runs `just build-all test-unit-tk test-integration-all test-system-all` across eight platforms:

| Platform | Runner | Status |
|---|---|---|
| Linux x86_64 | ubuntu-24.04 | Fully implemented |
| Linux ARM64 | ubuntu-24.04-arm | Implemented via Linux x86 alias |
| macOS 15 x86_64 | macos-15-intel | **Partially broken** |
| macOS 15 ARM | macos-15 | **Partially broken** |
| macOS 26 x86_64 | macos-26-intel | **Partially broken** |
| macOS 26 ARM | macos-26 | **Partially broken** |
| Windows x86_64 | windows-2025-vs2026 | Implemented |
| Windows ARM64 | windows-11-vs2026-arm | Implemented |

Linux is the only fully-implemented platform. macOS has partial infrastructure but broken test delegation. Windows is implemented but lacks some test parity.

## What works on Linux (reference implementation)

Linux x86_64 has the canonical implementation that all other platforms should mirror:

1. **Setup:** `just setup-linux-x86-gcc` (orchestrator.py: core, essential, toolchain, build, zig, ssl, ops, quality, secrets)
2. **Hugepages/memlock:** `sudo prlimit`, `fd_shmem_cfg init`, `fd_shmem_cfg alloc-auto`
3. **Build:** `just build-all` (runs `build-fd` + `build-tk`)
4. **Unit tests:** `just test-unit-tk` (runs `test-unit-tk-linux-x86` — Zig build with `-Dtest=true`, `run-tests`)
5. **Integration tests:** `just test-integration-all` (runs `test-integration-tk-linux-x86` — Zig build with `-Dtest=true`, `integration-test`)
6. **System tests:** `just test-system-all` (runs `test-system-tk-linux-x86` — `bash contrib/test/run_live_investment_demo.sh`)

## Gap analysis by category

### 1. macOS — Unit tests: delegation to Linux x86 (BROKEN)

**Current code in justfile:**
```
test-unit-tk-macos-x86: test-unit-tk-linux-x86
test-unit-tk-macos-arm: test-unit-tk-linux-x86
```

**Problem:** These are bare delegation aliases. They run the Linux x86 recipe which:
- Uses `fd_tickoni_lib = build/fd-tickoni-fd/lib` (Linux build dir)
- macOS builds output to `build/fd-macos-x86/lib` (different BUILDDIR)
- No macOS-specific build step before the test

**Fix:** Implement per-platform test recipes that use the correct lib directory.

```
test-unit-tk-macos-x86:
    ZIG_GLOBAL_CACHE_DIR=.zig-global-cache TK_LOG_LEVEL=0 zig build \
        -Dtest=true -Dfd-lib-dir={{ fd_tickoni_lib }} \
        test --summary all
    ZIG_GLOBAL_CACHE_DIR=.zig-global-cache TK_LOG_LEVEL=0 zig build \
        -Dtest=true -Dfd-lib-dir={{ fd_tickoni_lib }} \
        run-tests
```

The lib directory question: the orchestrator builds to platform-specific BUILDDIRs (`fd-macos-x86`, `fd-tickoni-fd` for Linux). The test recipe must use the matching lib directory. Options:
- **Option A:** Have the orchestrator symlink/copy to canonical `fd-tickoni-fd` dir (preferred — single source of truth)
- **Option B:** Define platform-specific `fd_tickoni_lib` aliases in justfile

Option A is cleaner. If the orchestrator already produces `build/fd-tickoni-fd/lib` (the canonical path), then the delegation aliases work by accident. If it produces `build/fd-macos-x86/lib`, the test commands fail with "library not found." Verify which it does.

**If Option A is correct (orchestrator → canonical lib dir):** The fix is simply removing the delegation aliases and making macOS test recipes identical to Linux (same commands, different runner). The Zig commands are platform-agnostic.

**If Option B is needed:** Add justfile aliases:
```
fd_tickoni_lib_macos := "build/fd-macos-x86/lib"
```
And reference `${{ fd_tickoni_lib_macos }}` in macOS test recipes.

### 2. macOS — Integration tests: delegation to Linux x86 (BROKEN)

**Current code in justfile:**
```
test-integration-tk-macos-x86: test-integration-tk-linux-x86
test-integration-tk-macos-arm: test-integration-tk-linux-x86
```

**Same problem as unit tests.** Fix the same way as above.

### 3. macOS — System tests: shared script, not macOS-specific

**Current code:**
```
test-system-tk-linux-x86: test-system-tk
test-system-tk-linux-arm: test-system-tk
test-system-tk-macos-x86: test-system-tk
test-system-tk-macos-arm: test-system-tk
```

**Current `test-system-tk`:**
```
test-system-tk:
    bash contrib/test/run_live_investment_demo.sh
```

This script is Linux-centric (uses `bash`, `python3` paths, `nproc`, etc.). It may work on macOS with Git Bash / WSL but will likely fail on native macOS.

**Fix:** Create `contrib/test/run_live_investment_demo_macos.sh` (or make the existing script detect macOS and adjust). The script needs to:
- Use `sysctl -n hw.ncpu` instead of `nproc` on macOS
- Handle Homebrew Python paths
- Use `infra-ensure-llamacpp` (already available for macOS in justfile)

Actually, looking more carefully: the CI system-test workflow (`_ci-system.yml`) already has `llamacpp: infra-ensure-llamacpp` for macOS runners. The question is whether `run_live_investment_demo.sh` itself is portable enough. Check if the script has any Linux-specific assumptions (e.g., `/proc/` paths, `pkill`, `ulimit -l`, etc.).

### 4. Linux ARM64 — Unit/integration tests: delegation to Linux x86

**Current code:**
```
test-unit-tk-linux-arm: test-unit-tk-linux-x86
test-integration-tk-linux-arm: test-integration-tk-linux-x86
```

This is a delegation alias. On ARM runners, the Linux x86 recipe will:
- Use `fd_tickoni_lib = build/fd-tickoni-fd/lib` (correct if orchestrator produces canonical dir)
- Run Zig build commands (Zig cross-compiles or natively compiles for the runner's arch)

**Risk:** If the orchestrator produces `build/fd-arm/lib` for ARM (different BUILDDIR from the `fd-tickoni-fd` used by x86), the lib path won't match. Verify orchestrator behavior.

**Fix:** If the lib dir is canonical, replace delegation with proper ARM recipes (same commands as x86). If not, add ARM-specific `fd_tickoni_lib` path.

### 5. Security checks — Linux-only by nature

The following security checks are **Linux-only by design** and should NOT be ported to macOS/Windows:

| Check | Why Linux-only |
|---|---|
| `security-seccomp-check-fd` | Seccomp is a Linux syscall filter; no equivalent on macOS/Windows |
| `security-proof-check-fd` (CBMC) | CBMC tools not installed for macOS/Windows (justfile has `setup-security-linux-x86` and `setup-security-macos-x86` but CBMC deb packages are Linux-only) |
| `security-codeql-check-fd` | Stub (`@true`), but when implemented, CodeQL requires specific runner images |
| Hugepage setup (`fd_shmem_cfg`) | Linux `/proc/sys/vm/` interface; no macOS equivalent |
| `sudo prlimit --memlock=unlimited` | Linux-specific resource limits |

**Action:** The `tests-dev-setup.yml` workflow should NOT run these on macOS/Windows. Currently it doesn't — the dev-setup workflow only runs `build-all test-unit-tk test-integration-all test-system-all`. The security checks only run in `_ci-security-deep.yml`. This is correct behavior.

However, the **sanitizer check** (`security-sanitize-check-fd` / `sanitize-check-tk`) should work cross-platform:
- `sanitize-check-fd` requires `clang` — available on macOS via Homebrew
- `sanitize-check-tk` uses `zig build -Dtest=1 -Doptimize=ReleaseSafe` — Zig's ReleaseSafe works on all platforms

**Fix:** Add a `setup-sanitize` recipe for macOS:
```
setup-sanitize-macos-x86:
    python3 contrib/setup/orchestrator.py core,build,toolchain,coverage
```

And add sanitizer runs to macOS/Windows test suites (optional, low priority).

### 6. Windows — Already implemented, verify completeness

Windows has explicit recipes for unit and integration tests:
```
test-unit-tk-windows-x86:  # builds FD libs, then Zig test + run-tests
test-integration-tk-windows-x86:  # builds FD libs, then Zig integration-test
test-system-tk-windows-x86:  # uses run_live_investment_demo_win.sh
```

These are more complete than macOS. Key Windows-specific files:
- `contrib/test/run_live_investment_demo_win.sh` — Windows system test runner
- `infra-ensure-llamacpp-win` / `infra-ensure-llamacpp-win-arm` — Windows llama.cpp setup

**Verify:** Check that `run_live_investment_demo_win.sh` handles both x86 and ARM Windows correctly.

### 7. macOS — Missing Windows-style system test script

Windows has `contrib/test/run_live_investment_demo_win.sh`. macOS does not have a corresponding macOS-specific system test runner. If `run_live_investment_demo.sh` has platform issues, create `run_live_investment_demo_macos.sh`.

## Implementation plan

### Phase 1: Verify orchestrator build directory behavior (P0)

Before implementing any fixes, verify what `contrib/build/orchestrator.py` produces for each platform's `fd-tickoni-fd` BUILDDIR:

1. Does `build-fd-macos-x86` produce `build/fd-tickoni-fd/lib` or `build/fd-macos-x86/lib`?
2. Does `build-fd-linux-arm-gcc` produce `build/fd-tickoni-fd/lib` or `build/fd-arm/lib`?
3. Does `build-fd-windows-x86` produce `build/fd-tickoni-fd/lib` or `build/fd-windows-x86/lib`?

This determines whether we need Option A (orchestrator canonicalizes) or Option B (per-platform lib dirs).

### Phase 2: Fix macOS test delegation (P0)

Once the lib dir behavior is known:

**If orchestrator produces canonical dir (`build/fd-tickoni-fd/lib`):**
- Replace `test-unit-tk-macos-x86: test-unit-tk-linux-x86` with a proper recipe that runs the same Zig commands
- Replace `test-integration-tk-macos-x86: test-integration-tk-linux-x86` similarly
- Same for ARM variants
- Same for Linux ARM variants

**If orchestrator produces platform-specific dirs:**
- Add per-platform `fd_tickoni_lib` aliases in justfile
- Update test recipes to use the correct lib dir
- Or change the orchestrator to produce canonical output (preferred)

### Phase 3: Fix macOS system tests (P1)

1. Audit `contrib/test/run_live_investment_demo.sh` for Linux-specific assumptions
2. If it has Linux-only paths/commands, create a macOS variant
3. Ensure `infra-ensure-llamacpp` works on macOS (already in justfile as `infra-ensure-llamacpp` recipe)

### Phase 4: Fix Linux ARM delegation (P1)

Same approach as Phase 2 — replace delegation aliases with proper ARM recipes if the orchestrator doesn't produce canonical lib dirs.

### Phase 5: Add macOS/Windows sanitizer support (P2, optional)

1. Add `setup-sanitize-macos-x86` and `setup-sanitize-macos-arm` recipes
2. Optionally run `security-sanitize-check-all` in the weekly dev-setup on macOS/Windows
3. Only if clang is available (macOS has clang via Xcode CLI tools)

## Risk assessment

| Risk | Impact | Mitigation |
|---|---|---|
| Orchestrator produces platform-specific lib dirs | All macOS/ARM test recipes broken | Canonicalize in orchestrator (Option A) |
| macOS llama.cpp build fails | System tests fail on macOS | Verify `infra-ensure-llamacpp` on GitHub macOS runners |
| CBMC proof checks never run on macOS/Windows | Low (Linux-only by design) | Document as expected; do not attempt |
| Hugepage setup fails on macOS | Dev setup fails on macOS | Skip hugepage setup on macOS; it's for FD lib workspace allocation |
| Zig ReleaseSafe sanitizer fails on Windows | Sanitizer checks fail | Gate behind `command -v clang` check |

## Dependencies

- Phase 1 must complete before any other phase
- Phase 2 blocks CI parity (most impactful change)
- Phase 3-5 are incremental improvements
