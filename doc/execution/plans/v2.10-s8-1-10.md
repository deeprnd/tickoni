# Plan: Decouple justfile from setup dependency knowledge

## Problem

The justfile setup recipes redundantly specify the full dependency prefix (`core,essential,toolchain,build`) for every recipe. This leaks dependency knowledge into two places:

- **tool-versions.json** owns the dependency graph (authoritative)
- **justfile** also owns it (via explicit category lists)

The resolver already resolves transitive dependencies. The justfile is supposed to be a dumb dispatcher, not a second copy of the dependency graph.

Examples of leakage:
- `setup-build-*` lists `toolchain` even though build does not depend on it
- `setup-gitleaks-*` redundantly lists `core,essential` when secrets only depends on core
- `setup-quality-*` redundantly lists `core,essential,toolchain`
- Every recipe that lists `core` or `essential` is leaking implementation knowledge

## Architecture Decision

**Single source of truth: tool-versions.json**

The dependency graph in `dependencies` resolves transitively. The justfile declares what it wants; the resolver figures out the rest.

```
justfile              resolver              tool-versions.json
─────────             ─────────             ────────────────
declares intent       resolves deps         owns category graph
  build                ────────────→        build → [core, essential]
  fd                   ────────────→         fd → [core]
  quality              ────────────→        quality → [core, build, go, zig, nodejs]

resolver output is deterministic;
justfile never lists core or essential explicitly.
```

## Implementation

### 1. Add `dev` preset category (tool-versions.json) ✅ DONE

```json
"dependencies": {
    "dev": ["build", "toolchain", "zig", "ssl", "ops", "quality", "secrets", "coverage", "security", "fd"]
}
```

This collapses the full developer stack into one category. Recipes can reference `dev` instead of listing 12 items.

### 2. Rewrite justfile setup recipes to minimal requests ✅ DONE

| Recipe group | Before | After |
|---|---|---|
| `setup-build-*` | `core,essential,toolchain,build` | `build` |
| `setup-fd-*` | `core,essential,toolchain,build` + `zig,ssl` | `build` then `zig,ssl` |
| `setup-env` | `core,essential,toolchain,build,zig,ssl,fd,quality,secrets,coverage,security,ops` | `dev` |
| `setup-linux-x86-gcc` (dev) | `core,essential,toolchain,build` + `zig,ssl,ops` + `quality,secrets` | `build` then `zig,ssl,ops` then `quality,secrets` |
| `setup-quality-*` | `core,essential,toolchain,build` + `quality` | `quality` |
| `setup-gitleaks-*` | `core,essential,secrets` | `secrets` |
| setup-coverage-* | core,build,toolchain,coverage | `coverage` ✅ |
| setup-security-* | core,security | `security` ✅ |

### 3. Verification ✅ DONE

- `python3 orchestrator.py --deps build` → resolves to `core, essential, build` ✅
- `python3 orchestrator.py --deps quality` → resolves to `core, essential, build, go, zig, nodejs, quality` ✅
- `python3 orchestrator.py dev --dry-run` → resolves to `core, essential, build, toolchain, zig, ssl, ops, go, nodejs, quality, secrets, coverage, security, fd` (31 tools) ✅
- No behavior change — the resolver does the same work, just without redundant input

## Implementation Complete ✅ DONE

## Rule

The justfile should never contain `core` or `essential` explicitly. They are leaf-level infrastructure managed by the setup system. Any recipe that lists them is leaking implementation knowledge into the wrong layer.
