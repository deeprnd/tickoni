# Plan: v2.10-s8-1-5 — Revert CI to single-runner build+test, remove -march patching

## Problem

The CI was refactored (commit c10527f56+) to split build and test into separate
stages: the Build stage compiles FD libraries, uploads the artifacts, then the
Unit Test stage downloads them and runs tests on a **different runner**.

This split creates GCC version/intrinsics mismatches between build and test
runners:

- Build runs on the CI runner's GCC (e.g. gcc-13 on ubuntu-24.04).
- Test may run on a different runner image or re-run the build recipe,
  hitting a different GCC with different inline/always_inline behavior for
  AVX-512 and AVX2 intrinsics.
- The result is endless patching of `native_config.sh` with `-march=haswell`
  and feature-specific flags (`-maes`, `-mpclmul`, `-mavx512f`, `-mavx512bw`)
  that fix one runner but break another, or fix one GCC but break another.

The fundamental issue: **the build and test must run on the same machine**,
with the same compiler, the same flags, in the same make invocation. This is
how the old CI worked (before the refactor).

## Root Cause

The old test-unit-fd recipe (`fd-build-lib.sh` + `make run-unit-test`) ran
everything in one shot on one machine. The new split removes that guarantee.

## Plan

### Phase 1: Revert -march and feature flags in native_config.sh

**Goal:** Remove all the ad-hoc `-march` and feature-specific flags added in
this branch. Restore `native_config.sh` to its original form.

**Files to revert:**
- `config/machine/native_config.sh` — revert to use `-march=native` (the original).
  Remove the hardcoded `-march=haswell -mtune=haswell` and the feature-specific
  `-maes -mpclmul`, `-mavx512f -mavx512bw` additions.
- No other machine .mk files need changes.

**How:** `git checkout origin/main -- config/machine/native_config.sh`

**Verify:** The file should contain the original `-march=native` detection
without any hardcoded fallback. It probes `__AVX512IFMA__`, `__AES__`, etc.
at compile time and sets `CPPFLAGS_NATIVE` only for detected features.

**Status: DONE** — reverted at commit `b23f23b84`. File now uses `-march=native -mtune=native` with runtime feature detection (no hardcoded flags).

### Phase 2: Merge test-unit-fd build+test into a single recipe

**Goal:** Restore the old pattern where each test-unit-fd recipe runs both
the build and the tests in one sequence, on the same runner.

**Current (broken) flow:**
1. Build stage: `just build-fd-linux-x86-gcc` → upload artifact
2. Test stage: download artifact → `just test-unit-fd-linux-x86-gcc`
   (which re-runs the build via orchestrator, but on a potentially different
   runner with different GCC)

**Target flow:**
1. Test stage: `just test-unit-fd-linux-x86-gcc` runs BOTH build and test
   sequentially in one make invocation.

**How to change justfile:**

The old `test-unit-fd-linux-x86-gcc` recipe already did this:

```
test-unit-fd-linux-x86-gcc:
    set timeout := 600
    bash contrib/build/fd-build-lib.sh {{ fd_tickoni_build }} gcc-12 test "" ""
    {{ make }} -f contrib/build/GNUmakefile -j"{{ cpu_count }}" MACHINE=tickoni_fd BUILDDIR={{ fd_tickoni_build }} \
        LDFLAGS_EXE="-Wl,-z,shstk" run-unit-test TEST_OPTS="--page-sz normal"
```

Restore this pattern. The orchestrator's `mode=test` already builds libs +
unit-test target in one call. The justfile recipes should use that same
single-call pattern instead of splitting into build-then-test.

**Changes:**
- `test-unit-fd-linux-x86-gcc`: restore to single recipe that calls
  `orchestrator.py build-fd fd-tickoni-fd test gcc-12` (which builds libs
  AND unit-test target in one make invocation).
- Remove the separate `build-fd-linux-x86-gcc` call from the test recipe.
- Keep the same pattern for macOS, Windows lanes.

### Phase 3: Fix all test stages to build+test on the same runner

**Goal:** Every test stage (unit, integration, system, demo) must build FD
libs and run tests on the **same runner**, using the same GCC, in the same
make invocation. The Build stage remains in the CI DAG for parallel CI
efficiency, but test stages do NOT download from it.

**Current CI structure (broken for all test stages):**
- `_ci-build.yml`: builds FD libs, uploads as artifact
- `_ci-unit.yml`: downloads artifact → runs tests ← GCC mismatch
- `_ci-integration.yml`: downloads artifact → runs tests ← GCC mismatch
- `_ci-system.yml`: downloads artifact → runs tests ← GCC mismatch
- `_ci-demo.yml`: downloads artifact → runs tests ← GCC mismatch

**Target CI structure:**
- `_ci-build.yml`: unchanged — builds FD libs in parallel for CI efficiency.
  Artifacts are still uploaded. This stage is still a dependency in the DAG.
- `_ci-unit.yml`: remove artifact download. Each job builds FD libs + runs
  tests in one recipe on the same runner.
- `_ci-integration.yml`: remove artifact download. Each job builds FD libs +
  runs tests in one recipe on the same runner.
- `_ci-system.yml`: remove artifact download. Each job builds FD libs + runs
  tests in one recipe on the same runner.
- `_ci-demo.yml`: remove artifact download. Each job builds FD libs + runs
  tests in one recipe on the same runner.
- `_ci-conformance.yml`: keeps downloading artifacts (it compares binary
  outputs across platforms, does NOT link against FD libs).

**DAG stays the same:** build → unit → integration/system/demo → conformance →
security-deep → dev-setup. The build→unit dependency remains, but unit tests
no longer consume the build output — they rebuild on their own runner.

**How to change justfile recipes:**

The `test-unit-fd-linux-x86-gcc` recipe should build libs and run tests in
one shot. The `test-unit-tk-linux-x86` recipe uses `fd_tickoni_build` which
is computed dynamically. The pattern for each platform lane:

1. Call `orchestrator.py build-fd <build-dir> test <compiler>` which builds
   FD libs AND the unit-test target in a single make invocation.
2. Then run the Tickoni test recipes (Zig tests, integration, demo, etc.)
   which link against the just-built FD libs.

The existing justfile already has this structure for `test-unit-fd-linux-x86-gcc`
(it calls orchestrator with `mode=test`). The key change is in CI: the recipe
runs in the same job that downloads nothing and builds everything locally.

**Changes to CI workflow files:**

For each test workflow (`_ci-unit.yml`, `_ci-integration.yml`, `_ci-system.yml`,
`_ci-demo.yml`):
1. Remove the "Download build artifact" step (actions/download-artifact).
2. Remove the "Verify build artifacts" step (or replace with a build step).
3. Add a "Build FD libs" step that runs the appropriate `build-fd-<platform>`
   just recipe.
4. Keep the "Setup toolchain", "Setup Firedancer deps", and "Run tests" steps.
5. For integration/system/demo: the build step should be `build-fd-<platform>`
   (libs only, no unit-test target) since those stages don't run unit-test.

**Changes to justfile:**

The build recipes used by test stages should be simple `build-fd-<platform>`
calls (mode=libs), since integration/system/demo don't need the unit-test
target. The orchestrator already supports this.

- `_ci-unit.yml`: uses `test-unit-fd-<platform>` (build + unit-test)
- `_ci-integration.yml`: uses `build-fd-<platform>` + `test-integration-tk-<platform>`
- `_ci-system.yml`: uses `build-fd-<platform>` + `test-system-tk-<platform>`
- `_ci-demo.yml`: uses `build-fd-<platform>` + `test-demo-tk-<platform>`

Each pair runs in the same job, on the same runner.

**Files to modify:**
- `.github/workflows/_ci-unit.yml` — remove download, add build step
- `.github/workflows/_ci-integration.yml` — remove download, add build step
- `.github/workflows/_ci-system.yml` — remove download, add build step
- `.github/workflows/_ci-demo.yml` — remove download, add build step
- `justfile` — no changes needed for most lanes; the existing
  `build-fd-<platform>` recipes already work for the libs-only case.
- `contrib/build/orchestrator.py` — no changes. It already supports both
  `mode=libs` and `mode=test`.

## Risks

- **Build time:** each test job now builds FD libs locally. The Build stage
  still runs in parallel in the DAG (for CI efficiency / parallel platform
  coverage), but test stages no longer share its output. This is a known
  trade-off: correctness over artifact reuse.
- **Duplicate builds:** the Build stage and test stages will each compile
  FD libs for the same platform. This is acceptable — the Build stage
  feeds CI efficiency (parallel coverage), test stages ensure correctness
  (same GCC on same runner).
