> **For Hermes:** Execute this plan task-by-task. Each task is self-contained — the build compiles after each one. Unit tests run in `test-unit-tk`; integration tests run in `test-integration-tk`.

**Story:** v2.14 (future — not yet assigned a story number)
**Status:** PLANNED

## Goal

Make the full 14-tile `investmentWorkflow()` runnable end-to-end by registering missing tiles as bounded stubs (no financial logic, no real data) and adding a `tkterm` Qt terminal tile that connects to `tkdisp` as Option C (protocol tile + terminal tile). The data flow will be structurally correct — events ingest, normalize, dedupe, pass through case, check policy, audit, dispatch, agent, model, tool, adapter — but the stubs pass data through without modification. The terminal tile renders results.

## Architecture Decision: Option C (tkdisp protocol + tkterm terminal)

```
tkdisp (Firedancer stem tile) — protocol endpoint
  ├─ reads policy decisions from tkcase via tkdisp→event_in channel
  ├─ sends agent requests on tkdisp → tkagnt link
  ├─ reads terminal results on tkagnt → tkdisp link
  └─ writes results to scratch for tkterm to read

tkterm (new Firedancer stem tile) — terminal UI
  ├─ reads committed results from tkdisp's scratch (shared memory)
  ├─ owns the Qt process lifecycle
  ├─ renders terminal UI (commands, results, status)
  └─ sends user commands back to the event pipeline (via tkings)
```

**Why Option C over Option B:** The terminal is a proper Firedancer tile with shared-memory access to tkdisp results (zero network hop), independent lifecycle management, and a clean protocol/presentation split. Future multi-session terminals can share a single tkdisp backend.

### Task 7: Create tkterm terminal tile

**New files:**
- `src/tickoni/c_abi/shim/tk_term_stem.c` — C stem tile
- `src/tickoni/c_abi/topo_run/tk_term_stem.h` — C header

**Architecture:** tkterm is a Firedancer stem tile that runs the Qt terminal process. It connects to tkdisp's scratch space (shared memory) to read committed results. The stem tile owns the Qt application lifecycle.

**Scratch access pattern:** tkterm joins tkdisp's workspace (via `fd_wksp_join`) and reads `tkdisp_results_of(ctx)` — the result ring array — via `tkdisp_result_at()` / `tkdisp_result_copy()` accessors. It polls for new results (CNC counter `scheduled` and `received` from tkdisp's CNC).

**Qt process:** The stem tile's `stem_run` loop contains:
1. Poll tkdisp CNC for new results
2. When results available, read via `tkdisp_result_copy()`
3. Render in Qt terminal UI (prompt → user input → model result display)
4. When user sends a command, write to tkdisp's event input channel via Firedancer link (or via a separate command channel)

**Simplification for MVP:** tkterm does NOT write back to the event pipeline. It only reads results from tkdisp. The event source is tkings (which produces synthetic events). tkterm is a read-only observer of the agent loop. User interaction is via simulated commands (pre-defined templates), not live input. This keeps MVP scoped.

**CNC counters:** `results_shown` (index 0) — how many results rendered. `user_commands` (index 1) — how many user commands issued.

**Build wiring:** tkterm needs Qt linked. Add Qt linkage to the build. The stem tile C file does NOT link Qt directly — the Qt process is launched from the stem tile's run entry point, and the Qt library is linked at the binary level (supervisor process).

**Simplification for MVP:** tkterm does NOT need to link Qt in the C shim. Instead, it writes results to scratch and a small Qt wrapper (linked into the supervisor binary) reads from scratch and renders. The stem tile is the protocol endpoint; the Qt render loop is a separate function in the same process. This avoids Qt dependency complexity.

**For MVP:** tkterm stem tile writes results to a dedicated scratch buffer that the supervisor's Qt wrapper reads. No direct Qt linkage in the tile.

### Task 15: Dispatch policy — build agent requests from event content

**Background:** Task 10 wired the 14-tile chain with stubs. `tkdisp` (the scheduler tile, `tk_disp_stem.c`) uses a **fixed request template** (`tkdisp_template_hdr` + `tkdisp_template_prompt` installed by `tkdisp_set_template()`) for every event. It reads only `ev->raw.source_offset` from the `PaymentMessage` and sets the template's `run_id` to `source_offset + 1`. Everything else (model_id, requested_tier, actor_role, workflow, capability, budget_id, max_context_tokens, max_output_tokens) is identical for every request. This is scaffolding, not dispatch policy.

The event arriving at `tkdisp`'s event input is a `PaymentMessage` (56 bytes) containing:
- `raw.source_offset` (uint64, offset 0) — already used
- `raw.account_id` (uint32, offset 24) — not used
- `raw.amount_cents` (int64, offset 16) — not used
- `raw.currency[3]` (bytes, offset 28) — not used
- `raw.malformed` (uint8, offset 31) — not used
- `decision` (uint8, offset 52) — policy outcome from `tkpoly`, not used
- `decided_by[6]` (bytes, offset 53) — not used

The `ModelRequestMsg` (272 bytes) that becomes the agent request body has these fields that must come from the event or the dispatch policy:
- `model_id[32]` (offset 80)
- `actor_role[16]` (offset 112)
- `workflow[16]` (offset 128)
- `capability[32]` (offset 144)
- `capability_envelope_id[32]` (offset 176)
- `policy_version[32]` (offset 208)
- `budget_id[32]` (offset 240)
- `requested_tier` (in `TkAgentRequestHdr.requested_tier`, offset 3)
- `max_context_tokens`, `max_output_tokens`, `timeout_ms` — from template today

**Goal:** Replace the fixed template with a dispatch function that reads the `PaymentMessage` and builds a per-event `TkAgentRequestHdr` + `ModelRequestMsg` scope. The MVP dispatch policy is conservative and simple — it uses the event's `account_id` to select the tier and model, and the policy decision to gate whether an agent run is dispatched at all.

**MVP dispatch policy (Task 15):**
- If `decision == POLICY_DENY` (1): skip the event; no agent request is dispatched. This ensures the agent chain is not a bypass around policy.
- If `decision == POLICY_ALLOW` (0): dispatch with tier/model derived from `account_id`:
  - `account_id % 3 == 0` → tier 0 (`classifier_fast`), model `"ops.model"`, workflow `"ops_control"`, capability `"trading_order.propose"`
  - `account_id % 3 == 1` → tier 1 (`classifier_hosted_newer`), model `"risk.model"`, workflow `"risk_control"`, capability `"payment_retry.propose"`
  - `account_id % 3 == 2` → tier 6 (`low`), model `"llm.model"`, workflow `"trading_control"`, capability `"trading_order.propose"`
- All other policy outcomes (`POLICY_REQUIRE_APPROVAL`, `POLICY_ESCALATE`, etc.) also dispatch with the `account_id`-based tier/model but set `replay_mode = 0` (live request), so `tkmodl` returns `MODEL_DENY_LIVE_PROVIDER_DISABLED` (8), exercising the denial path.

**Files:**

**`src/tickoni/c_abi/shim/tk_disp_stem.c`**
