# V2.10.S6: CI Cutover to an Exclusive `just` Command Surface

## Goal

Make `just` the exclusive command surface for all repository work performed by
CI. Every setup, dependency installation, build, quality check, security
check, test, coverage run, benchmark run, conformance export, resource-limit
configuration, and related operation must be exposed by and invoked through a
`just` recipe.

CI workflows and composite actions must not directly execute shell scripts,
Zig, Make, Python repository tools, package managers, Homebrew, LLVM installers,
`apt-get`, `prlimit`, or any other repository/setup command. If an operation is
missing, add the appropriate qualified `just` recipe and invoke that recipe
from CI.

The existing CI jobs and supported lanes must be preserved except for the
explicit deletion of `benchmark.yml` and `book.yml`. Do not add replacement
benchmark or book jobs, schedules, triggers, or platform coverage.

The change is limited to CI and build-system command routing. It must not
change Tickoni runtime, topology, policy, audit, replay, adapter, API,
storage, or financial semantics.

## Command-surface contract

1. Every executable CI operation belonging to the repository or its toolchain
   is implemented by a `just` recipe.
2. Every workflow invocation names a canonical, platform/compiler-qualified
   recipe when a lane-specific recipe exists. Examples include:
   `build-fd-linux-x86-gcc`, `build-fd-macos-x86`,
   `test-unit-tk-linux-x86`, and `test-unit-fd-linux-x86-gcc`.
3. Bare host-dispatching recipes remain available for local convenience but
   must not be called from CI.
4. Compatibility aliases remain only for local/migration compatibility; CI
   must call canonical qualified recipes.
5. Custom composite actions are not required for repository behavior. Keep a
   custom action only when it removes repeated GitHub-specific orchestration
   without hiding the command surface. If retained, its executable steps must
   call `just`, not scripts or installers directly.
6. GitHub-native orchestration actions such as checkout, cache management,
   matrix control, and artifact upload/download may remain as actions. They
   must not perform repository setup or build work outside `just`.
7. `just` must be available before CI invokes it. Do not add a direct package
   manager or shell-based installation of `just` to a workflow. If a runner
   does not provide `just`, resolve that as a runner/toolchain prerequisite;
   fail clearly rather than bypassing the command-surface contract.
8. Do not delete local bare dispatchers or add developer targets to Firedancer
   Makefiles.

## Scope

### Workflows to retain and convert

The live command-bearing workflows are:

- `.github/workflows/build-fd.yml`
- `.github/workflows/build-tk.yml`
- `.github/workflows/coverage.yml`
- `.github/workflows/quality.yml`
- `.github/workflows/security.yml`
- `.github/workflows/tests-long.yml`
- `.github/workflows/tests-short.yml`
- `.github/workflows/tests-xlong.yml`

Retain their existing jobs, matrix entries, triggers, schedules, timeouts,
artifacts, fail-fast behavior, disabled-job state, and system/model-test
behavior unless a direct command must be moved behind a `just` recipe.

### Workflows to delete

Delete these workflows completely:

- `.github/workflows/benchmark.yml`
- `.github/workflows/book.yml`

Remove references to these workflows from workflow documentation, badges,
indexes, and contributor instructions where applicable. Do not replace them
with new workflows or schedules.

### Custom composite actions

Custom composite actions are optional, not an additional build-system layer.
Audit these existing actions and choose explicitly whether each one is removed
or retained as a thin GitHub-orchestration wrapper:

- `.github/actions/setup-public-gh-runner/action.yml`
- `.github/actions/deps/action.yml`
- `.github/actions/build-fd-tk-libs/action.yml`

The default decision is to remove them when workflows can call the equivalent
qualified `just` recipes directly without losing GitHub-specific behavior.
Retain an action only when it provides real reuse for inputs, outputs, cache
coordination, or other GitHub orchestration. A retained action must contain no
direct setup, dependency, shell, Zig, Make, Python, installer, or platform
detection logic; any executable step may invoke only a qualified `just`
recipe.

## Implementation sequence

### 1. Inventory the live CI command surface — DONE

Before editing, enumerate every workflow and composite-action step,
including `run:`, action inputs containing commands, matrix command strings,
and shell fragments. Record:

- all retained workflow jobs and matrix entries;
- every direct command and installer;
- every `just` recipe currently called;
- every bare dispatcher or compatibility alias;
- every referenced recipe's presence in `justfile`;
- every artifact path and upload/download condition.

Create a stable repository-local command-surface checker under `contrib/test/`
or an equivalent approved location. The checker must fail if covered CI code
contains a direct shell, Zig, Make, Python, package-manager, Homebrew, LLVM,
`apt-get`, `prlimit`, helper-script, or other setup/build/test command. It must
also fail when CI calls a bare or compatibility recipe while a canonical
qualified recipe exists.

The checker must report deleted workflow files as absent and must ensure no
references to `benchmark.yml` or `book.yml` remain in active CI configuration.

Verification: repeated runs produce stable output, and a synthetic direct
command causes a failure.

### 2. Complete the qualified `just` recipe grid — DONE

Audit `justfile` and add the smallest set of missing recipes required by the
retained CI lanes. Required families include:

- FD builds: `build-fd-linux-x86-gcc`, `build-fd-linux-x86-clang`,
  `build-fd-linux-arm-gcc`, `build-fd-macos-x86`, `build-fd-macos-arm`,
  `build-fd-windows-x86`, and `build-fd-windows-arm`;
- qualified FD unit-test recipes for every retained runner;
- qualified Tickoni build, unit, integration, demo, system, and e2e recipes
  for every retained platform lane;
- qualified coverage recipes with explicit compiler/toolchain scope;
- qualified quality and security recipes for every retained CI matrix lane;
- qualified setup and dependency recipes for all retained runner/toolchain
  combinations;
- qualified conformance-export and test-preparation recipes;
- qualified resource-limit and live-model preparation recipes where needed.

Each recipe may call underlying shell, Zig, Make, Python, or helper code
internally. Those implementation details must not be exposed in CI YAML or
composite-action command steps. Preserve existing retry and diagnostic
behavior when moving helper-script behavior behind a recipe.

Use `contrib/platform.sh` and fixed canonical lane values. Do not reintroduce
inline runner/OS/architecture detection in workflows or duplicate platform
classification in recipes.

Verification: run `just --list`, `just --dump`, recipe existence checks, and
available Linux dry-runs/tests before changing workflows.

### 3. Move setup and dependency behavior into `just` — DONE

Add or complete qualified `just setup-*` and dependency recipes, then update
workflows to call those recipes directly. Do not dynamically assemble
unsupported recipe names or branch into direct installers.

Move all normal setup operations behind `just`, including:

- zstd and other dependency installation;
- compiler and LLVM setup;
- `buf`, gitleaks, and other quality/security tool setup;
- Windows setup and security-mode handling;
- macOS Homebrew prerequisites;
- cache-miss build prerequisites;
- any resource-limit or test-environment preparation.

If an existing composite action is retained, its inputs may select from an
explicit table of supported qualified recipes, and its outputs/cache handling
may remain. Otherwise remove the action and its workflow references. In both
cases, no action may execute setup or repository commands directly; all such
behavior must be inside `just`.

Verification: validate action syntax, run the available Linux setup/dependency
path, repeat it to check idempotency, and confirm the checker finds no direct
executable setup operation.

### 4. Convert retained build workflows — DONE

Modify `build-fd.yml` and `build-tk.yml` so every build operation invokes a
canonical qualified `just` recipe.

Replace calls such as:

- `just build-fd-gcc` with `just build-fd-linux-x86-gcc`;
- `just build-fd-clang` with `just build-fd-linux-x86-clang`;
- `just build-fd-arm` with `just build-fd-linux-arm-gcc`;
- `just build-fd-macos-x86_64` with `just build-fd-macos-x86`;
- direct `ci-run-build-tk.sh` calls with the appropriate qualified Tickoni
  recipe;
- direct `brew install make` with the appropriate qualified setup recipe.

Do not map a platform lane to another platform's recipe merely to remove a
command. Verify each lane's actual implementation and add a qualified recipe
when the current recipe grid is incomplete.

Remove `build-fd-tk-libs/action.yml` unless it provides meaningful
GitHub-specific orchestration. If retained, make it a thin wrapper around the
appropriate qualified `just` recipe and remove all platform/build branching
from the action itself.

Verification: job and matrix counts, triggers, timeouts, and artifact behavior
are unchanged for retained workflows; no direct build command or bare build
recipe remains; Linux builds execute locally and unavailable-platform results
come from CI.

### 5. Convert quality and security workflows — DONE

Modify `quality.yml` and `security.yml` so every quality/security operation,
including provisioning, invokes a qualified `just` recipe.

Replace aggregate or bare matrix command strings with explicit qualified Linux
recipes where the job has a fixed platform. Preserve matrix separation,
fail-fast behavior, security mode, and existing gate semantics. Do not
hardcode `SECURITY=off` over caller-provided security configuration.

Verification: every command references an existing qualified recipe; available
Linux quality and security lanes run successfully; the checker reports no
direct operation.

### 6. Convert test, system, e2e, and coverage workflows — DONE

Modify `tests-short.yml`, `tests-long.yml`, `tests-xlong.yml`, and `coverage.yml`.

Move all of the following behind qualified `just` recipes:

- unit, integration, demo, system, e2e, and coverage execution;
- direct supervisor builds;
- conformance bundle export;
- Zig build/test invocation;
- LLVM installation/configuration;
- `prlimit` and other resource-limit setup;
- test-environment and live-model preparation.

Preserve artifact paths, `if: always()` uploads, disabled e2e status, model and
system-test behavior, and the existing Windows job set. Keep live-model setup
behind explicit system-test recipes and keep deterministic unit/demo lanes
independent of live-model access.

Verification: available Linux unit, integration, demo, and coverage recipes
perform actual test execution; macOS, Windows, and live-model evidence comes
from CI; no direct command remains in the workflow files.

### 7. Delete benchmark and book workflows — DONE

Delete `.github/workflows/benchmark.yml` and `.github/workflows/book.yml`.
Remove their badges, documentation references, workflow indexes, and related
instructions if present. Do not migrate benchmark Make commands or book build
commands into replacement workflows. The retained CI surface must contain no
references to either deleted workflow.

Verification: file searches find neither workflow file nor active references,
and the command-surface checker passes the reduced workflow inventory.

### 8. Remove obsolete custom actions and update execution documentation — DONE

Update affected execution and contributor documentation, including as needed:

- `doc/execution/ci.md`;
- `doc/execution/build.md`;
- `doc/execution/development.md`;
- `doc/execution/testing-tickoni.md`;
- `doc/execution/security.md`;
- `doc/execution/quality.md`;
- workflow/contributor instruction files that document deleted workflows or
  direct CI commands.

Document one unambiguous rule: CI performs repository work only by invoking
qualified `just` recipes. Document local bare dispatchers separately as local
convenience commands, not CI interfaces. Document that custom actions are
optional thin GitHub-orchestration wrappers, not owners of setup/build/test
behavior. Document that benchmark and book workflows no longer exist.

### 9. Final verification and handoff

Run the narrowest available checks first, then the aggregate gates where
prerequisites permit:

```bash
just --list
just --dump
just setup-env
just build-all
just quality-check-all
just security-check-all
just test-all
just tests-all
```

Run the command-surface checker and require:

- every retained CI executable operation is a `just` recipe invocation;
- zero direct shell, Zig, Make, Python, installer, package-manager,
  Homebrew, LLVM, `apt-get`, `prlimit`, or helper-script operations in CI;
- zero bare or compatibility recipe calls where a qualified recipe exists;
- every referenced recipe exists in `justfile`;
- `benchmark.yml` and `book.yml` are deleted and unreferenced;
- no retained workflow job, matrix entry, trigger, schedule, timeout, or
  artifact contract changed;
- changed documentation references existing recipes and the retained workflow
  set;
- no runtime or financial-boundary files changed;
- unavailable-platform claims are explicitly marked unverified unless backed
  by CI results.

Update story evidence/status only after implementation and real CI results.
Do not commit as part of this plan unless explicitly requested.

## Out of scope

- New CI jobs, schedules, triggers, matrix entries, or platform coverage.
- Replacement benchmark or book workflows.
- Removal of local bare `just` dispatchers.
- Developer tooling targets in Firedancer Makefiles.
- Tickoni runtime, topology, policy, audit, replay, model, tool, adapter,
  execution, API, UI, or storage changes.
- Claims that static YAML inspection proves cross-platform execution.
