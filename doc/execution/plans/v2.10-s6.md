# V2.10.S6 CI and Repository Command Surface Implementation Plan

> **For Hermes:** Use the subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Make `just` the only repository-facing command surface for setup, build, quality, security, and test execution, while preserving the existing CI jobs and making every CI lane explicit and reproducible.

**Architecture:** Keep implementation in the root `justfile` and thin, platform-qualified recipes. GitHub Actions should select those recipes and retain only orchestration actions such as checkout, caching, artifact upload, and matrix control. Underlying shell, Python, Zig, Make, package-manager, and OS commands remain implementation details of `just` recipes or setup actions, not commands called directly by workflows.

**Tech Stack:** `just`, Bash/PowerShell helper scripts, Zig build, Firedancer GNU Make, GitHub Actions YAML, `contrib/platform.sh`.

---

## Audit baseline

Audit performed against the live tree on the `story/just-distpatcher` branch.

### Story contract

`doc/strategy/roadmap/stories/v2.10-s6.md` requires:

- fully-qualified recipe calls in CI;
- `setup-public-gh-runner/action.yml` to delegate to `just setup-*`;
- `deps/action.yml` to avoid runner-specific zstd branching;
- no new scheduled lanes;
- all existing lanes to pass;
- `doc/execution/ci.md` to document the final convention.

The story says “7 workflow files,” but the repository currently contains 10 workflow files:

- active build/test/quality/security surface: `build-fd.yml`, `build-tk.yml`, `coverage.yml`, `quality.yml`, `security.yml`, `tests-long.yml`, `tests-short.yml`, `tests-xlong.yml`;
- optional workflows: `benchmark.yml`, `book.yml`.

The implementation must first define whether optional workflows are included in the command-surface audit. The recommended scope is: all workflows containing repository build/test/quality/security commands are included; `benchmark.yml` and `book.yml` are included only where they currently execute repository commands, without adding or changing their triggers.

### Already present

- `contrib/platform.sh` exists and is used for top-level `justfile` OS/arch/core variables.
- `justfile` contains setup recipes for Linux, macOS, and Windows plus `setup-env`.
- Qualified build recipes exist for the main Firedancer lanes and Tickoni build aliases.
- Qualified Tickoni unit/integration recipes and Windows system recipes exist.
- Qualified quality and security aliases exist for the Linux/x86-only families.
- `setup-public-gh-runner/action.yml` already invokes `just setup-*` for POSIX lanes, but still contains inline `runner.os`/`runner.arch` mapping and invokes Windows setup scripts directly.
- Most CI checks already call `just`, and `ci.md` describes the intended qualified naming policy in several places.

### Missing or incomplete

1. CI still calls bare recipes such as `just build-fd-gcc`, `just test-unit-tk`, `just test-cov-tk`, `just quality-*-all`, and `just security-*-all`. These must be replaced with explicit lane recipes or an explicitly approved aggregate exception.
2. CI still bypasses `just` in multiple places: `bash contrib/ci-run-build-tk.sh`, direct `zigw.sh`, direct Python conformance export, direct `apt-get`, direct LLVM setup, direct `prlimit`, and the benchmark workflow’s direct Make commands.
3. `build-tk.yml` has direct macOS Homebrew setup and calls a helper script instead of a `just` build recipe.
4. `tests-short.yml` has direct Zig and Python commands in conformance jobs; the corresponding build/export flow needs qualified `just` recipes.
5. `tests-long.yml` performs direct resource-limit setup and calls bare `just test-unit-fd`.
6. `coverage.yml` calls bare coverage recipes and installs/configures LLVM outside `just`.
7. `quality.yml` uses aggregate commands and installs `buf` directly instead of using the setup/quality command surface.
8. `security.yml` uses aggregate/bare commands and matrix command strings rather than explicit qualified recipes.
9. `deps/action.yml` still branches on `runner.os` for hashing, cache conditions, zstd installation, compiler setup, and package installation. The story specifically calls out zstd detection, but the broader “just-only” goal requires deciding which of this action remains orchestration and which moves into qualified setup recipes.
10. `build-fd-tk-libs/action.yml` still branches on `runner.os` and directly chooses Windows recipes; it needs a qualified recipe interface or a documented orchestration-only exception.
11. `ci.md`, `build.md`, `development.md`, and `testing-tickoni.md` still document bare recipes and direct `zig build` commands as normal developer/CI paths.
12. S4 remains marked `Backlog` even though substantial implementation exists. S6 should not silently close or rewrite S4; its final verification must identify any S4 prerequisites still blocking qualified recipes.

### Non-goals and constraints

- Do not add CI jobs, schedules, or new platform coverage.
- Do not change Tickoni runtime, policy, audit, replay, adapter, API, or storage behavior.
- Do not add developer targets to Firedancer Makefiles.
- Do not remove the bare local convenience dispatchers unless a separate decision explicitly changes S4.
- Do not claim cross-platform execution from static YAML checks; unavailable platforms require CI evidence or an explicitly documented dry-run.
- Preserve the existing dirty files and do not stage or rewrite them as part of this plan.

## Task 1: Freeze the command-surface contract

**Objective:** Establish the exact definition of a permitted CI command before editing workflows.

**Files:**
- Modify: `doc/strategy/roadmap/stories/v2.10-s6.md`
- Modify: `doc/strategy/roadmap/backlog/proposals/build-tooling-consolidation.md` (only if the policy wording is inconsistent)
- Create: `doc/execution/plans/v2.10-s6-command-inventory.txt` or an equivalent repository-local checker under `contrib/test/`

**Steps:**
1. Enumerate all workflow and composite-action `run:` commands.
2. Classify each as one of: `just` recipe, orchestration-only command, or forbidden direct repository operation.
3. Define the allowed exceptions explicitly: checkout, cache, artifact upload, GitHub metadata, and unavoidable runner bootstrap needed before `just` exists.
4. Decide whether aggregate `just` recipes are permitted in CI. Recommended rule: CI uses qualified recipes for lane work; aggregate recipes remain local convenience/composition targets only.
5. Record the actual eight active command-bearing workflows and the treatment of optional workflows. Do not preserve the stale “7” count without evidence.

**Verification:** Run the inventory checker and require it to print stable counts by category. The checker must fail if a new direct `zig`, `make`, `python`, `bash contrib`, package-manager, or bare lane command appears in a covered workflow.

## Task 2: Complete the qualified `justfile` recipe grid

**Objective:** Add only the missing recipes required to replace direct CI commands and preserve platform/compiler specificity.

**Files:**
- Modify: `justfile`
- Test: repository-local command-surface checker from Task 1

**Steps:**
1. Map every current CI lane to an exact qualified recipe, including compiler where the lane has a compiler distinction.
2. Add missing qualified recipes for coverage, demo build/export, system preparation, and any platform-specific quality/security lane required by the existing jobs.
3. Move CI-only preparation currently embedded in YAML into `just` recipes where it is part of setup, build, quality, security, or test execution.
4. Keep aggregate recipes (`build-all`, `test-all`, `quality-*-all`, `security-*-all`) as local composition helpers unless Task 1 explicitly approves them for a platform-neutral CI job.
5. Ensure qualified recipes call `platform.sh`-derived values or fixed lane values and do not reintroduce inline `uname`/`runner` detection.
6. Ensure all nested recipe calls preserve the correct qualified target and do not rely on the just nested-parameter quoting pitfall.

**Verification:** Run `just --list`, `just --dump`, and the checker. Run the available Linux qualified build, quality, security, and test recipes; use CI for unavailable platforms.

## Task 3: Make setup and dependency actions thin `just` wrappers

**Objective:** Ensure setup and dependency provisioning are represented by the same repo-owned `just setup-*` contract locally and in CI.

**Files:**
- Modify: `.github/actions/setup-public-gh-runner/action.yml`
- Modify: `.github/actions/deps/action.yml`
- Modify: `.github/actions/build-fd-tk-libs/action.yml`
- Modify: `justfile`
- Modify or create: `contrib/setup/*` only where an existing lane script lacks a required setup operation

**Steps:**
1. Replace the setup action’s inline platform mapping with an explicit input-to-qualified-recipe mapping. Do not use a dynamically assembled recipe name if it obscures the supported matrix; a case table is preferable.
2. Route Windows through `just setup-windows-x86` or `just setup-windows-arm`, including security mode through the existing supported setup interface.
3. Move zstd installation and other lane prerequisites that belong to setup into the relevant setup recipe/helper, while keeping action-level conditions only for orchestration such as cache hit/miss.
4. Change the dependency action to consume the qualified setup/dependency contract rather than directly invoking package managers for normal lane requirements.
5. Make the Firedancer-library action call the qualified build recipe for each existing lane, with no new jobs or profiles.
6. Preserve idempotency and fail-closed missing-tool behavior from S5.

**Verification:** Run static action checks and the Linux setup/dependency path. Run setup twice where practical. Verify no action invokes a setup script directly when an equivalent `just setup-*` recipe exists.
