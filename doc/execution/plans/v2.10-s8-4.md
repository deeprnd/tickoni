# Developer Setup + Full Test Validation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Create a plan (and optional CI workflow) that validates the developer setup by running `just setup-env` followed by `just tests-all` on all six platform/compiler combinations: Linux x86, Linux ARM, macOS x86, macOS ARM, Windows x86, Windows ARM.

**Architecture:** A single new CI workflow (`tests-dev-setup.yml`) that mirrors what a developer does locally: checkout → `just setup-env` → `just tests-all`. The plan also documents what each step entails per platform and the known blockers.

**Tech Stack:** GitHub Actions, justfile recipes, contrib/setup/ scripts, Zig, Firedancer build system.

---

## What `just setup-env` and `just tests-all` Do

### `just setup-env` (bare, no toolchain arg)

Routes to platform-specific scripts:

| Platform | Architecture | Script Path |
|----------|-------------|-------------|
| Linux | x86 | `contrib/setup/linux-x86-essential.sh` ×2 (gcc + clang) + `linux-x86-ops.sh` |
| Linux | arm | `contrib/setup/linux-arm-essential.sh` ×2 (gcc + clang) + `linux-arm-ops.sh` |
| macOS | x86 | `contrib/setup/macos-x86-essential.sh` (SECURITY=off) + `macos-x86-ops.sh` |
| macOS | arm | `contrib/setup/macos-arm-essential.sh` (SECURITY=off) + `macos-arm-ops.sh` |
| Windows | x86 | `contrib/setup/windows-x86.ps1` |
| Windows | arm | `contrib/setup/windows-arm.ps1` |

Each script installs: Zig, compilers (gcc/clang), build deps, git hooks, and optionally LLM tooling.

### `just tests-all`

Runs this sequence:
1. `just build-all` → `just build-fd && just build-tk`
2. `just quality-format-check-all` → `quality-format-check-fd && quality-format-check-tk`
3. `just quality-lint-check-tk` → lint-check-tk (zig build, links tickoni-supervisor)
4. `just quality-proto-check-all` → proto + buf lint
5. `just security-check-all` → engine check, codeql, gitleaks, seccomp, proof, sanitize
6. `just security-engine-check-changes` → engine checks
7. `just test-all` → test-unit-all → test-cov-all → test-system-all → test-e2e-all

## Known Blockers & Considerations

1. **Windows ARM:** No `setup-windows-arm` justfile recipe exists for CI in the current `setup-env` path — the justfile routes Windows to `setup-windows-x86` only. Windows ARM CI uses `setup-windows-ci-arm`. Need to add `setup-windows-arm` and `setup-windows-ci-arm` recipes, plus the justfile dispatcher paths.

2. **Windows `setup-env` routes to `setup-windows-x86` only.** The justfile `setup-env` recipe (line 103-107) only has `setup-windows-x86` in the Windows branch. Windows ARM needs `setup-windows-arm` added.

3. **System tests require LLM models.** `test-system-tk` needs llama.cpp and a GGUF model downloaded from HuggingFace. This requires `hf` CLI auth and significant disk space. These tests are optional for dev-setup validation but are included in `tests-all`.

4. **Coverage tests.** `test-cov-all` calls `test-cov-tk` which runs `coverage.sh coverage-tk` — requires clang-18/llvm-18 toolchain on Linux. This may not be installed by `setup-env` on all paths.

5. **Security checks.** `security-check-all` calls `security-sanitize-check-fd` which builds with ASan/UBSan — this is a heavy build and may cause timeouts. On macOS, security tools may be limited (SECURITY=off path).

6. **Justfile line 232-242 (`build-tk` bare dispatcher) has a bug:** Windows ARM maps to `just build-tk-windows-arm` but there's no `build-tk-windows-arm` recipe defined — only the bare dispatcher routes to it. Actually looking again, `build-tk-windows-arm: build-tk-linux-x86` exists at line 228. But `build-tk-linux-arm: build-tk-linux-x86` at line 220 means arm just aliases to x86 — this is likely a placeholder and won't actually build for ARM.

7. **Memory/hugepages.** Firedancer unit tests need hugepages. CI currently handles this in workflow YAML (not justfile). Dev setup validation on Linux needs `sudo` for hugepage allocation.

## Plan: CI Workflow for Dev Setup Validation

### Task 1: Create the CI workflow skeleton

**Objective:** Create `.github/workflows/tests-dev-setup.yml` with one detect-changes job and a matrix of platform jobs.

**Files:**
- Create: `.github/workflows/tests-dev-setup.yml`

**Steps:**

The workflow structure mirrors `build-tk.yml` but adds `tests-all` after setup:

```yaml
name: Dev Setup Validation

on:
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: dev-setup-${{ github.ref }}
  cancel-in-progress: true

jobs:
  detect-changes:
    name: Detect Changes
    runs-on: ubuntu-slim
    outputs:
      run: ${{ steps.detect.outputs.run }}
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: ./.github/actions/detect-changes
        id: detect

  dev-setup-linux-x86:
    name: Dev Setup / Linux x86_64
    needs: detect-changes
    if: needs.detect-changes.outputs.run == 'true'
    runs-on: ubuntu-24.04
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v7
      - uses: ./.github/actions/setup-public-gh-runner
        with:
          zig: 'true'
          setup-recipe: setup-linux-x86-gcc
      - name: Run full test suite
        run: just tests-all

  dev-setup-linux-arm:
    name: Dev Setup / Linux ARM64
    needs: detect-changes
    if: needs.detect-changes.outputs.run == 'true'
    runs-on: ubuntu-24.04
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v7
      - uses: ./.github/actions/setup-public-gh-runner
        with:
          zig: 'true'
          setup-recipe: setup-linux-arm-gcc
      - name: Run full test suite
        run: just tests-all
```

### Task 2: Add missing Windows ARM setup recipes to justfile

**Objective:** The justfile `setup-env` routes Windows only to `setup-windows-x86`. Need `setup-windows-arm` and `setup-windows-ci-arm`.

**Files:**
- Modify: `justfile` around lines 150-163

**Steps:**

Add after the existing Windows x86 recipes:

```
# Windows ARM64 — dev mode (includes LLM tooling)
setup-windows-arm:
    powershell -ExecutionPolicy Bypass -File contrib/setup/windows-arm.ps1

# Windows x86_64 — CI mode (no LLM tooling, no security tools)
setup-windows-ci-x86:
    powershell -ExecutionPolicy Bypass -File contrib/setup/windows-x86.ps1 -NoLLM

# Windows ARM64 — CI mode (no LLM tooling, no security tools)
setup-windows-ci-arm:
    powershell -ExecutionPolicy Bypass -File contrib/setup/windows-arm.ps1 -NoLLM
```

Also need to add the Windows ARM case to the `setup-env` dispatcher (line 103-107):

```
      windows) \
        if [ -n "{{ toolchain }}" ] && [ "{{ toolchain }}" != "clang" ]; then \
          echo "unsupported toolchain on Windows: {{ toolchain }} (expected clang)" >&2; exit 1; \
        fi; \
        if [ "{{ arch }}" = "arm" ]; then \
          just setup-windows-arm; \
        else \
          just setup-windows-x86; \
        fi ;; \
```

### Task 4: Handle system test and coverage blockers

**Objective:** `just tests-all` includes system tests and coverage, both of which have infrastructure dependencies that may not be available on all platforms in CI.

**Approach:** Create a `tests-all-ci` recipe variant that skips system tests (which require LLM models) but keeps unit, integration, demo, and coverage tests. Or alternatively, accept that system tests will be skipped on platforms where `hf` CLI auth isn't configured.

Option A — Add `tests-all-ci` that excludes system tests:
```
tests-all-ci:
    @just build-all
    @just quality-format-check-all
    @just quality-lint-check-tk
    @just quality-proto-check-all
    @just security-check-all
    @just test-all
    @just test-demo-tk
```

Option B — Keep `tests-all` but accept `test-system-tk` failure as expected on CI (document this).

Recommendation: **Option A** — add `tests-all-ci` for CI use, keep `tests-all` for local dev. The CI workflow uses `tests-all-ci`.

## Risks and Mitigations

1. **Timeouts.** `tests-all` on Linux may take 30-45 minutes (FD build + tests). macOS may take 40-60. Windows may take 60-90. Set appropriate timeouts per platform.

2. **Windows ARM is untested.** No existing CI tests `test-unit-tk-windows-arm` or `test-integration-tk-windows-arm`. The first run will likely fail. Consider starting with just the build step (`just build-all`) on Windows ARM before adding `tests-all`.

3. **Disk space.** Full setup + FD libs + Zig cache + test artifacts may exceed the 14GB runner disk on Windows. Consider cleanup steps between phases.

4. **Clang dual-install on Linux.** `setup-env` installs both gcc and clang toolchains. This is heavy but necessary for dev parity.

5. **macOS security tools.** `SECURITY=off` path on macOS means some security checks may be skipped or fail. Document this limitation.
