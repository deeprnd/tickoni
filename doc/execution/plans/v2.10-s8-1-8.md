# Plan: Replace Windows libuuid stub with Win32 RPC UuidCreate

|**Status:** Draft|
|**Created:** 2025-08-29|
|**Updated:** 2025-08-29|
|**Story:** V2.10.S8|

---

## Problem

The Windows `libuuid_stub.c` produces a `libuuid.a` that zeroes all 16 bytes
via `memset(out, 0, 16)`. This is a placeholder because the comment says
prebuilt Windows Firedancer libs reference `libuuid.a` as a linker dependency,
and Zig's C source inclusion only adds `.obj` — it does not satisfy the library
lookup.

Investigation found:
- No code in the repo calls `uuid_generate()`. Zero callers across the entire
  codebase.
- `nm -u` on every built `.a` file shows zero undefined uuid symbols.
- RocksDB doesn't use libuuid; its deps are snappy, zlib, lz4, zstd, and
  platform threading.
- The libs that do have UUID-related symbols (`libfd_disco.a`) reference
  `BundleUuid` protobuf field names (Solana-specific), not `libuuid.a`.

The dependency is likely a phantom — added as a precaution when someone set up
the Windows build path. Zig may silently ignore the missing archive when the
symbol isn't actually needed.

## Implementation

### Phase 1: Remove the dependency entirely

Try the simplest thing first: delete the stub and see if the build works.

1. **Delete `src/tickoni/c_abi/shim/libuuid_stub.c`**
2. **Remove `addObjectFile("libuuid.a")` from `build.zig`**
   - Line 2283 in `linkTickoniFiredancer()` — remove the line:
     `step.root_module.addObjectFile(.{ .cwd_relative = b.fmt("{s}/libuuid.a", .{fd_lib_dir}) });`
   - Line 2477 in `addTickoniTopoRunShims()` — same removal.
   - Update the comments at lines 2320-2324 that reference libuuid_stub.
3. **Remove `compile_libuuid_stub()` call from `windows.py`**
   - Remove the function entirely (lines 139-206).
   - Remove its call site from `orchestrator.py` (lines 296-298).
   - Update the docstring/header of `windows.py` (line 5 mentions libuuid_stub).
4. **Verify the build works:**
   - `just build-fd && just build-tk` — should build all FD libs + Tickoni exe.
   - `just test-unit-tk` — should pass unit tests.
   - On Linux: verify no new undefined symbols appear.
   - On Windows: same checks (requires Windows environment).

If Phase 1 passes (build succeeds, tests pass), **stop here**. No Windows
implementation needed.

If Phase 1 fails (build breaks with missing `uuid_generate`), proceed to Phase 2.

### Phase 2: Replace stub with Win32 RPC UuidCreate (only if Phase 1 fails)

Replace the stub body with a Win32 RPC call.

```c
// Minimal libuuid wrapper for Windows — wraps UuidCreate.
//
// Windows prebuilt FD libs (from CI) carry RocksDB metadata that references
// libuuid.a. This stub provides the uuid_generate symbol the linker expects.
// macOS/Linux prebuilt libs do not carry this dependency.
//
// On Windows, UuidCreate() from rpcrt4.dll generates a real UUID v4-equivalent
// (random, 128-bit) — the Win32 RPC runtime is part of every Windows install
// since Windows 2000.

#include <rpc.h>
#include <string.h>

void uuid_generate(unsigned char out[16]) {
    UUID win_uuid;
    UuidCreate(&win_uuid);
    memcpy(out, &win_uuid, 16);
}
```

Key details:

- `rpc.h` is in the Windows SDK, available with any MSVC or MinGW-w64 toolchain.
- `UuidCreate()` returns a packed 16-byte `UUID` struct that maps directly to
  the `unsigned char out[16]` expected by the libuuid API.
- `memcpy(out, &win_uuid, 16)` is correct — `UUID` is a 16-byte packed struct
  (not the 16-char string representation).
- No new dependencies — `rpcrt4.lib` is linked by the build script, not added
  to the C source.

In `windows.py`, add `-lrpcrt4` to the compile args (covers both MSVC via
`#pragma comment` and MinGW/clang). Add this to the stub:

```c
#ifdef _MSC_VER
#pragma comment(lib, "rpcrt4.lib")
#endif
```

And pass `-lrpcrt4` in `windows.py`'s compile args for non-MSVC compilers.

Verify:
1. `python3 contrib/build/orchestrator.py build-fd fd-tickoni-fd libs` (Windows)
2. Check that `libuuid.a` contains a real `uuid_generate` that returns non-zero bytes.
3. `just build-tk` — Tickoni exe should link cleanly.
4. Verify on both MSVC and MinGW-w64 clang paths.

## Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Phase 1 works — dependency is phantom | **Medium** | Zero callers found, nm shows no uuid refs, RocksDB doesn't use uuid. Most likely outcome. |
| Phase 1 fails — real dependency exists | Low | Falls through to Phase 2. |
| `rpcrt4.lib` not found on Windows setups | Low | Ships with Windows SDK on all modern installs; LLVM WinGet and MSVC include it. |
| MinGW-w64 doesn't find `rpcrt4` | Low | `gcc` on MSYS2 links `rpcrt4` by default (part of system32 DLL set). |
| ABI mismatch between Win32 UUID layout and expected format | None | `UuidCreate` returns a 16-byte packed struct identical to `uuid_t` from libuuid. |
| ARM64 Windows path | None | `UuidCreate` works identically on ARM64 Windows. |

---

## Why This Order (Remove First, Implement Second)

1. **If Phase 1 works, we save an entire feature.** No Windows-specific code,
   no new dependencies, no build script changes. Just two `build.zig` lines and
   one `.c` file deleted.
2. **If Phase 1 fails, Phase 2 is guaranteed to work.** `UuidCreate()` is a
   well-tested Win32 API on every Windows version. It's a drop-in replacement.
3. **The current stub is already wrong** — it returns all-zeroes. Even if the
   dependency is real, we're shipping broken behavior. Phase 2 fixes it; Phase 1
   eliminates it.

---

## What This Does NOT Change

- ARM64 Linux path — uses real FD libs from local build, not the Windows stub.
- Linux/macOS — never used these platforms; the stub is Windows-only.
- Tickoni runtime code — `uuid_generate()` is never called.
- CaseOps UI, tkapi, agents, or any higher-layer code.
- The overall build orchestration flow in `orchestrator.py` (Phase 2 only).
