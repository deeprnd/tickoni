# Plan: v2.10-s2-4 — Refactor duplicated dispatch logic after structural split

**Story:** v2.10-s2-4
**Status:** **DONE**
**Predecessor:** v2.10-s2-3 (split justfile into import-based sub-files)
**Successor:** (future) unify quality/security platform aliases when they diverge

## Problem

After the structural split (v2.10-s2-3), the dispatch logic for platform-specific commands is duplicated across 5 inline `#!/usr/bin/env bash` recipes. Each dispatcher repeats the same 6-branch `case "os-arch"` pattern with `exec just` forwarding — only the dispatcher name and target command change.

The duplicated dispatchers are:

| File | Dispatcher | Target command pattern | Branches |
|------|-----------|----------------------|----------|
| `just/build/all.just` | `build-tk` | `build-tk-{platform}` | 6 |
| `just/build/all.just` | `build-fd` | `build-fd-{platform}[-compiler]` | 6 |
| `just/test/unit.just` | `test-unit-tk` | `test-unit-tk-{platform}` | 6 |
| `just/test/unit.just` | `test-unit-fd` | `test-unit-fd-{platform}[-compiler]` | 5 (no linux-clang) |
| `just/test/integration.just` | `test-integration-tk` | `test-integration-tk-{platform}` | 6 |

Each one contains ~15 lines of nearly-identical bash:
```bash
#!/usr/bin/env bash
set -euo pipefail
case "{{ os }}-{{ arch }}" in
  linux-x86) exec just build-tk-linux-x86 ;;
  linux-arm) exec just build-tk-linux-arm ;;
  macos-x86) exec just build-tk-macos-x86 ;;
  macos-arm) exec just build-tk-macos-arm ;;
  windows-x86) exec just build-tk-windows-x86 ;;
  windows-arm) exec just build-tk-windows-arm ;;
  *) echo "unsupported host platform for build-tk: {{ os }}-{{ arch }}" >&2; exit 1 ;;
esac
```

## Target state

Create a single shared dispatcher helper script that all dispatchers call. Each dispatcher recipe becomes a one-liner:

```
build-tk:
    bash scripts/dispatch build-tk
```

The helper script (`scripts/dispatch`) contains the dispatch map and the routing logic in one place.

### Dispatcher map format

A JSON file maps each dispatcher name to its platform-to-command mapping:

### The dispatcher script

`scripts/dispatch` — a small Python script that:
1. Reads the dispatcher map JSON from its own directory.
2. Accepts the dispatcher name as `$1`.
3. Looks up the platform mapping for that dispatcher.
4. Reads `os` and `arch` from `contrib/platform.sh`.
5. Constructs `os-arch` key and looks it up in the map.
6. If found: `exec just <target-command>`.
7. If not found: prints error message to stderr and exits 1.

The script is ~40 lines of Python and uses only `json`, `subprocess`, and `sys`.

### New justfile recipe form

Every dispatcher recipe becomes a one-liner:

```
# Bare dispatcher; canonical platform/compiler recipes are in the dispatch map.
build-tk:
    bash scripts/dispatch build-tk

build-fd:
    bash scripts/dispatch build-fd

test-unit-tk:
    bash scripts/dispatch test-unit-tk

test-unit-fd:
    bash scripts/dispatch test-unit-fd

test-integration-tk:
    bash scripts/dispatch test-integration-tk
```

## Migration steps

### Phase 1: Create `scripts/dispatch` script

1. Create `scripts/` directory.
2. Create `scripts/dispatch` with the dispatcher map embedded as a JSON string.
3. Create `scripts/dispatch-map.json` as the canonical source (the script reads this file at runtime).
4. Make the script executable.

### Phase 2: Remove inline dispatchers

Remove the 5 inline bash case-dispatchers from their respective files:
- `just/build/all.just` — remove `build-tk` and `build-fd` recipes (keep the 15 lines of bash each)
- `just/test/unit.just` — remove `test-unit-tk` and `test-unit-fd` recipes
- `just/test/integration.just` — remove `test-integration-tk` recipe

Replace each with the one-liner `bash scripts/dispatch <name>`.

### Phase 3: Verify

1. `just --dump > /dev/null` — parse check
2. `just --list` — verify all dispatchers appear
3. `just build-tk` — runs on local platform
4. `just build-fd` — runs on local platform
5. `just test-unit-tk` — runs on local platform
6. `just test-unit-fd` — runs on local platform
7. `just test-integration-tk` — runs on local platform

## What stays the same

- All platform-specific implementation recipes are untouched.
- All CI-facing recipe names stay the same.
- CI workflows need no changes.
- `kill-test` dispatcher (also bash case) is intentionally **not** refactored — it has OS-level logic, not just `exec just`, and belongs to a different concern (process cleanup, not command routing).
- `tests-all` and `test-all` dispatchers are cross-category (call `just build-all`, `just test-all`, etc.) — they don't follow the platform-routing pattern and stay as-is.
