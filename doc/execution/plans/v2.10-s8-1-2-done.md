# v2.10-s8-1-2: Consolidate zig install + zigw.sh into single Python script

## Problem

Zig toolchain is split across two disconnected scripts:

- `contrib/setup/install/strategies/zig.py` — downloads, extracts, installs zig to `$HOME/.local/zig-<target>-<version>/`
- `contrib/build/zigw.sh` — bash wrapper that searches PATH, $HOME/.local, and Windows registry to find zig and execs it

This split causes multiple bugs:
1. `zig.py` writes the binary path (`install_dir/zig`) to GITHUB_PATH, but GitHub Actions expects a directory — zig never reaches PATH in subsequent CI steps
2. `zigw.sh` reimplements OS/arch detection (already done by `platform.sh`), has Windows ARM x64 detection logic that's fragile, and fails with "zig not found" when zig isn't on PATH
3. Every CI lane needs both: install zig via orchestrator, then resolve it via zigw.sh
4. Two places to maintain for a trivial "download one binary, run it" operation

Compare to `go_install`: installs `go` → modifies `os.environ['PATH']` in the same process → next step works. Zero separate scripts.

## Root cause of CI quality lane failures

`quality-format-check-linux-x86` and `quality-lint-check-linux-x86` call `zigw.sh fmt` and `zigw.sh build`, which need `zig` on PATH. The CI runs:

1. `just setup-quality-linux-x86` — installs zig via `zig.py`, writes binary path to GITHUB_PATH (wrong — should be directory)
2. `just build-fd-tk-libs` — builds C libs, doesn't use zig
3. `just quality-format-check-linux-x86` — `zigw.sh` can't find zig because GITHUB_PATH had a binary path, not a directory

The `*-linux-x86` qualified aliases in justfile are unnecessary — the bare `quality-format-check-all` / `quality-lint-check-all` work on Linux/x86. But even the bare recipes would fail if zig isn't on PATH.

## Design

### Principle

One script. One responsibility. Install zig → make it available → callers just run `zig`.

No separate discovery/wrapper script. The orchestrator's install strategy should:
1. Install the binary to a known location
2. Write the directory to GITHUB_PATH (CI) so zig is on PATH for all subsequent steps
3. Print activation instructions (local dev) — same as today, but correct

### Scope

**In scope:**
1. Fix `zig.py` to write the install directory (not binary path) to GITHUB_PATH
2. Fix `zig.py` to modify `os.environ['PATH']` in-process (like `go_install` does) so the same orchestrator run's subsequent tools can find zig
3. Remove `contrib/build/zigw.sh` entirely
4. Update all justfile recipes that call `zigw.sh` to call `zig` directly or `python3 contrib/setup/install/strategies/zig.py`'s output
5. Update `contrib/quality/quality.sh` `cmd_format_check_tk` / `cmd_lint_check_tk` to call `zig` directly
6. Update CI workflow references to zigw.sh
7. Update all callers across the repo

**Out of scope:**
1. Changing how other tools are installed
2. Refactoring the orchestrator pattern itself
3. Consolidating other tool install strategies

## Implementation Steps

### Step 1: Fix zig.py PATH handling
**DONE** — `zig.py` now writes the install directory (not binary path) to GITHUB_PATH, modifies `os.environ['PATH']` in-process, and prints correct activation message.

**File:** `contrib/setup/install/strategies/zig.py`

In both `_handle_windows_path` and `_handle_posix_path`:

- Change from `bin_dir = str(install_dir / "zig")` to `bin_dir = str(install_dir)` (directory, not binary)
- Add `os.environ['PATH'] = f"{bin_dir}:{os.environ['PATH']}"` after writing to GITHUB_PATH (mirrors `go_install` behavior)
- Update activation message to `export PATH="{bin_dir}:$PATH"` (not `{bin_dir}/zig`)
- On Windows, the binary is at `bin_dir/zig.exe` — adding the directory to PATH means `zig.exe` is found on PATH

- But justfile recipes run in subshells — `os.environ['PATH']` from the Python process won't propagate to `just` subshells. The GITHUB_PATH fix handles CI steps. For local dev, each justfile recipe that needs zig should either:
  - Source the activation line, OR
  - Accept that the user runs `just setup-env` first which sets up PATH permanently

Actually, looking at how other recipes work: the build/test recipes already expect zig on PATH (they pass `ZIG_GLOBAL_CACHE_DIR` env vars). The GITHUB_PATH + in-process PATH modification should suffice.

## Risk assessment

- **Low risk**: The change is mechanical — replace `zigw.sh` wrapper calls with direct `zig` invocations
- **Medium risk**: If zig install fails, all build/test/quality recipes break. Mitigation: ensure the orchestrator's `zig` dependency is correct in all relevant category chains
- **Medium risk**: Windows ARM x64 Zig workaround in zigw.sh is lost. Mitigation: this workaround was in zigw.sh's auto-discovery, not in the install itself. If needed, the install strategy can place the binary in a Windows-compatible location. For now, CI Windows uses pre-installed Zig from Microsoft's winget or the local install — verify this works.
