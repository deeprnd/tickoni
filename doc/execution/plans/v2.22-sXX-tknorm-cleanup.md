### Task 2: Update `mod.zig` — handle `runOneSequentialForTest`

**Goal:** The sequential pipeline tests in `mod.zig` call `runNormalize(state)` which invokes `normalize.zig`'s thread-mode loop. These tests verify the end-to-end pipeline behavior using in-process queue-based communication (not Firedancer topology). They need to continue working after the process-mode code is removed.

**Two options:**

**A. Keep `runNormalize` in `normalize.zig` but move it to a new file.**
The thread-mode loop in `normalize.zig` is a valid test harness — it exercises the same validation + hash + hops-increment logic as the stem tile, but uses in-process queues instead of Firedancer dcache. Move it to a separate file (e.g., `normalize_thread.zig`) and keep it for test harness use. The stem tile's `tknorm_during_frag` and `tknorm_after_credit` handle the same logic in Firedancer mode.

**B. Remove `runNormalize` entirely and update the sequential test.**
The sequential test (`mod.zog:46-71`) verifies:
- `normalized == 1` after one valid event
- `invalid == 1` and `normalized == 0` after a malformed event
- `audited == 1` and correct `policy_decision.outcome`

These can be verified by:
- Testing the C stem tile's `tknorm_during_frag` directly (via `stem_norm_unit.zig`)
- Testing the full pipeline via integration tests (`test_norm_stem_tile.zig`)
- The sequential test's specific assertions about `state.normalized` and `state.invalid` atomics can be replaced with unit tests on the C hash + framing validation.

**Recommendation: Option B.** The thread-mode loop is dead weight once the stem tile is activated. The sequential test can be replaced by:
1. Unit test for framing validation (already covered by `stem_norm_unit.zig` — valid/invalid currency checks)
2. Unit test for FNV-1a hash (already in `stem_norm_unit.zig`)
3. Integration test for stem tile lifecycle (already in `test_norm_stem_tile.zig`)

**Update `mod.zig`:**

```zig
// Remove:
const normalize = @import("normalize.zig");
pub const runNormalize = normalize.runNormalize;
// From runOneSequentialForTest:
runNormalize(state);
// From test block:
_ = @import("normalize.zig");
```

**Update `runOneSequentialForTest`** — since `normalize` was the second stage (tkings → tknorm → tkdedu → tkpoly → tkaudt), removing it means the test would send events directly from `q_ing_norm` to `q_norm_dedu` without normalization. This breaks the test.

**Better approach:** Replace `runNormalize(state)` with a call to a **stub normalizer** that performs the same transformation inline:

```zig
fn normalizeEvent(raw: runtime.RawPayment) runtime.PaymentMessage {
    var msg: runtime.PaymentMessage = .{ .raw = raw, .pipeline_hops = 1 };
    if (!runtime.validFraming(raw)) {
        msg.decision = .malformed_drop;
        msg.decided_by = audit_shared.tile_id_tknorm;
    } else {
        msg.event_hash = runtime.stableEventHash(raw);
    }
    return msg;
}
```

This keeps the test exercising the same pipeline stages without depending on the thread-mode loop. The test's assertions (`normalized == 1`, `invalid == 1`) need updating since the in-process state now tracks differently — replace with assertions on the event_hash and decision fields that reach downstream stages.

**Verification:** `zig build test-unit-tk` passes — the sequential pipeline test still exercises the pipeline.

### Task 3: Wire `tile_registry.zig` to stem tile for tknorm

**Goal:** Replace `tkrnormProcess` (process-mode wrapper) with stem-based dispatch.

**Current flow in `tile_registry.zig` (line 132-141):**

```zig
fn tkrnormProcess(io: std.Io, wksp: *c_abi.wksp.Wksp, spec: *const rt.launch_spec.LaunchSpec, cnc: *c_abi.cnc.Cnc, allocator: std.mem.Allocator) anyerror!void {
    if (spec.in_cnt != 1 or spec.out_cnt != 1) return error.MissingLink;
    var input = try rt.link.Consumer.join(wksp, spec.inLinks()[0]);
    defer input.leave();
    var output = try rt.link.Producer.join(wksp, spec.outLinks()[0]);
    defer output.leave();
    const cfg = try loadProcessConfig(io, spec);
    tiles.process.runNormalizeProcess(cfg, spec.fd_tile_idx, &input, &output, cnc);
}
```

This function is registered as the `process_fn` for tknorm in `tile_registry.zig:198`. The `tile_run.c` dispatch (`TKNORM_RUN`) is already wired and calls `stem_run()` directly from the C shim.

**The question is how the Zig registry should route to the stem tile.** Looking at the existing pattern:

- `tile_process.zig` calls `c_abi.topo_run.runTileSimple(...)` which invokes `tk_topo_run_tile_simple()` in `tile_run.c`
- `tk_topo_run_tile_simple()` dispatches to `TKNORM_RUN` based on `tile_is_normalize()` — this happens at the C level
- The Zig `process_fn` is the Zig callback that runs BEFORE `tile_process.zig`'s dispatch to C

**Current understanding:** The `process_fn` in `tile_registry.zig` is called by `tile_process.zig` to set up tile-specific state. For stem tiles, the C shim owns the run loop entirely. The `process_fn` should be a no-op (or minimal setup) because `tile_run.c` handles the dispatch.

**For tknorm specifically:** The stem tile's `tknorm_privileged_init` and `tknorm_unprivileged_init` are called by `fd_topo_run_tile()` before `stem_run()`. These set up the context, workspace pointers, and CNC. No Zig-side setup is needed.

**Change to `tile_registry.zig`:**

```zig
// Replace tkrnormProcess with a no-op or minimal setup:
fn tkrnormProcess(io: std.Io, wksp: *c_abi.wksp.Wksp, spec: *const rt.launch_spec.LaunchSpec, cnc: *c_abi.cnc.Cnc, allocator: std.mem.Allocator) anyerror!void {
    // tknorm is stem-driven. tile_run.c dispatches to TKNORM_RUN
    // which calls stem_run() directly. No Zig-side setup needed.
    _ = io;
    _ = wksp;
    _ = spec;
    _ = cnc;
    _ = allocator;
}
```

**Verification:** The build compiles. The integration tests (`test_norm_stem_tile.zig`) must pass — this confirms the stem tile runs correctly.

**Risk:** This changes the runtime path for tknorm. Before: Zig `tkrnormProcess` → `runNormalizeProcess` → process-mode while loop. After: `tile_run.c` dispatch → `TKNORM_RUN` → `stem_run()` → C callbacks. The integration tests are the gate.

## Risks and Mitigations

1. **Sequential test breakage:** `mod.zig`'s `runOneSequentialForTest` calls `runNormalize(state)` which is being removed. **Mitigation:** Replace with inline normalization (Task 2) so the test still exercises the pipeline stages.

2. **Hash parity:** The C stem tile's inline FNV-1a must match Zig's `stableEventHash`. If the C hash is wrong, downstream dedupe will see different hashes. **Mitigation:** `stem_norm_unit.zig` already verifies FNV-1a determinism. A separate parity test with Zig's `stableEventHash` is a follow-up if needed.

3. **Framing validation difference:** The C inline check (currency A-Z, account_id > 0) may differ from Zig's `validFraming` (which also checks `malformed` flag and specific currency strings like "USD"). **Mitigation:** Verify against the same fixture events used by the Zig unit test. If the C check is more permissive (allows more currencies), this is intentional — the C tile focuses on structural validity; semantic validation (specific currency strings) is a downstream concern.

4. **Backward compatibility:** On non-Linux targets, tknorm falls back to `TK_TILE_RUN` (WorkFn path). The WorkFn dispatches to `tkrnormProcess` which still exists until Task 4-5. **Risk:** The non-Linux path will break after Tasks 4-5. **Mitigation:** Keep the process-mode code until non-Linux support is explicitly dropped, or gate the removal with `#if FD_HAS_LINUX` — but this adds complexity. **Better approach:** Execute the removal only after confirming non-Linux targets are not in scope for the current release.
