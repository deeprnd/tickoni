# Plan: Replace hand-tuned AES-GCM assembly (.S files) with OpenSSL EVP

**Story:** v2.10-s2-5
**Status:** Draft
**Created:** 2025-08-09
**Updated:** 2025-08-09
**Story:** V2.10.S2

---

## Problem

AES-GCM is implemented via hand-tuned x86_64 assembly (`.S`) files compiled by the Makefile path (`Local.mk`), not by `build.zig`. The assembly files were copied from the Linux kernel (`arch/x86/crypto/`) and heavily modified over 15+ commits to fix cross-platform issues (`.cfi_*` guards, rodata sections, macro fixes, IBT/SHSTK, pointer alias fixes). The result is:

- **Maintenance burden:** 2,500+ lines of assembly requiring platform-specific preprocessor guards, custom macro systems (`FD_IMM_XXX`, `SYM_FUNC_START/END`, `GNU_TYPE/ALIGN/SIZE`), and per-platform section directives (`.rodata` on Linux vs `__TEXT,__const` on macOS).
- **Link-time fragility:** The Linux `.S` files emit DWARF CFI unwind tables (`.eh_frame`) that can OOM the linker under low memory — a real CI failure mode. macOS avoids this because CFI directives are no-ops.
- **Build path mismatch:** `build.zig` has zero references to `aes_gcm` or `.S` files — they don't exist in the Zig build. OpenSSL is already vendored (3.6.2) and installed via `contrib/setup/helpers/deps.sh`, and already used by 70+ files via `#if FD_HAS_OPENSSL` guards — but `FD_HAS_OPENSSL` is only defined in `config/extra/with-openssl.mk` (Makefile), never wired into `build.zig`.
- **No audit advantage:** The `.S` files are Google-authored (Eric Biggers) and are the same code OpenSSL uses internally on x86. We've already edited them through 15+ commits — the "small audit surface" argument is gone.

---

## Product Outcome

AES-GCM is implemented via OpenSSL's EVP API behind a thin wrapper that exposes the exact same public API (`fd_aes_128_gcm_init`, `fd_aes_gcm_encrypt`, `fd_aes_gcm_decrypt`). The hand-tuned assembly files are removed. All callers continue to work without changes. The AES-GCM code is compiled by both `build.zig` (via `-lcrypto`) and the Makefile (via `with-openssl.mk`).

## Implementation

### Phase 1: Add OpenSSL detection to build.zig and define FD_HAS_OPENSSL

1. **Add `FD_HAS_OPENSSL` default to `src/util/fd_util_base.h`**
   - Add `#define FD_HAS_OPENSSL 0` after the other `FD_HAS_*` defaults (~line 228).
   - This ensures any code that does `#if FD_HAS_OPENSSL` compiles without error even when OpenSSL isn't detected.

2. **Wire `FD_HAS_OPENSSL=1` into `build.zig`'s `shimCFlagsFor()`**
   - On x86_64 Linux/macOS: add `-DFD_HAS_OPENSSL=1` to the shim cflags.
   - On Windows x86_64: same.
   - On non-x86 platforms: keep as 0 (OpenSSL works but we don't need the AES-GCM dispatch there; the fallback ref path handles it).
   - This is the simplest path: unconditionally enable OpenSSL if the compiler has access to `<openssl/evp.h>` and `-lcrypto`.

3. **Add OpenSSL include path and `-lcrypto` linking**
   - In `build.zig`, add `step.addCSourceFile(.{ .file = .{ .path = "src/ballet/aes/fd_aes_gcm_ossl.c" }, .flags = &.{} });` to the module compilation.
   - Add OpenSSL include: `step.addIncludePath(.{ .path = prefix + "/include" })` where prefix comes from `FD_PREFIX` env var or system path.
   - Add library: `step.linkLibC(); step.linkSystemLibrary("crypto");` — `linkSystemLibrary` handles `-lcrypto` and searches standard paths.
   - For the vendored OpenSSL (installed to `$PREFIX`), check `$PREFIX/lib` and `$PREFIX/include` first.

4. **Verify detection works**
   - `zig build` should succeed with OpenSSL linked.
   - If OpenSSL isn't available at system path, fall back to `FD_PREFIX` env var or error clearly.

### Phase 2: Write the EVP wrapper

Create `src/ballet/aes/fd_aes_gcm_ossl.c` implementing the three public functions:

```c
// fd_aes_gcm_ossl.c — OpenSSL EVP wrapper for AES-GCM

#include "fd_aes_gcm.h"

#if FD_HAS_OPENSSL

#include <openssl/evp.h>
#include <openssl/err.h>
#include <string.h>

struct fd_aes_gcm_ossl {
    EVP_CIPHER_CTX *ctx;
};

void
fd_aes_128_gcm_init(fd_aes_gcm_t *aes_gcm,
                    uchar const    key[16],
                    uchar const    iv[12])
{
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    FD_TEST(ctx);

    int ok = EVP_EncryptInit_ex(ctx, EVP_aes_128_gcm(), NULL, NULL, NULL);
    FD_TEST(ok);

    // Set IV length (12 bytes for GCM)
    ok = EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);
    FD_TEST(ok);

    // Set key
    ok = EVP_EncryptInit_ex(ctx, NULL, NULL, key, iv);
    FD_TEST(ok);

    aes_gcm->ctx = ctx;
}

void
fd_aes_gcm_encrypt(fd_aes_gcm_t *aes_gcm,
                   uchar *        c,
                   uchar const *  p,
                   ulong          sz,
                   uchar const *  aad,
                   ulong          aad_sz,
                   uchar          tag[16])
{
    EVP_CIPHER_CTX *ctx = aes_gcm->ctx;
    int outlen = 0;
    int taglen = 16;

    // Process AAD first
    if (aad && aad_sz) {
        int ok = EVP_EncryptUpdate(ctx, NULL, &outlen, aad, (int)aad_sz);
        FD_TEST(ok);
    }

    // Encrypt data
    if (sz) {
        int ok = EVP_EncryptUpdate(ctx, c, &outlen, p, (int)sz);
        FD_TEST(ok);
    }

    // Finalize — writes the authentication tag
    int ok = EVP_EncryptFinal_ex(ctx, c + outlen, &outlen);
    FD_TEST(ok);

    // Retrieve the tag
    ok = EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);
    FD_TEST(ok);
}

int
fd_aes_gcm_decrypt(fd_aes_gcm_t *aes_gcm,
                   uchar const *  c,
                   uchar *        p,
                   ulong          sz,
                   uchar const *  aad,
                   ulong          aad_sz,
                   uchar const    tag[16])
{
    EVP_CIPHER_CTX *ctx = aes_gcm->ctx;
    int outlen = 0;
    int ok;

    // Set expected tag BEFORE finalizing
    ok = EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_TAG, 16, (void *)tag);
    FD_TEST(ok);

    // Process AAD first
    if (aad && aad_sz) {
        ok = EVP_DecryptUpdate(ctx, NULL, &outlen, aad, (int)aad_sz);
        FD_TEST(ok);
    }

    // Decrypt data
    if (sz) {
        ok = EVP_DecryptUpdate(ctx, p, &outlen, c, (int)sz);
        FD_TEST(ok);
    }

    // Finalize — verifies the tag
    // Returns 1 if tag matches, 0 if authentication fails
    ok = EVP_DecryptFinal_ex(ctx, p + outlen, &outlen);
    return ok;
}

#endif /* FD_HAS_OPENSSL */
```

Key design decisions:
- **Opaque struct:** `struct fd_aes_gcm_ossl { EVP_CIPHER_CTX *ctx; }` — callers don't see EVP internals.
- **FD_TEST macros:** Fail loudly on EVP errors (they shouldn't happen with correct inputs).
- **Tag placement:** Encrypt writes tag to `tag[16]` output parameter; decrypt compares against `tag[16]` input parameter — matches the existing API contract.
- **No AAD in the data buffer:** AAD is processed via `EVP_EncryptUpdate`/`EVP_DecryptUpdate` with a NULL output buffer, which is the correct EVP pattern for GCM AAD.
- **No memset of the struct:** The struct only holds a pointer; `EVP_CIPHER_CTX_free()` is called in a future cleanup function (or callers can just leak it since `EVP_CIPHER_CTX` is per-packet and short-lived).

## Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| OpenSSL EVP API behaves differently than the .S files on edge cases | **Low** | EVP AES-GCM is FIPS-published (NIST SP 800-38D). The test fixtures from `test_aes.c` (imported from OpenSSL's own test vectors) will verify parity. |
| `linkSystemLibrary("crypto")` fails on CI runners without OpenSSL | **Medium** | OpenSSL is already vendored via `contrib/setup/helpers/deps.sh` to `$PREFIX`. Add `$PREFIX/lib` and `$PREFIX/include` to the build.zig module. If neither system nor prefix path works, error clearly with instructions. |
| EVP context cleanup (memory leak) | **Low** | AES-GCM in this codebase is used for QUIC retry tokens and packet protection — per-packet contexts that are stack-allocated (`fd_aes_gcm_t aes_gcm[1]`). Leaking `EVP_CIPHER_CTX` per packet is a small concern for high-throughput paths, but AES-GCM here is used for auth tokens (retry tokens, packet protection keys), not in the TPS hot loop. Acceptable for now; add cleanup if profiling shows it matters. |
| `FD_HAS_OPENSSL` not detected on macOS (no AVX10 anyway) | **None** | OpenSSL on macOS (via brew or vendored install) provides the same EVP API. Apple Silicon Macs get EVP AES-GCM which uses ARM NEON crypto instructions under the hood. |
| Windows OpenSSL path differs | **Low** | OpenSSL 3.x on Windows (via MSYS2/MinGW or prebuilt) places headers in `include/openssl/` and library as `libcrypto.a`/`crypto.lib`. `linkSystemLibrary("crypto")` handles this. The vendored install to `$PREFIX` provides consistent paths. |
| ABI mismatch between EVP and existing struct usage | **None** | The struct is opaque (`fd_aes_gcm_t` is typedef'd). Callers don't access struct fields. `sizeof(fd_aes_gcm_t)` may differ (EVP context pointer vs ~500 bytes of state), but callers use `fd_aes_gcm_t aes_gcm[1]` (stack allocation with sizeof), so it adapts automatically. |

## What This Does NOT Change

- **Public API:** `fd_aes_128_gcm_init`, `fd_aes_gcm_encrypt`, `fd_aes_gcm_decrypt` — all signatures unchanged.
- **Call sites:** QUIC retry tokens, QUIC packet protection — zero caller changes.
- **OpenSSL elsewhere:** `fd_openssl.h/c` (BIO/SSL helpers), event encryption, bundle encryption, gRPC, TLS — all unchanged.
- **Build orchestration:** `just` recipes, CI workflows — no changes needed (same `just build-tk` commands).
- **Firedancer infrastructure tiles:** The TPS-critical path (tango queues, workspace, topology) doesn't use AES-GCM.
- **Other ballet crypto:** SHA-256, SHA-512, Blake3, ChaCha, Ed25519, Reed-Solomon — untouched.

## Why This Order

1. **Build wiring first** — if OpenSSL can't be linked, there's nothing to wrap. Get the dependency working before writing code.
2. **EVP wrapper second** — the wrapper is the only new code. It's a straightforward 1:1 mapping of the 3 public functions.
3. **Header update third** — replace the macro dispatch with the OpenSSL branch. This is the "seam" where the old and new implementations diverge.
4. **Tests fourth** — the same tests pass with EVP because the API is identical and the vectors are OpenSSL's own.
5. **Cleanup last** — delete the old files only after verification passes. This ensures a revert path exists if something breaks.

## Post-Implementation Notes

- **Performance:** EVP has a tiny per-call overhead vs. inline `.S` due to function indirection and context setup. For QUIC retry tokens (rare) and packet protection (moderate), this is negligible. If profiling shows it matters in a hot path, consider keeping the AESNI backend for the hot path and using EVP only for the non-critical paths. But the hot path in Firedancer/Tickoni is the tango queue poll loop, which doesn't call AES-GCM at all.
- **Future:** If the project wants to drop OpenSSL entirely in the future (to reduce attack surface), the refactoring is reversible: the wrapper becomes a thin layer over the reference C implementation, and the assembly files can be restored. The API stays the same either way.
- **Security:** EVP AES-GCM is the same algorithm the `.S` files implement (both copied from Google/Linux kernel code). There is no security regression — OpenSSL's EVP layer is more battle-tested than our hand-edited assembly.
