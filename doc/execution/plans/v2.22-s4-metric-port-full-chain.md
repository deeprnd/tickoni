### 6. Port counter helper for integration tests

All integration tests that start the process pipeline share the default port 7999. When tests run in parallel or back-to-back (especially on CI where TIME_WAIT can linger), this causes `EADDRINUSE` on the metric tile's HTTP server.

**Create a shared helper in each integration test file:**

A static global counter that auto-increments, starting at 7999. Each test that calls `startPaymentPipelineProcess` (or any function that builds a topology with tkmetr) gets a distinct port.

```zig
// Per-file static counter — auto-increments on each call, starting at 7999.
// Each integration test file gets its own counter because the module is
// compiled separately.  7999 is the Firedancer default; incrementing
// avoids EADDRINUSE when tests run in parallel or back-to-back with
// TIME_WAIT sockets from previous runs.
fn metricPort() u16 {
    const counter = staticCounter();
    return counter;
}

var _metric_port_counter: u16 = 7999;
fn staticCounter() u16 {
    const result = _metric_port_counter;
    _metric_port_counter += 1;
    return result;
}
```

## Risks

- Version bump to TopologySpec v2: any stale topology.spec files from prior builds will be rejected at runtime. Since these files live under the supervisor's run directory and are rewritten every boot, this is safe.
- Adding a field to TopologySpec changes `@sizeOf(TopologySpec)` by 2 bytes. The `readFromFile()` length check (`n != @sizeOf(TopologySpec)`) will catch truncated v1 files correctly (they'll be shorter).
- Static counters in each integration test file mean the counter state is per-module, not global across files. This is correct — each file is a separate test binary compilation unit, so they never share state. The counter starts at 7999 in each file, meaning two tests in different files could collide if run in parallel. If that becomes an issue later, use a file-unique offset (e.g., 7900 + file_number) instead of a flat increment.
