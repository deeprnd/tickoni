# s8.1.4: Consolidate SHA/minisign keys into tool-versions.json

## Problem

- `zig-minisign` is a standalone entry under `versions` in `tool-versions.json`. It is not a version — it is a static verification key. The zig tool entry references it via `version_ref_sig: "zig-minisign"`, creating an indirect cross-reference.
- llama.cpp download metadata (version, SHA256, filename, extract_dir, server_bin, base_url) lives in `build-config.json`, not in `tool-versions.json`. The setup install strategy reads it from `build-config.json` at runtime, while the version is declared in `tool-versions.json`. This means two files must be kept in sync.
- Both issues violate the principle that `tool-versions.json` is the single source of truth for tool versions and their verification data.

## Goal

Move all verification material (minisign keys, SHA256 checksums) into `contrib/setup/tool-versions.json` under each tool's `"options"` sub-object, keyed by platform where applicable. Remove `zig-minisign` as a top-level version entry. Remove llama.cpp's dependency on `build-config.json` for checksums.

Then normalize the entire file so every `versions` entry has a uniform shape, no bare strings, no cross-referencing between entries, and all platform-specific metadata is explicit.

## Normalization rules (industry standard)

### Rule 1: Every version entry is an object — no bare strings

Current file has `"zig": "0.17.0-dev.1941+71115f0ab"` (string) alongside `"openssl": {"version": "...", "tag": "..."}` (object). This is type-inconsistent — the same key position holds different types.

**Fix:** Every `versions.<name>` is `{version: "string"}`. Simple versions: `{version: "1.58.0"}`. Complex versions: `{version: "...", options: {...}}`.

**Never:** `"zig": "0.17.0"` (bare string). **Always:** `"zig": {"version": "0.17.0"}`.

### Rule 2: Platform-specific data goes in `options`

If a tool has per-platform variants (SHA256, gcc version, filename, extract_dir), they all live under `versions.<tool>.options` as a flat object keyed by platform:

```json
"options": {
    "linux-x86": {"sha256": "...", "filename": "..."},
    "linux-arm": {"sha256": "...", "filename": "..."}
}
```

This avoids nested `artifacts` maps inside a separate file (`build-config.json`).

### Rule 3: Verification material belongs with versions

minisign keys, SHA256 checksums, GPG keys — these are properties of the *artifact*, not a separate tool. They go under the version entry's `options`, not as standalone version entries.

### Rule 4: No cross-referencing between version entries

`version_ref_sig: "zig-minisign"` creates an indirect pointer from one version entry to another. This is fragile — renames break it, editors can't follow it, and it violates single-responsibility (the zig version entry owns its verification data).

### Rule 5: `build-config.json` and `tool-versions.json` do not duplicate

`build-config.json` serves two unrelated purposes — but only one belongs in `tool-versions.json`:

**Build-system fields (stay in `build-config.json`):**
- `targets` — lib/obj directory paths for `contrib/build/orchestrator.py`
- `platforms` — compiler names per platform (e.g. `"gcc-12"`, `"clang-18"`) used at build time, passed to `make CC=...`
- `libs` — library archive names to build
- `source_sets` — source directories to compile
- `excludes` — path exclusion regex

These are all consumed by `contrib/build/orchestrator.py` only. They have nothing to do with tool installation or version pinning.

**Install-system fields (move to `tool-versions.json`):**
- `llama_cpp.version` — download version tag
- `llama_cpp.artifacts` — per-platform SHA256, filename, extract_dir, server_bin
- `llama_cpp.base_url` — download URL template
- `llama_cpp.install_dir` — where to extract

After migration, `build-config.json` keeps only the build-system fields above. The `llama_cpp` block is removed entirely.

### Rule 6: `versions` and `tools` are separate concerns

- `versions.<name>` = what version, what verification data (SHA256, minisign key, tag)
- `tools.<name>` = how to install (install_method, parameters, idempotent_check, version_ref)
- `tools.<name>.version_ref` = the key into `versions` (always matches the versions key)
- `tools.<name>.parameters.version_ref` = the same key (redundant but backward compat)

### Rule 7: Stable, dash-free version keys

Version keys are tool identifiers: `zig`, `llama-cpp`, `openssl`. They must match between `versions.<key>` and `tools.<key>.version_ref`. No derived keys like `zig-minisign` or `zig-sig`.

Key changes from the current file:

1. **`zig`** — was a bare string, now an object with `options.minisign_key`. No separate `zig-minisign` entry.
2. **`llama-cpp`** — was a bare string, now an object with `options.sha256` (per-platform), `options.filename`, `options.extract_dir`, `options.server_bin` (all per-platform). This replaces the `artifacts` map in `build-config.json`.
3. **`gcc`, `clang`, `msvc`** — were objects with platform keys directly under them, now wrapped in `options` for consistency. The `version` field says `"multi"` to signal per-platform dispatch.
4. **`openssl`** — already an object, now has `version` + `options.tag` (the `tag` was at the same level as `version` before; the `version` field keeps the semver for `resolve_version`).
5. **`zig-minisign`** — removed entirely. Its key is now `versions.zig.options.minisign_key`.

### What `resolve_version` must support after normalization

```python
def resolve_version(config, version_ref):
    entry = config['versions'].get(version_ref, {})
    if isinstance(entry, str):
        return entry
    return entry.get('version', '')
```

This works for all entries: bare strings (legacy fallback), simple objects (`{"version": "x.y"}`), and complex objects (`{"version": "...", "options": {...}}`).

### What `tools` looks like (unchanged except zig)

The `tools` block stays as-is — it describes *how* to install. Only `tools.zig` changes: remove `version_ref_sig`.

```json
"tools": {
    "zig": {
        "category": "zig",
        "platform": "all",
        "install_method": "install_zig",
        "parameters": {
            "install_root": "$HOME/.local"
        },
        "idempotent_check": "command -v zig",
        "version_ref": "zig"
    }
}
```

Note: `version_ref` moved from `parameters.version_ref` to `tools.zig.version_ref` at the tool level (but keep `parameters.version_ref` for backward compat with existing orchestrator code that reads from there).

## Step-by-step

### Step 0: Audit consumers before touching anything ✅ DONE

Audit complete. Consumers:
- `build-config.json`: read by `orchestrator.py` (only `targets`/`platforms`/`libs`/`source_sets`/`excludes` — never `llama_cpp`) and `llama_cpp_download.py` (reads `llama_cpp`). Safe to remove `llama_cpp` block.
- `version_ref_sig`: only used in `resolver.py` (propagation) and `zig.py` (key resolution). Safe to remove.
- `resolve_version`: called by many strategies, already handles both bare strings and objects. Already backward-compatible.

### Step 1: Restructure `tool-versions.json`

Rewrite the entire `versions` block to the normalized shape. Do it as a full rewrite (not patches) to guarantee consistency:

1. **Every entry is an object.** No bare strings. `versions.zig` becomes `{version: "0.17.0-dev.1941+71115f0ab", options: {minisign_key: "RWSGOq2NVecA2UPNdBUZykf1CCb147pkmdtYxgb3Ti+JO/wCYvhbAb/U"}}`.
2. **Remove `zig-minisign` entirely.** Its key is now `versions.zig.options.minisign_key`.
3. **Normalize `gcc`, `clang`, `msvc`.** They currently have platform keys directly under the version object. Wrap them: `{version: "multi", options: {"linux-x86": "12", ...}}`.
4. **Normalize `openssl`.** It already has `version` + `tag` at the same level. Keep `version` for `resolve_version`, move `tag` into `options`.
5. **Move llama.cpp from build-config.json.** Copy `llama_cpp.version`, `llama_cpp.artifacts` (SHA256, filename, extract_dir, server_bin) into `versions.llama-cpp`. Flatten the artifacts map into `options.sha256`, `options.filename`, `options.extract_dir`, `options.server_bin`, all keyed by platform.
6. **The `tools` block.** Remove `version_ref_sig` from `tools.zig`. Add `version_ref` at the `tools.zig` level (not just in parameters) for forward compat.

Write a Python script to do this, then validate with `python3 -m json.tool`.

**Do not write the JSON by hand** — write a migration script that reads the current file, applies transformations, and outputs the new file. This ensures nothing is dropped.

### Step 2: Update `zig.py`

Replace the `_get_minisign_pubkey` method:

```python
def _get_minisign_pubkey(self, config: dict) -> str:
    """Read minisign key from versions.<version_ref>.options.minisign_key."""
    version_ref = self._tool.get('parameters', {}).get('version_ref')
    if not version_ref:
        return ''
    version_entry = config.get('versions', {}).get(version_ref, {})
    if isinstance(version_entry, str):
        # Legacy: bare string version with top-level zig-minisign (backward compat)
        zig_minisign = config.get('versions', {}).get('zig-minisign')
        if isinstance(zig_minisign, dict):
            return zig_minisign.get('key', '')
        return str(zig_minisign or '')
    options = version_entry.get('options', {})
    return options.get('minisign_key', '')
```

- This preserves backward compat if someone still has the old shape.
- Remove the `version_ref_sig` fallback path — it is no longer needed once all consumers use the new shape.

### Step 3: Update `llama_cpp_download.py`

Replace `_resolve_from_config()` to read **everything** from `tool-versions.json` — no more `build-config.json` reads:

```python
@staticmethod
def _resolve_from_config(platform_str: str, config: dict) -> dict:
    """Read artifact metadata from tool-versions.json."""
    llama_entry = config.get('versions', {}).get('llama-cpp', {})
    if isinstance(llama_entry, str):
        sha256 = None
        filename = None
        extract_dir = '.'
        server_bin = 'llama-server'
    else:
        options = llama_entry.get('options', {})
        sha256 = options.get('sha256', {}).get(platform_str)
        filename = options.get('filename', {}).get(platform_str)
        extract_dir = options.get('extract_dir', {}).get(platform_str, '.')
        server_bin = options.get('server_bin', {}).get(platform_str, 'llama-server')

    if filename is None:
        print(f"ERROR: no llama.cpp filename for platform {platform_str}", file=sys.stderr)
        sys.exit(1)

    return {
        'sha256': sha256,
        'filename': filename,
        'extract_dir': extract_dir,
        'server_bin': server_bin,
    }
```

Update `execute()` to:
1. Remove the `Path(__file__).../build-config.json` read entirely.
2. Pass `config` to `_resolve_from_config`.
3. Build the URL from `base_url` (now read from `tool-versions.json` options or passed as a parameter).
4. Use `resolved['filename']` instead of reading from the artifact dict.

### Step 4: Clean up `build-config.json`

Remove the `llama_cpp` block entirely from `build-config.json`. Before deleting, confirm no non-setup code reads it:

```bash
grep -r 'build-config.json' --include='*.py' --include='*.zig' --include='*.sh' --include='*.mk' . | grep -v 'contrib/setup'
```

If grep returns nothing (no non-setup consumers), delete the `llama_cpp` block. Keep `targets`, `platforms`, `libs`, `source_sets`, `excludes` only if the build system (not setup scripts) reads them.
