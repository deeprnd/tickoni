# Plan: Integrate tkmetr as a Tickoni fd_stem Tile

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Integrate `tkmetr` (metric tile) as a native Tickoni fd_stem tile, following the pattern established by the Firedancer `fd_metric_tile.c` — using `fd_http_server` and Prometheus metrics output. This closes the architectural gap between Tickoni's current console-only sampling (in `src/tickoni/tiles/payment_pipeline/metric.zig`) and Firedancer's real-time `/metrics` HTTP endpoint.

**Architecture:** tkmetr is already a registered tile in `tile_registry.zig` (idx 6) with a thread-mode `runMetric` function in `metric.zig`. The fd_stem migration (v2.22-s5) scaffolding already exists: `tkmetr` will register 5 fd_stem callbacks (before_credit, during_frag, after_credit, metrics_write, should_shutdown). On Linux, fd_stem calls `before_credit` → `fd_http_server_poll` → serves `/metrics` → writes counters via `metrics_write`. On macOS/Windows, tkmetr keeps using the existing thread-mode polling loop.

**Tech Stack:** Zig, Firedancer `fd_http_server`, fd_stem callbacks, Prometheus text format (via `fd_prometheus.h`).

## Architecture

```
Linux:
  tile_run.c → tk_stem_run() → fd_stem loop
    → tkmetr before_credit: fd_http_server_poll(ctx->metrics_server, 1ms)
    → if /metrics request: fd_prometheus_render_all(ctx->topo, ctx->metrics_server)
    → tkmetr metrics_write: write TileMetricSnapshot counters to Prometheus metrics
    → heartbeat/halt loop

macOS/Windows:
  tile_run.c → tk_tile_run() → g_ctx.work()
    → metric.runMetric() — existing polling loop (no change)
    → reads state.snapshotMetrics(), prints deltas to stderr
```

**Key decision:** tkmetr does NOT need a separate process-mode spawn. It's a 0-input/0-output tile that doesn't participate in the data pipeline. It can run as a thread within the supervisor's main process (current behavior) or as a standalone process (future option). The fd_stem callbacks handle the Linux path; the existing thread-mode runner handles macOS/Windows.

## Task 1: Add `fd_http_server` and `fd_prometheus.h` Zig bindings

**File:** `src/tickoni/c_abi/fd_http.zig` (new) or extend existing `c_abi` module

**Objective:** Create Zig bindings for Firedancer's `fd_http_server` and `fd_prometheus` C APIs, so the tkmetr fd_stem callbacks can call them.

**Step 1: Examine Firedancer's C API**

Review `src/waltz/http/fd_http_server.h` and `src/util/fd_prometheus.h` to understand the public interface:

- `fd_http_server_new()`, `fd_http_server_join()`, `fd_http_server_listen()`
- `fd_http_server_poll()` — returns non-zero if there are pending requests
- `fd_http_server_request_t` — contains path, method, ctx pointer
- `fd_http_server_response_t` — status, content_type
- `fd_prometheus_render_all()` — renders all registered metrics to HTTP response body
- `fd_prometheus_register_*()` — register metric names for tracking

**Step 2: Create Zig bindings**

```zig
const std = @import("std");

extern fn fd_http_server_new(params: *anyopaque, callbacks: *anyopaque, ctx: *anyopaque) *anyopaque;
extern fn fd_http_server_join(server: *anyopaque) *anyopaque;
extern fn fd_http_server_listen(server: *anyopaque, addr: u32, port: u16) void;
extern fn fd_http_server_poll(server: *anyopaque, timeout_ms: c_int) c_int;
extern fn fd_prometheus_render_all(topo: *anyopaque, server: *anyopaque) void;

// Bindings for the metric tile context
pub const HttpServer = struct {
    ptr: *anyopaque,

    pub fn poll(self: *HttpServer, timeout_ms: c_int) c_int {
        return fd_http_server_poll(self.ptr, timeout_ms);
    }
};
```

## Integration Notes

This plan intentionally **does not** create a separate shared memory metrics area (unlike the old v2.22-s4-metrics-tile.md). Instead:

1. tkmetr reuses the existing `TileMetricSnapshot` from `metric_watchdog.zig` and the per-tile counters already tracked via cnc app-region counters
2. The fd_stem `metrics_write` callback reads these counters and writes to Prometheus
3. No new shared memory layout is needed — tkmetr reads from the same counters the supervisor's `snapshotProcessMetrics()` reads

This keeps the integration minimal and avoids the complexity of a parallel metrics subsystem.

---

## Architecture Decision: Thread-mode vs fd_stem

tkmetr can run in two modes:
- **Thread-mode (macOS/Windows):** `metric.runMetric()` polling loop — reads counters every ~100ms, prints deltas
- **fd_stem (Linux):** `before_credit` → `fd_http_server_poll` → serves `/metrics` on-demand

The thread-mode mode is simpler and works today. The fd_stem mode is the target for Linux — it follows Firedancer's `fd_metric_tile.c` pattern exactly. Both modes serve the same purpose: making Tickoni's metrics visible during execution.
