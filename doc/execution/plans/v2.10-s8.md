Yes. GitHub Actions already supports the model you want; there is no need to introduce Jenkins/Buildkite/etc. yet. The main change should be to stop treating **duration as workflow taxonomy** and instead model CI as a **fan-out / fan-in staged DAG**.

The current repo has already reached the point where `short/long/xlong` is misleading: `tests-short.yml` contains unit tests, system tests, demos, and cross-platform conformance, while `tests-xlong.yml` contains system/E2E work.   And your existing `demo-conformance-compare` is effectively a manually written fan-in barrier over seven platform jobs already.

### I would move Tickoni to this conceptual pipeline

```text
                    ┌─ linux
                    ├─ macOS 15 x64
                    ├─ macOS 15 arm64
QUALITY ──> BUILD ──┼─ macOS 26 x64
                    ├─ macOS 26 arm64
                    ├─ Windows x64
                    └─ Windows arm64
                         │
                         │ all builds succeeded
                         ▼
                       UNIT
                    [same matrix]
                         │
                         │ all succeeded
                         ▼
                    INTEGRATION
                    [same matrix]
                         │
                         ▼
                      SYSTEM
                    [supported matrix]
                         │
                         ▼
                       DEMO
                    [same matrix]
                         │
                         ▼
                   CONFORMANCE
                 [single fan-in job]
                         │
                         ▼
                 HEAVY SECURITY
                         │
                         ▼
                    CI REQUIRED
```

GitHub's `needs` semantics provide exactly the cascading behavior: a dependent job does not run unless its prerequisite job completed successfully; failure propagates down the dependency chain. ([GitHub Docs][1])

More importantly, GitHub supports matrices as the producing stage and another matrix as the consuming stage. GitHub's own documentation shows a matrix producing artifacts followed by a second matrix with `needs: produce-artifacts`, which creates the barrier you want. ([GitHub Docs][2])

So conceptually:

```yaml
build:
  strategy:
    fail-fast: false
    matrix: ...
  ...

unit:
  needs: build
  strategy:
    fail-fast: false
    matrix: ...
  ...

integration:
  needs: unit
  strategy:
    fail-fast: false
    matrix: ...
```

The important property is:

```text
build/linux      ─┐
build/mac-x64    ─┤
build/mac-arm    ─┤
build/win-x64    ─┼── ALL SUCCESS ──> unit/* starts
build/win-arm    ─┘
```

If `build/mac-arm` fails, **no unit variant starts**.

I would deliberately set:

```yaml
strategy:
  fail-fast: false
```

within each stage. GitHub's `fail-fast: true` cancels the other matrix jobs when one member fails. ([GitHub Docs][3]) For Tickoni that is probably undesirable: if macOS fails, it is useful to discover during the same run whether Windows also fails. Let the entire current layer finish, but don't let the next layer begin.

That gives you a useful distinction:

```text
parallel within a layer
serial between layers
```

which is a standard CI DAG pattern.

## Build once, then test the artifact

There is another major improvement available here.

Right now many Tickoni test jobs rebuild the FD/Tickoni libraries themselves. For example, unit, demo, system, and conformance jobs repeatedly invoke `build-fd-tk-libs`.

Instead:

```text
build/mac-arm
    │
    └── upload artifact build-mac-arm
                     │
                     ▼
unit/mac-arm
    download build-mac-arm
```

GitHub artifacts are explicitly designed for sharing build outputs between jobs; dependent jobs can download an artifact generated earlier in the same workflow. ([GitHub Docs][4])

This is more than a performance optimization. It gives you the much stronger CI invariant:

> **The thing tested is the thing that passed the build gate.**

Rather than every stage independently reconstructing a possibly slightly different build.

Use cache for downloaded dependencies/Zig compilation acceleration; use **artifacts for correctness handoff**. Those are different concepts.

For example:

```text
build-linux-x64.tar
build-macos15-x64.tar
build-macos15-arm64.tar
...
```

Only package the binaries/libraries/runtime data subsequent stages actually need, not the complete compiler cache.

## Your retry problem becomes much better

GitHub currently supports re-running an individual job, failed jobs, or the whole workflow. Its API explicitly defines rerunning a job together with its dependent jobs, and rerunning all failed jobs together with their dependents. ([GitHub Docs][5])

Suppose:

```text
BUILD
✓ linux
✓ mac15-arm
✗ mac15-x64
✓ win-x64
✓ win-arm

UNIT
skipped
```

You rerun only:

```text
build / mac15-x64
```

If it passes, the dependency graph can proceed.

You no longer get the current situation where expensive test workflows have already been running while you discover that one fundamental platform build was broken.

The same principle applies later:

```text
UNIT
✓ linux
✓ mac-arm
✗ windows-arm
✓ windows-x64
```

Integration hasn't started. You rerun the failed Windows ARM unit job rather than repeating quality/build/Linux/macOS unnecessarily.

## One platform definition, not seven copies everywhere

This is particularly important in Tickoni.

There is already platform-label drift: `build-tk.yml` uses `macos-15-intel` and `macos-26-intel` for x86_64 builds, while some x86_64 test/conformance jobs use plain `macos-15` / `macos-26`.

Don't duplicate this configuration anymore.

Have one CI planning job define something like:

```json
{
  "include": [
    {
      "id": "linux-x64",
      "runner": "ubuntu-24.04",
      "profile": "linux"
    },
    {
      "id": "macos15-x64",
      "runner": "macos-15-intel",
      "profile": "macos-x86_64"
    },
    {
      "id": "macos15-arm64",
      "runner": "macos-15",
      "profile": "macos-arm"
    },
    {
      "id": "windows-x64",
      "runner": "windows-2025-vs2026",
      "profile": "windows-x86_64"
    }
  ]
}
```

and feed that same matrix to build/unit/integration/etc.

GitHub supports defining a matrix once as output and consuming that matrix in multiple later jobs. ([GitHub Docs][2])

You can therefore have:

```text
plan
 ├── determines changed areas
 └── produces platform matrix
```

rather than every workflow knowing independently what "macOS x86_64" means.

## I would also consolidate orchestration into one workflow

Something along these lines:

```text
.github/workflows/
    ci.yml                    # ONLY PR orchestration entry point

    _ci-quality.yml           # workflow_call
    _ci-build.yml             # workflow_call
    _ci-unit.yml              # workflow_call
    _ci-integration.yml       # workflow_call
    _ci-system.yml            # workflow_call
    _ci-demo.yml              # workflow_call
    _ci-security.yml          # workflow_call

    benchmark.yml
    coverage.yml
    book.yml
```

GitHub supports calling reusable workflows from matrix jobs, and reusable-workflow callers support both `strategy` and `needs`. ([GitHub Docs][6]) GitHub explicitly documents using matrix variables when invoking reusable workflows. ([GitHub Docs][7])

Then `ci.yml` becomes the readable architecture:

```yaml
jobs:
  plan:
    ...

  quality:
    needs: plan
    uses: ./.github/workflows/_ci-quality.yml

  build:
    needs: [plan, quality]
    strategy:
      fail-fast: false
      matrix: ...
    uses: ./.github/workflows/_ci-build.yml
    with:
      platform: ${{ matrix.id }}
      runner: ${{ matrix.runner }}

  unit:
    needs: [plan, build]
    strategy:
      fail-fast: false
      matrix: ...
    uses: ./.github/workflows/_ci-unit.yml
    ...

  integration:
    needs: [plan, unit]
    ...

  system:
    needs: [plan, integration]
    ...

  demo:
    needs: [plan, system]
    ...

  conformance:
    needs: demo
    ...

  security:
    needs: conformance
    ...
```

That top-level file becomes almost a **CI architecture document**.

Reusable workflows contain implementation details. Your existing composite actions remain useful for setup/build mechanics.

## Stop using duration as the classification

I would delete the concepts:

```text
Tests / Short
Tests / Long
Tests / XLong
```

Duration should determine **sharding and scheduling**, not meaning.

Instead:

| Stage       | Meaning                                                 |
| ----------- | ------------------------------------------------------- |
| Quality     | format, lint, generated/proto consistency               |
| Build       | code compiles/links/packages                            |
| Unit        | isolated component behavior                             |
| Integration | multiple components/processes interacting               |
| System      | complete Tickoni behavior / live model / infrastructure |
| Demo        | shipped/user-visible scenarios work                     |
| Conformance | outputs agree across supported platforms                |
| Security    | sanitizers, seccomp, CodeQL/etc.                        |

Then if unit tests become 50 minutes:

```text
Unit / shard 1
Unit / shard 2
Unit / shard 3
Unit / shard 4
```

They remain **unit tests**.

That's much more stable than promoting something from short → long → xlong whenever runtime changes.

## One thing I would change in your proposed ordering

I would **not put all security last**.

Your existing `security.yml` makes this distinction implicitly already: Gitleaks is cheap and unconditional, while sanitizers are heavier.

I would make:

```text
           ┌─ quality
PREFLIGHT ─┤
           └─ secret scan / gitleaks
                  │
                  ▼
                build
                  ↓
                unit
                  ↓
             integration
                  ↓
               system
                  ↓
                demo
                  ↓
             conformance
                  ↓
        expensive security
     sanitizers / deep analysis
```

Secret leakage detection is cheap enough that there is little reason to wait potentially hours before discovering it.

Heavy sanitizer/security builds can reasonably remain at the end if the objective is avoiding expensive computation on fundamentally broken code.

## Also fix Quality

There's a slight contradiction in the current architecture: `quality.yml` currently invokes `build-fd-tk-libs` inside each of its format/lint/proto matrix jobs.

So your intended:

```text
quality -> build
```

is currently actually:

```text
build inside quality
build inside quality
build inside quality
       ↓
official build
```

I'd force Quality to be genuinely static.

Anything that requires compilation belongs in:

```text
Build
```

or possibly a compile-check subsection immediately after static quality.

That will make the stage semantics much cleaner.

## Keep a single required PR status

I would also add one final job:

```text
CI / Required
```

with:

```yaml
needs:
  - quality
  - build
  - unit
  - integration
  - system
  - demo
  - conformance
  - security

if: always()
```

and explicitly make it fail if any required stage failed/cancelled unexpectedly.

Why `always()`? Because GitHub reports skipped jobs as successful for status-check purposes, so making a naturally skipped downstream job itself your merge gate is unsafe. ([GitHub Docs][8])

Then branch protection only requires:

```text
CI / Required
```

rather than:

```text
Build/Linux
Build/mac15...
Unit/Linux
...
```

GitHub branch protection/rulesets can require named status checks, and GitHub specifically warns that required job names should be unique. ([GitHub Docs][9])

That also means adding `macOS 27` later doesn't require rethinking your branch protection configuration.

---

So for Tickoni specifically, I'd target this end state:

```text
                     PR
                      │
                    PLAN
                      │
          ┌───────────┴───────────┐
       QUALITY                 GITLEAKS
          └───────────┬───────────┘
                      ▼
               BUILD [matrix]
                      │
               UNIT [matrix]
                      │
           INTEGRATION [matrix]
                      │
             SYSTEM [matrix]
                      │
              DEMO [matrix]
                      │
          CONFORMANCE [fan-in]
                      │
         SECURITY-HEAVY [matrix]
                      │
               CI / REQUIRED
```

I would **keep `benchmark.yml`, `coverage.yml`, and `book.yml` outside this correctness DAG** unless you explicitly decide they should block merging; those are different operational lanes, not test stages. The repository already has them as separate workflows.

The strongest change here is not the YAML cleanup. It is introducing three invariants:

1. **Stages are semantic, never duration-based.**
2. **A stage is a global cross-platform barrier before the next stage.**
3. **Build artifacts are produced once per platform and promoted through the pipeline.**

That structure fits the direction Tickoni has already evolved toward, particularly the all-platform demo-conformance fan-in you have now; it generalizes that mechanism instead of manually replicating it.
