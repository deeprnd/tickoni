# Refactor: Tool-scoped setup for CI lanes

**Status:** Plan
**Created:** 2026-08-29
**Scope:** `contrib/setup/` scripts — split monolithic platform scripts into category-specific helpers, add category dispatch to `justfile`, add recursive category dependency resolution in `tool-versions.json`, update CI workflows to request only needed top-level categories.

---

## Problem Statement

Every CI lane currently installs the full developer environment through `just setup-linux-x86-gcc` or similar, which pulls in compilers, Zig, OpenSSL, quality tools, coverage tools, security tools, and ops tooling — even when a lane only needs a subset. This makes setup slow, opaque (hard to audit what a lane installs), and fragile (a change to one tool's install script can break an unrelated lane).

The setup scripts accept no parameters and unconditionally call every `ensure_*` helper in `common.sh`. There is no way for a CI lane to request "just compilers + Zig" without also getting shellcheck, actionlint, kcov, gitleaks, buf, pre-commit, OpenSSL, and PowerShell.

A related problem: language runtimes like Python, Perl, and Go are needed by multiple categories but live inside `essential` or `toolchain`. `security` needs pip (via Python) for `cbmc-viewer` and `cbmc-starter-kit`. `quality` needs pipx (via Python) for `pre-commit` and Go for `buf`. `llm-server` needs pip for `huggingface-cli`. `zig` needs python3 to run `install-zig.py`. If a CI lane picks `security` or `zig` without the language runtimes it needs, it breaks. The fix is explicit, recursive dependency resolution: each category declares which other categories it depends on, and the installation process resolves them automatically.

---

## Target State

### Principle

Every CI lane installs exactly the tools it needs, with dependencies resolved automatically. The `justfile` exposes per-category setup recipes per platform. `just setup-env` remains the developer convenience aggregator. CI workflows call the smallest explicit top-level category, and category dependencies are resolved recursively.

### Category Dependency Resolution

`contrib/setup/tool-versions.json` includes a `dependencies` object that maps each category to its required categories. When a lane requests a category, the setup process resolves all transitive dependencies before running any installers.

**Rules:**
- `dependencies` lists direct (non-recursive) category dependencies. The setup process resolves all transitive dependencies.
- `core` has no dependencies. It installs first. It contains only curl and git — the bare bootstrap tools every category needs (wget/curl for downloads, git for cloning repos, SSH, etc.).
- `essential` depends on `core`. It installs build-essential (apt), libiberty-dev, libdebuginfod-dev, libdw-dev, libelf-dev, libcurl4-openssl-dev, binutils-dev (apt), coreutils (brew), minisign.
- `build` depends on `core, essential` (build-essential provides gcc/g++ which is needed for make, cmake, etc.).
- `toolchain` depends on `core, build` (clang/gcc need build infrastructure).
- `python` depends on `core` (curl for downloading Python; python3, pipx, pip are installed by ensure_python3 on Linux via apt, by brew on macOS, by winget on Windows).
- `perl` depends on `core` (installed by ensure_perl on Linux via apt, by brew on macOS; Windows uses strawberry perl via choco/winget).
- `zig` depends on `python, core` (install-zig.py needs python3).
- `ssl` depends on `core, build` (OpenSSL build needs make, cmake).
- `fd` depends on `ssl, core, build` (snappy/rockdb need OpenSSL and build tools).
- `security` depends on `core, build, python` (CBMC debs need apt/build; cbmc-viewer and cbmc-starter-kit are pip packages).
- `quality` depends on `core, build, python, go` (shellcheck/actionlint/yamllint are system packages; pre-commit is pip; buf needs Go).
- `coverage` depends on `core, build, llvm` (kcov needs build; llvm-18 toolchain installed by llvm category).
- `secrets` depends on `core, build` (gitleaks is a binary).
- `ops` depends only on `core` (pwsh needs curl for installation).
- `go` depends on `core` (Go installer needs curl).
- `llvm` depends on `core, build` (LLVM installation on Windows/macOS may need build tools).
- `mvsc` has no dependencies (MSVC builds on a Windows system that already has git/python from the CI image).
- `llm-server` depends on `core, build, python` (llama.cpp needs build; huggingface-cli is pip).
- Circular dependencies are detected and reported as errors.
- A tool can belong to multiple categories (e.g., `ensure_gitleaks` belongs to both `secrets` and `security`). It installs once (idempotent).
- `read_packages` and `read_tool_version` are pure lookup functions — always available regardless of categories.
- `ensure_just`, `ensure_gcc`, `ensure_clang` need sudo — the category dispatch preserves this.

**Why this works:** Every CI lane only needs to specify which top-level category it cares about. The dependency resolver handles the rest. The `core` category (curl, git) sits at the base of the dependency tree so no category ever needs to pull in a dependency that transitively requires it. Language runtimes (Python, Perl, Go) are installed in their own categories; any category that needs pip, pipx, or Go-based tooling transitively depends on `python` or `go`.

### Key Design Decisions

1. **`common.sh` is the single source of truth for tool install logic.** No code duplication — each `ensure_*` function already has idempotency checks (`tool_exists`). We add two more checks: does its category appear in `$SETUP_CATEGORIES`? Is its category in the resolved set (after recursive dependency expansion)?

2. **Platform scripts call `common.sh` with a category list.** Every platform script follows the same pattern. Example — `linux-x86-python.sh`:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   SCRIPT_DIR="$(cd -- "$( dirname -- "${BASH_SOURCE[0]}" )" && pwd)"
   source "${SCRIPT_DIR}/helpers/common.sh"

   SETUP_CATEGORIES="python" bash "${SCRIPT_DIR}/helpers/common.sh"
   ```
   Example — `windows-x86-python.ps1` (PowerShell equivalent):
   ```powershell
   param([string]$Categories = "python")
   $SCRIPT_DIR = Split-Path -Parent $MyInvocation.MyCommand.Path
   . "$SCRIPT_DIR\helpers\common.sh"

   $env:SETUP_CATEGORIES = $Categories
   & "$SCRIPT_DIR\helpers\common.sh"
   ```

3. **Category dependency resolution is done before category dispatch.** The setup process reads `dependencies` from `tool-versions.json`, resolves all transitive dependencies, deduplicates, and then passes the full set to `common.sh`. A lane requesting `fd` automatically gets `ssl, build, essential, toolchain` (via toolchain → build → essential).

4. **The `justfile` maps one recipe per category per platform.** No aggregation in the justfile — each recipe is independent and auditable. `setup-env` is the only place that aggregates all categories into one recipe.

5. **CI workflows call individual top-level categories.** The dependency resolver expands them. Example: a lane that needs Zig, OpenSSL, Snappy/RocksDB just calls `just setup-linux-x86-fd` — the resolver expands `fd` → `ssl,build,core` → `core,build,python` (via build) → `core,build,essential,python`, giving `core,build,essential,python,ssl,fd`.

## Implementation Plan

### Phase 1: Add `dependencies` to `tool-versions.json`

**File:** `contrib/setup/tool-versions.json`

Add a `dependencies` object at the top level. Each key is a category name, each value is an array of direct (non-recursive) category dependencies. See the "Category Dependency Resolution" section above for the full mapping.

This is the source of truth for category dependency graph. The `justfile` and platform scripts read it at runtime.

### Phase 2: Add recursive dependency resolver to `common.sh`

**File:** `contrib/setup/helpers/common.sh`

Add a `resolve_dependencies(categories)` function that:
1. Reads `dependencies` from `tool-versions.json`
2. Starts with the input categories
3. For each category, looks up its direct dependencies and adds them
4. Repeats until no new categories are added (fixpoint)
5. Deduplicates and returns the sorted list

The function is called at the top of each platform script:
```bash
resolved="$(resolve_dependencies "$SETUP_CATEGORIES")"
export SETUP_CATEGORIES="$resolved"
```

If `$SETUP_CATEGORIES` is unset or empty, all categories are implied (preserves current behavior for direct script invocations and local dev).

### Phase 3: Modify `common.sh` to accept categories

**File:** `contrib/setup/helpers/common.sh`

Add a `$SETUP_CATEGORIES` variable (space-delimited list of category names). Every `ensure_*` function checks if its category is in the list before proceeding.

Each tool gets assigned to exactly one category:

```bash
# Category assignment table (documented at top of file):
#   essential:    ensure_build_essential, ensure_minisign,
#                 ensure_libiberty_dev, ensure_libdebuginfod_dev,
#                 ensure_libdw_dev, ensure_libelf_dev,
#                 ensure_libcurl4_openssl_dev, ensure_binutils_dev
#   build:        ensure_make, ensure_cmake, ensure_zstd, ensure_pkgconfig,
#                   ensure_ccache — Windows: ccache
#   toolchain:    ensure_just, ensure_clang, ensure_winget, ensure_choco,
#                 ensure_strawberry_perl
#   python:       ensure_python3, ensure_pipx, ensure_python3_pip
#   perl:         ensure_perl — Windows: strawberry perl (via Git for Windows)
#   mvsc:         ensure_msvc — Windows-only
#   zig:          ensure_zig
#   ssl:          ensure_openssl
#   fd:           ensure_snappy, ensure_rockdb — fd scripts call deps.sh with categories=fd
#   quality:      ensure_shellcheck, ensure_actionlint,
#                   ensure_precommit, ensure_yamllint, ensure_buf
#   secrets:      ensure_gitleaks
#   coverage:     ensure_kcov
#   security:     ensure_cbmc_toolchain
#   ops:          ensure_pwsh
#   go:           ensure_go (installed transitively via ensure_buf)
#   llvm:         ensure_llvm (Windows/macOS; winget/brew)
#   llm-server:   ensure_llama_cpp, ensure_openblas, ensure_ccache,
#                   ensure_winlibs, ensure_huggingface_cli — Windows LLM server toolchain
```

**Rules:**
- If `$SETUP_CATEGORIES` is unset or empty, all categories are implied (preserves current behavior for direct script invocations and local dev).
- If `$SETUP_CATEGORIES` is set, only tools whose category appears in the list are installed.
- A tool can belong to multiple categories (e.g., `ensure_gitleaks` belongs to both `secrets` and `security`). It installs once (idempotent).
- `read_packages` and `read_tool_version` are pure lookup functions — always available regardless of categories.
- `ensure_just`, `ensure_gcc`, `ensure_clang` need sudo — the category dispatch preserves this.

**Implementation approach:** Each `ensure_*` function gets a `TOOL_CATEGORY` variable at the top. The function wraps its logic in:
```bash
if [ -n "${SETUP_CATEGORIES:-}" ]; then
    category_found=false
    for cat in $SETUP_CATEGORIES; do
        if [ "$cat" = "$TOOL_CATEGORY" ]; then
            category_found=true; break
        fi
    done
    if [ "$category_found" = false ]; then
        log_info "${TOOL}: not requested (${SETUP_CATEGORIES})"
        return 0
    fi
fi
```

### Phase 4: Create category-specific platform scripts

For each platform and each category, create a new script that sets `SETUP_CATEGORIES` and delegates to `common.sh`. Quality, coverage, security, and secrets are **linux-x86-only** (shellcheck, gitleaks, CBMC, kcov don't run on macOS/Windows/linux-arm). Windows also needs `mvsc` scripts.

All platform scripts follow the same delegation pattern — same variable name (`SETUP_CATEGORIES`), same invocation of `common.sh`, same directory layout. Only the file extension differs (`.sh` for Unix, `.ps1` for Windows).

### Phase 7: Update composite action `setup-public-gh-runner`

**File:** `.github/actions/setup-public-gh-runner/action.yml`

The current action takes a single `setup-recipe` parameter and calls `just "$SETUP_RECIPE"`. This needs to change to accept a list of top-level categories. The dependency resolver handles expansion.

**New inputs:**
```yaml
inputs:
  categories:
    description: Comma-separated list of just setup category recipes to run
    required: true
  fd-deps-recipe:
    description: FD deps recipe (optional)
    required: false
    default: ''
  python-tools:
    description: Space-delimited Python packages to pip install (optional)
    required: false
    default: ''
  apt-packages:
    description: Space-delimited apt packages (for tools not in categories)
    required: false
    default: ''
```

**New step logic:**
```yaml
- name: Install toolchain
  shell: bash
  run: |
    set -euo pipefail
    IFS=',' read -ra CATEGORIES <<< "${{ inputs.categories }}"
    for cat in "${CATEGORIES[@]}"; do
      just "$cat"
    done

- name: Install FD deps
  if: inputs.fd-deps-recipe != ''
  shell: bash
  run: |
    if [[ -n "${{ inputs.fd-deps-recipe }}" ]]; then
      just ${{ inputs.fd-deps-recipe }}
    fi
```

`fd-deps-recipe` is kept as an optional input for lanes that still need FD-specific deps (e.g., OpenSSL/RocksDB/Snappy not yet fully absorbed into the `fd` category scripts). After Phase 6 is complete, this input can be removed from all lane calls.

## Risks

1. **`common.sh` has ~50 `ensure_*` functions.** Each needs a `TOOL_CATEGORY` assignment. **Mitigation:** automate with a script that reads the category assignment table and inserts `TOOL_CATEGORY` checks.
2. **Platform scripts call each other.** `common.sh` is sourced by every platform script; `setup-linux-x86-fd.sh` may call `setup-linux-x86-ssl.sh` or `setup-linux-x86-build.sh` for shared tooling. **Mitigation:** every platform script sets `SETUP_CATEGORIES` before sourcing `common.sh`, and `common.sh` resolves the full transitive closure. Shared tools are installed once (idempotent).
3. **CI workflows hardcode tool paths.** Some workflows assume specific tool names or paths (e.g., `clang-14` vs `clang-18`). **Mitigation:** audit each CI workflow lane's tool usage after refactor and update paths/versions accordingly.
4. **`common.sh` is the single point of failure.** If it breaks, all lanes break. **Mitigation:** comprehensive tests for each category's tool installation and dependency resolution.
5. **Circular dependencies in `tool-versions.json` dependencies.** If categories A depends on B and B depends on A, the resolver would loop forever. **Mitigation:** detect cycles during resolution and abort with a clear error.
6. **`common.sh` has platform-specific logic.** The `$SETUP_CATEGORIES` filtering must be platform-aware — some `ensure_*` functions are no-ops on certain platforms. **Mitigation:** each `ensure_*` function already has platform checks (`uname -s`, `uname -m`); the category filter is applied *before* the platform check, so a tool not requested by any category is skipped entirely.
7. **`setup-env` is the only place that calls all categories.** After refactor, `setup-env` calls `just` with a list of category recipes (e.g., `just setup-linux-x86-core setup-linux-x86-essential ...`). `just` runs them sequentially. **Mitigation:** verify that `just` handles multiple recipe arguments correctly on all platforms.
