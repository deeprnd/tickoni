# Refactor: Tool-scoped setup for CI lanes

**Status:** Plan
**Created:** 2026-08-29
**Scope:** `contrib/setup/` scripts — split monolithic platform scripts into category-specific helpers, add category dispatch to `justfile`, add recursive category dependency resolution in `tool-versions.json`, update CI workflows to request only needed top-level categories.

---

## Problem Statement

Every CI lane currently installs the full developer environment through `just setup-linux-x86-gcc` or similar, which pulls in compilers, Zig, OpenSSL, quality tools, coverage tools, security tools, and ops tooling — even when a lane only needs a subset. This makes setup slow, opaque (hard to audit what a lane installs), and fragile (a change to one tool's install script can break an unrelated lane).

The setup scripts accept no parameters and unconditionally call every `ensure_*` helper in `common.sh`. There is no way for a CI lane to request "just compilers + Zig" without also getting shellcheck, actionlint, kcov, gitleaks, buf, pre-commit, OpenSSL, and PowerShell.

A related problem: tools like Python are needed by multiple categories. `essential` installs Python. `security` needs pip (via Python) for `cbmc-viewer` and `cbmc-starter-kit`. `quality` needs pipx (via Python) for `pre-commit`. `llm-server` needs pip for `huggingface-cli`. If a CI lane picks `security` without `essential`, it breaks. The fix is explicit, recursive dependency resolution: each category declares which other categories it depends on, and the installation process resolves them automatically.

---

## Target State

### Principle

Every CI lane installs exactly the tools it needs, with dependencies resolved automatically. The `justfile` exposes per-category setup recipes per platform. `just setup-env` remains the developer convenience aggregator. CI workflows call the smallest explicit top-level category, and category dependencies are resolved recursively.

### Category Dependency Resolution

`contrib/setup/tool-versions.json` includes a `dependencies` object that maps each category to its required categories. When a lane requests a category, the setup process resolves all transitive dependencies before running any installers.

```json
{
  "categories": {
    "essential": { "tools": [...] },
    "toolchain": { "tools": [...] },
    ...
  },
  "dependencies": {
    "zig": [
      "essential",
      "toolchain",
      "build"
    ],
    "ssl": [
      "essential",
      "build"
    ],
    "fd": [
      "ssl",
      "build"
    ],
    "security": [
      "essential",
      "build"
    ],
    "quality": [
      "essential"
    ],
    "coverage": [
      "essential",
      "toolchain",
      "build"
    ],
    "secrets": [],
    "ops": [
      "essential"
    ],
    "build": [
      "essential"
    ],
    "llm-server": [
      "essential",
      "build",
      "ops"
    ],
    "mvsc": [
      "essential",
      "build"
    ],
    "go": [
      "essential"
    ],
    "llvm": [
      "essential"
    ],
    "build-windows": [
      "essential",
      "build"
    ]
  }
}
```

**Rules:**
- `dependencies` lists direct (non-recursive) category dependencies. The setup process resolves all transitive dependencies.
- If `$SETUP_CATEGORIES` requests `fd`, the resolver expands it to: `fd` → `ssl,build` → `essential` (from ssl+build), `toolchain` (from build) → resulting in: `essential, toolchain, build, ssl, fd`.
- If `$SETUP_CATEGORIES` requests `security`, it expands to: `security` → `essential,build` → `essential,toolchain` (from build) → `essential,toolchain,build,security`.
- If `$SETUP_CATEGORIES` requests `llm-server`, it expands to: `llm-server` → `essential,build,ops` → `toolchain` (from build) → `essential,toolchain,build,ops,llm-server`.
- `essential` has no dependencies (leaf node). It installs first.
- Circular dependencies are detected and reported as errors.
- A tool can belong to multiple categories (e.g., `ensure_gitleaks` belongs to both `secrets` and `security`). It installs once (idempotent).
- `read_packages` and `read_tool_version` are pure lookup functions — always available regardless of categories.
- `ensure_just`, `ensure_gcc`, `ensure_clang` need sudo — the category dispatch preserves this.

**Why this works:** Every CI lane only needs to specify which top-level category it cares about. The dependency resolver handles the rest. Python is installed once in `essential`; any category that needs pip, pipx, or Python-based tooling transitively depends on `essential`.

### Key Design Decisions

1. **`common.sh` is the single source of truth for tool install logic.** No code duplication — each `ensure_*` function already has idempotency checks (`tool_exists`). We add two more checks: does its category appear in `$SETUP_CATEGORIES`? Is its category in the resolved set (after recursive dependency expansion)?

2. **Platform scripts call `common.sh` with a category list.** Every platform script follows the same pattern. Example — `linux-x86-essential.sh`:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   SCRIPT_DIR="$(cd -- "$( dirname -- "${BASH_SOURCE[0]}" )" && pwd)"
   source "${SCRIPT_DIR}/helpers/common.sh"

   SETUP_CATEGORIES="essential" bash "${SCRIPT_DIR}/helpers/common.sh"
   ```
   Example — `windows-x86-essential.ps1` (PowerShell equivalent):
   ```powershell
   param([string]$Categories = "essential")
   $SCRIPT_DIR = Split-Path -Parent $MyInvocation.MyCommand.Path
   . "$SCRIPT_DIR\helpers\common.sh"

   $env:SETUP_CATEGORIES = $Categories
   & "$SCRIPT_DIR\helpers\common.sh"
   ```

3. **Category dependency resolution is done before category dispatch.** The setup process reads `dependencies` from `tool-versions.json`, resolves all transitive dependencies, deduplicates, and then passes the full set to `common.sh`. A lane requesting `fd` automatically gets `ssl, build, essential, toolchain`.

4. **The `justfile` maps one recipe per category per platform.** No aggregation in the justfile — each recipe is independent and auditable. `setup-env` is the only place that aggregates all categories into one recipe.

5. **CI workflows call individual top-level categories.** The dependency resolver expands them. Example: a lane that needs Zig, OpenSSL, Snappy/RocksDB just calls `just setup-linux-x86-fd` — the resolver expands `fd` → `ssl,build` → `essential,toolchain`, giving `essential,toolchain,build,ssl,fd`.

## Implementation Plan

### Phase 1: Add `dependencies` to `tool-versions.json`

**File:** `contrib/setup/tool-versions.json`

Add a `dependencies` object at the top level. Each key is a category name, each value is an array of direct (non-recursive) category dependencies. See the "Category Dependency Resolution" section above for the full mapping.

This is the source of truth for category dependency graph. The `justfile` and platform scripts read it at runtime.

### Phase 2: Add recursive dependency resolver to `common.sh`

**File:** `contrib/setup/helpers/common.sh`

Add a `resolve_dependencies(categories)` function that:
1. Reads `dependencies` from `tool-versions.json`
2. Starts with the input categories
3. For each category, looks up its direct dependencies and adds them
4. Repeats until no new categories are added (fixpoint)
5. Deduplicates and returns the sorted list

The function is called at the top of each platform script:
```bash
resolved="$(resolve_dependencies "$SETUP_CATEGORIES")"
export SETUP_CATEGORIES="$resolved"
```

If `$SETUP_CATEGORIES` is unset or empty, all categories are implied (preserves current behavior for direct script invocations and local dev).

### Phase 3: Modify `common.sh` to accept categories

**File:** `contrib/setup/helpers/common.sh`

Add a `$SETUP_CATEGORIES` variable (space-delimited list of category names). Every `ensure_*` function checks if its category is in the list before proceeding.

Each tool gets assigned to exactly one category:

```bash
# Category assignment table (documented at top of file):
#   essential:    ensure_curl, ensure_git, ensure_python3,
#                 ensure_python3_pip, ensure_pipx
#   toolchain:    ensure_just, ensure_clang, ensure_winget, ensure_choco,
#                 ensure_strawberry_perl
#   build:        ensure_make, ensure_cmake, ensure_zstd, ensure_pkgconfig,
#                   ensure_ccache, ensure_openblas — Windows: ccache, openblas
#   mvsc:         ensure_msvc — Windows-only
#   zig:          ensure_zig
#   ssl:          ensure_openssl
#   fd:           ensure_snappy, ensure_rockdb — fd scripts call deps.sh with categories=fd
#   quality:      ensure_shellcheck, ensure_actionlint,
#                   ensure_precommit, ensure_yamllint, ensure_buf
#   secrets:      ensure_gitleaks
#   coverage:     ensure_kcov
#   security:     ensure_cbmc_toolchain
#   ops:          ensure_pwsh
#   go:           ensure_go (installed transitively via ensure_buf)
#   llvm:         ensure_llvm (Windows/macOS; winget/brew)
#   llm-server:   ensure_llama_cpp, ensure_openblas, ensure_ccache,
#                   ensure_winlibs, ensure_huggingface_cli — Windows LLM server toolchain
```

**Rules:**
- If `$SETUP_CATEGORIES` is unset or empty, all categories are implied (preserves current behavior for direct script invocations and local dev).
- If `$SETUP_CATEGORIES` is set, only tools whose category appears in the list are installed.
- A tool can belong to multiple categories (e.g., `ensure_gitleaks` belongs to both `secrets` and `security`). It installs once (idempotent).
- `read_packages` and `read_tool_version` are pure lookup functions — always available regardless of categories.
- `ensure_just`, `ensure_gcc`, `ensure_clang` need sudo — the category dispatch preserves this.

**Implementation approach:** Each `ensure_*` function gets a `TOOL_CATEGORY` variable at the top. The function wraps its logic in:
```bash
if [ -n "${SETUP_CATEGORIES:-}" ]; then
    category_found=false
    for cat in $SETUP_CATEGORIES; do
        if [ "$cat" = "$TOOL_CATEGORY" ]; then
            category_found=true; break
        fi
    done
    if [ "$category_found" = false ]; then
        log_info "${TOOL}: not requested (${SETUP_CATEGORIES})"
        return 0
    fi
fi
```

### Phase 4: Create category-specific platform scripts

For each platform and each category, create a new script that sets `SETUP_CATEGORIES` and delegates to `common.sh`. Quality, coverage, security, and secrets are **linux-x86-only** (shellcheck, gitleaks, CBMC, kcov don't run on macOS/Windows/linux-arm). Windows also needs `mvsc` scripts.

All platform scripts follow the same delegation pattern — same variable name (`SETUP_CATEGORIES`), same invocation of `common.sh`, same directory layout. Only the file extension differs (`.sh` for Unix, `.ps1` for Windows).

**Existing scripts to modify:** `linux-x86-essential.sh`, `linux-x86-ops.sh`, `macos-x86-ops.sh`, `macos-arm-ops.sh`, `windows-x86.ps1`, `windows-arm.ps1` — each becomes a category-specific dispatcher.

### Phase 9: Verification

**Dry-run verification:** For each representative CI lane, run `just --list | grep setup-<lane-category>` to confirm the recipe exists and shows no side-effect. Then run `just --dry-run <recipe>` to confirm it only executes the expected script.

**Aggregate verification:** `just --dry-run setup-env` should show all category recipes being called.

**Dependency resolution verification:** Test that `just setup-linux-x86-fd` expands to `essential, toolchain, build, ssl, fd` by checking the resolved categories printed by the resolver. Test that `just setup-linux-x86-coverage` expands to `essential, toolchain, build, coverage`.

**Auditable trace:** Each CI workflow should be readable top-to-bottom and the setup command should unambiguously reveal which tools are installed. Example:

### Phase 10: Remove orphan setup scripts — consolidate under contrib/setup/

**File:** `.github/actions/setup-public-gh-runner/scripts/setup-windows.ps1` — delete

This script is a duplicate of the category-based `contrib/setup/` scripts. It installs:

No workflow or action references this script directly (it is not called from `action.yml`). The `action.yml` calls `just "$SETUP_RECIPE"` which resolves to the `contrib/setup/` scripts. This file is dead code — remove it to eliminate duplication and enforce the rule that all setup scripts live under `contrib/setup/`.

## Risks and Mitigations

1. **`ensure_*` functions are called indirectly from multiple paths.** Some CI lanes may call `just setup-linux-x86-gcc` directly (not via the composite action). All such references in the justfile and CI workflows must be updated. **Mitigation:** delete old recipes and verify no remaining references.

2. **The composite action currently handles `fd-deps`, `security`, `kcov`, `zig`, `compiler`, `compiler-version` as separate inputs.** These map to categories but the mapping isn't 1:1. **Mitigation:** the new action takes a flat list of category recipes, removing the need for the mapping.

3. **Windows setup scripts use different syntax (PowerShell).** The category filter must be implemented in the PowerShell `ensure_*` functions. **Mitigation:** Windows scripts already have `if (Test-CommandExists ...)` idempotency checks; add `$categories` check similarly.

4. **`ensure_gitleaks` belongs to both `secrets` and `security` categories.** It must install once regardless of which category triggers it. **Mitigation:** the idempotency check (`tool_exists gitleaks`) handles this — the category filter only gates whether the function runs at all.

5. **`setup-python-tools` is a general-purpose pip installer, not tied to any category.** It handles `huggingface_hub[cli]` and `pre-commit` via pip (not pipx). **Mitigation:** keep `setup-python-tools` as-is in the justfile; it's not part of the category system.

6. **Circular dependencies in `tool-versions.json` dependencies.** If categories A depends on B and B depends on A, the resolver would loop forever. **Mitigation:** detect cycles during resolution and abort with a clear error.

7. **Adding new categories requires updating `tool-versions.json` dependencies AND creating the platform scripts.** **Mitigation:** the dependency map and script creation are the only two places to touch. The category assignment table at the top of `common.sh` documents which tools belong to which category.

## Out of Scope

- Changes to CI lane definitions (which lanes run, what they test) — these stay the same.
- Changes to build recipes or test recipes — these stay the same.
- Changes to Firedancer deps (`deps.sh`) — these remain standalone.
- Changes to `contrib/build/` — out of scope for this plan.
- Changes to `contrib/test/` — out of scope.
- Changes to `contrib/security/security.sh` — out of scope.
- Changes to `contrib/quality/quality.sh` — out of scope.
- Adding new tool categories beyond the 11 defined — this plan is about refactoring existing tool installs, not adding new ones.
- Changing the dependency graph — once `dependencies` is set in `tool-versions.json`, changes to it should be deliberate and reviewed, not ad hoc.
