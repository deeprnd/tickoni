# Refactor: Tool-scoped setup for CI lanes

**Status:** Plan
**Created:** 2026-08-29
**Scope:** `contrib/setup/` scripts — split monolithic platform scripts into category-specific helpers, add category dispatch to `justfile`, update CI workflows to request only needed tools.

---

## Problem Statement

Every CI lane currently installs the full developer environment through `just setup-linux-x86-gcc` or similar, which pulls in compilers, Zig, OpenSSL, quality tools, coverage tools, security tools, and ops tooling — even when a lane only needs a subset. This makes setup slow, opaque (hard to audit what a lane installs), and fragile (a change to one tool's install script can break an unrelated lane).

The setup scripts accept no parameters and unconditionally call every `ensure_*` helper in `common.sh`. There is no way for a CI lane to request "just compilers + Zig" without also getting shellcheck, actionlint, kcov, gitleaks, buf, pre-commit, OpenSSL, and PowerShell.

---

## Target State

### Principle

Every CI lane installs exactly the tools it needs. The `justfile` exposes per-category setup recipes per platform. `just setup-env` remains the developer convenience aggregator. CI workflows call the smallest explicit set of setup recipes.

### Setup Categories

The `contrib/setup/` scripts follow the same pattern and naming for all platforms: `<platform>-<category>.sh` (or `.ps1` for Windows). The only difference is which categories exist:
- **Linux x86_64 and Linux ARM64**: 11 categories (essential, toolchain, zig, ssl, fd, quality, secrets, coverage, security, ops, build)
- **macOS x86_64 and macOS ARM64**: 7 categories (essential, toolchain, zig, ssl, fd, ops, build) — no quality, secrets, coverage, security
- **Windows x86_64 and Windows ARM64**: 7 base categories + 5 extras (mvsc, build-windows, go, llvm, llm-server) — no quality, secrets, coverage, security

### Key Design Decisions

1. **`common.sh` is the single source of truth for tool install logic.** No code duplication — each `ensure_*` function already has idempotency checks (`tool_exists`). We add one more check: does its category appear in `$SETUP_CATEGORIES`?

2. **Platform scripts call `common.sh` with a category list.** Every platform script follows the same pattern. Example — `linux-x86-essential.sh`:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   SCRIPT_DIR="$(cd -- "$( dirname -- "${BASH_SOURCE[0]}" )" && pwd)"
   source "${SCRIPT_DIR}/helpers/common.sh"

   SETUP_CATEGORIES="essential" bash "${SCRIPT_DIR}/helpers/common.sh"
   ```
   Example — `windows-x86-essential.ps1` (PowerShell equivalent):
   ```powershell
   param([string]$Categories = "essential")
   $SCRIPT_DIR = Split-Path -Parent $MyInvocation.MyCommand.Path
   . "$SCRIPT_DIR\helpers\common.sh"

   $env:SETUP_CATEGORIES = $Categories
   & "$SCRIPT_DIR\helpers\common.sh"
   ```

3. **The `justfile` maps one recipe per category per platform.** No aggregation in the justfile — each recipe is independent and auditable. Windows includes an extra `mvsc` category that does not exist on other platforms.

4. **`setup-env` is the developer convenience aggregator.** It's the only place that aggregates all categories into one recipe. It calls `just <category-recipe> ...` for each category on the current platform — no script accepts an "all" flag; aggregation is done at the `just` level.

5. **CI workflows call individual category recipes.** Example: `just setup-linux-x86-essential setup-linux-x86-toolchain setup-linux-x86-zig setup-linux-x86-ssl setup-linux-x86-fd`.

## Implementation Plan

### Phase 1: Modify `common.sh` to accept categories

**File:** `contrib/setup/helpers/common.sh`

Add a `$SETUP_CATEGORIES` variable (space-delimited list of category names). Every `ensure_*` function checks if its category is in the list before proceeding.

Each tool gets assigned to exactly one category:

```bash
# Category assignment table (documented at top of file):
#   essential:    ensure_curl, ensure_git, ensure_python3,
#                 ensure_python3_pip, ensure_pipx
#   toolchain:    ensure_just, ensure_clang, ensure_winget, ensure_choco,
#                 ensure_strawberry_perl
#   build:        ensure_make, ensure_cmake, ensure_zstd, ensure_pkgconfig,
#                   ensure_ccache, ensure_openblas — Windows: ccache, openblas
#   mvsc:         ensure_msvc — Windows-only
#   zig:          ensure_zig
#   ssl:          ensure_openssl
#   fd:           ensure_snappy, ensure_rockdb — fd scripts call deps.sh with categories=fd
#   quality:      ensure_shellcheck, ensure_actionlint,
#                   ensure_precommit, ensure_yamllint, ensure_buf
#   secrets:      ensure_gitleaks
#   coverage:     ensure_kcov
#   security:     ensure_cbmc_toolchain
#   ops:          ensure_pwsh
#   go:           ensure_go (installed transitively via ensure_buf)
#   llvm:         ensure_llvm (Windows/macOS; winget/brew)
#   llm-server:   ensure_llama_cpp, ensure_openblas, ensure_ccache,
#                   ensure_winlibs, ensure_huggingface_cli — Windows LLM server toolchain
```

**Rules:**
- If `$SETUP_CATEGORIES` is unset or empty, all categories are implied (preserves current behavior for direct script invocations and local dev).
- If `$SETUP_CATEGORIES` is set, only tools whose category appears in the list are installed.
- A tool can belong to multiple categories (e.g., `ensure_gitleaks` belongs to both `secrets` and `security`). It installs once (idempotent).
- `read_packages` and `read_tool_version` are pure lookup functions — they are always available regardless of categories.
- `ensure_just`, `ensure_gcc`, `ensure_clang` need sudo — the category dispatch preserves this.

**Implementation approach:** Each `ensure_*` function gets a `TOOL_CATEGORY` variable at the top. The function wraps its logic in:
```bash
if [ -n "${SETUP_CATEGORIES:-}" ]; then
    category_found=false
    for cat in $SETUP_CATEGORIES; do
        if [ "$cat" = "$TOOL_CATEGORY" ]; then
            category_found=true; break
        fi
    done
    if [ "$category_found" = false ]; then
        log_info "${TOOL}: not requested (${SETUP_CATEGORIES})"
        return 0
    fi
fi
```

### Phase 2: Create category-specific platform scripts

For each platform and each category, create a new script that sets `SETUP_CATEGORIES` and delegates to `common.sh`. Quality, coverage, security, and secrets are **linux-x86-only** (shellcheck, gitleaks, CBMC, kcov don't run on macOS/Windows/linux-arm). Windows also needs `mvsc` scripts.

All platform scripts follow the same delegation pattern — same variable name (`SETUP_CATEGORIES`), same invocation of `common.sh`, same directory layout. Only the file extension differs (`.sh` for Unix, `.ps1` for Windows).

**Existing scripts to modify:** `linux-x86-essential.sh`, `linux-x86-ops.sh`, `macos-x86-ops.sh`, `macos-arm-ops.sh`, `windows-x86.ps1`, `windows-arm.ps1` — each becomes a category-specific dispatcher.

### Phase 5: Update composite action `setup-public-gh-runner`

**File:** `.github/actions/setup-public-gh-runner/action.yml`

The current action takes a single `setup-recipe` parameter and calls `just "$SETUP_RECIPE"`. This needs to change to accept a list of category recipes.

**New inputs:**
```yaml
inputs:
  categories:
    description: Comma-separated list of just setup category recipes to run
    required: true
  fd-deps-recipe:
    description: FD deps recipe (optional)
    required: false
    default: ''
  python-tools:
    description: Space-delimited Python packages to pip install (optional)
    required: false
    default: ''
  apt-packages:
    description: Space-delimited apt packages (for tools not in categories)
    required: false
    default: ''
```

**New step logic:**
```yaml
- name: Install toolchain
  shell: bash
  run: |
    set -euo pipefail
    IFS=',' read -ra CATEGORIES <<< "${{ inputs.categories }}"
    for cat in "${CATEGORIES[@]}"; do
      just "$cat"
    done

- name: Install FD deps
  if: inputs.fd-deps-recipe != ''
  shell: bash
  run: |
    set -euo pipefail
    just ${{ inputs.fd-deps-recipe }}

- name: Install Python tools
  if: inputs.python-tools != ''
  shell: bash
  run: |
    set -euo pipefail
    just setup-python-tools "${{ inputs.python-tools }}"
```

### Phase 7: Verification

**Dry-run verification:** For each representative CI lane, run `just --list | grep setup-<lane-category>` to confirm the recipe exists and shows no side-effect. Then run `just --dry-run <recipe>` to confirm it only executes the expected script.

**Aggregate verification:** `just --dry-run setup-env` should show all category recipes being called.

**Auditable trace:** Each CI workflow should be readable top-to-bottom and the setup command should unambiguously reveal which tools are installed. Example:
```yaml
# This lane installs: essential, toolchain, zig, ssl, fd
- uses: ./.github/actions/setup-public-gh-runner
  with:
    categories: setup-linux-x86-essential,setup-linux-x86-toolchain,setup-linux-x86-zig,setup-linux-x86-ssl,setup-linux-x86-fd
```

## Risks and Mitigations

1. **`ensure_*` functions are called indirectly from multiple paths.** Some CI lanes may call `just setup-linux-x86-gcc` directly (not via the composite action). All such references in the justfile and CI workflows must be updated. **Mitigation:** delete old recipes and verify no remaining references.

2. **The composite action currently handles `fd-deps`, `security`, `kcov`, `zig`, `compiler`, `compiler-version` as separate inputs.** These map to categories but the mapping isn't 1:1. **Mitigation:** the new action takes a flat list of category recipes, removing the need for the mapping.

3. **Windows setup scripts use different syntax (PowerShell).** The category filter must be implemented in the PowerShell `ensure_*` functions. **Mitigation:** Windows scripts already have `if (Test-CommandExists ...)` idempotency checks; add `$categories` check similarly.

4. **`ensure_gitleaks` belongs to both `secrets` and `security` categories.** It must install once regardless of which category triggers it. **Mitigation:** the idempotency check (`tool_exists gitleaks`) handles this — the category filter only gates whether the function runs at all.

5. **`setup-python-tools` is a general-purpose pip installer, not tied to any category.** It handles `huggingface_hub[cli]` and `pre-commit` via pip (not pipx). **Mitigation:** keep `setup-python-tools` as-is in the justfile; it's not part of the category system.
