# Refactor: JSON-driven tool orchestrator for CI lanes

**Status:** Plan
**Created:** 2026-08-30
**Scope:** Replace the existing platform-specific setup scripts in `contrib/setup/` and `contrib/setup/helpers/` with a single generic Python orchestrator driven entirely by `contrib/setup/tool-versions.json`.
**Depends on:** None (supersedes v2.10-s8-1).

---

## Problem Statement

Every CI lane currently installs the full developer environment through `just setup-linux-x86-gcc` or similar, which pulls in compilers, Zig, OpenSSL, quality tools, coverage tools, security tools, and ops tooling — even when a lane only needs a subset.

The current setup model uses platform-specific shell scripts (one per platform × one per category) that source `common.sh`, which has ~50 `ensure_*` functions with hardcoded shell logic. The `SETUP_CATEGORIES` variable filters which functions run.

**Baseline assumption:** Python 3 is available on every CI runner image (GitHub `ubuntu-latest` ships it, `macos-latest` ships it, `windows-latest` ships it via the Python installer action). Dev machines are assumed to have Python 3 — not installed by the orchestrator. On CI, Python is installed as a built-in tool (not left to chance) so the orchestrator can always run itself.

This is still "scripts over scripts":
- Platform-specific scripts (one per platform per category, ~6 per category)
- 50 `ensure_*` functions in `common.sh`, each with platform-specific install logic
- Adding Go as quality's dependency means quality's script must somehow trigger go's script
- Every new category requires: new JSON entry + new platform scripts + new ensure_* function
- Dependency resolution is a string filter on category names, not a true data-driven graph
- Platform scripts call each other for shared tooling — the graph is implicit, not auditable
- Windows `.ps1` files vs Unix `.sh` files — two codebases for the same logic

**Root cause:** The install logic is in shell functions, not in data. The JSON describes WHAT categories exist but not HOW tools are installed. That logic lives in `common.sh`, which must be edited every time a tool is added or an install method changes.

## Target State

### Principle

A single generic orchestrator script reads `tool-versions.json` and installs tools based on category dependencies — all driven by data. No per-category dispatcher scripts. No `ensure_*` functions in shell. No platform scripts at all.

```
just setup-linux-x86-fd
  → orchestrator.sh reads tool-versions.json
  → resolves "fd" → [core, essential, build, ssl, fd] (transitive deps)
  → for each category, for each tool, reads install_method + parameters
  → installs tools in dependency-safe order (deduped, idempotent)
```

### Data Model

`tool-versions.json` is the complete source of truth. Each tool declares:
- **install_method**: how to install it (apt, brew, winget, pip, go_install, github_release, python_script, build_from_source, binary_download, none)
- **parameters**: install_method-specific parameters (package name, download URL, build args, etc.)
- **platform**: platform scope (all, linux, macos, windows, or specific os-arch combos)
- **category**: which category owns it
- **depends_on**: direct tool-level dependencies (optional, for tools that need prerequisites)
- **version**: version pin or reference to versions section

Each category declares:
- **tools**: list of tool names belonging to this category
- **description**: human-readable description
- **platforms**: which platforms this category exists on (optional — defaults to all)

Dependencies are defined at the category level (not tool level). The orchestrator resolves the category graph, then installs all tools in the resolved categories.

```json
{
  "versions": { ... },
  "categories": {
    "core": {
      "description": "Bootstrap tools",
      "tools": ["curl", "git"]
    },
    "quality": {
      "description": "Lint, format, and quality checks",
      "tools": ["shellcheck", "actionlint", "yamllint", "pre-commit", "buf"],
      "platforms": ["linux-x86", "linux-arm"]
    }
  },
  "dependencies": {
    "core": [],
    "quality": ["core", "build", "python", "go"]
  },
  "tools": {
    "curl": {
      "category": "core",
      "platform": "all",
      "install_method": "apt",
      "parameters": { "package": "curl" },
      "idempotent_check": "command -v curl"
    },
    "git": {
      "category": "core",
      "platform": "all",
      "install_method": "apt",
      "parameters": { "package": "git" },
      "idempotent_check": "command -v git"
    },
    "go": {
      "category": "go",
      "platform": "all",
      "install_method": "binary_download",
      "parameters": {
        "url_pattern": "https://go.dev/dl/go{version}.{os}-{arch}.tar.gz",
        "install_dir": "/usr/local/go"
      },
      "idempotent_check": "command -v go",
      "post_install": "export PATH=\"/usr/local/go/bin:$PATH\"",
      "version_ref": "go"
    },
    "buf": {
      "category": "quality",
      "platform": "all",
      "install_method": "go_install",
      "parameters": { "module": "github.com/bufbuild/buf/cmd/buf" },
      "idempotent_check": "command -v buf"
    },
    "shellcheck": {
      "category": "quality",
      "platform": "all",
      "install_method": "apt",
      "parameters": { "package": "shellcheck" },
      "idempotent_check": "command -v shellcheck"
    }
  }
}
```

### Install Methods

Each install method is a branch in the orchestrator. The orchestrator dispatches based on `install_method`:

| Method | Description | Parameters |
|--------|-------------|------------|
| `apt` | apt-get install | `package`: apt package name |
| `brew` | brew install | `package`: brew formula name |
| `winget` | winget install | `package`: winget package ID |
| `pip` | pip install | `package`: pip package name |
| `pipx` | pipx install | `package`: pipx package name |
| `go_install` | go install | `module`: Go module path |
| `github_release` | download from GitHub releases | `owner`, `repo`, `version_ref`, `asset_pattern` |
| `binary_download` | download arbitrary binary | `url_pattern`, `install_dir` |
| `python_script` | run Python script | `script_path`, `args` |
| `build_from_source` | git clone + build | `repo`, `install_dir`, `build_command`, `install_command` |
| `none` | no-op (tool already present or platform-specific) | none |

Each method handles its own idempotency check (the `idempotent_check` field). If the check passes, the tool is skipped.

### Orchestrator Design

A single Python script: `contrib/setup/orchestrator.py`

Inputs: comma-separated category list
Output: installs all tools in resolved categories

Flow:
1. Read `tool-versions.json`
2. Resolve category dependencies (recursive, cycle-detection)
3. For each resolved category, collect its tools
4. For each tool, read its install_method + parameters from the `tools` section
5. Apply platform filter (skip if `platform` doesn't match current platform)
6. Install in dependency-safe order (deduped — a tool in multiple resolved categories installs once)
7. Log progress

```

  tool-versions.json       # complete source of truth — categories, deps, tools, install methods
  helpers/

    install-openssl.sh     # remains (called by orchestrator via binary_download/build_from_source)
    common.ps1             # remains (Windows helper for MSVC detection, path setup)
  README.md                # updated
```

**Deleted:**
- All existing platform scripts: `linux-x86-*.sh`, `linux-arm-*.sh`, `macos-x86-*.sh`, `macos-arm-*.sh`, `windows-*.ps1`
- `helpers/common.sh` — replaced by `orchestrator.py`
- `helpers/common.ps1` — replaced by `orchestrator.py`

### Justfile Changes

One recipe per logical setup (not per category per platform). The orchestrator detects the platform internally. See Phase 4 for the complete recipe list.

No per-category-per-platform scripts. One orchestrator, called with the top-level category.

### CI Workflow Changes

The `setup-public-gh-runner` composite action accepts: `setup-recipe`, `deps-recipe`, `compiler`, `python-tools`, `security`, `zig`, `fd-deps`, `kcov`. After migration:

- `setup-recipe` → direct `just setup-*` call (orchestrator detects platform)
- `fd-deps` → unchanged (still calls `just fd-deps-*` which runs `deps.sh check`)
- `compiler` → handled by JSON tool entries (gcc/clang are separate tool entries with platform-specific package names)
- `python-tools` → orchestrator installs via pip/pipx entries
- `zig` → orchestrator installs via zig entry
- `security` → orchestrator installs via security category
- `kcov` → orchestrator installs via coverage category

## Implementation Plan

### Phase 1: Redesign tool-versions.json

**File:** `contrib/setup/tool-versions.json`

Restructure from the current flat format to the new data-driven model:

1. Keep `versions` section as-is (version pins).
2. Keep `categories` section but add `platforms` field per category.
3. Add `dependencies` section (same as v2.10-s8-1).
4. **Add `tools` section**: each tool gets an entry with `install_method`, `parameters`, `platform`, `idempotent_check`, and optional `version_ref`.

This requires auditing every existing `ensure_*` function in `common.sh` and translating its install logic into an `install_method` + `parameters` pair.

Tools to define (from current common.sh):
- **`python3` → apt/brew/winget** (CI baseline only — dev machines assumed to have it. `ubuntu-latest` and `macos-latest` runner images ship Python 3; `windows-latest` provides it via the setup-python action. CI workflows must ensure it's present before running the orchestrator, e.g. via `actions/setup-python` or the runner's default toolchain — the orchestrator itself requires Python to execute, so Python is a self-bootstrapping prerequisite on CI.)
- `curl`, `git` → apt
- `python3`, `pipx`, `python3-pip` → apt
- `build-essential`, `libiberty-dev`, etc. → apt
- `minisign` → apt
- `coreutils` → brew
- `make`, `cmake`, `zstd`, `pkg-config` → apt/brew
- `ninja`, `ccache` → winget (build infrastructure — installed in core packages on Windows; `llm-server` on Windows depends on them as build deps for llama.cpp, but they are not llm-server-owned tools)
- `just` → github_release
- `gcc`, `clang`, `llvm` → apt/brew (Linux: `clang-18` + `llvm-18` from apt are the same toolchain version; macOS: `brew install llvm` is unversioned — see note below)
- `msvc` → winget
- `choco`, `winget` → platform-specific (already present on some images)
- `zig` → python_script (install-zig.py)
- `openssl` → build_from_source (install-openssl.sh)
- `snappy`, `rockdb` → build_from_source (deps.sh logic)
- `gitleaks` → github_release
- `actionlint` → github_release (with checksum verification)
- `cbmc`, `litani`, `universal-ctags` → github_release (CBMC) + apt (universal-ctags)
- `cbmc-viewer`, `cbmc-starter-kit` → pip
- `kcov` → build_from_source
- `shellcheck`, `actionlint`, `yamllint` → apt/brew
- `pre-commit` → pipx
- `buf` → go_install
- `go` → binary_download
- `pwsh` → apt/brew
- `llama-cpp` → build_from_source (clone + build)
- `huggingface_hub` → pip
- `openblas`, `winlibs` → winget
- `ccache` is listed in both `build` and `llm-server` categories in tool-versions.json — this is redundant; ccache is build infrastructure installed in core packages on Windows, not llm-server-owned. `ninja` is used by llama.cpp as a CMake build generator but is also build infrastructure, not llm-server-owned.

**LLVM/Clang consolidation note:** On Linux apt, `clang-18` and `llvm-18` are two packages from the same LLVM 18 toolchain (`clang-18` provides the compiler frontend, `llvm-18` provides the tooling: llvm-ar, llvm-cov, llvm-profdata, llvm-objdump, etc.). They are NOT separate LLVM versions — they are the same version installed via separate apt packages. The plan should define a single `clang-llvm` tool entry that installs both on Linux (`apt install clang-18 llvm-18`), handles macOS `brew install llvm` (unversioned, pulls latest), and Windows `winget install LLVM.LLVM`. The `llvm` category in `tool-versions.json` is redundant with `toolchain` (which already lists `llvm` as a tool); collapse into `toolchain` only. The `coverage` category dependency should reference `toolchain` directly (which includes the clang-llvm tool) instead of a separate `llvm` category.

### Phase 2: Write orchestrator.sh

**File:** `contrib/setup/orchestrator.sh`

Single script that:
1. Reads `tool-versions.json` using Python (inline `python3 -c` or a small helper script)
2. Resolves category dependencies (recursive DFS with cycle detection)
3. Collects tools from resolved categories
4. Filters by platform
5. Deduplicates
6. Installs each tool using the appropriate install method
7. Logs progress and errors

The orchestrator uses Python for JSON parsing and dependency resolution, then dispatches install commands via `subprocess` or shell calls. Alternatively, the entire orchestrator can be Python — it's a setup script, not a runtime component.

**Recommendation:** Make it Python (`orchestrator.py`). It reads JSON, resolves deps, and runs install commands. No shell parsing of JSON. Cleaner, more maintainable.

```python
#!/usr/bin/env python3
"""CI tool orchestrator — reads tool-versions.json and installs tools."""
import json, sys, subprocess, os, hashlib

def main():
    if len(sys.argv) < 2:
        print("Usage: orchestrator.py <category1,category2,...>", file=sys.stderr)
        sys.exit(1)

    # Load tool-versions.json
    json_path = os.path.join(os.path.dirname(__file__), 'tool-versions.json')
    with open(json_path) as f:
        config = json.load(f)

    # Parse requested categories
    requested = [c.strip() for c in sys.argv[1].split(',')]

    # Resolve dependencies
    resolved = resolve_deps(requested, config['dependencies'])

    # Collect tools
    tools = collect_tools(resolved, config['categories'], config['tools'])

    # Filter by platform
    platform = get_platform()
    tools = [t for t in tools if matches_platform(t, platform)]

    # Deduplicate (preserve order by dependency resolution)
    seen = set()
    unique = []
    for t in tools:
        if t['name'] not in seen:
            seen.add(t['name'])
            unique.append(t)

    # Install each tool
    for tool in unique:
        install_tool(tool, config)

def resolve_deps(requested, dependencies):
    """Resolve category dependencies recursively. Detects cycles."""
    resolved = set()
    visiting = set()  # for cycle detection

    def visit(cat):
        if cat in resolved:
            return
        if cat in visiting:
            print(f"ERROR: circular dependency detected: {cat}", file=sys.stderr)
            sys.exit(1)
        visiting.add(cat)
        for dep in dependencies.get(cat, []):
            visit(dep)
        resolved.add(cat)
        visiting.discard(cat)

    for cat in requested:
        visit(cat)

    return sorted(resolved)

def collect_tools(categories, cat_config, tool_config):
    """Collect all tools from resolved categories."""
    tools = []
    for cat in categories:
        for tool_name in cat_config.get(cat, {}).get('tools', []):
            tools.append(tool_config[tool_name])
    return tools

def get_platform():
    """Detect current platform."""
    import platform
    os_name = platform.system().lower()  # linux, darwin, windows
    arch = platform.machine().lower()
    arch = 'x86' if 'x86_64' in arch or 'amd64' in arch else 'arm' if 'arm' in arch else arch
    return f"{os_name}-{arch}"

def matches_platform(tool, platform):
    """Check if tool matches current platform."""
    p = tool.get('platform', 'all')
    if p == 'all':
        return True
    return platform in p or p in platform

def install_tool(tool, config):
    """Install a tool using its configured method."""
    name = tool['name']
    method = tool['install_method']
    params = tool.get('parameters', {})

    # Idempotency check
    check = tool.get('idempotent_check', '')
    if check:
        try:
            subprocess.run(check.split(), capture_output=True, timeout=10)
            print(f"[OK] {name} already installed")
            return
        except (FileNotFoundError, subprocess.TimeoutExpired):
            pass

    print(f"[INSTALL] {name} (method={method})")

    if method == 'apt':
        _install_apt(params['package'])
    elif method == 'brew':
        _install_brew(params['package'])
    elif method == 'winget':
        _install_winget(params['package'])
    elif method == 'pip':
        _install_pip(params['package'], config.get('versions', {}).get(name))
    elif method == 'pipx':
        _install_pipx(params['package'])
    elif method == 'go_install':
        _go_install(params['module'])
    elif method == 'github_release':
        _github_release(params, config)
    elif method == 'binary_download':
        _binary_download(params, config)
    elif method == 'python_script':
        _python_script(params, config)
    elif method == 'build_from_source':
        _build_from_source(params, config)
    elif method == 'none':
        print(f"[SKIP] {name} (no-op)")
    else:
        print(f"[ERROR] unknown install_method: {method}", file=sys.stderr)
        sys.exit(1)

    # Post-install hooks
    post = tool.get('post_install', '')
    if post:
        os.system(post)

    print(f"[DONE] {name}")
```

### Phase 3: Migrate install logic from common.sh

Translate each `ensure_*` function into a tool entry in the `tools` section of `tool-versions.json`.

This is the bulk of the work. Each function becomes 5-15 lines of JSON. For example:

```json
"ensure_gitleaks": {
    "category": "secrets",
    "platform": ["linux-x86", "linux-arm"],
    "install_method": "github_release",
    "parameters": {
        "owner": "gitleaks",
        "repo": "gitleaks",
        "version_ref": "gitleaks",
        "asset_pattern": "gitleaks_{version}_linux_{{arch}}.tar.gz",
        "install_dir": "/usr/local/bin"

    "idempotent_check": "command -v gitleaks"
}
```

Complex installs (OpenSSL, kcov, CBMC) need the `build_from_source` method with `build_command` and `install_command` fields. The orchestrator runs these in a temp directory.

| Aspect | Old (v2.10-s8-1) | New (this plan) |
|--------|-------------------|-----------------|
| Install logic location | `common.sh` (50+ ensure_* functions) | `orchestrator.py` (one dispatch per method) |
| Per-category scripts | ~30 platform scripts | 1 script (orchestrator.py) |
| Adding a tool | Edit common.sh + JSON | Edit JSON only |
| Adding a category | Edit JSON + create ~6 platform scripts | Edit JSON only |

| Windows support | Separate .ps1 codebase | Same Python script, platform field + common.ps1 removed |
| Lines of code | ~3000+ (scripts + common.sh) | ~500 (orchestrator.py) |

## Verification

1. **Dry-run**: `python3 orchestrator.py fd --dry-run` prints what it would install without executing.
2. **Dependency audit**: `python3 orchestrator.py --deps quality` prints the resolved dependency graph.
3. **Tool listing**: `python3 orchestrator.py --list core` prints all tools in a category.
4. **Platform filter**: `python3 orchestrator.py --dry-run fd` on macOS skips linux-only tools.
5. **CI parity**: `just setup-env` on each platform installs the same tool set as before (auditable).
6. **Re-run safety**: Running the same command twice produces no second installs.

---

## Risks

1. **Migrating 50+ ensure_* functions to JSON.** Each function has platform-specific branches, error handling, and edge cases. **Mitigation:** automate the migration by parsing common.sh and generating JSON entries; then manually verify each. Start with the most common tools (apt/brew/winget installs) and handle complex ones (build_from_source) later.

2. **orchestrator.py is a new dependency.** Every CI lane runs this script. **Mitigation:** it uses only stdlib (json, subprocess, os, platform, hashlib). No pip install needed. Python 3.6+ is guaranteed on all CI runners.

3. **Build-from-source tools need temp directories and cleanup.** `kcov`, `openssl`, `llama-cpp` clone repos and build. **Mitigation:** orchestrator creates a temp dir, runs the build, cleans up. Errors don't leave artifacts.

4. **Platform detection accuracy.** `platform.system()` + `platform.machine()` must match all platform keys. **Mitigation:** add a `get_platform()` test in orchestrator.py that runs on each platform during CI.

5. **CI composite action removal.** If other workflows or actions depend on `setup-public-gh-runner`, they need updating. **Mitigation:** grep the repo for references before deletion.

6. **PowerShell tools on Windows.** `winget` installs may require different handling. **Mitigation:** orchestrator uses `subprocess.run(['winget', 'install', ...])` which is the same API as apt/brew.

## contrib/build Folder Constraint

**Do not break anything in `contrib/build/`.** This folder is used by Firedancer's own build pipeline and CI. Any change that causes a Firedancer build to fail is unacceptable.

By the end of this plan:

- All install/setup logic for libraries and 3rd-party tools must flow through `just setup-*` commands, which wire into `contrib/setup/`.
- `contrib/build/deps.sh` remains the Firedancer entry point. It may be simplified to call `just setup-*` or `python3 contrib/setup/orchestrator.py` instead of running its own platform-specific installers, but the script itself remains. No Firedancer build target should depend on a tool being present without going through `deps.sh`.
- If something is currently wired into `contrib/build/` that performs tool installs (e.g. `deps.sh` calling platform-specific installers), rewrite that install logic into `contrib/setup/` and have `contrib/build/` call the orchestrator instead.
- At most, we can disable problematic install/setup paths in existing scripts using `if false; then ... fi` (shell) or `exit 0` at the top of a function. These are temporary scaffolds for the transition period — document what they bypass and why.
- This constraint applies to Firedancer's `deps.sh`, `common.sh`, and any platform scripts under `contrib/build/` that install tools. Tickoni's own install logic (under `contrib/setup/`) is the new home for all such logic.
- **Compiler-specific justfile recipes** (`setup-linux-x86-gcc`, `setup-linux-x86-clang`, etc.) currently pass compiler env vars to `contrib/build/deps.sh`. After migration, these recipes call `orchestrator.py` with the appropriate category, and the compiler env var is handled by tool entries in the JSON (e.g. `gcc` and `clang` are separate tool entries). The `fd-deps-*` recipes that invoke `deps.sh check` stay as-is — they install Firedancer's C library dependencies, not developer tooling.

## Out of Scope

- Changes to CI lane definitions (which lanes run, what they test) — these stay the same.
- Changes to build recipes or test recipes — these stay the same.
- Changes to Firedancer deps (deps.sh) — these remain standalone, called by orchestrator.
- Changes to contrib/build/ — out of scope (see contrib/build folder constraint above).
- Changes to contrib/test/ — out of scope.
- Changes to contrib/security/security.sh — out of scope.
- Changes to contrib/quality/quality.sh — out of scope.
- Adding new tool categories beyond those defined — this plan is about refactoring existing tool installs, not adding new ones.
