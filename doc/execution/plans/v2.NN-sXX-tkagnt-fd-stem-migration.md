# Plan: Migrate tkagnt to a proper fd_stem agent-worker tile with multi-tkmodl fan-out

**Status:** Planned. Phase 0 baseline and contract decisions are below. No tkagnt process tile or stem specialization exists yet beyond the current passive result-sink stub.

**Goal:** Give `tkagnt` a proper `fd_stem` lifecycle as an **active agent-worker tile** that dispatches model requests to one or more `tkmodl` instances and consumes their results, while preserving the bounded-agent invariant: no direct shell, unrestricted syscall, or unrestricted network access.

Execute in dependency order: decide the contracts, write tests, implement the tile, wire it into a runnable topology, then prove it with real-process evidence. A file or a passing in-process fixture test is not evidence that the process tile works.

## References and scope

- [`tile-orchestration.md`](../../knowledge/tile-orchestration.md#fd_stem-tile-implementation-standard) and [`contribution/tickoni.md`](../contribution/tickoni.md#fd_stem-callback-contract) define the current stem standard.
- The completed [`tknorm`](v2.NN-sXX-tknorm-fd-stem-migration-done.md), [`tkdedu`](v2.NN-sXX-tkdedu-fd-stem-migration-done.md), [`tkaudt`](v2.NN-sXX-tkaudt-stem-contract-done.md), [`tkmodl`](v2.NN-sXX-tkmodl-fd-stem-migration-done.md), and [`tkpoly`](v2.NN-sXX-tkpoly-fd-stem-migration-done.md) plans show the build, test, and registration patterns.
- The [`tkdiag` fan-in plan](v2.10-s14-tkdiag-fan-in.md) defines the Firedancer multi-link fan-in model (multiple producers → one consumer). The same pattern applies in reverse for fan-out (one producer → multiple consumers).
- `src/tickoni/tiles/agent/` holds the existing in-process agent module. This plan covers the `tkagnt` fd_stem tile and the minimum approved wiring needed to prove it. It does not authorize new agent role policies, financial capability semantics, approval rules, or external services.

## Decision gate: approve the runtime contract before implementation

These choices change link semantics, public messages, audit/replay behavior, or service authority. The framework owner must decide and record them.

1. **Agent scope and bounded memory.** Define the agent's role, memory limits, prompt template scope, and maximum reasoning steps. State whether the agent can hold state across requests or is stateless per-request.

2. **Request source and routing.** Define who sends requests to `tkagnt` (currently `tkdisp` in the investment workflow, or a synthetic source in the minimal topology). Define how `tkagnt` selects which `tkmodl` instance to send to — by model ID, by role, or by policy decision.

3. **Multi-tkmodl fan-out topology.** `tkagnt` must support up to 11 configured `tkmodl` tiles; no tier or count of 11 is mandatory for every topology. Define which tiers are present for each workflow, and each instance's `live_provider_enabled` flag, allowlisted models, and fixture table. A request for an absent tier must fail explicitly.

4. **Embedding model support.** Define whether embedding models are supported alongside chat/completion models within each tkmodl instance, or as separate embedding-only instances. Define embedding wire format (text input → vector output), dimension support, batch request support, and embedding-specific governance.

5. **Lifecycle and scope.** Decide whether the first runnable topology is a focused minimal topology or the full investment workflow; specify restart, in-flight request recovery, cancellation, and shutdown drain rules.

6. **Wire contracts and link bounds.** Define bounded request and result payloads (chat/completion and embedding); versioning; oversized handling; maximum logical input/output bytes, fragment MTU and count, and exact depth/MTU for all links. Large model messages must work across multiple fragments.

   The `tkagnt → tkmodl` request must carry the full bounded model input, and the `tkmodl → tkagnt` result must carry the full bounded model output, including when either exceeds one fragment. The separate `tkmodl → tkaudt` record carries hashes and attribution metadata only. Specify the prompt/message count and byte limits, output byte limit, embedding count/dimension limits, and framing before choosing fragment MTUs or scratch footprints. These limits are independent of the model context/token limits.

7. **Result correlation.** Define how `tkagnt` correlates a `tkmodl` result back to the original dispatch — `request_id`, `run_id`, or a composite key.

8. **Zig agent decision boundary.** Define how the `fd_stem` process obtains Zig-owned model-routing and result-interpretation decisions without reimplementing them in C. The existing C ABI is Zig-to-C; do not assume a C-to-Zig callback or move agent policy into the shim. Resolve this boundary before implementing classifier escalation.

9. **Return, audit order, and drain.** Approve the `tkmodl → tkagnt` result link for every configured model instance, the final `tkagnt → tkdisp` result link in the full workflow, and a named final-result consumer in the minimal process test. Define an agent audit link and a committed-audit barrier before final-result publication. Approve the correlation key, deterministic audit ordering rule, bounded out-of-order capacity, terminal failure behavior, and shutdown/restart treatment of in-flight calls.

### Proposed return and audit contract (pending framework-owner approval)

- **Separate transport from audit.** `tkagnt → tkmodl` carries the complete bounded prompt/messages or embedding input plus model request scope. `tkmodl → tkagnt` returns the complete bounded model response or embedding vectors, including status, correlation fields, and token usage. `tkmodl → tkaudt` carries the canonical input/output hashes and non-body metadata needed for attribution and replay verification. Neither the prompt, response text, nor embedding vectors belong in audit records. `tkagnt` interprets classifier content; `tkmodl` returns it without making an agent-routing decision.
- **Large-message framing.** The current stems process each fragment as a complete fixed-size record; Firedancer SOM/EOM does not reassemble it for them. Define a versioned header that binds every fragment to `(run_id, model_request_id, direction, content_type)`, declares total length and fragment offset/length, and includes scope or a verified reference to scope captured on the first fragment. Use SOM/EOM consistently, require contiguous non-interleaved fragments on each producer link for the initial contract, and accept a logical message only after all bytes and the final boundary are verified. Bound total bytes, fragment count, concurrent partial messages, and aggregate reassembly memory. Detect gaps, duplicates, overlap, overflow, malformed boundaries, overrun, timeout, restart, and shutdown with a terminal failure; never dispatch a partial input or interpret a partial output. The exact byte ceilings and fragment MTUs need approval; they must permit messages larger than one fragment.
- **Multipart publication and flow control.** A producer keeps bounded state for the remaining fragments and emits them over successive stem iterations under reliable-link credits. Its `STEM_BURST` must cover the actual maximum publishes per iteration, including audit or terminal records; a queued-output drain must remain active through shutdown until every accepted message is completed or has a terminal failure. The proposed depth is a count of fragments, so it must be sized and tested with the chosen fragment MTU, producer burst, and consumer rate. No single callback may assume it can publish the entire logical message at once.
- **Hash and replay discipline.** Compute or verify each audit hash against the actual bytes crossing the model boundary; do not trust a caller-supplied `prompt_hash` without checking the payload. Replay must reconstruct the model input from captured run inputs or read an approved input capture outside the audit, then verify its hash. It also needs the captured response bytes, including classifier content and vectors, in a versioned replay capsule or approved content-addressed evidence outside the audit record. Bind that capture to the substitution ID, model ID, request/input hash, and response/output hash; reject a missing or mismatched capture and never call a provider during replay. The artifact location, access controls, and retention are separate approval decisions.
- **Return path.** Each configured `tkmodl` instance publishes one result to `tkagnt` for each accepted model request, including denials. In the full workflow, `tkagnt` publishes one terminal agent result to `tkdisp` for each accepted agent request and sends a proposal hash, denial, or failure record to `tkaudt`, with no raw model response in that audit record. The current C audit stem only accepts payment and model records, so the agent audit envelope and its `tkaudt` handling require an approved schema change. The minimal process topology needs a bounded consumer of that terminal result; the existing scratch ring is an inspection aid, not delivery. Name and register that consumer before fixing tile/link counts.
- **Correlation.** Assign a deterministic `model_request_id` to each model dispatch, including each classifier follow-up. A bounded `tkagnt` pending entry maps `(run_id, model_request_id)` to the parent agent request, configured model instance, expected model ID, and step ordinal. A result must match that entry and its source input link; an unknown, duplicate, stale, wrong-instance, or wrong-model result cannot complete a run. Record a terminal failure through the approved audit path instead of silently dropping an accepted request. The current `request_id`-only rule and wire records need an approved extension or an equivalent documented mapping.
- **Audit order.** `tkaudt` remains the sole owner of append order and hash chaining. For the same accepted event/case order and captured model outputs, the committed agent/model audit sequence and hashes must be identical even when model completions arrive in a different order. Use a deterministic order key based on accepted case/run order, agent-request ordinal, model-step ordinal, and record phase; buffer out-of-order arrivals within an explicit bound. A missing predecessor requires an audited terminal outcome before later records in that order can commit. Never use result arrival time or CNC counters as the ordering key. The ordering key's schema, bound, and merge with existing financial-event records require approval.
- **Commit barrier.** Publishing a model audit fragment and result from one `AFTER_FRAG` commit does not prove that `tkaudt` appended the audit record before `tkagnt` sees the result. Specify an explicit committed-audit acknowledgment or equivalent barrier, tied to the model call and final agent record, before `tkagnt` publishes a terminal result. This may require a new return link from `tkaudt`; its link shape and `tkaudt` lifecycle are not yet approved. CNC progress is advisory and cannot serve as the barrier.
- **Shutdown and restart.** On shutdown, stop accepting new agent requests, finish or produce an audited terminal failure for every accepted in-flight dispatch, wait for the audit commit barrier, then publish terminal results and exit. A fixed result-count gate or immediate CNC HALT must not abandon pending calls. Define the finite drain deadline, cancellation outcome, and restart reconstruction from accepted requests, audit records, and replay capsules before implementation; a crash must not turn a retried model call into an uncorrelated duplicate or an external call during replay.

## Preserved agent contract

- Every request carries actor/role, workflow, run or case identity, capability envelope, policy version, budget, model ID, and replay mode. Missing or malformed required scope fails closed.
- Agents are **proposal-first**. They may inspect, classify, summarize, draft, recommend, prepare evidence, and propose; they must not directly place trades, move money, post ledger entries, freeze accounts, approve payouts, or override risk/compliance controls.
- Model access must go through `tkmodl`. Agents must not call cloud providers, local LLM servers, or local GPU inference directly.
- Financial tool and adapter access must go through `tktool` and `tkadpt`. Model-native function calls and MCP-style requests are integration formats, not trust boundaries.
- The in-process `runInvestmentAgent` is scaffolding, not an authority template for this tile: its direct `adapter_backend.call` and paper-order branch must not be copied into `tkagnt`. A future tool request must cross the governed `tktool`/`tkadpt` boundary; execution requires its separately approved path.
- Keep model work outside the deterministic financial event path. No agent, UI, or ordinary API handler gains direct provider credentials or access.
- Replay substitutes captured model output by the approved identifier and never calls HTTP, a local LLM server, or another provider.
- Model input and output bodies travel only on the bounded `tkagnt ↔ tkmodl` transport and in approved replay/evidence capture; audit records store their verified hashes and attribution metadata, never the bodies.
- Embedding requests follow the same governance when an embedding instance is configured: `request_type`, `model_id`, `dimensions` are validated against its allowlists. Embedding vectors are never stored in audit records; their verified hashes and attribution metadata are. Vectors travel through the result link and may be stored in an inspection ring.
- Embedding results are replay-substituted by the approved composite dispatch identity, with captured vector bytes verified against the audit hash. No live embedding API call occurs during replay.

### Agent and model ownership in the process tile

- Zig-owned `src/tickoni/tiles/agent/` defines the agent's bounded run state, approved model-tier selection, result interpretation, and any classifier escalation rule. C stem callbacks may validate framing, stage fragments, maintain bounded transport/correlation state, and publish already-authorized requests. They must not independently encode agent routing or interpret model content as business decisions.
- `tkmodl` validates model scope and allowlists, enforces configured model limits, resolves fixture/replay or approved backend responses, accounts for tokens, and emits model-call audit references. It must not decide the agent's next step, choose a financial proposal, or gain tool/adapter authority.
- Before Phase 2, specify and test the narrow interface that lets the stem process apply Zig-owned agent decisions. The current Zig-to-C ABI does not itself provide that interface. If it cannot be implemented within the approved tile architecture, return to the framework owner instead of duplicating the decisions in C.

## Risks and completion gate

- **The current C file is a sink, not a worker.** The `tk_agent_sink_stem.c` file must be substantially rewritten to become an active agent dispatch tile. The ring-buffer result storage pattern can be preserved, but new request-dispatch logic must be added.
- **Domain logic can drift across the C ABI.** The existing stem is C while the agent's decisions belong in Zig. Phase 2 is blocked until the Zig-owned decision interface is specified and tested; copying routing, classifier escalation, adapter calls, or paper execution into the C shim is not an acceptable shortcut.
- **Multi-input fan-in changes the registry.** The maximum model configuration has one agent-request input and 11 model-result inputs before any audit acknowledgment. Model-request, agent-audit, and terminal-result outputs also exceed the current sink shape. Derive and validate cardinality from approved links; verify the maximum early.
- **Model completion arrival is nondeterministic.** Directly appending from multiple `tkmodl` audit links would make the hash chain depend on process timing. The approved tkaudt ordering/buffering rule and completion-order permutation test are required before the multi-model topology can be called replay-stable.
- **A published audit fragment is not a committed audit record.** The current `tkmodl` publishes audit and result in one callback, while `tkaudt` commits later. A final agent result needs an explicit committed-audit barrier; CNC counters and `tkagnt`'s scratch ring do not establish one.
- **The existing event-count shutdown gate can abandon in-flight work.** Define a bounded drain, terminal failure record, and restart reconciliation before replacing the passive sink with an active agent.
- **A request link alone is not an agent proof.** Prove committed agent dispatches, result attribution, and replay substitution through tkmodl and tkaudt; CNC counters are operational hints only.
- **A configured classifier cascade adds latency.** The classifier_fast → classifier_complex → classifier_escalation → hosted escalation can take up to 4 round-trips before a final decision. `MAX_CLASSIFIER_DEPTH = 4` is a hard cap; if the hosted model also returns uncertain, the result is returned with `confidence` = low and `recommended_tier` = fallback.
- **Large content needs multipart transport and memory bounds.** The current hash-only request/result records and fixture hashes cannot supply prompt or response bytes to an active agent. A single Firedancer fragment is capped at 65,535 bytes by `fd_frag_meta_t.sz`; increasing the link MTU above that would truncate the published size. Define bounded fragment streams, whole-message byte ceilings, reassembly memory, credit/depth sizing, and timeout behavior. Fail closed on incomplete or oversized input/output instead of truncating it.
- **Audit and replay capture have different data exposure.** Keep prompt, response, and vector bytes off the audit link and out of audit records. A replay capsule or evidence artifact must still retain the captured bytes needed for substitution under separately approved access and retention rules; hashes alone cannot reproduce the model result.
- **Embedding vectors inflate the result link and ring.** A 1024-dimensional `f32` vector is 4096 bytes before the result header; batching multiplies that size. A ring slot must track its result type. Consider separate chat and embedding rings only if the approved capacity calculation warrants them.
- **Embedding dimension validation.** If an agent requests a dimension not in the tkmodl instance's `allowed_embedding_dimensions`, the request must fail closed and record `agent_denied`. No silent truncation or padding.

## Multi-tkmodl fan-out design (integrated, not future work)

This plan includes multi-model fan-out as the core design. `tkagnt` supports up to 11 configured `tkmodl` instances, one per selected model tier; a topology instantiates only the tiers it needs. Each configured instance is a separate Firedancer process with its own workspace, scratch, CNC, and `TkModlRuntimeConfig`.

### Architecture: illustrative 11-instance maximum

```
tkings ──agent request──→ tkagnt
                           │
                           ├─output[0]→ tkmodl[classifier_fast]     (fast, low-cost tier)
                           ├─output[1]→ tkmodl[classifier_complex]  (more capable tier)
                           ├─output[2]→ tkmodl[classifier_escalation] (accuracy-focused tier)
                           ├─output[3]→ tkmodl[classifier_hosted]   (proprietary general-purpose)
                           ├─output[4]→ tkmodl[classifier_hosted_newer] (proprietary, improved)
                           ├─output[5]→ tkmodl[embedding]          (shared embedding)
                           ├─output[6]→ tkmodl[low]                (fast/cheap LLM)
                           ├─output[7]→ tkmodl[medium]             (balanced LLM)
                           ├─output[8]→ tkmodl[high]               (capable LLM)
                           ├─output[9]→ tkmodl[extra-high]          (very capable LLM)
                           └─output[10]→ tkmodl[max]                (most capable LLM)

tkmodl[0]  ──result──→ tkagnt (input 1)   ← classifier_fast
tkmodl[1]  ──result──→ tkagnt (input 2)   ← classifier_complex
tkmodl[2]  ──result──→ tkagnt (input 3)   ← classifier_escalation
tkmodl[3]  ──result──→ tkagnt (input 4)   ← classifier_hosted
tkmodl[4]  ──result──→ tkagnt (input 5)   ← classifier_hosted_newer
tkmodl[5]  ──result──→ tkagnt (input 6)   ← embedding (full vector; MTU pending)
tkmodl[6]  ──result──→ tkagnt (input 7)   ← low
tkmodl[7]  ──result──→ tkagnt (input 8)   ← medium
tkmodl[8]  ──result──→ tkagnt (input 9)   ← high
tkmodl[9]  ──result──→ tkagnt (input 10)  ← extra-high
tkmodl[10] ──result──→ tkagnt (input 11)  ← max

All tkmodl[0..10] ──audit──→ tkaudt
tkagnt ──agent audit──→ tkaudt
tkagnt ──terminal result──→ tkdisp (full workflow; minimal consumer pending)
tkaudt ──committed-audit acknowledgment or equivalent barrier──→ tkagnt (pending approval)
```

Each configured tkmodl instance independently sends hash/metadata-only audit records to `tkaudt` and complete content-bearing results to `tkagnt`, using multiple fragments when needed. Embedding results carry complete vector data; chat results carry complete response content. Fragment MTUs and total-message byte bounds are separate pending decisions. The terminal-result and committed-audit paths above are proposed links, not part of the current minimal or investment topology.

### Model tier classification flow

1. Incoming agent request arrives at tkagnt (input 0) with `model_tier` or `model_id`.
2. The Zig-owned agent decision selects the initial tier from the configured set. If tier is `classifier_fast` or `model_id` is unspecified under the approved routing rule, and the classifier cascade is configured:
   - Dispatch to `tkmodl[classifier_fast]` first (fast, low-cost).
   - If classifier_fast result indicates uncertainty, escalate to `tkmodl[classifier_complex]`.
   - If classifier_complex result indicates high uncertainty, escalate to `tkmodl[classifier_escalation]` (accuracy-focused).
   - If classifier_escalation still cannot resolve, dispatch to `tkmodl[classifier_hosted]` or `[classifier_hosted_newer]` (hosted proprietary for final judgment).
   - The Zig-owned agent logic validates and interprets `recommended_tier` and `confidence` from the classifier response content. `tkmodl` governs and returns that content but does not make the escalation decision.
   - All escalation is bounded by `MAX_CLASSIFIER_DEPTH = 4` (fast → complex → escalation → hosted). If a selected next tier is absent, return the approved terminal outcome; do not silently reroute.
3. If tier is `low`/`medium`/`high`/`extra-high`/`max`:
   - Dispatch directly to the matching LLM instance if configured; otherwise return the approved terminal outcome.
4. If request is an embedding request:
   - Dispatch to `tkmodl[embedding]` if configured; otherwise return the approved terminal outcome.
   - Embedding result returns with vector data.
5. Result returns from the appropriate tkmodl to tkagnt's corresponding result input link.
6. tkagnt matches `(run_id, model_request_id)` to its pending entry, verifies the source instance and expected model, and applies the Zig-owned next-step decision. It records the terminal agent outcome through `tkaudt` and publishes the terminal result only after the approved committed-audit barrier. Ring storage is observational.

### Why support up to 11 instances

- **Classifier cascade:** The proposed classifier instances can enforce separate model allowlists and resource profiles. The agent's Zig-owned logic selects and escalates between them; each `tkmodl` instance governs its own model request and does not own classifier routing.
- **Embedding isolation:** Embedding is a shared utility with different latency/cost characteristics than LLM inference. A dedicated instance avoids contention and allows embedding-specific governance (dimension allowlists, vector storage limits).
- **LLM isolation:** Each LLM tier gets dedicated resources (scratch, CNC, workspace). A slow max model doesn't starve low-tier requests.
- **Maximum tier set:** The design can represent five classifier, one embedding, and five LLM tiers. A workflow configures only the tiers it actually uses.
- **Audit clarity:** Each instance's audit output is self-contained and tied to its model's decisions. Classifier escalation is traceable through audit records.
- **Replay substitution:** Each instance has its own fixture table. Replay can substitute results per-model without cross-model ambiguity.
- **Firedancer-native:** The fan-out/fan-in pattern is already in the topology system. Each tkmodl instance is just another tile in the topology — like tkdiag's N input links, each with its own `*_tkdiag` channel.

The supported maximum is 11 `tkmodl` instances per `tkagnt`. Increasing it requires a separate contract and capacity decision, including topology, registry, memory, link, audit, and test bounds.

Completion means an approved topology and ordering contract, a delivered terminal agent result for every accepted request, committed model and agent audit records in replay-stable order, bounded in-flight shutdown/restart handling, passing registered unit and real-process tests, no model-provider bypass, zero external effects in replay, and a clearly stated live-provider status. Do not close this plan based on a compiled shim, fixture-only tests, or a result stored only in scratch.
