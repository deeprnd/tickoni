# V2.10.S11 — Plan

## Scope Summary

Three distinct problems, one story:

1. **5 failing Firedancer unit tests** — `test_alloc`, `test_wksp`, `test_bundle_client`, `test_bundle_client_wraparound`, and `test_store` — fail when `--page-sz normal` is used without explicit page count overrides (OOM from `fd_numa_mlock` when the workspace tries to allocate more pages than `--page-cnt` provides).
2. **CI memory freeing** — `tests-long.yml` uses `prlimit --memlock=unlimited` and `echo 3 > /proc/sys/vm/drop_caches` to free memory. These need removal as it wont be needed anymore.
3. **llama.cpp setup/build/run scattered** — 10+ files across `contrib/test/` and the justfile manage cloning, building (CPU vs GPU), downloading models, starting the server, and running tests. GPU support is unnecessary for CI or local dev testing; consolidate to OpenBLAS CPU-only.

## 1. Fix the 5 Failing Unit Tests

### Research Findings — How Tests Are Actually Called

**Runner pipeline:**
1. `just test-unit-fd-linux-x86-gcc` → `make ... run-unit-test TEST_OPTS="--page-sz normal -j 3"`
2. `config/everything.mk` `run-unit-test` target invokes `contrib/test/run_unit_tests.sh --tests <file> --page-sz normal -j 3`
3. `run_unit_tests.sh` iterates each test binary and calls it with `--page-sz "$PAGE_SZ" -j "$JOBS"`
4. Each test binary parses `--page-sz` and `--page-cnt` independently via `fd_env_strip_cmdline_*`

**Critical finding: `--job-mem` does not exist anywhere in the runner.** The plan story references `JOB_MEM=1073741824` and `--job-mem 1073741824`, but:
- `run_unit_tests.sh` has no `--job-mem` argument handler
- The justfile does not pass `--job-mem` (only `--page-sz normal -j 3`)
- No test binary parses `--job-mem`
- Only `orchestrator.py` line 264 (cov-report mode) contains `--job-mem 268435456`, but the cov-report path is not used by the normal justfile recipes
- The runner's `--page-cnt` defaults are per-test, not global

This means the 1 GB budget is a story-level concept, not an enforced runtime constraint. The actual failure mechanism is: each test creates a workspace with its own `--page-cnt` default, and when the default is 1 gigantic page (~1GB), the runner passes `--page-sz normal` which changes the page size but NOT the page count. So `--page-sz normal --page-cnt 1` creates a workspace of only 4 KB — far too small.

### Per-Test Workspace Defaults (from reading each test's main())

| Test | `--page-sz` default | `--page-cnt` default | Memory created |
|------|---------------------|----------------------|----------------|
| `test_alloc` | `gigantic` | `1` (~1GB) | 131072 allocs of up to 37KB each → needs several GB |
| `test_wksp` | `gigantic` | `1` (~1GB) | 65536 allocs of up to 256KB each → needs ~16 GB worst case |
| `test_bundle_client` | N/A (fd_unit_test framework) | N/A | Workspace created externally by harness |
| `test_bundle_client_wraparound` | `normal` | `256` (1 MB) | Already adapted for normal pages |
| `test_store` | `gigantic` | `1` (~1GB) | `fec_max=8-64`, `fec_data_max=31840-63985` → max ~4 MB |

### Per-Test Analysis

**test_alloc (src/util/alloc/test_alloc.c)**
- **What it does:** Concurrent allocator torture test. Allocates 131072 blocks (default `--alloc-cnt`) of random sizes up to 37KB, fills them with patterns, frees them randomly, verifies data integrity.
- **Default behavior:** `--page-sz gigantic --page-cnt 1` → ~1GB workspace. With `--page-sz normal --page-cnt 1` (what the runner passes), it gets only 4 KB.
- **Is it a huge-page-specific test?** No. It's a general allocator test. The gigantic-page default is a convenience — the test needs lots of memory regardless of page type.
- **Fix:** Override `--page-cnt` to a large enough value for normal pages. Needs ~5000+ normal pages for the default allocation count, but with 131072 allocs at 37KB avg, probably needs ~524288 (1 GB of usable space after workspace overhead).

**test_wksp (src/util/wksp/test_wksp.c)**
- **What it does:** Concurrent workspace allocator torture test. 65536 alloc/free cycles with random sizes up to 256KB, random alignment, multi-threaded with remote tiles.
- **Default behavior:** `--page-sz gigantic --page-cnt 1` → ~1GB workspace. With `--page-sz normal --page-cnt 1`, gets 4 KB.
- **Is it a huge-page-specific test?** No. It's a workspace allocator test that needs lots of memory regardless of page type.
- **Fix:** Override `--page-cnt` to a large enough value. With 65536 allocs at 256KB avg, needs ~16 GB. But the test uses random sizes, so average is lower. ~262144 normal pages (1 GB) should suffice for the average case.

**test_bundle_client (src/disco/bundle/test_bundle_client.c)**
- **What it does:** gRPC bundle client logic tests — stream handling, timeouts, header validation, key switching, status reporting, reset behavior.
- **Workspace creation:** Uses `fd_unit_test.c` template — no custom main, no `--page-sz`/`--page-cnt` parsing. The workspace is created by the test harness framework.
- **Memory needs per test env:** mcache (~1KB), dcache (~128KB), grpc_client (~16KB buf_max + stream pool), pending_txn (128 entries). Total per env is probably < 1 MB.
- **Is it a huge-page-specific test?** No. These are logic tests that just need a workspace to exist.
- **Fix:** The harness likely defaults to 1 gigantic page. Need to verify how the harness creates the workspace and override its page count. May be simpler than the others.

**test_bundle_client_wraparound (src/disco/bundle/test_bundle_client_wraparound.c)**
- **What it does:** Tests H2 buffer wraparound when receiving oversized gRPC messages — validates that the H2 rx buffer correctly handles data spanning the circular buffer boundary.
- **Default behavior:** `--page-sz normal --page-cnt 256` → 1 MB workspace. **Already adapted for normal pages.**
- **Is it a huge-page-specific test?** No. It's testing circular buffer wraparound logic, which works the same on any page size.
- **Fix:** This test is already handled. No change needed. Verify it passes with the current `--page-sz normal` runner flag (it should, since it already defaults to normal pages).

**test_store (src/disco/store/test_store.c)**
- **What it does:** FEC store tests — insert/query/remove merkle root → FEC data mappings, hash collisions, partitioned concurrent inserts.
- **Default behavior:** `--page-sz gigantic --page-cnt 1` → ~1GB workspace. With `--page-sz normal --page-cnt 1`, gets 4 KB.
- **Memory needs:** `fd_store_footprint(fec_max, fec_data_max)` = `128 + fec_max * fec_data_max`. With `fec_max=64, fec_data_max=63985`: ~4 MB. The test uses `fec_max=8` for `test_api`/`test_api2`, `fec_max=16` for `test_hash`, `fec_max=64` for `test_part`.
- **Is it a huge-page-specific test?** No. It's a store logic test. The gigantic-page default is just to ensure there's enough room without thinking about it.
- **Fix:** Override `--page-cnt` to a value that provides enough room. ~10000 normal pages (40 MB) should be more than enough for the worst-case footprint of ~4 MB.

### Approach

The plan's original approach (a `TEST_NORMAL_PAGES` dictionary + `test_pages()` function in the runner) would require modifying `run_unit_tests.sh` to support per-test page count overrides, which is non-trivial.

**Simpler approach (preferred):** Add a global `--page-cnt` flag to `run_unit_tests.sh` that overrides the per-test default, and pass the appropriate count from the justfile:

```bash
# In run_unit_tests.sh, add:
PAGE_CNT=""
while [[ $# -gt 0 ]]; do
  case "$1" in
    ...
    --page-cnt) PAGE_CNT="$2"; shift 2 ;;
    ...
  esac
done
```

Then in each test binary, when `--page-cnt` is not explicitly set by the test author AND `PAGE_CNT` is provided by the runner, use the runner's value. This way:
- Tests that explicitly set `--page-cnt` (like `test_bundle_client_wraparound` with 256) keep their explicit values
- Tests that don't set it (like `test_alloc`, `test_wksp`, `test_store`) get the runner's override
- `test_bundle_client` (no main) depends on the harness

**Alternative (even simpler):** Just pass `--page-cnt <N>` for each failing test individually in the justfile by modifying the test list generation. But this requires understanding how the test list is assembled.

**Verification of test_bundle_client_wraparound:** This test should already pass since it defaults to `--page-sz normal --page-cnt 256`. Run it separately to confirm.

### Verification

After changes, run:
```

```
All 5 should pass. Then run the full `test-unit-all` to confirm no regressions.

## 2. Remove CI Memory Freeing

### Current State

In `.github/workflows/tests-long.yml`, step "Set resource limits and run tests":
```yaml
sudo prlimit --pid $$ --nofile="$open_files:$open_files" --memlock=unlimited
sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches' || echo "drop-caches skipped"
just test-unit-fd-linux-x86-gcc
```

Per CI memory note: `prlimit` inside a justfile recipe fails (can't raise CAP_SYS_RESOURCE on GH Actions). `drop_caches` with `|| true` masks real failures. These were added in commits `9ac725089` and `4b4ab9737` but are unreliable.

### Approach

**Remove both lines entirely** from `tests-long.yml`:

- `prlimit --memlock=unlimited` — The Firedancer test launcher already computes its own page budget from `JOB_MEM`. If `fd_numa_mlock` fails, the test itself reports it. Forcing unlimited memlock actually *hurts* by hiding the real budget problem.
- `echo 3 > /proc/sys/vm/drop_caches` — `drop_caches` on a CI runner provides negligible benefit (the runner is freshly provisioned) and `|| true` silently masks failure. The 1 GB per-job budget is what matters.

The step simplifies to:
```yaml
- name: Set resource limits and run tests
  run: just test-unit-fd-linux-x86-gcc
```

### Verification

After removing, push and confirm `tests-long.yml` runs successfully on PR. If tests still OOM, go back to Option A above.

| `tests-short.yml` | CI: Windows system tests (calls just recipes) | ~50 |

### Problems

1. **GPU code paths everywhere** — `ensure_llama_cpp.sh` has `--gpu` flag with CUDA cmake flags. `run_llm_server.sh` has GPU detection + CUDA cmd. `run_llm_server_win.sh` has GPU fallback. Windows `ensure_llama_cpp_win.sh` has entire CUDA build blocks for MSVC x64.
2. **Model defaults are wrong** — `ensure_hf_model.sh` defaults to `unsloth/gemma-4-E2B-it-qat-GGUF` / `gemma-4-E2B-it-qat-UD-Q4_K_XL.gguf` (~16 GB). Story says replace with `Qwen2.5-1.5B-Instruct-Q4_K_M.gguf` (~1 GB).
3. **Duplicate backend detection** — Both `run_system_model_tests.sh` and the justfile's `infra-ensure-llamacpp` recipe detect nvidia-smi and choose GPU vs CPU. `ensure_llama_cpp.sh` also detects GPU from `--gpu` flag. Triple redundancy.
4. **Windows ARM complexity** — `ensure_llama_cpp_win.sh` is 608 lines with MSVC root discovery, SDK tool aliasing, host C++ wrapper generation, embed.cpp patching, CMakeLists.txt patching, toolchain file generation. Most of this is needed because llama.cpp's build system is complex on Windows, not because we need GPU.

### Approach

**Create one unified script: `contrib/test/ensure_llama_cpp.sh` (replacing both POSIX and Windows versions)**

The new script handles:
- Clone llama.cpp if missing
- Always build with `-DGGML_BLAS=ON -DGGML_BLAS_VENDOR=OpenBLAS` (no CUDA, no CPU-only-only cmake flags)
- On Windows: use the existing clang+MSVC toolchain detection but strip all CUDA/GPU code paths
- Copy built binaries to the llama.cpp root
- Always exit 0 if binary exists and is built with OpenBLAS

**Simplify `run_llm_server.sh` and `run_llm_server_win.sh`:**
- Remove the GPU command path entirely
- Accept only `--cpu` (or just run CPU unconditionally, removing the backend argument)
- Remove `nvidia-smi` checks, `CUDA_VISIBLE_DEVICES`, `--device cuda0`, `-ngl all`, etc.
- Keep the CPU command as-is (it's fine)

**Simplify `run_system_model_tests.sh` and `run_system_model_tests_win.sh`:**
- Remove backend detection (`nvidia-smi`, `ldd` cuda check)
- Always call `ensure_llama_cpp.sh` with no GPU flag
- Always run the server in CPU mode
- Hard-code `backend=cpu`

**Update `ensure_hf_model.sh`:**
- Change defaults to Qwen2.5-1.5B-Instruct-Q4_K_M:
  - `TK_HF_REPO_ID=Qwen/Qwen2.5-1.5B-Instruct-GGUF`
  - `TK_HF_MODEL_FILE=Qwen2.5-1.5B-Instruct-Q4_K_M.gguf`
  - `TK_HF_MODEL_DIR=$HOME/work/models/qwen2.5-1.5b`

**Update justfile:**
- Remove `infra-run-llamacpp` and `infra-run-llamacpp-win` recipes (no more GPU detection, no need for separate "ensure" + "run" split — the system test scripts handle that)
- Simplify `infra-ensure-llamacpp` and `infra-ensure-llamacpp-win` to just call the unified script
- Keep `infra-ensure-model`

**Update CI workflows:**
- `tests-xlong.yml`: Remove `apt-packages: 'cmake libopenblas-dev libopenblas64-dev'` — keep it (OpenBLAS is needed). The build step stays but calls the simplified script.
- `tests-short.yml` Windows sections: Remove any `--gpu` flags from `ensure_llama_cpp_win.sh` calls.

## Execution Order

1. **Fix 6 failing tests** (surgical patch to `run_unit_tests.sh`)
2. **Remove CI memory freeing** (2-line deletion in `tests-long.yml`)
3. **Consolidate llama.cpp** (rewrite 2 files, strip 4 files, update justfile, update CI)

Steps 1 and 2 are independent and can be done in any order. Step 3 depends on neither. Do 1 first (lowest risk), then 2 (also low risk), then 3 (highest impact).

## Risk Assessment

- **Step 1:** Low risk — adding entries to a per-test page override dictionary. If a page count is wrong, the test just fails again with a different error (still ENOMEM), and the count can be bumped.
- **Step 2:** Low risk — removing unreliable CI hacks. If tests start failing again, the root cause is the memory budget, and Step 1 addresses it.
- **Step 3:** Medium risk — large refactoring across 9 files. The GPU path is dead code (no GPU in CI), so stripping it is safe. The main risk is breaking the Windows build or the model download. Mitigation: keep environment variable overrides (`TK_LLAMA_CPP_DIR`, `TK_HF_REPO_ID`, etc.) so developers can still customize if they want GPU builds locally.
