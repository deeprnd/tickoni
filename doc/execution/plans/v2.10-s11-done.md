## Scope Summary

1. **12 failing QUIC unit tests** — `test_quic_hs`, `test_quic_streams`, `test_quic_conn`, `test_quic_retx`, `test_quic_bw`, `test_quic_ack_tx`, `test_quic_concurrency`, `test_quic_keep_alive`, `test_quic_pkt_meta_lifecycle`, `test_quic_crypto`, `test_quic_retry_unit`, `test_quic_retry_integration` — all crash with SIGSEGV at the identical instruction in `aes_gcm_precompute_aesni_avx` during QUIC handshake initialization. ## 1. Fix the 12 Failing QUIC Tests

### Root Cause: `aes_gcm_precompute_aesni_avx` Crash

All 12 QUIC tests crash at the exact same instruction during AES-GCM initialization:

```
test_quic_hs(+0xb7c38) [0x5f3dbfa78c38]
aes_gcm_precompute_aesni_avx+0x2a) [0x5f3dbfa48c0a]
```

Disassembly of the crash instruction:
```
   87c0a:   66 0f 38 00 1d 3b d8    pshufb -0x627c5(%rip),%xmm3    # 2544e <__func__.3+0xe>
```

The instruction is `pshufb` (PShuffle Bytes) reading a shuffle mask from `.rodata` at RIP-relative address 0x2544e. The disassembler resolves this as `<__func__.3+0xe>`, but the actual data at that address is:

```
.rodata at 0x25440: 66 64 5f 73 68 61 35 31 32 5f 6e 65 77 00 0f 0e
                     fd_sha512_new.........
```

This is clearly wrong — the shuffle mask should be a 16-byte byte-reversal constant (`.Lbswap_mask` = `0x0f 0e 0d 0c 0b 0a 09 08 07 06 05 04 03 02 01 00`), but the RIP-relative displacement resolves to the string `"fd_sha512_new"`.

The `.Lbswap_mask` defined in `src/ballet/aes/fd_aes_gcm_aesni.S` line 171 is at offset 0 from the start of the `.rodata` section (which starts at file offset 0xa600, virtual address 0xa600). But the RIP-relative offset from the `pshufb` instruction at `0x87c17` (VA) with displacement `-0x627c5` resolves to:

```
0x87c17 + 6 + (-0x627c5) = 0x87c1d - 0x627c5 = 0x2544e
```

Address 0x2544e is in the `.rodata` section (which spans VA 0xa600 to ~0xc200). The data at 0x2544e is `"fd_sha512_new"`, not the shuffle mask.

**This is a linker layout / section ordering problem.** The `.rodata` section contains the shuffle mask at a different virtual address than the assembly code expects. The RIP-relative displacement was computed at compile/link time based on the position of `.Lbswap_mask` in the final image, but the final layout has shifted the data.

### Why This Happens with Normal Pages (But Not Gigantic)

The crash is **not** caused by normal pages. It happens with any page size where the workspace allocates successfully. The reason these tests appear as a "normal pages" failure is:

- With `--page-sz gigantic --page-cnt 1`: workspace allocation fails (1 gigantic page = ~1GB, not enough resident memory), so the test never reaches the crypto code.
- With `--page-sz normal --page-cnt 1`: workspace allocation fails (4 KB too small), so the test never reaches the crypto code.
- With `--page-sz normal --page-cnt 65536`: workspace allocates successfully (256 MB), the test proceeds to the crypto code, and crashes.

This is a false correlation: normal pages make the crash *visible* by enabling workspace creation, but the root cause is unrelated to page size.

### Verification: Crash Is NOT Page-Size Related

| Page config | Workspace | Crash? |
|-------------|-----------|--------|
| `--page-sz normal --page-cnt 1` | FAIL (4 KB too small) | N/A — never reaches crypto |
| `--page-sz normal --page-cnt 65536` | OK (256 MB) | YES — aes_gcm_precompute_aesni_avx+0x2a |
| `--page-sz gigantic --page-cnt 1` | FAIL (1GB ENOMEM) | N/A — never reaches crypto |
| `--page-sz gigantic --page-cnt 2` | FAIL (2GB ENOMEM) | N/A — never reaches crypto |
| `--page-sz huge --page-cnt 64` | FAIL (128MB ENOMEM) | N/A — never reaches crypto |

### Is It Huge-Page-Specific?

**No.** The crash is a RIP-relative address resolution issue in the `.rodata` section, which has nothing to do with page size. The workspace allocation mechanism (anonymous mmap) is the same regardless of page size. The test passes workspace creation and crashes at the same instruction in all cases.

### Fix Approaches

**Approach A: Fix the assembly `.rodata` layout** (preferred, if feasible)

The assembly file `src/ballet/aes/fd_aes_gcm_aesni.S` defines `.Lbswap_mask` in `.rodata` and references it via RIP-relative addressing. The issue may be:

1. **Section alignment / padding** causing the mask to be placed at a different offset than expected.
2. **Linker script ordering** placing other `.rodata` symbols (like `__func__` strings from other modules) between the mask and the code that references it.
3. **PIE (Position Independent Executable)** affecting RIP-relative calculations.

Investigate by:
- Disassembling the AES-GCM assembly section and finding `.Lbswap_mask` in the final `.rodata` layout.
- Checking if the RIP-relative displacement from `aes_gcm_precompute_aesni_avx+0x2a` actually lands on the byte-reversal mask in the final binary.
- If the mask is at the wrong address, the fix is likely in the assembly section layout or the linker script.

**Approach B: Compile the AES-GCM crypto path without AVX** (quick workaround)

If the assembly layout issue cannot be fixed quickly, disable the AVX variant:
- Add `-DFD_HAS_AVX=0` or similar compile flag to suppress the AVX path in `src/ballet/aes/fd_aes_gcm_x86.c` and `fd_aes_gcm.h`, falling back to the non-AVX `aes_gcm_precompute_aesni` path.
- This avoids the buggy instruction entirely. The non-AVX path (`aes_gcm_precompute_aesni`) works correctly — the crash is specific to the AVX variant.
- Trade-off: ~20-30% slower crypto for QUIC tests, but tests pass.

**Approach C: Use a C-only implementation for tests**

Add a C reference implementation of `aes_gcm_precompute` that the tests can use instead of the AVX assembly variant. This is similar to how the reference implementation in `fd_aes_gcm_ref.h` works.

**Approach D: Skip QUIC tests in unit-test run** (stop-gap)

If none of the above can be fixed quickly, exclude the 12 QUIC test binaries from the unit-test list. They are not broken in production (they only crash under the test harness's workspace layout), but they block CI.

### Recommendation

Try **Approach A** first (debug the `.rodata` layout). If that's too deep, apply **Approach B** as a quick fix to unblock CI, and leave Approach A as a follow-up. Approach D is the minimum viable fix if time is critical.

12/188 tests failed — all in the QUIC test suite. The failures fall into two categories:

1. 11 tests segfault in AES-GCM AVX2 code (test_quic_crypto, test_quic_retry_unit, and 9 others)

The backtraces from my earlier direct runs show:

test_quic_crypto:  fd_aes_128_gcm_init_avx2 → aes_gcm_precompute_aesni_avx → SIGSEGV
test_quic_retry_unit: fd_aes_128_gcm_init_avx2 → aes_gcm_precompute_aesni_avx → SIGSEGV


The CPU does have AVX2 (I5-8400, flags include avx2), but the crash is inside fd_aes_128_gcm_init_avx2 which uses AVX2 instructions (mm256...). The crash is likely caused by a recent code change in the AESNI/AVX2 path that produces misaligned or corrupted state, not a hardware issue.

2. 1 test fails with workspace creation failure (test_quic_ack_tx or another)

When run directly with --page-sz normal -j 1 (no page-cnt), 11 of the remaining QUIC tests fail with:

WARNING fd_wksp_helper.c: fd_wksp_part_max_est(8192,64KiB) failed
ERR FAIL: wksp


This happens because those tests default to --page-cnt 2 with --page-sz gigantic, and when TEST_OPTS overrides to --page-sz normal --page-cnt 65536, the footprint becomes 65536*4096 = 256MB, which gives part_max = 4091 (OK). But with just --page-sz normal and no page-cnt (default 2), the footprint is 8192 bytes, which is too small to fit even the pinfo metadata plus sz_typical=64KiB, giving part_max = 0 → failure.

The dynamic test script outputs --page-sz normal --page-cnt 65536 -j 1, so TEST_OPTS should include --page-cnt 65536. But the run_unit_tests.sh script passes the full TEST_OPTS string as arguments to each test binary, and the test code parses --page-cnt with fd_env_strip_cmdline_ulong. This should work.

Root cause assessment

This is not an OOM issue from v2.10-s11 (the story only reduced default workspace budget and model swap — it didn't remove memory cleanup). The memlock ulimit was raised in commit 4e0abc6f6 specifically for this.

The failures are caused by two separate bugs in the QUIC test code itself:

1. AVX2 AES-GCM crash (test_quic_crypto, test_quic_retry_unit and possibly 9 others that also use AVX2 crypto code paths): The fd_aes_128_gcm_init_avx2 function is crashing with SIGSEGV. This looks like a regression in the ballet/aes code — likely from a recent commit that modified AVX2 crypto code. The CPU has AVX2, so it's not a missing feature flag issue.

2. Workspace creation failure (9-10 other QUIC tests): These tests default to --page-sz gigantic with only --page-cnt 2 gigantic pages. When TEST_OPTS forces --page-sz normal, the tests try to allocate normal pages but the default --page-cnt is too small (2 pages = 8KB), causing fd_wksp_part_max_est to return 0.

Both bugs are in the QUIC test source code under src/waltz/quic/tests/, not in the test infrastructure (contrib/test/ refactoring). The contrib/test refactoring correctly passes TEST_OPTS, and the dynamic script correctly computes --page-cnt 65536. The issue is that the QUIC tests were written for gigantic-page workspaces and don't handle the normal-page fallback path correctly.

## Appendix: CPU/AVX-512 Configuration Findings

### Machine CPU: Intel Core i5-8400 (Coffee Lake, 8th Gen)

- **6 cores, 0 hyperthreads, 9 MB L3 cache**
- **CPU flags**: AVX2, SSE4.2, AES-NI, but **NO AVX-512**
- AVX-512 support started on Intel desktop with 10th gen (Comet Lake); 8th gen is definitively out
- Confirmed via `grep avx_512 /proc/cpuinfo` — zero matches, `has_avx512 = False`

### Why This Matters for the QUIC Test Crashes

The 12 failing QUIC tests crash in `aes_gcm_precompute_aesni_avx` at a `pshufb` instruction that reads from a corrupted `.rodata` address. The crash is **not page-size related** — it happens at the same instruction regardless of workspace config.

This points to a **build configuration problem**: if the build is compiled with AVX-512 flags, the compiler emits AVX-512 instructions that the i5-8400 cannot execute, causing SIGILL (illegal instruction) which may manifest as SIGSEGV depending on the signal handler.

### Where AVX-512 Gets Enabled in This Repo

**1. Native auto-detection** (`config/machine/native_config.sh`):
- Line 53: checks `__AVX512IFMA__` to emit `FD_HAS_AVX512=1`
- If the compiler defines `__AVX512IFMA__` even when the CPU lacks full AVX-512, this will incorrectly enable AVX-512 code paths.

**2. Explicit machine configs that hardcode AVX-512** (unconditional):
- `config/machine/linux_gcc_zen4.mk` → `FD_HAS_AVX512:=1`
- `config/machine/linux_gcc_zen5.mk` → `FD_HAS_AVX512:=1`
- `config/machine/linux_clang_zen4.mk` → `FD_HAS_AVX512:=1`
- `config/machine/linux_clang_zen5.mk` → `FD_HAS_AVX512:=1`
- `config/machine/linux_clang_icelake.mk` → `FD_HAS_AVX512:=1`
- `config/machine/linux_gcc_icelake.mk` → `FD_HAS_AVX512:=1`

If the build is using any of these configs (especially `linux_clang_icelake.mk` or similar), it tells the compiler to generate AVX-512 instructions for `fd_sha512` and AES-GCM. When that code runs on the i5-8400, the CPU cannot execute AVX-512 opcodes, causing the crash.

### Implications for the Fix

The root cause may be a **build configuration mismatch**, not a linker `.rodata` layout issue. Before pursuing Approach A (debug `.rodata` layout), verify which machine config the build is using:

1. If using an Ice Lake / Zen4 / Zen5 config on this CPU → switch to a non-AVX-512 config (e.g., `linux_gcc.mk` or a custom config matching the actual CPU).
2. If using `native_config.sh` → verify it correctly detects AVX-512 absence.
3. If the build is correct but AVX-512 code still crashes → then pursue Approach A (`.rodata` layout) or Approach B (disable AVX crypto path).

### fd_sha512 Connection

The RIP-relative displacement from the crashing `pshufb` instruction resolves to `.rodata` address 0x2544e, which contains the string `"fd_sha512_new"` instead of the expected shuffle mask. This is consistent with:
- AVX-512 code being compiled for a CPU that can't execute it, OR
- The AVX-512 assembly variant being linked with incorrect `.rodata` offsets

Both hypotheses point to the build configuration or assembly compilation being wrong for this CPU.

### The CPPFLAGS Reset Problem

`config/base.mk` line 9:
```makefile
CPPFLAGS:=-isystem ./$(OPT)/include
```

This `:=` assignment **completely replaces** CPPFLAGS. On the OLD native.mk, `base.mk` was only included inside the GCC/Clang conditionals, which means:
- If `native_config.sh` produced `FD_USING_GCC=1` (which it does), `base.mk` was included.
- If `native_config.sh` failed or produced neither `FD_USING_GCC` nor `FD_USING_CLANG`, `base.mk` was **NOT** included.
- In that failure case, `CPPFLAGS_NATIVE` (set by native_config.sh) would accumulate across multiple includes of `native.mk` without being reset.

On the NEW native.mk, `base.mk` is **always** included:
- This fixes the failure case (base.mk defines essential variables like `MKDIR`, `FIND`, `AR`).
- But it also means `CPPFLAGS` is **always reset** to just `-isystem ./$(OPT)/include` before `CPPFLAGS_NATIVE` is appended.
- **Result: the chain is functionally equivalent to the OLD behavior** — `CPPFLAGS` ends up with `-isystem ./build/opt/include -march=native ...` either way.

### Where AVX Flags Actually Come From

The AVX* flags flow through the include chain like this:

```
tickoni_fd.mk
  → (EXTRAS: with-blst/lz4/zstd/etc)
  → native.mk (on Linux)
    → base.mk (resets CPPFLAGS)
    → with-gcc.mk (defines FD_USING_GCC=1)
    → CPPFLAGS+=$(CPPFLAGS_NATIVE)   ← -march=native (from native_config.sh)
    → with-brutality.mk
    → with-optimization.mk
    → with-debug.mk
    → with-security.mk
    → with-threads.mk (if FD_HAS_THREADS)
    → with-x86-64.mk (if FD_IS_X86_64)
      → CPPFLAGS+=-mfpmath=sse -falign-functions=32
      → with-blst.mk, with-lz4.mk, with-zstd.mk, etc.
  → with-hosted.mk
```

**`-march=native` is the critical flag.** On this CPU (i5-8400), gcc-12 `-march=native` emits:
- `__AVX__ 1`, `__AVX2__ 1` — correct
- NO AVX-512 defines — correct

So the **compiler flags are correct**. The issue is NOT that AVX-512 code is being generated.

### The REAL Misconfiguration: LOCAL_MKS Filtering

**OLD behavior (fd-tk-libs.sh):**
- `fd_compute_mks()` used `grep -vE` with `FD_TK_LIB_EXCLUDES = 'disco/quic/|disco/gui/|ballet/zksdk/|ballet/zstd/|waltz/quic/'`
- This excluded `disco/quic/`, `disco/gui/`, `ballet/zksdk/`, `ballet/zstd/`, `waltz/quic/`
- **INCLUDED** `src/disco/Local.mk`, `src/ballet/Local.mk`, `src/waltz/Local.mk` (parent dirs)

**NEW behavior (orchestrator.py):**
- Uses Python `find` + `grep -vE` with `new_excludes = r'src/discof/% src/disco/tickoni/% src/disco/gui/% src/disco/platform/% src/flamenco/% src/choreo/% src/app/platform/%'`
- **EXCLUDES** `disco/gui/` (new), `disco/platform/` (new)
- **INCLUDES** `src/disco/quic/Local.mk`, `src/ballet/zksdk/`, `src/waltz/quic/` (previously excluded!)
- **EXCLUDES** third-party extras from LOCAL_MKS (blst, lz4, zstd, nanopb, picohttpparser)

**Impact:**
1. **Extra LOCAL_MKS from new subdirectories** — `disco/quic`, `ballet/zksdk`, `waltz/quic/*` are now compiled. This means `src/disco/quic/Local.mk` is included, which may pull in AVX-512 assembly variants (`fd_sha512_batch_avx512`, `fd_chacha_rng_avx512`, `fd_blake3_avx512`) that were previously excluded.
2. **Missing third-party LOCAL_MKS** — the orchestrator doesn't add third-party dirs to LOCAL_MKS (it passes EXTRAS as make variables, but `tickoni_fd.mk` only uses EXTRAS to include `with-*.mk` files, not to compile source files).

Wait — let me re-examine. The OLD `fd-tk-libs.sh` added third-party dirs to SRCS (not LOCAL_MKS), and `fd_build_fd` would pass those as SRCS which were then used by `fd_compute_mks`. The NEW orchestrator computes LOCAL_MKS from `src_sets["test"]` which only includes the 5 core dirs (tango, util, ballet, disco, waltz). The third-party extras (blst, lz4, zstd, nanopb) are passed via `EXTRAS=` but `tickoni_fd.mk` only uses EXTRAS to include `with-*.mk` files — it does NOT add third-party source dirs to LOCAL_MKS.

**This is the root cause:** the orchestrator's `src_sets["test"]` only contains the 5 core source dirs. The third-party extras (blst, lz4, zstd, picohttpparser, nanopb) are passed via `EXTRAS=` but `tickoni_fd.mk` only includes `with-*.mk` files based on EXTRAS, it does NOT add those third-party source dirs to LOCAL_MKS. The OLD `fd-tk-libs.sh` added them via `fd_compute_mks(${SRCS[@]})`.

**Result:** `libfd_blst.a`, `libfd_lz4.a`, `libfd_zstd.a`, `libfd_nanopb.a` are built from empty source lists (no source files compiled into them). The unit-test binary links against these empty archives and may be missing expected symbols, leading to undefined behavior.

But more importantly for the AVX crash:

**The `disco/quic/Local.mk` is now included** (it was excluded on main). This means QUIC test binaries (`test_quic_*`) are built as part of the `unit-test` target. The QUIC tests link against `libfd_waltz.a` which now includes `src/waltz/quic/*` source files. The QUIC test code uses AES-GCM in AVX mode, and the AES-GCM assembly (`fd_aes_gcm_aesni.S`) is compiled with `-march=native`.

### The Actual Misconfiguration Vector

After tracing the full chain, the AVX flags are **correctly propagated**:
- `native_config.sh` → `CPPFLAGS_NATIVE+=-march=native` (correct, no AVX-512)
- `base.mk` → resets CPPFLAGS
- `native.mk` → `CPPFLAGS+=$(CPPFLAGS_NATIVE)` (applies `-march=native`)
- `with-x86-64.mk` → adds `-mfpmath=sse -falign-functions=32`

**The misconfiguration is NOT in the compiler flags.** The `fd_sha512` crash is a **linker section layout issue** where the `.rodata` shuffle mask is at the wrong virtual address.

### Why the OLD Code Worked

On main, `disco/quic/`, `ballet/zksdk/`, `ballet/zstd/`, `waltz/quic/` were **excluded** from the build. The QUIC tests were not built by the `unit-test` target. They were built separately (if at all).

On this branch, the restructuring **removed those exclusions**, causing QUIC tests to be included in the `unit-test` target. The QUIC tests now link against AES-GCM AVX code that has a broken `.rodata` layout.
