### Task 4: Audit and align tile_registry process_fn entries with stem dispatch

**Goal:** Determine whether `tile_registry.zig`'s process_fn entries for tkaudt and tknorm are live or dead code, then update them accordingly.

**Current state:** The stem dispatch is **already wired in C** — `tile_run.c` routes `tile_is_audit()` → `TK_AUDIT_RUN` and `tile_is_normalize()` → `TK_NORM_RUN` via `tk_topo_run_tile`. The registry's process_fn entries (`tkaudtProcess`, `tkrnormProcess`) may be live (used by non-stem dispatch paths like testing or fallback) or dead code.

**What needs to happen:**
1. Trace how the supervisor selects which dispatch path to use for each tile — does it go through `tile_run.c` (stem path) or directly call `tile_registry.zig`'s process_fn?
2. If the registry's process_fn entries are dead code for stem tiles, set them to `null` (or remove them) and update the test `"process_fn is set for the 5 pipeline-stage tiles"` to exclude stem tiles.
3. If they're live (used for testing, fallback, or non-stem deployment), document the dual-path and keep them.

**Approach:** Check the supervisor's tile dispatch logic and `tile_main.zig` to trace the actual runtime path. The integration tests (`test_audit_stem_tile.zig`, `test_norm_stem_tile.zig`) already exercise the stem tile and confirm it runs — use them as the verification gate.

**Verification:** Build compiles. Integration tests pass. The dispatch path for tkaudt and tknorm is verified to go through stem (not process-mode wrappers) in production.

**Risk:** Low — this is a trace-and-update task, not a behavioral change. If process_fn entries are live, we preserve them; if dead, we remove them.

## Risks and Mitigations

1. **Backward compatibility:** The `audit_sink.zig` compatibility shim (Task 2) ensures no consumer breaks mid-refactor. It can be removed in Task 5 after all imports are verified.

2. **Schema unification alignment:** `audit_mod` (translate-c) must produce structs with identical layout to the original Zig definitions. This is enforced at compile time — if the layouts differ, the build fails. Same invariant the parity test checked.

3. **Stem tile activation:** Task 4 is the highest-risk step — it changes which code path runs at runtime. The integration tests for the stem tile (`test_audit_stem_tile.zig`, `test_norm_stem_tile.zig`) must pass before attempting Task 5.

4. **Sequential test impact:** `mod.zig`'s `runOneSequentialForTest` calls `runAudit` (from `audit_stage.zig`). Removing `audit_stage.zig` means this test must be updated — either to use the stem tile's behavior directly or to remove the audit stage call and rely on the stem tile integration tests for audit coverage.

5. **Import cycles:** `audit_shared.zig` imports `runtime.zig` (for `PolicyDecision` enum used in `buildPolicyDecisionEvent`). `runtime.zig` imports `audit_shared.zig` (for `audit_seed`). This creates a cycle: `audit_shared → runtime → audit_shared`. **Solution:** Move `PolicyDecision` to `audit_shared.zig` as well, or move `buildPolicyDecisionEvent` to `audit_log.zig` and have `audit_shared.zig` only hold constants. The simpler fix: `audit_shared.zig` holds only constants (tile_id, audit_seed), `buildPolicyDecisionEvent` stays in `audit_log.zig` where it already imports `runtime.zig` via `audit.AuditEvent`.
