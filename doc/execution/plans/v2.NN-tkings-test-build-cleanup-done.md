# Eliminate test-only code from production tkings binary

> **Goal:** Remove test-only code from the production tkings stem tile binary.
> Currently `tkings_set_request_source`, `tkings_set_stuck_hook`,
> `tkings_set_crash_after_heartbeats`, and the agent-request source path
> (struct fields `request_builder`, `fragment_hook`, `tx`, `tx_active`,
> `stuck_after`, `stuck_sleep_ns`, `crash_after_heartbeats`; global params
> `tkings_*_param`; callback functions `tkings_stage_request`,
> `tkings_publish_request_fragment`; and `buildRequest`/`injectFault` in Zig)
> are compiled into the production binary. `test_build.enabled` gates the Zig
> callers, but the C shim has no `#ifdef` guard. The production binary carries
> ~50 lines of test code plus a larger context struct.
>
> **Fix:** Remove test-only code from `tkings` entirely. `tkings` is the
> universal event ingestion tile — the single entry point for all events
> (reads, writes, proposals, executions, investigations, replay capsules).
> It doesn't need to know domain semantics; it frames events canonically and
> pushes them through the generic pipeline. Every event carries a `case_id`
> (set by `tkapi` for user requests, generated by `tkcase` for downstream
> events) so the entire lifecycle of one request is traceable. The test
> harness owns test data generation and injects events through `tkings`'s
> input link. No preprocessor guards, no `FD_STEM_TEST_BUILD`, no dual-source
> design.

---

## Why this matters

### What's wrong with the current design

The current `tkings` tile owns **two** event sources in the same binary:

1. **Payment events** — the production path: synthetic offsets, `PaymentMessage`
   generation, `tkings_stage_payment` / `tkings_publish_payment_fragment`.
2. **Agent-request events** — the test-only path: multipart `TkAgentRequestHdr`
   + prompt streams, `request_builder`, `fragment_hook`, `tkings_stage_request`,
   `tkings_publish_request_fragment`, plus fault injection (`stuck_after`,
   `crash_after_heartbeats`).

These two sources share one context struct, one set of callbacks, and one
binary. A `#ifdef FD_STEM_TEST_BUILD` guard at the C level and a
`runtime.test_build.enabled` gate at the Zig level prevent the agent-request
path from executing in production — but the code is still compiled, linked, and
present in every binary.

**This is architecturally wrong.** `tkings` is the **universal event ingestion
tile** — the single entry point for all events. Its designated domain is:
receive events, frame them canonically, assign source offsets, apply ingress
backpressure, and push them through the generic pipeline. It does not own test
data generation, agent-request routing, or fault injection.

### Why the dual-source design was introduced

The dual-source design was a shortcut for two reasons:

1. **Missing `tkdisp` scheduler mode:** The investment workflow topology requires
   agent requests to flow through `tkdisp → tkagnt → tkmodl`, but `tkdisp`'s
   scheduler mode depends on `tkcase`, which is a placeholder. Without `tkcase`,
   there was no entry point for agent requests into the agent pipeline.

2. **Use cases bypass `tkings` entirely:** All 11 use cases go through
   `tkapi` directly — `tkapi` calls `tkpoly`, `tkport`, `tkcase`, `tkdisp`
   as an orchestrator. `tkings` doesn't appear in any use case flow. This
   made `tkings` irrelevant to the product vision.

Adding a test-only source to `tkings` was a workaround for (1), and the
use cases' direct `tkapi → tkpoly/tkcase/tkdisp` routing meant (2) there was
no product reason for `tkings` at all. The dual-source design violated the
tile domain boundary in both directions.

### The correct design: single generic pipeline, tile domains, trace IDs

**The single pipeline for all events:**
```
External event (from tkapi or tkrepl)
  -> tkings (canonical framing, source offset)
  -> tknorm (canonical normalization)
  -> tkdedu (deduplication)
  -> tkcase (case scoping — case_id assigned here)
  -> tkpoly (policy check — allow/deny/require_approval)
  -> tkaudt (append-only audit chain — trace_id recorded in every record)
  -> tkdisp (agent dispatch — only for events needing analysis)
```

Every event — dashboard read, trade proposal, rebalancing investigation,
trade execution, retrospective analysis, replay capsule — flows through the
same spine. No special cases, no different flows per use case.

**Trace ID propagation:**
- `tkapi` sets the initial `case_id` when it receives a user request
- `tkcase` generates `run_id` values for downstream agent runs
- Every event in `tkaudt` carries the `case_id` (for the original request)
  and optionally `run_id` (for agent sub-runs)
- `tkrepl` reads the `case_id` from the completed audit and re-injects the
  replay capsule with the same `case_id` so the replay result is traceable

**`tkings` (universal ingestion):**
- Receives events on its input link (from `tkapi` or `tkrepl`)
- Frames events canonically (source identity, workflow, capability envelope,
  case/run id, instrument, side, notional)
- Assigns source offsets deterministically
- Applies ingress backpressure
- Produces events on its output link
- **Does not know domain semantics.** It doesn't need to know "this is a
  trade proposal" or "this is a replay capsule." It just frames the event
  canonically and pushes it through the pipeline. The downstream tiles
  (`tkcase`, `tkpoly`, `tkdisp`) understand the semantics.

**`tkapi` (thin transport + auth):**
- Receives HTTP/WebSocket requests
- Validates transport shape, authenticates client
- Sets the initial `case_id` on the event
- Routes the event to `tkings` for canonical framing
- Returns responses from downstream results
- **Does not orchestrate.** It doesn't call `tkpoly`, `tkport`, `tkcase`,
  or `tkdisp` directly. It delegates to the pipeline.

**`tkrepl -> tkings` (replay loop):**
- `tkrepl` reads completed audit records from `tkaudt`
- Extracts the replay capsule
- Re-injects the capsule through the `tkrepl_tkings` link (reliable,
  `permit_no_producers`) — the same `tkings` input link used by `tkapi`
- `tkings` processes it through the same spine, with external effects
  disabled by `tkexec` (when implemented) or by policy
- Divergence is reported if replay results differ from captured results
- The replay result carries the same `case_id` so the full lifecycle
  (original request + replay verification) is traceable in `tkaudt`

**Test harness (separate module, not part of `tkings`):**
- Builds synthetic test events in the format `tkings` expects on its input link
- Injects events through `tkings`'s input link (same link `tkapi` uses and
  `tkrepl` will use for replay)
- Handles fault injection at the harness level (process kill, link corruption,
  corrupted replay capsules), not via hooks inside `tkings`
- Does not call `tkings` setters

**Result:** `tkings` is a clean production tile. The test harness exercises
it by feeding events through its public interface (the input link), just like
`tkapi` does in production. No setters, no test structs, no preprocessor
guards. Every use case follows the same pipeline — no special cases. Every
event is traceable via `case_id`.

### Why this matters for the system

1. **Single pipeline.** Every use case follows the same flow. No special cases,
   no routing logic in `tkapi`. The pipeline is generic and domain-agnostic.
   `tkings` frames, downstream tiles route.

2. **Full traceability.** Every event carries a `case_id` from creation
   (`tkapi`) through the entire pipeline to replay (`tkrepl`). There is no
   "lost" event — every request is auditable end-to-end.

3. **Replay is part of the pipeline.** Replay doesn't bypass `tkings` or
   have its own special mechanism. It re-injects through the same input link,
   goes through the same spine, and produces traceable results.

4. **Security.** Test fault-injection code in production binaries is a surface
   area that should not exist. Even if gated, it violates the principle that
   production code should be minimal and auditable.

5. **Testability.** When the test harness owns event injection, it tests
   `tkings` through its actual interface (the input link), not through
   internal setters. This is the same interface `tkapi` uses in production
   and `tkrepl` uses for replay.

6. **Domain clarity.** `tkings` doesn't need domain semantics — it just needs
   to frame events canonically. Domain understanding lives in `tkpoly` (what
   events are allowed), `tkcase` (how events are scoped), and `tkdisp` (how
   agents are routed).

### Step 9: Test harness feeds events through `tkings`'s input link

**Goal:** The test harness (previously `model_request_source.zig`)
injects test events into `tkings` through the same mechanism that
`tkrepl` will use for replay. `tkings` does not know or care about
data provenance.

**What this means for the test harness:**
- The harness builds test events (payment events or agent-request
  events) in the same format `tkings` expects on its input link.
- The harness calls the same C shim functions that a real producer
  would call: `fd_dcache_publish`, `fd_stem_publish`, or whatever
  mechanism `tkings`'s input link uses.
- `tkings` receives the fragments, stages them, and processes them
  through its normal path: `tkings → tknorm → tkdedu → tkpoly → tkaudt`.
- If `tkings` needs to handle agent-request events (multipart streams),
  that is a **production capability**, not a test-only feature. It
  belongs in `tkings` if the product requires it.

**What this means for `tkings`:**
- `tkings` is a black box: it accepts events on its input link and
  produces events on its output link. It does not need any special
  code to handle test data.
- If the test harness injects malformed events, `tknorm` rejects them
  (production behavior). If it injects duplicates, `tkdedu` drops them
  (production behavior). If it injects policy-violating events, `tkpoly`
  denies them (production behavior).
- Fault injection (stuck, crash) happens at the test harness level, not
  in `tkings`.

**Verification:** Tests that previously used `tkings`'s agent-request
source now use the test harness to inject events through the input link.
The stem tile under test receives the same events, processes them
through the same path, and produces the same outputs.

**Risk:** Medium — this is the behavioral change. If the test harness
injects events that `tkings` was not designed to handle (e.g.,
agent-request multipart streams in a payment-only tile), that is a
product requirement gap, not a test problem. Either:
1. The tile needs to support the event type (production feature), or
2. The test harness injects only events the tile handles correctly.

## Key design points

1. **No preprocessor guards.** We do not need `FD_STEM_TEST_BUILD`. The
   production binary simply does not contain test code. The C compiler
   compiles what the Zig build system tells it to compile.

2. **`tkings` is a production tile.** It accepts events on its input
   link and produces events on its output link. It does not own test
   data generation. The test harness builds and injects test events
   through the input link — the same link `tkrepl` will use for replay.

3. **No dual-source design.** `tkings` has one source: events on its
   input link. The payment generator is configured by
   `tile_main_config.zig`. No second source exists.

4. **The test harness is the test data owner.** `model_request_source.zig`
   (or its test-harness location) builds synthetic events and injects
   them. It does not call `tkings` setters. It uses the same
   producer-to-link mechanism that `tkrepl` will use.

5. **Fault injection moves out of `tkings`.** Stuck and crash behavior
   is tested by the harness (e.g., by killing the `tkings` process,
   injecting bad frames on the link, or using `tkrepl` to replay
   corrupted capsules). `tkings` itself has no hooks for this.

6. **`setEventCount` stays.** Setting `event_count = 0` is a valid
   production value (idle producer). The test uses it, but it is not
   test-only.

7. **If `tkings` needs to handle agent-request events**, that is a
   product capability, not a test feature. It would be a production
   change to `tkings` (supporting multipart streams in the payment
   pipeline), gated by a product requirement, not a test-build flag.

## Implementation record (revision 1)

Status: implemented on `story/tkings-fd-stem` (uncommitted). Partly
superseded by revision 2 below: the payment generator still lives in tkings,
and the agent topology routes `tkings -> tkagnt` around the spine.

### Resolved design (decided while implementing)

1. **tkings had no input link** (`tkings_unprivileged_init` refused one), so
   Step 9's "feed events through tkings's input link" had nothing to feed.
   Decision (product owner): tkings gets a real input link and forwards
   multipart agent-request streams, a production capability.
   - The link has no producer tile. `rt.link.external_src` marks it, and
     topo_build sets Firedancer's own `fd_topo_link_t.permit_no_producers` on
     it. Only a `tango_shm` channel may have one (`Topology.validate`), and
     only into tkings (`tile_registry.validate`, error
     `ExternalLinkNotIngest`). tkings's `.ingest` cardinality expects exactly
     that one input, or none.
   - The topology shape decides what tkings ingests. With no input it runs the
     payment generator, as before. With one input it forwards each fragment
     unchanged (bytes, signature, SOM/EOM) in `AFTER_FRAG` and counts a
     message at EOM. It checks only bounds (empty, over the input MTU, chunk
     outside the dcache). Stream validation stays with the receiver (`tkagnt`,
     `tk_multipart.h`).
   - `topologies.agentProcess(n)` gains that input as its last channel
     (3N+4 channels).
   - The integration test harness
     `src/tickoni/test/integration/agent_request_harness.zig` is the producer.
     It joins the link through `Supervisor.linkHandles`, publishes with
     `rt.link.Producer` (credit backpressure, never drops), and owns the
     stream faults (`drop_middle`, `omit_last`, `corrupt_payload`). It runs
     on its own thread and is finished before the supervisor unmaps the
     workspace.
2. **Crash and stuck faults are tile infrastructure, not tkings data stubs.**
   Decision (product owner): removing the stubs must not change the shutdown
   path or other tile infrastructure. The faults moved out of tkings into
   the shared stem liveness path. `stk_cnc_liveness` calls
   `tk_cnc_liveness_fault_check` (`tango.c`), which `tile_main.zig` installs
   from the LaunchSpec for any stem tile in test builds. This mirrors how
   `tile_process.zig` applies `crash_after_heartbeats` to Zig tiles. The stuck
   hook moved from `payment_pipeline.config` (`StuckTileHook`, now gone) to
   `LaunchSpec.stuck_after_heartbeats` (LaunchSpec v3, process config v7). It
   now counts heartbeats instead of tkings messages. The only tests that use
   it pass 0, which behaves the same either way.

### Deviations to note

- **Step 8:** `model_request_source.zig` is still reachable from the
  production binary through `tile_main_config.loadDispatchTemplate` (tkdisp's
  dispatch template, test-build-gated). That is a tkdisp concern, outside
  this plan. Moving the module under `test/` stays the follow-up the plan
  names.
- With `omit_last`, the faulty stream never reaches EOM, so tkings forwards
  one message fewer than `event_count` and idles until HALT instead of
  exhausting. That is the true count of what it ingested.

## Revision 2: universal ingestion (implemented)

Rechecking revision 1 against the updated design above found three gaps:

1. **Two sources.** tkings still runs the payment generator when it has no
   input. The design says its only source is its input link.
2. **Special route.** `agentProcess(n)` sends `tkings -> tkagnt`, skipping
   the spine. The design says every event takes the same spine.
3. **No canonical framing.** On its input path tkings forwards bytes
   unchanged and assigns no source offset. No schema carries a request-trace
   id. tknorm, tkdedu, tkpoly, tkaudt and tkdisp accept only `PaymentMessage`.

Decisions taken (product owner, this session):

| # | Decision |
| --- | --- |
| D1 | tkings's only source is its input link. The payment generator leaves tkings; every topology gives tkings an externally produced input. |
| D2 | Agent requests go through the spine: `tkings -> tknorm -> tkdedu -> tkcase -> tkpoly -> tkaudt`, `tkcase -> tkdisp -> tkagnt`. No topology routes `tkings -> tkagnt`. |
| D3 | The canonical envelope is done in this plan, not as a follow-up. |
| D4 | The request-trace id is **`trace_id`**, not `case_id`. One inbound request carries one `trace_id` until its reply or a state change. **The producer stamps it** (tkapi, tkrepl, or the test harness standing in for tkapi). tkings validates that it is present and nonzero but never assigns it. `case_id` stays tkcase's (a CaseOps case may group many traces). `run_id` stays the agent sub-run. |
| D5 | An agent request crosses the spine as **scope plus a prompt reference**, never the prompt bytes. tkdisp routes the event to tkagnt with scope + prompt_ref. **tkagnt** retrieves the prompt (from a config-installed, content-addressed prompt table verified against the hash, like tkmodl's fixture table) and handles the multipart conversation with tkmodl. tkdisp is blind to the internal agent–model protocol. |
| D6 | `tickoni-supervisor run` starts the topology idle. Only tests inject events until tkapi exists. |

### Proposed envelope: `TkEvent` (new `shim/tk_event_wire.h`, one source of truth; Zig reads it through `audit_mod`)

One fragment per event. The spine links' MTU rises from 128 to 512 bytes
(the agent scope alone, `ModelRequestMsg`, is 272 bytes).

| Field | Type | Stamped by | Meaning |
| --- | --- | --- | --- |
| `version` | u16 | producer | `TK_EVENT_WIRE_VERSION` |
| `kind` | u8 | producer | `TK_EVENT_KIND_PAYMENT`, `TK_EVENT_KIND_AGENT_REQUEST` (only kinds with a consumer today) |
| `source` | u8 | producer | `TK_EVENT_SOURCE_TKAPI`, `TK_EVENT_SOURCE_TKREPL`. The harness stands in for tkapi, so the enum has no test value |
| `flags` | u8 | producer | `replay` bit (set by tkrepl only) |
| `trace_id` | u64 | producer | D4; nonzero |
| `idempotency_key` | u64 | producer | as today |
| `source_offset` | u64 | **tkings** | per-`source` monotone counter, so it is deterministic in arrival order |
| `event_hash` | u64 | tknorm | canonical hash over the kind's canonical fields |
| `case_id` | u64 | tkcase | 0 until a case is attached (tkcase plan) |
| `run_id` | u64 | tkdisp | agent sub-run, `source_offset + 1` as today |
| `pipeline_hops`, `duplicate`, `decision`, `decided_by[6]` | as `PaymentMessage` | spine tiles | as today |
| `body` | union | producer | `payment`: today's `RawPayment` fields. `agent_request`: `request_type`, `requested_tier`, `ModelRequestMsg scope`, `prompt_ref {prompt_hash u64, prompt_len u32}` |

### Tile responsibilities

- **tkings:** validates framing: size is `sizeof(TkEvent)`, known version,
  kind and source, `trace_id != 0`. It drops what fails and counts it as
  `invalid` (new CNC slot 1), assigns `source_offset`, and forwards. It has
  no generator, no `tkings_set_payment_generator` and no
  `loadIngestConfig`.
- **tknorm:** checks the kind's fields (payment: today's currency, amount
  and malformed checks; agent request: scope version and lengths), then
  computes `event_hash` over the canonical fields.
- **tkdedu:** unchanged rule (`idempotency_key`, `event_hash`).
- **tkcase:** still a placeholder; forwards. `case_id` assignment stays in
  the tkcase plan.
- **tkpoly:** payment: today's amount limit. Agent request: **resolved decision
  O1** — allow (agent requests pass without policy catalog gate at this stage).
- **tkaudt:** every record header carries `trace_id` (and `case_id`). Audit
  schema version bump; the Zig codec mirror and replay hashes follow.
- **tkdisp (scheduler):** routes agent-request events to tkagnt with scope +
  prompt_ref. **tkagnt** retrieves the prompt from a config-installed,
  content-addressed prompt table (verified against the hash, like tkmodl's
  fixture table) and handles the multipart conversation with tkmodl. tkdisp
  is blind to the internal agent–model protocol. For a payment event:
  **resolved decision O2** — keep template dispatch.
- **Test harness:** publishes `TkEvent`s on tkings's input: payments for the
  payment topologies (replacing the generator) and agent requests for the
  agent tests. Malformed, duplicate and policy-violating events are rejected
  by the owning tile (Step 9).

### Resolved decisions

- **O1 — tkpoly on an agent-request event.** Decision: **allow**. An
  agent-request event passes tkpoly with outcome `allow`. No policy catalog
  is needed at this stage; the agent scope was stamped by the trusted
  producer (tkapi, tkrepl, or test harness) and tkagnt retrieves the prompt
  from a content-addressed table verified against the same hash. Agent
  requests are proposal-first and never execute, so there's no financial
  exposure to gate.
- **O2 — tkdisp on a payment event.** Decision: **keep template dispatch**
  for payment events (current behavior). tkdisp dispatches the payment
  workflow template (policy decision → model call → proposal) for every
  payment event, preserving the existing workflow test expectations without
  changes.

### Open decisions (needed before code)

None remaining for the tkings spine cleanup. O3 (transport-fault coverage)
and O4 (N-model agent topology) are about agent-pipeline test coverage, not
about removing test code from tkings. They belong in a separate plan.

### Implementation decisions (product owner, rev 2 kickoff)

| # | Decision |
| --- | --- |
| I1 | **tkdisp -> tkagnt is one fixed fragment**, `TkAgentRequestMsg` (scope + `prompt_ref`), not a multipart stream. The same struct is the agent-request body of a `TkEvent`, so the spine and the agent link share one definition. tkagnt -> tkmodl and tkmodl -> tkagnt stay multipart. The request-stream fault tests (`drop_middle`, `omit_last`, `corrupt_payload`, HALT mid-reassembly) lose their target and are removed with `StreamFault`; transport-fault coverage is O3's separate plan. |
| I2 | **trace_id is threaded through every record.** `ModelRequestMsg` and `ModelAuditMsg` carry it (tkmodl wire v2); `TkAgentRequestMsg` carries it in its scope, `TkAgentAuditMsg` and `TkAgentResultMsg` carry it (agent wire v2). tkdisp stamps `scope.trace_id` and `scope.run_id` from the event. Every committed audit record header carries the event's `trace_id`. |
| I4 | **tkdisp bounds its in-flight requests** (found while implementing). D2 puts tkdisp and tkagnt in a loop (requests one way, terminal results back), and fd_stem polls no input while any reliable output is short of credits, so an unbounded tkdisp deadlocks with tkagnt under load (reproduced by the HALT-mid-run drain test: tkdisp stopped reading results with 30 of them queued). tkdisp sends a request only while fewer than `TKDISP_MAX_INFLIGHT` (16) requests await their terminal result, and refuses at init a request or result link whose depth does not exceed that bound. Every request ends in exactly one terminal result, so the count is exact. |
| I3 | **D6 changes no plumbing.** The supervisor's start path and the tiles' lifecycle are unchanged; `start-process` simply has no producer on tkings's input until tkapi lands (the next plan) and says so. |

Layout notes:

- `run_id` is not a `TkEvent` field: no spine tile stamps it. tkdisp writes it
  into the agent request it emits (`source_offset + 1`, as today).
- The audit header gains `trace_id` (offset 8) and `case_id` (offset 88) inside
  existing padding, so its size is unchanged. Schema version 3; the SipHash k1
  follows the schema version. Both fields are hashed, in layout order.
- tkagnt's prompt table is a bounded, content-addressed store installed from a
  supervisor-written `tkagnt.prompts` file, mirroring tkmodl's capture store:
  at most `TKAGNT_PROMPT_CAP` (16) prompts in `TKAGNT_PROMPT_STORE_BYTES`
  (512 KiB). Each prompt is verified against its hash when installed and
  looked up by `(prompt_hash, prompt_len)` at admission; an unknown reference
  is an audited `DENY_INVALID_REQUEST` with failed scope `prompt_ref`.
- tkings counts dropped framing in CNC slot 1 (`ingest_invalid`) and publishes
  its diagnostic fragment like every other spine tile.

## Follow-up: Align use case docs with single pipeline

All use cases currently bypass `tkings` — they describe `Terminal → tkapi →
[direct to tkpoly/tkport/tkcase/tkdisp]`. The use case docs need updating to
reflect that every event flows through the same pipeline, regardless of use case.

**The single pipeline for all events:**
```
Terminal → tkapi → tkings → tknorm → tkdedu → tkcase → tkpoly → tkaudt → tkdisp → [agents]
```

**Replay loop (applies to all use cases):**
```
tkaudt (case_id=X) → tkrepl → tkings (case_id=X) → same spine → tkaudt (replay_result)
```

**Trace ID propagation:**
- `tkapi` sets `case_id` on user request
- `tkcase` generates `run_id` for agent sub-runs
- Every audit record carries `case_id` (and `run_id` where applicable)
- `tkrepl` reads `case_id` from completed audit, re-injects replay capsule
  with same `case_id`, result traceable back to original request

**What needs to change in each use case:**

**UC-01 (dashboard):**
```
OLD: Terminal → tkapi → tktkr/tkport → response
NEW: Terminal → tkapi (case_id=X) → tkings → tkcase (case_id=X)
     → tkpoly → tkaudt → tkdisp → tktool → tkadpt → tkport → response
```
Dashboard read is an event: `tkings` frames it, `tkcase` scopes it,
`tkpoly` allows it (read), `tkdisp` schedules the data retrieval.

**UC-03 (trade proposal):**
```
OLD: Terminal → tkapi → tkport → tkpoly → tkaudt
NEW: Terminal → tkapi (case_id=X) → tkings → tkcase (case_id=X)
     → tkpoly → tkaudt → tkdisp → tkagnt → tkmodl → tkaudt (run_id=Y)
```
`tkapi` delegates to `tkings`. `tkcase` scopes it. `tkpoly` policy-checks.
`tkdisp` schedules the agent run for evidence gathering.

**UC-08 (rebalancing):**
```
OLD: Terminal → tkapi → tkcase → tkdisp → tkagnt → tkmodl → tkexec → tkaudt
NEW: Terminal → tkapi (case_id=X) → tkings → tkcase (case_id=X)
     → tkpoly → tkaudt → tkdisp → tkagnt → tkmodl → tkaudt (run_id=Y)
     → [tkexec later, with human approval]
```
Same pipeline. Investigation flows through the spine.

**UC-09 (retrospective):**
```
OLD: tkexec → tkport → tkcase → tkdisp → tkagnt → tkmodl → tkaudt
NEW: (triggered by tkexec after position close, flows through pipeline)
     → tkings → tkcase (case_id=Z, run_id=W) → tkpoly → tkaudt
     → tkdisp → tkagnt → tkmodl → tkaudt
```
Retrospective analysis goes through the pipeline like any other event.

**Replay flow (applies to all use cases):**
```
tkaudt (case_id=X) → tkrepl → tkings (case_id=X) → same spine
  → tkaudt (case_id=X, replay_result) → tkdiag (replay_status)
```
Replay doesn't bypass anything. It goes through the same pipeline and
produces a traceable result.
