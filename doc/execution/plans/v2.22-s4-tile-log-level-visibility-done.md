# Plan: Per-Tile Log-Level Visibility (Issue #142)

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Fix V2.22.S4 telemetry audit FAIL #2 ("Per-tile visibility: only atomic counters, no log-level") by adding structured key-value log entries with per-event context to all 8 tile run loops. Not just enter/exit markers and atomic counters — actual log-level visibility describing what each tile does per event.

**Source:** GitHub issue #142 — audit summary table line 223 marks FAIL. Finding 3 (enter/exit) is FIXED but the audit distinguishes between enter/exit markers and actual log-level visibility during event processing. The tile run loops currently log "produced event" / "normalized event" / "allowed at offset" with no structured context — just bare strings.

**Architecture:** No new infrastructure, no new files. Enrich existing tile run loops with `log.kv()` calls carrying per-event context (offset, account_id, amount, decision rationale, hash). Uses the existing logger API (`kv()`, `info()`, `debug()`) already present in all 8 files. The `--verbose` flag already unlocks debug logs; these entries are debug-level so they only appear when verbose is enabled.

**Tech Stack:** Zig runtime, existing `logger.zig` with `log.kv()`, existing per-tile log calls.

    if (expected_seq >= state.audit.count) {
        log.kv("tkrepl", "deterministicReplayDivergences",
            "seq={d} reason=missing_audit_record expected_seq={d} actual_count={d}",

        log.kv("tkrepl", "deterministicReplayDivergences",
            "seq={d} expected_hash={x} actual_hash={x} reason=hash_mismatch",
            .{ expected_seq, expected.header.record_hash,
               state.audit.records[@intCast(expected_seq)].header.record_hash }) catch {};
    }
}

## Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Log format buffer overflow (1024-byte kv buffer) | Low | All per-event context fits well within 1024 bytes; the logger's `kv()` falls back to message-only on overflow. |
| Performance degradation from frequent structured logging | None | All entries are debug-level — completely disabled without --verbose. No impact in production. |
| Log entries expose sensitive data (account_id, amounts) | Low | Only visible with --verbose (debug level). No PII, raw identifiers, or high-cardinality data — only bounded enum values and numeric counters. Complies with label policy (Finding 9). |
| Existing tests break from new log output | None | Log calls are inside existing functions; tests only check state, not stderr output. |

## Relationship to Other Plans

This plan is **independent** of both periodic sampling (v2.22-s4-periodic-s4-periodic-sampling.md) and the metrics tile (v2.22-s4-metrics-tile.md):

- **Periodic sampling** makes *counters* visible during execution. This plan makes *log entries* visible during execution. They are complementary, not overlapping.
- **Metrics tile** provides HTTP `/metrics` endpoint. This plan provides structured log output. They serve different observability surfaces.

This plan can be done before, after, or in parallel with the other two plans. No dependencies either way.
