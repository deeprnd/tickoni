# Plan: Migrate tkagnt to a proper fd_stem agent-worker tile with multi-tkmodl fan-out

**Status:** Implemented and verified (2026-11-19). The owner approved the contracts, removed the classifier cascade, confirmed the committed-audit watermark, chose a crash-only agent, deferred the embedding audit fields, asked for the full investment workflow in this migration, approved the run-directory capture files, and set the audit order of the full workflow (one chain, in event order). See "Decisions recorded 2026-11-19". `tkagnt` is an active `fd_stem` agent worker (`shim/tk_agent_stem.c`) that admits requests, routes them through Zig-owned hooks, dispatches to the `tkmodl` instance serving the requested tier, correlates results, and delivers one terminal result per accepted request to `tkdisp` after its audit record is committed. The full 14-tile investment workflow runs end to end, with config-driven placeholders for the case, tool and adapter tiles (see "Full investment workflow").

**Goal:** Give `tkagnt` a proper `fd_stem` lifecycle as an **active agent-worker tile** that dispatches model requests to one or more `tkmodl` instances and consumes their results, while preserving the bounded-agent invariant: no direct shell, unrestricted syscall, or unrestricted network access.

Execute in dependency order: decide the contracts, write tests, implement the tile, wire it into a runnable topology, then prove it with real-process evidence. A file or a passing in-process fixture test is not evidence that the process tile works.

## Decision gate: approve the runtime contract before implementation

These choices change link semantics, public messages, audit/replay behavior, or service authority. The framework owner must decide and record them.

1. **Agent scope and bounded memory.** Define the agent's role, memory limits, prompt template scope, and maximum reasoning steps. State whether the agent can hold state across requests or is stateless per-request.

2. **Request source and routing.** Define who sends requests to `tkagnt` (currently `tkdisp` in the investment workflow, or a synthetic source in the minimal topology). Define how `tkagnt` selects which `tkmodl` instance to send to — by model ID, by role, or by policy decision.

3. **Multi-tkmodl fan-out topology.** `tkagnt` must support up to 11 configured `tkmodl` tiles; no tier or count of 11 is mandatory for every topology. Define which tiers are present for each workflow, and each instance's `live_provider_enabled` flag, allowlisted models, and fixture table. A request for an absent tier must fail explicitly.

   Use the existing `tkmodl` tile ID with Firedancer's per-name `kind_id` for each configured process. Define a deterministic mapping from semantic tier to instance and from that instance to its request/result links. Registration order may assign compact kind IDs, but it must not silently change a tier's meaning or replay attribution.

4. **Embedding model support.** Define whether embedding models are supported alongside chat/completion models within each tkmodl instance, or as separate embedding-only instances. Define embedding wire format (text input → vector output), dimension support, batch request support, and embedding-specific governance.

5. **Lifecycle and scope.** Decide whether the first runnable topology is a focused minimal topology or the full investment workflow; specify restart, in-flight request recovery, cancellation, and shutdown drain rules.

6. **Wire contracts and link bounds.** Define bounded request and result payloads (chat/completion and embedding); versioning; oversized handling; maximum logical input/output bytes, fragment MTU and count, and exact depth/MTU for all links. Large model messages must work across multiple fragments.

   The `tkagnt → tkmodl` request must carry the full bounded model input, and the `tkmodl → tkagnt` result must carry the full bounded model output, including when either exceeds one fragment. The separate `tkmodl → tkaudt` record carries hashes and attribution metadata only. Specify the prompt/message count and byte limits, output byte limit, embedding count/dimension limits, and framing before choosing fragment MTUs or scratch footprints. These limits are independent of the model context/token limits.

7. **Result correlation.** Define how `tkagnt` correlates a `tkmodl` result back to the original dispatch — `request_id`, `run_id`, or a composite key.

8. **Zig agent decision boundary.** Define how the `fd_stem` process obtains Zig-owned model-routing and result-interpretation decisions without reimplementing them in C. The existing C ABI is Zig-to-C; do not assume a C-to-Zig callback or move agent policy into the shim. Resolve this boundary before implementing result interpretation in the stem.

9. **Return, audit order, and drain.** Approve the `tkmodl → tkagnt` result link for every configured model instance, the final `tkagnt → tkdisp` result link in the full workflow, and a named final-result consumer in the minimal process test. Define an agent audit link and a committed-audit barrier before final-result publication. Approve the correlation key, deterministic audit ordering rule, bounded out-of-order capacity, terminal failure behavior, and shutdown/restart treatment of in-flight calls.

#### Committed-audit barrier (confirmed by the owner 2026-11-19)

Constraints: `tkaudt` remains the sole owner of append order and the hash chain, and it stays a sink (no output links); CNC counters are advisory; the barrier must not depend on arrival timing.

Recommendation: a **committed-order watermark** — a single-writer, monotonic `u64` cursor that `tkaudt` owns and publishes in shared memory, using Firedancer's existing `fseq` primitive. This is the same shape as a write-ahead-log commit LSN or a stream-processing low watermark.

- Every agent and model audit record carries the deterministic order key already required above (case/run order, agent-request ordinal, record phase), packed into one monotonic `u64`.
- `tkaudt` releases records from its bounded reorder buffer in order-key order. After it appends and chains a record, it advances the watermark to that record's key with a release store. The watermark therefore means "every record with a key at or below this value is committed".
- `tkagnt` maps the cursor read-only. It publishes a terminal result only when `watermark >= key(final agent record)`. A missing predecessor is resolved by an audited terminal-failure record, so the watermark cannot stall indefinitely.
- No new link and no `tkaudt` output. The object is declared in the topology (one `fseq` object, `tkaudt` read-write, each barrier consumer read-only), so it appears in workspace layout, parent/child parity checks, and replay.
- The consumed-sequence `fseq` on a link is not used as the barrier. It advances when a fragment is consumed, not when the reorder buffer commits it.

Rejected: a `tkaudt → tkagnt` acknowledgment link, because it breaks the sink contract and adds a lifecycle dependency from `tkaudt` back to an agent. Rejected: polling CNC counters, because the plan already excludes them.

Still to specify and test with the Phase 2 `tkaudt` change: the watermark object's schema, its topology declaration, and the order-key packing.

### Proposed return and audit contract (approved 2026-11-19, except the commit barrier)

- **Separate transport from audit.** `tkagnt → tkmodl` carries the complete bounded prompt/messages or embedding input plus model request scope. `tkmodl → tkagnt` returns the complete bounded model response or embedding vectors, including status, correlation fields, and token usage. `tkmodl → tkaudt` carries the canonical input/output hashes and non-body metadata needed for attribution and replay verification. Neither the prompt, response text, nor embedding vectors belong in audit records. `tkagnt` interprets classifier content; `tkmodl` returns it without making an agent-routing decision.
- **Large-message framing.** The current stems process each fragment as a complete fixed-size record; Firedancer SOM/EOM does not reassemble it for them. Define a versioned header that binds every fragment to `(run_id, model_request_id, direction, content_type)`, declares total length and fragment offset/length, and includes scope or a verified reference to scope captured on the first fragment. Use SOM/EOM consistently, require contiguous non-interleaved fragments on each producer link for the initial contract, and accept a logical message only after all bytes and the final boundary are verified. Bound total bytes, fragment count, concurrent partial messages, and aggregate reassembly memory. Detect gaps, duplicates, overlap, overflow, malformed boundaries, overrun, timeout, restart, and shutdown with a terminal failure; never dispatch a partial input or interpret a partial output. The exact byte ceilings and fragment MTUs need approval; they must permit messages larger than one fragment.
- **Multipart publication and flow control.** A producer keeps bounded state for the remaining fragments and emits them over successive stem iterations under reliable-link credits. Its `STEM_BURST` must cover the actual maximum publishes per iteration, including audit or terminal records; a queued-output drain must remain active through shutdown until every accepted message is completed or has a terminal failure. The proposed depth is a count of fragments, so it must be sized and tested with the chosen fragment MTU, producer burst, and consumer rate. No single callback may assume it can publish the entire logical message at once.
- **Hash and replay discipline.** Compute or verify each audit hash against the actual bytes crossing the model boundary; do not trust a caller-supplied `prompt_hash` without checking the payload. Replay must reconstruct the model input from captured run inputs or read an approved input capture outside the audit, then verify its hash. It also needs the captured response bytes, including classifier content and vectors, in a versioned replay capsule or approved content-addressed evidence outside the audit record. Bind that capture to the substitution ID, model ID, request/input hash, and response/output hash; reject a missing or mismatched capture and never call a provider during replay. The artifact location, access controls, and retention are separate approval decisions.
- **Return path.** Each configured `tkmodl` instance publishes one result to `tkagnt` for each accepted model request, including denials. In the full workflow, `tkagnt` publishes one terminal agent result to `tkdisp` for each accepted agent request and sends a proposal hash, denial, or failure record to `tkaudt`, with no raw model response in that audit record. The current C audit stem only accepts payment and model records, so the agent audit envelope and its `tkaudt` handling require an approved schema change. The minimal process topology needs a bounded consumer of that terminal result; the existing scratch ring is an inspection aid, not delivery. Name and register that consumer before fixing tile/link counts.
- **Correlation.** Assign a deterministic `model_request_id` to each model dispatch (one per agent request). A bounded `tkagnt` pending entry maps `(run_id, model_request_id)` to the parent agent request, configured model instance, and expected model ID. A result must match that entry and its source input link; an unknown, duplicate, stale, wrong-instance, or wrong-model result cannot complete a run. Record a terminal failure through the approved audit path instead of silently dropping an accepted request. The current `request_id`-only rule and wire records need an approved extension or an equivalent documented mapping.
- **Audit order.** `tkaudt` remains the sole owner of append order and hash chaining. For the same accepted event/case order and captured model outputs, the committed agent/model audit sequence and hashes must be identical even when model completions arrive in a different order. Use a deterministic order key based on accepted case/run order, agent-request ordinal, and record phase; buffer out-of-order arrivals within an explicit bound. A missing predecessor requires an audited terminal outcome before later records in that order can commit. Never use result arrival time or CNC counters as the ordering key. The ordering key's schema, bound, and merge with existing financial-event records require approval.
- **Commit barrier.** Publishing a model audit fragment and result from one `AFTER_FRAG` commit does not prove that `tkaudt` appended the audit record before `tkagnt` sees the result. Specify an explicit committed-audit acknowledgment or equivalent barrier, tied to the model call and final agent record, before `tkagnt` publishes a terminal result. This may require a new return link from `tkaudt`; its link shape and `tkaudt` lifecycle are not yet approved. CNC progress is advisory and cannot serve as the barrier.
- **Shutdown and restart.** On shutdown, stop accepting new agent requests, finish or produce an audited terminal failure for every accepted in-flight dispatch, wait for the audit commit barrier, then publish terminal results and exit. A fixed result-count gate or immediate CNC HALT must not abandon pending calls. Define the finite drain deadline, cancellation outcome, and restart reconstruction from accepted requests, audit records, and replay capsules before implementation; a crash must not turn a retried model call into an uncorrelated duplicate or an external call during replay.

### Topology capacity and instance contract (approved 2026-11-19)

- **Keep one canonical model tile type.** The user-facing shorthand `tkmodl[0]` through `tkmodl[N-1]` means N configured instances of the existing `tkmodl` tile, each with a distinct Firedancer `kind_id`; it does not create `tkmdl_1` tile IDs. N is topology-dependent, from 0 to 11. A model-backed run needs at least one configured instance. Keep the semantic tier in the instance configuration and validate a unique tier-to-instance mapping for the selected workflow. A missing requested tier fails explicitly. Preserve the configured mapping in replay inputs so changing the subset cannot silently reattribute a model result.
- **Raise Tickoni handoff bounds, not Firedancer's.** Propose `TopologySpec` capacity of at least 32 tiles and 64 channels, and `LaunchSpec` capacity matching Firedancer's 128 input and 32 output links per tile. The exact Tickoni capacities are subject to the approved full-workflow graph and memory budget; reject graphs that exceed them before workspace allocation. Version both raw-byte handoff structs when their shape changes, and make the supervisor and child validate counts, endpoint indexes, IDs and topology reconstruction. Firedancer's existing 256-tile/256-link, 128-input/32-output limits already cover the proposed `tkagnt` headroom of 20 outputs.
- **Carry exact process identity.** Add an instance ordinal to the Tickoni tile descriptor and `TopologySpec`, with compact `kind_id` values assigned deterministically among configured `tkmodl` entries. Reject duplicate `(tile ID, kind_id)` pairs, gaps, and mismatches between descriptor order and Firedancer's assigned kind ID. Carry the resolved identity in `LaunchSpec`; child startup must find `(name, kind_id)` and verify it is the launched tile, not always find kind 0. Preserve descriptor-to-Firedancer index mapping through metric-tile reordering. Fix `TopologySpec.toTopology()` to reconstruct each name from its own array index rather than using a tile ID as an array subscript.
- **Bind links to instances.** In `topo_build`, use each endpoint's resolved `(name, kind_id)` for `topobTileIn`, `topobTileOut`, scratch properties and validation; do not use kind 0 or a name-only first match. Build a checked route table from configured semantic tier to the exact `tkagnt` request output and result input, using verified channel endpoints as the source of truth; add a serialized channel-role enum if multiple links between the same endpoints would otherwise be ambiguous. Link indexes are compact and topology-dependent. Reject an extra, missing, duplicate or misdirected request/result/audit link at topology validation and tile init. The registry remains keyed by canonical tile type but validates `tkagnt` and `tkaudt` cardinality from the configured graph; each `tkmodl` keeps its own 1-in/2-out contract. Any additional diagnostic/tool links need explicit roles and consumers before they count toward the 20-output target.
- **Check audit and metric fan-in.** `tkaudt` currently derives one workspace from input 0 and ignores the input index when validating fragments. Either keep every audit input in one explicitly shared workspace or give it per-input workspace mapping; in both cases validate each input's own chunk range before dereferencing it. Do not assume separate model processes imply separate audit workspaces. The metric observer receives one observed input per applicable channel, so include its actual Firedancer `in_cnt`, scratch footprint and 128-input ceiling in the maximum graph check. Preserve deterministic audit ordering across model inputs as specified above.
- **Give each model child its own configuration.** Replace the single supervisor `model_config` and shared `tkmodl.config` file with a bounded per-instance configuration set. Key each file and its contents by the launch identity plus the semantic tier, validate a one-to-one match with configured model tiles, and fail closed on missing, duplicate or mismatched configuration before child startup. A process-local C `tkmodl_configure` value remains valid because each tile runs in its own process. Metrics, audit and replay records must retain enough instance and tier attribution to distinguish concurrent model tiles.
- **Count the graph from declared edges.** The illustrative N-model base has `N+4` tiles and `1+3N` channels: one agent-request link and, per model, request, result and model-audit links. At N=11 that is 15 tiles and 34 channels. Agent-audit and terminal-result links make 36; a separate audit-acknowledgment link makes 37. A distinct minimal terminal-result consumer adds a tile. Diagnostic or tool links add their own channels and may add tiles. `tkagnt` has `1+N` inputs before acknowledgment, and `N+2` outputs before optional diagnostic/tool links. Validate all totals after graph construction rather than hardcoding a 15-tile/34-channel runtime requirement.

## Decisions recorded 2026-11-19 (after implementation began)

- **No classifier cascade.** The owner removed classifier escalation: the topology defines which model tiers `tkagnt` uses and adds exactly those, with no auto-deduction or discovery of further tiers, and a classifier result with low confidence is reported as it is. This supersedes the plan's earlier cascade (`classifier_fast` → `classifier_complex` → `classifier_escalation` → hosted), `MAX_CLASSIFIER_DEPTH = 4`, step ordinals, follow-up dispatches, and the "fallback tier" and "which hosted classifier" questions. A request names its tier explicitly; there is no default start tier.
- **Committed-audit barrier confirmed.** The `tkaudt`-owned committed-order watermark described above is approved (`tkaudt` stays a sink; `tkagnt` reads the watermark read-only). The schema of the watermark object and the packing of the order key into one `u64` are implementation details to be specified and tested with the Phase 2 `tkaudt` change.
- **Crash-only agent (owner, 2026-11-19).** No restart reconstruction: a crashed `tkagnt` stops the run and in-flight requests are not resumed. The restart verification item is dropped. HALT drain remains and is tested.
- **Embedding audit fields deferred (owner, 2026-11-19).** The embedding audit record keeps hashes, model id and token estimate; `request_type`, `embedding_count` and `dimensions` are not added to the audit payload in this migration.
- **Full investment workflow included (owner, 2026-11-19), as config-driven placeholders.** `tkcase`, `tktool` and `tkadpt` are bounded pass-through or idle stem tiles with no financial logic, and `tkdisp` is a scheduler that turns each event it receives into one agent request from a fixed, config-supplied template (tier and prompt from run config, never from event contents). See "Full investment workflow" below.

- **Audit order of the full workflow (owner, 2026-11-19): one chain, in event order.** "Audit is event based, chronological, and all in a single event audit chain." The committed sequence is, for event n: its payment (policy decision) record, then its model record (if any), then its agent record, then event n+1. Payment records reach `tkaudt` in event order and agent runs are admitted in event order, so the n-th of each belong together. Mechanism (`tk_audit_stem.c`): a payment record is left queued upstream (`BEFORE_FRAG` returns -1; lossless backpressure) until the agent record of event n-1 is committed, and an agent record is committed only after its own event's payment record. Where there is no payment chain, or no agent runs, the earlier rules stand (arrival order, or admission ordinal). An event whose payment record never reaches `tkaudt` leaves its agent record held: fail closed, consistent with the crash-only decision.

## Full investment workflow

`topologies.investmentWorkflow()` is runnable (`investment_workflow_status = .runnable`): 14 tiles, 16 reliable shared-memory links in one workspace, validated by the registry (`Supervisor.init`) and started by `startPaymentPipelineProcess`.

| Path | Links | Notes |
| --- | --- | --- |
| Events | `tkings → tknorm → tkdedu → tkcase → tkpoly → tkaudt` | 64 deep, MTU 128 (one `PaymentMessage`). |
| Dispatch | `tkcase → tkdisp → tkagnt` | `tkdisp → tkagnt` is the multipart agent-request link. |
| Model | `tkagnt ⇄ tkmodl`, `tkmodl → tkaudt` | As in the agent topology. |
| Agent | `tkagnt → tkaudt` (audit), `tkagnt → tkdisp` (terminal result) | As in the agent topology. |
| Idle | `tkagnt → tktool → tkadpt`, `tktool → tkaudt`, `tkadpt → tkaudt` | Declared and bound; nothing is published on them, because no tool or adapter call exists yet. |

What each tile does here:

- **`tkcase`** (`tk_pass_stem.c`, shared with the next two): forwards each event unchanged to both consumers. No case state, no case id.
- **`tktool`, `tkadpt`**: idle bounded consumers that stop on HALT. They have no tool or adapter logic and no audit record type.
- **`tkdisp` as scheduler**: with a `tkcase` in the topology it has two inputs (events, `tkagnt` results) and one output (the agent request link). For each event it queues the event's source offset and sends one multipart agent request built from the **dispatch template**; only the run id (`source_offset + 1`) comes from the event. The queue is bounded (64) and full means the event stays upstream (lossless backpressure). Without `tkcase` it is the terminal-result sink of the agent topology, unchanged.
- **Dispatch template**: `ProcessPipelineConfig.dispatch_template` (a `ModelRequestSource`; its first slot builds the template), carried in `payment_pipeline.config` (version 5), installed by `tile_main_config.loadDispatchTemplate` before the C harness runs, fail closed on a missing template, a production build, or a template the tile refuses. The supervisor requires it exactly when the topology has `tkcase`. Test-build only today: the synthetic source is the only template author.
- **`tkagnt`** binds at most one idle output to `tktool`; the link counts must match the configured tiers plus that link.
- **`tkaudt`** gives `tktool` and `tkadpt` inputs an idle role (a fragment on one is not audited). With a payment chain and agent runs in one `tkaudt`, it commits one chain in event order (the owner's audit-order decision above), and its event-count gate waits for both the agent ordinals and the payment records.
- **Registry**: `tkcase`, `tktool`, `tkadpt` entries; `tkdisp` shape, `tkaudt` fan-in and `tkagnt` outputs follow from the configured tiles (`expectedInCnt` / `expectedOutCnt`).
- **`tkaudt → tkrepl`** is not a link: the committed chain has no consumer tile yet (`tkrepl` observes through its own process role).

Proof: `test_tile_tkagnt.zig` "the full investment workflow turns each event into one audited agent run" runs all 14 processes: `tkcase` forwards every event, the idle tiles consume nothing, each event yields exactly one request, admission and terminal result (run id = event offset + 1), and the committed chain is, for each event in order, its policy decision, its model record and its agent record, with a contiguous hash chain that the Zig codec re-derives for the model and agent records. A second test runs the workflow three times and requires the same chain head each time (the chain no longer depends on timing). Mutations failed the tests: a run id off by one in `tkdisp`; removing the rule that an agent record waits for its event's payment record (six `test_tkaudt_during_frag.c` checks).

Limits, stated so they are not mistaken for behavior:

- **The audit order pairs the n-th payment record with the n-th admitted agent run.** That holds because every event reaches both `tkpoly` and `tkdisp` through `tkcase`, and each stream keeps event order. A dispatch policy that skipped events, or a rejected request that consumed no ordinal, would need its own pairing rule; the placeholders do neither.
- **The template makes every request identical** (same tier, fixture and prompt); only the run id differs. How an event should become an agent request is dispatch policy the plan does not define.
- `tkcase`, `tktool` and `tkadpt` are placeholders; none of the case, tool or adapter behavior in the product docs exists yet.

## Preserved agent contract

- Every request carries actor/role, workflow, run or case identity, capability envelope, policy version, budget, model ID, and replay mode. Missing or malformed required scope fails closed.
- Agents are **proposal-first**. They may inspect, classify, summarize, draft, recommend, prepare evidence, and propose; they must not directly place trades, move money, post ledger entries, freeze accounts, approve payouts, or override risk/compliance controls.
- Model access must go through `tkmodl`. Agents must not call cloud providers, local LLM servers, or local GPU inference directly.
- Financial tool and adapter access must go through `tktool` and `tkadpt`. Model-native function calls and MCP-style requests are integration formats, not trust boundaries.
- The in-process `runInvestmentAgent` is scaffolding, not an authority template for this tile: its direct `adapter_backend.call` and paper-order branch must not be copied into `tkagnt`. A future tool request must cross the governed `tktool`/`tkadpt` boundary; execution requires its separately approved path.
- Keep model work outside the deterministic financial event path. No agent, UI, or ordinary API handler gains direct provider credentials or access.
- Replay substitutes captured model output by the approved identifier and never calls HTTP, a local LLM server, or another provider.
- Model input and output bodies travel only on the bounded `tkagnt ↔ tkmodl` transport and in approved replay/evidence capture; audit records store their verified hashes and attribution metadata, never the bodies.
- Embedding requests follow the same governance when an embedding instance is configured: `request_type`, `model_id`, `dimensions` are validated against its allowlists. Embedding vectors are never stored in audit records; their verified hashes and attribution metadata are. Vectors travel through the result link and may be stored in an inspection ring.
- Embedding results are replay-substituted by the approved composite dispatch identity, with captured vector bytes verified against the audit hash. No live embedding API call occurs during replay.

### Agent and model ownership in the process tile

- Zig-owned `src/tickoni/tiles/agent/` defines the agent's bounded run state, approved model-tier selection and result interpretation. C stem callbacks may validate framing, stage fragments, maintain bounded transport/correlation state, and publish already-authorized requests. They must not independently encode agent routing or interpret model content as business decisions.
- `tkmodl` validates model scope and allowlists, enforces configured model limits, resolves fixture/replay or approved backend responses, accounts for tokens, and emits model-call audit references. It must not decide the agent's next step, choose a financial proposal, or gain tool/adapter authority.
- Before Phase 2, specify and test the narrow interface that lets the stem process apply Zig-owned agent decisions. The current Zig-to-C ABI does not itself provide that interface. If it cannot be implemented within the approved tile architecture, return to the framework owner instead of duplicating the decisions in C.

## Risks and completion gate

- **The current C file is a sink, not a worker.** The `tk_agent_sink_stem.c` file must be substantially rewritten to become an active agent dispatch tile. The ring-buffer result storage pattern can be preserved, but new request-dispatch logic must be added.
- **Domain logic can drift across the C ABI.** The existing stem is C while the agent's decisions belong in Zig. Phase 2 is blocked until the Zig-owned decision interface is specified and tested; copying routing, result interpretation, adapter calls, or paper execution into the C shim is not an acceptable shortcut.
- **Multi-input fan-in changes the registry.** The maximum model configuration has one agent-request input and 11 model-result inputs before any audit acknowledgment. Model-request, agent-audit, and terminal-result outputs also exceed the current sink shape. Derive and validate cardinality from approved links; verify the maximum early.
- **Tickoni handoffs and name-only lookups are below the required capacity.** `TopologySpec` stops at 8 tiles/8 channels, `LaunchSpec` at 4 links per direction, and the builder/child select kind 0 for repeated names. Raise the versioned bounds, bind every endpoint to its exact `(name, kind_id)`, and prove supervisor/child reconstruction before launching 11 models. The underlying Firedancer 32-output limit is sufficient for a 20-output `tkagnt`; it is still a hard ceiling for this architecture.
- **A shared model config would give instances the wrong governance.** The supervisor currently writes one `tkmodl.config`. Require one identity-bound file per configured process; a missing or mismatched file fails before a model call. Make audit and replay attribution include the selected semantic tier and process instance rather than relying on a mutable positional link index.
- **Model completion arrival is nondeterministic.** Directly appending from multiple `tkmodl` audit links would make the hash chain depend on process timing. The approved tkaudt ordering/buffering rule and completion-order permutation test are required before the multi-model topology can be called replay-stable.
- **A published audit fragment is not a committed audit record.** The current `tkmodl` publishes audit and result in one callback, while `tkaudt` commits later. A final agent result needs an explicit committed-audit barrier; CNC counters and `tkagnt`'s scratch ring do not establish one.
- **The existing event-count shutdown gate can abandon in-flight work.** Define a bounded drain, terminal failure record, and restart reconciliation before replacing the passive sink with an active agent.
- **A request link alone is not an agent proof.** Prove committed agent dispatches, result attribution, and replay substitution through tkmodl and tkaudt; CNC counters are operational hints only.
- **No classifier cascade (owner decision, 2026-11-19).** The topology defines which model tiers `tkagnt` uses and adds exactly those; there is no automatic escalation, deduction or discovery of further tiers. A classifier result with low confidence is reported as it is.
- **Large content needs multipart transport and memory bounds.** The current hash-only request/result records and fixture hashes cannot supply prompt or response bytes to an active agent. A single Firedancer fragment is capped at 65,535 bytes by `fd_frag_meta_t.sz`; increasing the link MTU above that would truncate the published size. Define bounded fragment streams, whole-message byte ceilings, reassembly memory, credit/depth sizing, and timeout behavior. Fail closed on incomplete or oversized input/output instead of truncating it.
- **Audit and replay capture have different data exposure.** Keep prompt, response, and vector bytes off the audit link and out of audit records. A replay capsule or evidence artifact must still retain the captured bytes needed for substitution under separately approved access and retention rules; hashes alone cannot reproduce the model result.
- **Embedding vectors inflate the result link and ring.** A 1024-dimensional `f32` vector is 4096 bytes before the result header; batching multiplies that size. A ring slot must track its result type. Consider separate chat and embedding rings only if the approved capacity calculation warrants them.
- **Embedding dimension validation.** If an agent requests a dimension not in the tkmodl instance's `allowed_embedding_dimensions`, the request must fail closed and record `agent_denied`. No silent truncation or padding.

## Multi-tkmodl fan-out design (integrated, not future work)

This plan includes multi-model fan-out as the core design. `tkagnt` supports up to 11 configured `tkmodl` instances, one per selected model tier; a topology instantiates only the tiers it needs. Each configured instance is a separate Firedancer process with its own scratch, CNC, and `TkModlRuntimeConfig`. Link workspace ownership and mapping follow the approved topology contract.

### Architecture: illustrative 11-instance maximum

```
tkings ──agent request──→ tkagnt
                           │
                           ├─output[0]→ tkmodl[classifier_fast]     (fast, low-cost tier)
                           ├─output[1]→ tkmodl[classifier_complex]  (more capable tier)
                           ├─output[2]→ tkmodl[classifier_escalation] (accuracy-focused tier)
                           ├─output[3]→ tkmodl[classifier_hosted]   (proprietary general-purpose)
                           ├─output[4]→ tkmodl[classifier_hosted_newer] (proprietary, improved)
                           ├─output[5]→ tkmodl[embedding]          (shared embedding)
                           ├─output[6]→ tkmodl[low]                (fast/cheap LLM)
                           ├─output[7]→ tkmodl[medium]             (balanced LLM)
                           ├─output[8]→ tkmodl[high]               (capable LLM)
                           ├─output[9]→ tkmodl[extra-high]          (very capable LLM)
                           └─output[10]→ tkmodl[max]                (most capable LLM)

tkmodl[0]  ──result──→ tkagnt (input 1)   ← classifier_fast
tkmodl[1]  ──result──→ tkagnt (input 2)   ← classifier_complex
tkmodl[2]  ──result──→ tkagnt (input 3)   ← classifier_escalation
tkmodl[3]  ──result──→ tkagnt (input 4)   ← classifier_hosted
tkmodl[4]  ──result──→ tkagnt (input 5)   ← classifier_hosted_newer
tkmodl[5]  ──result──→ tkagnt (input 6)   ← embedding (full vector; MTU pending)
tkmodl[6]  ──result──→ tkagnt (input 7)   ← low
tkmodl[7]  ──result──→ tkagnt (input 8)   ← medium
tkmodl[8]  ──result──→ tkagnt (input 9)   ← high
tkmodl[9]  ──result──→ tkagnt (input 10)  ← extra-high
tkmodl[10] ──result──→ tkagnt (input 11)  ← max

All tkmodl[0..10] ──audit──→ tkaudt
tkagnt ──agent audit──→ tkaudt
tkagnt ──terminal result──→ tkdisp (full workflow; minimal consumer pending)
tkaudt ──committed-audit acknowledgment or equivalent barrier──→ tkagnt (pending approval)
```

Each configured tkmodl instance independently sends hash/metadata-only audit records to `tkaudt` and complete content-bearing results to `tkagnt`, using multiple fragments when needed. Embedding results carry complete vector data; chat results carry complete response content. Fragment MTUs and total-message byte bounds are separate pending decisions. The terminal-result and committed-audit paths above are proposed links, not part of the current minimal or investment topology.

### Model tier classification flow

1. Incoming agent request arrives at tkagnt (input 0) with `model_tier` or `model_id`.
2. The Zig-owned agent decision validates the tier the request names against the configured set. An unnamed or contradictory tier, or one that is not configured, is an explicit denial; the request is never rerouted to a different model. If the tier is a classifier tier, dispatch to that `tkmodl` and treat its result as follows:
   - The Zig-owned agent logic validates the structured response and reports `confidence` and `recommended_tier` from it. `tkmodl` governs and returns that content but makes no routing decision.
   - There is no escalation: a low `confidence` is reported as it is, and the run ends with that one result.
3. If the tier is `low`/`medium`/`high`/`extra-high`/`max`:
   - Dispatch directly to the matching LLM instance if configured; otherwise return the approved terminal outcome.
4. If request is an embedding request:
   - Dispatch to `tkmodl[embedding]` if configured; otherwise return the approved terminal outcome.
   - Embedding result returns with vector data.
5. Result returns from the appropriate tkmodl to tkagnt's corresponding result input link.
6. tkagnt matches `(run_id, model_request_id)` to its pending entry, verifies the source instance and expected model, and applies the Zig-owned next-step decision. It records the terminal agent outcome through `tkaudt` and publishes the terminal result only after the approved committed-audit barrier. Ring storage is observational.

### Why support up to 11 instances

- **Classifier tiers:** The classifier instances can enforce separate model allowlists and resource profiles. The topology configures the tiers a workflow needs and the request names one; each `tkmodl` instance governs its own model request and does not own routing.
- **Embedding isolation:** Embedding is a shared utility with different latency/cost characteristics than LLM inference. A dedicated instance avoids contention and allows embedding-specific governance (dimension allowlists, vector storage limits).
- **LLM isolation:** Each LLM tier gets dedicated resources (scratch, CNC, workspace). A slow max model doesn't starve low-tier requests.
- **Maximum tier set:** The design can represent five classifier, one embedding, and five LLM tiers. A workflow configures only the tiers it actually uses.
- **Audit clarity:** Each instance's audit output is self-contained and tied to its model's decisions. The tier that served each request is traceable through audit records.
- **Replay substitution:** Each instance has its own fixture table. Replay can substitute results per-model without cross-model ambiguity.
- **Firedancer-native:** The fan-out/fan-in pattern is already in the topology system. Each tkmodl instance is just another tile in the topology — like tkdiag's N input links, each with its own `*_tkdiag` channel.

The supported maximum is 11 `tkmodl` instances per `tkagnt`. Increasing it requires a separate contract and capacity decision, including topology, registry, memory, link, audit, and test bounds.

Completion means an approved topology and ordering contract, a delivered terminal agent result for every accepted request, committed model and agent audit records in replay-stable order, bounded in-flight shutdown/restart handling, passing registered unit and real-process tests, no model-provider bypass, zero external effects in replay, and a clearly stated live-provider status. Do not close this plan based on a compiled shim, fixture-only tests, or a result stored only in scratch.
