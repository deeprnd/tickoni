## ISO/IEC 25010 Maintainability Characteristics

### 1. Modularity

**Finding M1 — HIGH: Audit logic fragmented across three directories for the same concern.**

Audit schema lives in `schema/audit/`, audit codec in `codec/audit/`, and C ABI shim in `c_abi/shim/`. While these represent different layers (schema → codec → interop), there is no single index module that ties them together. A developer landing on "audit" has to visit three different top-level paths to understand the full picture.

**Affected paths:** `schema/audit/mod.zig`, `codec/audit/mod.zig`, `c_abi/shim/tk_audit_stem.c`

**Recommendation:** Add a `src/tickoni/audit.zig` umbrella module (similar to `@import("runtime")`) that re-exports schema, codec, and shim types so external consumers have one entry point.

**Finding M2 — MEDIUM: `payment_pipeline/` now owns audit pipeline logic but is named for payments.**

The `audit_sink.zig`, `replay.zig`, `audit_stage.zig` files under `payment_pipeline/` handle generic audit events, not payment-specific ones. This is a naming/coupling concern: future audit consumers (investment, treasury) will look in `payment_pipeline/` for audit functionality.

**Affected paths:** `tiles/payment_pipeline/audit_sink.zig`, `tiles/payment_pipeline/replay.zig`, `tiles/payment_pipeline/audit_stage.zig`

**Recommendation:** Either rename the directory to `pipeline/` or add a `tiles/audit_pipeline/` directory. The current naming conflates "pipeline" with "payment pipeline" — the audit stage is not payment-specific.

**Finding M3 — PASS: Deleted files are clean removals with clear rationale.**

`tiles/audit/` was consolidated into `payment_pipeline/`. `audit_shared.zig` was extracted into `audit_consts.h`/`audit_consts.zig`. Deletions are all accounted for in git diff with no orphaned imports.

### 2. Reusability

**Finding R1 — PASS: `audit_consts.zig` and C `audit_consts.h` share a single seed value.**

Both `src/tickoni/codec/audit/audit_consts.zig` and `src/tickoni/c_abi/shim/audit_consts.h` define `audit_seed` as `0xcbf29ce484222325` (FNV-1a initial hash value). This is a shared constant pattern, though the duplication means a future change to the seed requires editing two files.

**Recommendation:** Generate the Zig constant from the C header via build.zig `comptime` parsing, or define a single source of truth (e.g., a `.json` or `.zig` file) and use `comptime` to emit the C header.

**Finding R2 — GOOD: Hash codec functions are reusable across audit and replay.**

`audit_trace.zig` reuses `replay.hashBytes`, `replay.hashQuoteSnapshot`, `replay.hashAffordability`, `replay.hashTicket`, `replay.hashPaperResult` (line 65-69) instead of reimplementing field-by-field mixing. This prevents silent divergence between fixture audit traces and replay checks.

**Finding R3 — MEDIUM: C ABI shim (`tk_audit_stem.c`) has no Zig wrapper layer.**

The C shim exposes raw C functions (`tk_audit_stem_audit_append`, `tk_audit_stem_record_hash`) directly. Zig consumers must use `extern "c"` declarations. There is no Zig-native wrapper that hides the C ABI.

**Affected paths:** `c_abi/shim/tk_audit_stem.c`, `c_abi/shim/audit_schema.h`

**Recommendation:** Add a thin Zig wrapper in `codec/audit/interop.zig` that provides Zig-typed functions wrapping the C extern declarations. This follows the project convention of "Zig owns logic, C shims are implementation detail."

### 3. Analysability

**Finding A1 — PASS: All audit event types use a tagged union (`AuditEvent`).**

`src/tickoni/schema/audit/audit.zig` defines `AuditEvent` as a tagged union with explicit variants (`source_event`, `normalization`, `deduplication`, `case_creation`, `policy_decision`, `model_call`, `financial_adapter_call`, `proposal`, `limit_check`, `denial`, `approval_required`, `replay_result`). Each variant is self-describing. A developer can trace any event type to its schema definition in one file.

**Finding A2 — PASS: Hash chaining is explicit and traceable.**

`audit_trace.zig` builds events in strict sequence, updating `prev_hash` after each event (lines 133, 142, 150, 160, 174, 189, 199, 209, 218, 228, 242, 251, 260, 269, 278). The chain integrity is visible in the code flow.

**Finding A3 — MEDIUM: `audit_trace.zig` is a large fixture file (528 lines).**

`audit_trace.zig` contains three build functions (`buildAllowedTradeChain`, `buildOversizedTradeBlockedChain`, `buildRestrictedInstrumentBlockedChain`) each building 7-15 events. The `buildAllowedTradeChain` function alone is 182 lines and handles thesis→normalization→dedup→case→policy→model→adapter→proposal→paper_fill→policy→proposal→approval→proposal→replay.

**Affected path:** `test/fixtures/investment/audit_trace.zig`

**Recommendation:** Split into three smaller files (`allowed_trade_trace.zig`, `blocked_limits_trace.zig`, `blocked_restricted_trace.zig`) or extract the shared `header()` function to a common fixture module.

### 4. Modifiability

**Finding MD1 — PASS: `@backingInt` used consistently for enum→int conversions.**

The commit `13584a4d4` (version: split compiler into zig and c compiler fields) and the use of `@backingInt(audit.PolicyOutcome.allow)` throughout the codebase confirms enum conversions use Zig's built-in `@backingInt` rather than manual casts. This is correct and future-proof.

**Finding MD2 — PASS: `audit_schema_version` is a single constant.**

`audit.audit_schema_version` is defined once in `schema/audit/audit.zig` and referenced everywhere. Schema version bumping touches one location.

**Finding MD3 — MEDIUM: `parseFixedAsciiBytes` duplicated across audit_trace.zig and not factored out.**

`parseFixedAsciiBytes(N: usize, value: []const u8) [N]u8` (audit_trace.zig:51-59) is only used within that file but is not imported from a shared fixture module. If the same pattern is needed in other test fixtures, it will be copy-pasted.

**Recommendation:** Move `parseFixedAsciiBytes` and `header()` to a shared fixture module under `test/fixtures/` or `util/`.

### 5. Testability

**Finding T1 — PASS: Unit tests exist and pass for all changed modules.**

Verified via `zig build -Dtest test-unit-tk` and `zig build -Dtest test-integration-tk`:
- `tier.zig`: 10 tests (tierName, detectOsString, detectArchString, version output format)
- `version.zig`: 12 tests (semver, VersionInfo, formatVersionInfo, setManifestVersion)
- `test_process_api.zig`: 15 tests (logger, CLI parsing)
- Investment integration tests: all pass (allowed trade, blocked limits, restricted instrument)

**Finding T2 — PASS: Replay substitution is explicitly tested.**

`test_investment_replay.zig` validates replay capsule creation and verification. The replay logic in `tiles/payment_pipeline/replay.zig` is tested against captured fixtures.

**Finding T3 — MEDIUM: No unit test for `audit_sink.zig` AuditLog.**

`audit_sink.zig` (2,943 chars) provides the `AuditLog` builder and `AuditAppendInput` type, but there is no dedicated unit test in this story. The integration tests exercise audit logging through the pipeline, but unit-level testing of `AuditLog.append()` and `AuditLog.flush()` is missing.

**Affected path:** `tiles/payment_pipeline/audit_sink.zig`

**Recommendation:** Add a unit test for `AuditLog` covering: sequential appends with hash chaining, flush with buffer overflow, and empty log edge case.

**Finding T4 — PASS: Test fixtures use deterministic data.**

`audit_trace.zig` uses fixed `run_id`, `prev_hash = 0`, `timestamp_ns = 0`. All fixed-size fields are parsed from ASCII. No randomness, no timestamps, no external state. This makes test outcomes deterministic and replayable.

## Additional Maintainability Reviews

### Cohesion and Coupling

**Finding C1 — PASS: High functional cohesion in audit modules.**

- `audit_consts.zig`: single responsibility (seed, schema version)
- `hash.zig`: single responsibility (Wyhash computation)
- `audit_sink.zig`: single responsibility (AuditLog builder)
- `replay.zig`: single responsibility (replay capsule management)
- `audit_stage.zig`: single responsibility (audit stage lifecycle)

**Finding C2 — LOW: Tight coupling between `audit_trace.zig` and tile IDs.**

`audit_trace.zig` hardcodes tile IDs (`tile_ids.tkings.slice()`, `tile_ids.tknorm.slice()`, etc.) in event headers. This is correct for fixtures but creates a hidden dependency: if a tile is renamed or removed, the fixture will silently produce incorrect tile IDs rather than failing to compile.

**Affected path:** `test/fixtures/investment/audit_trace.zig`

**Recommendation:** No immediate fix needed. This is the expected behavior for a fixture — it documents the *expected* tile ID values. If tile IDs change, the fixture should be updated to match.

**Finding C3 — MEDIUM: `runtime.zig` in `payment_pipeline/` depends on `PaymentPipelineState`.**

`runtime.zig` defines `PaymentPipelineState` which is used by `audit_sink.zig`, `replay.zig`, `audit_stage.zig`, and `process.zig`. This is correct — shared state belongs in `runtime.zig`. However, `PaymentPipelineState` is payment-specific (it tracks payment events), while audit events are generic.

**Affected path:** `tiles/payment_pipeline/runtime.zig`

**Recommendation:** Consider extracting `AuditPipelineState` (or `AuditLogState`) from `PaymentPipelineState` into a shared `audit/` module. The audit pipeline should not depend on payment-specific state.

### Separation of Concerns

**Finding S1 — PASS: Clear separation between schema, codec, shim, and pipeline.**

- `schema/audit/` — data definitions (structs, enums)
- `codec/audit/` — serialization/deserialization (hash, binary)
- `c_abi/shim/` — C interop layer
- `tiles/payment_pipeline/` — runtime pipeline logic

No layer violates its boundary. Schema modules don't import codec. Codec doesn't import pipeline. Pipeline imports schema and codec.

**Finding S2 — PASS: Agents are not in the audit critical path.**

Audit events are recorded by the pipeline (`audit_sink.zig`) before any agent execution. This follows the invariant: "AI is not in the deterministic financial event critical path."

**Finding S3 — MEDIUM: `VersionInfo` imports `audit_schema` for schema version.**

`version.zig:79` imports `audit_schema` to get `audit_schema_version`. This couples version to audit, which is fine for now but could create a circular dependency if audit needs version info.

**Affected path:** `version.zig:79`

**Recommendation:** Pass schema version via build options (`build_opts.AUDIT_SCHEMA_VERSION`) instead of importing the module. This follows the pattern of `build_opts.BUILD_VERSION`.

### API and Ownership Boundaries

**Finding B1 — PASS: Tile ownership is explicit and preserved.**

Each audit event header carries `tile_id` set from `tile_ids.{tile}.slice()`. This preserves the Firedancer convention that every event is attributed to the owning tile.

**Finding B2 — PASS: Capability envelope ID is deterministic.**

`capabilityEnvelopeId()` in `audit_trace.zig:71-74` computes `thesis_hash ^ basket.basket_id`. This is deterministic and replayable.

**Finding B3 — PASS: No agent or UI code accesses audit data directly.**

Audit data flows through `AuditLog` in the pipeline. External consumers (CaseOps, API) must go through the audit log API, not the schema/codec directly.

### Naming and Documentation

**Finding N1 — PASS: All public types have doc comments.**

`AuditLog`, `AuditAppendInput`, `Decision`, `Tier`, `VersionInfo`, `AuditChain` variants — all have `///` doc comments explaining purpose and usage.

**Finding N2 — PASS: Tile IDs are used consistently.**

`tile_ids.tkings`, `tile_ids.tknorm`, `tile_ids.tkdedu`, `tile_ids.tkcase`, `tile_ids.tkpoly`, `tile_ids.tkmodl`, `tile_ids.tkadpt`, `tile_ids.tkagnt`, `tile_ids.tkrepl`, `tile_ids.tkdiag` — all follow the `tk<shortname>` convention.

**Finding N3 — LOW: `tier.zig` has a comment saying "Full tier-codification ... lives in S1/S2".**

This is honest documentation about scope boundaries, but it means `tier.zig` is a stub for a larger feature. The comment is appropriate and follows the contribution guideline's "no speculative features" rule.

**Finding N4 — MEDIUM: `VersionInfo.init()` allocates memory without a corresponding `deinit()` in the caller's scope.**

`version.zig:75` — `VersionInfo.init()` allocates `semver` via `gpa.dupe()`. The struct has a `deinit()` method, but callers must remember to call it. This is a memory leak risk.

**Affected path:** `version.zig:75-94`

**Recommendation:** Use `std.AutoHashMap`-style arena allocation, or document that `VersionInfo` must be deinit'd by the caller (which is already done in `test_process_api.zig` via `info.deinit(std.testing.allocator)`). Add a `@deinit` comment to `VersionInfo.init()`.

### Duplication

**Finding D1 — MEDIUM: `audit_schema.h` and `audit.zig` share schema version.**

`c_abi/shim/audit_schema.h:4` defines `#define AUDIT_SCHEMA_VERSION 1` while `schema/audit/audit.zig` defines `pub const audit_schema_version: u16 = 1`. Two sources of truth for the same value.

**Finding D2 — LOW: `policy_version = "tickoni.v1"` defined in `audit_trace.zig`.**

`audit_trace.zig:41` defines `const policy_version = "tickoni.v1"` locally. If the policy version string changes, the fixture won't automatically pick up the change.

**Affected path:** `test/fixtures/investment/audit_trace.zig:41`

**Recommendation:** Move `policy_version` to a shared fixture constant or import it from the policy module.

### Unnecessary Complexity

**Finding UC1 — PASS: No speculative features.**

All code serves a clear purpose documented in the migration plan. No "configurability for future use" — `Tier` enum has exactly 4 variants matching the documented platform tiers.

**Finding UC2 — PASS: Tagged unions used instead of stringly-typed enums.**

`AuditEvent` uses a tagged union (`AuditEvent.Tag`) not string-based type names. `PolicyOutcome` uses an enum with `@backingInt` coercion. No dynamic dispatch or string matching for type discrimination.

**Finding UC3 — MEDIUM: `VersionInfo` struct has 14 fields, most of which are optional/default.**

`version.zig:60-119` — `VersionInfo` has 14 fields. The `setManifestVersion` and `deinit` methods add to the complexity. The struct could be simplified by using a builder pattern or by separating version metadata from runtime tier info.

**Affected path:** `version.zig:60-161`

**Recommendation:** Consider splitting into `SemverInfo` (version, build id, git sha) and `RuntimeInfo` (os, arch, tier, compilers). The `--version` output can combine them.

### Empty `catch {}` Blocks

**Finding E1 — MEDIUM: 4 instances of `std.Thread.yield() catch {};` in pipeline code.**

| File | Line | Context | Justification |
|------|------|---------|---------------|
| `tiles/payment_pipeline/diag.zig` | 21 | Diag polling loop yield | ACCEPTABLE — `std.Thread.yield()` on failure is a best-effort backoff. Thread yield returning an error is extremely rare (OS scheduling failure) and retrying or aborting would not improve behavior. |
| `tiles/payment_pipeline/queue.zig` | 42 | Queue poll yield | ACCEPTABLE — Same reasoning as diag.zig. |
| `tiles/payment_pipeline/queue.zig` | 58 | Queue poll yield | ACCEPTABLE — Same reasoning as above. |
| `tiles/payment_pipeline/replay.zig` | 29 | Replay polling yield | ACCEPTABLE — Same reasoning as above. |

**Recommendation:** Add a comment above each `catch {};` block explaining the justification:

```zig
// Thread.yield() error is a scheduling failure — retrying or aborting
// provides no benefit; the loop will naturally slow down and recover.
std.Thread.yield() catch {};
```

**Finding E2 — PASS: No `catch {}` in codec, schema, or C shim files.**

The critical audit logic (hash computation, binary parsing, C interop) has no silent error handling. Errors propagate up.

**Finding E3 — PASS: Test file `catch {}` blocks are in test teardown.**

`test_investment_replay.zig:335` (`defer w.interface.flush() catch {};`) and `test_tkaudt_integration.zig:207,232` (`stopProcess catch {};`) are in defer blocks — test cleanup. Silently failing cleanup in a test is correct because: (1) test results are already captured, (2) the test process exits immediately, (3) no production state is at risk.
