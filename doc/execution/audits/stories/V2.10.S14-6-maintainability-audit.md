entanglement:

### 2. Reusability

**Finding — ADEQUATE.**

Shared code is centralized:

- `model_tier.zig` provides a single `TkAgntModelTier` enum that topology
  validation, per-instance config, and the tkagnt route table all derive from.
- `file_io.zig` provides `openFile`, `createFile`, and `createOwnerOnlyFile`
  that handle both absolute and relative path branches in one place.
- The C stem files share the `stem_helpers.h` macros (`STK_GET_CTX`,
  `STK_UNPRIV_INIT`, `STK_EVENT_EXHAUSTED`) and the multipart
  (`tk_mp_rx_t`, `tk_mp_tx_t`) transport layer.

**No duplication of tier definitions, file I/O, or multipart transport found.**

### 3. Analysability

**Finding — STRONG.**

The codebase is highly analysable:

- **Module doc comments** explain the architecture and constraints:
  - `decision.zig` (lines 1–15): "One request, one model dispatch, one
    result. There is no cascade."
  - `tk_agent_stem.c` (lines 1–48): "Scope: bounded transport, correlation
    and ordering only."
  - `tk_model_stem.c` (lines 1–34): "Fixture/replay only. No provider
    transport."
- **Explicit error paths**: Every function returns explicit outcomes.
  `decision.zig`'s `route()` returns `RouteDirective` with `verdict`, `tier`,
  `confidence`, and `recommended_tier` — never a boolean or void that hides
  the reason.
- **Parity tests**: `tkpoly.zig` includes `policyOutcomeZig()` with 15 C/Zig
  parity tests and a bulk sweep over 91 (amount, limit) pairs. This makes
  it impossible for the Zig implementation to silently diverge from the C
  helper.
- **Structured logging**: The C stem files use `FD_LOG_NOTICE` / `FD_LOG_ERR`
  / `FD_LOG_WARNING` with descriptive messages (e.g.,
  `"tkagnt: unprivileged init tiers=%lu mask=0x%x req_in=%lu audit_out=%lu term_out=%lu"`).

### 4. Modifiability

**Finding — STRONG.**

- **Configuration is externalized**: All tile behavior is driven by topology
  links and configuration files, not hardcoded values.
- **No tile-index-dependent routing**: The tkagnt tile identifies its output
  consumers by **name** (`strcmp(consumer->name, TILE_ID_TKAUDT)`) and
  **kind_id**, not by link index or tile ordinal. This means tiles can be
  removed, reordered, or replaced without changing the C logic.
- **Callback-driven architecture**: The Zig decision hooks (`hooks.route`,
  `hooks.interpret`) are registered at init time via `setHooks()`. The C stem
  never hardcodes routing logic — it always delegates to Zig.
- **The C stem files follow the fd_stem callback contract exactly**:
  DURING_FRAG stages only, AFTER_FRAG commits, AFTER_CREDIT publishes.
  This is a well-documented pattern that any contributor following the
  contribution guide will recognize.

- **30 tests in `model_instances.zig`** covering: sparse tier validation,

- **Integration tests**: 20 tile process + topology tests and 4 model

### Separation of concerns

**Result: STRONG.**

2. **Decision** (Zig `decision.zig`): Pure functions over fixed-size data.
3. **FFI** (Zig `tkmodl.zig`, `tkagnt.zig`, `tkpoly.zig`): Thin wrappers
   over C extern declarations.
4. **Configuration** (Zig `model_tier.zig`, `model_instances.zig`): File
   I/O and enum management.
5. **Supervisor** (Zig `supervisor.zig`): Tile lifecycle orchestration —
   agnostic to tile-specific logic.

### API and ownership boundaries

**Result: STRONG.**

- **Decision hooks** are the one approved C→Zig call path. The C stem
  never decides routing itself — it always calls `hooks.route()`.
- **Scratch accessors** are defined in the C file and called from Zig
  through extern declarations. No Zig mirrors C structs.
- **Counter publishing** goes through `stk_publish_counter()` to the CNC
  — the supervisor reads them, it doesn't push them.
- **No agent has shell access, unrestricted network access, or direct
  database credentials.** Model access goes through `tkmodl`, tool access
  through `tktool`, execution through `tkexec` (future).

## Tile-agnostic orchestration (no tile-index-dependent decisions)

**Finding — STRONG.**

The orchestration code does NOT rely on specific tile indexes for logic
decisions:

1. **tkagnt output binding** (`tk_agent_stem.c` lines 456–498): Output
   consumers are identified by **name** (`strcmp(consumer->name, ...)`),
   not by link index. Any tile can be added, removed, or reordered.
2. **tkmodl output binding** (`tk_model_stem.c` lines 455–466): Same
   pattern — outputs are identified by consumer name (`tkaudt` / `tkagnt`),
   not by position.
3. **tkmodl link consumer** (`tk_model_stem.c` lines 419–427): The
   `tkmodl_link_consumer()` helper iterates all tiles to find the consumer
   by name. No hardcoded tile IDs.
4. **tkagnt link consumer** (`tk_agent_stem.c` lines 383–391): Same
   pattern — `tkagnt_link_consumer()` uses `strcmp` on tile name.
5. **Tier routing** (`tk_agent_stem.c` lines 295–304): `tkagnt_set_route()`
   stores `(tier, kind_id)` pairs. The `tkagnt_tier_of_kind()` function
   searches the route table by kind_id. No tile ordinal is used.
6. **Supervisor tile lifecycle** (`supervisor.zig`, `tile_process.zig`):
   Tile launch uses topology descriptors, not hardcoded tile IDs.

**Conclusion:** Removing any tile from the topology will not break the
remaining tiles' logic. The system is fully tile-agnostic.
