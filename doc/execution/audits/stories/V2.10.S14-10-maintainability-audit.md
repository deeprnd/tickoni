### 3.2 Tile Pattern Compliance

**STRENGTH.** tkrepl follows the fd_stem tile pattern:

- **Context struct** (tkrepl_ctx_t): owns all mutable state (hooks, observation, verdict, stage)
- **Alignment**: TKREPL_CTX_ALIGN derived from alignof(tkrepl_ctx_t), not hardcoded
- **Footprint**: fd_ulong_align_up(sizeof(tkrepl_ctx_t), TKREPL_CTX_ALIGN)
- **DURING_FRAG**: stages only (clears stale flag, validates frag, copies to scratch)
- **AFTER_FRAG**: commits (fold for events, verdict+publish for summary)
- **SHOULD_SHUTDOWN**: replay_checked OR CNC HALT
- **STEM_BURST**: 1 (one publish per run)
- **tile->allow_shutdown = 1** set before run returns
- **setHooks** fails closed: refuses start without verdict hook

## 4. Findings and Remediation

### 4.1 MOD-01: mod.zig duplication across verify functions

**Severity:** INFO  
**Status:** Accepted — documented debt  
**Owner:** V2.10.S14 maintainer  
**Follow-up:** V2.10.S15 or future story

**Finding:** `src/tickoni/tiles/replay/mod.zig` (606 lines) contains four verify functions that share ~60% of their body. The pattern is:

1. Load capsule from JSON
2. Check versions (schema, catalog, taxonomy, policy)
3. Check replay assertions (no_live_model_call, no_live_adapter_call, etc.)
4. Check structural invariants (event_count, ticket_id, substitution counts)
5. Check hash expectations (basket_id, proposal_hash, rebalance_hash, payment_hash)
6. Load and verify model fixture hash
7. Load and verify adapter fixture hashes

`verifyAllowedTradeWithCapsulePath` and `verifyOversizedTradeBlock` are nearly identical except for specific assertion values (e.g., `adapter_substitutions.len != 3` vs `!= 2`, `policy_outcome_matches == "allow"` vs `"deny"`, etc.). There are 75 `divergences.note` calls across the file, many of which follow the exact same pattern:

```zig
if (!capsule.replay_assertions.no_live_model_call) divergences.note("no_live_model_call", N);
```

**Why accepted:** The four functions serve different replay scenarios (allowed, oversized, restricted, tampered) that are tested independently. Introducing a templated/parameterized helper would add complexity (comptime dispatch or function pointer tables) for a gain that is mostly in test readability rather than runtime correctness. The functions are self-documenting: each one clearly shows what assertions a given replay scenario must satisfy. The duplication is a test-style pattern, not a runtime concern.

**Remediation (future):** Extract the common assertion pattern into a comptime parameterized struct:

```zig
pub const ReplayAssertion = struct {
    assertion_name: []const u8,
    check_fn: fn (capsule: ReplayCapsuleWire) bool,
    seq: u64,
};
```

This would reduce the 75 divergences.note calls to ~15 entries in an assertions table per scenario. Not urgent — no correctness risk.

### 4.4 MOD-05: payment_pipeline/replay.zig vs tiles/replay/ separation

**Severity:** INFO  
**Status:** Accepted  
**Owner:** V2.10.S14 maintainer  
**Follow-up:** N/A

**Finding:** Two separate replay implementations exist:
- `src/tickoni/tiles/replay/` — fd_stem tkrepl tile (capsule side-channel, Zig verdict)
- `src/tickoni/tiles/payment_pipeline/replay.zig` — payment pipeline deterministic replay (audit chain comparison)

**Why accepted:** These serve fundamentally different replay purposes:
- `tiles/replay/` (tkrepl): replay the case capsule with external effects disabled, compare observation against tkcase's summary
- `payment_pipeline/replay.zig`: replay synthetic payment events against the actual audit chain, record divergences

Both are legitimate replay modes. They are kept separate because they operate on different data sources (capsule vs audit chain) and produce different outputs (verdict vs divergence count). A future unification would require a common replay abstraction layer that doesn't exist yet.

## 16. Overall Assessment

**Maintainability rating: STRONG.**

The tkrepl fd_stem migration code demonstrates excellent adherence to the Tickoni contribution guide and Firedancer integration patterns. Key strengths:

1. **Clean C/Zig boundary:** The function-pointer hook (TkReplVerifyFn) keeps the C stem free of product logic and the Zig verdict free of transport concerns.
2. **Single-source-of-truth wire contract:** One C header (tkrepl_frag.h) with _Static_assert checks, translated to Zig via translate-c — no mirrored structs.
3. **Executable invariants:** _Static_assert on every struct size/offset, compile-time Zig tests on wire sizes, test headers listing proven behaviors.
4. **Comprehensive test coverage:** C unit tests drive the real stem with a fake stem, Zig tests are pure, integration tests cover full pipeline replay.
5. **No violations:** No empty catch blocks anywhere in the repository (test harness catch {} blocks replaced with structured logging — §4.3), no TODOs/FIXMEs, no dead code, no boundary violations, no platform-specific code in the throughput path.

The primary area for future improvement is `mod.zig`'s duplication across verify functions (§4.1), but this is a test-style concern with no correctness risk and is accepted as documented debt.
