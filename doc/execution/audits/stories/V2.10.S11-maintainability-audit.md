## 2. ISO/IEC 25010 Maintainability Characteristics

### 2.1 Modularity

**Finding M1 — PASS (HIGH IMPROVEMENT)**

The `run_unit_tests.sh` rewrite is the strongest modularity win in this story. The old implementation was a 473-line bash script implementing a NUMA-aware greedy test scheduler — a monolithic component with 12+ associative arrays, 5+ named functions, and complex dispatch/reap logic. It handled NUMA topology, CPU slotting, memory admission control, coverage setup, process management, and test execution all in one file.

The new implementation is 55 lines: a sequential test runner that reads a test list file and runs each binary with `--page-sz` and `--page-cnt` flags. NUMA awareness was removed (tests run sequentially on a single NUMA node), and the scheduling logic was replaced by `run_unit_tests_dynamic.sh` which computes optimal `--page-cnt` and `-j` values at runtime.

**Finding M2 — PASS (GOOD)**

The test infrastructure Python modules follow a clean facade pattern:

```
contrib/test/orchestrator.py  (facade — 5 subcommands)
├── infra/llama_server.py     (server lifecycle — start/stop/health)
├── infra/zig_build.py        (zig build execution)
└── infra/dynamic_test_opts.py (resource detection)
```

Each module has a single responsibility and imports are local (inside methods), avoiding circular dependencies. This is a good application of the Strategy + Facade pattern described in `doc/execution/contribution/tickoni.md` under "Tiles vs Libraries".

**Finding M3 — DEBT (MEDIUM)**

The justfile has proliferated platform-specific recipe aliases. For every test category (unit, integration, demo, system, coverage), there are now 5 platform aliases (`linux-x86`, `linux-arm`, `macos-x86`, `macos-arm`, `windows-x86`) plus a bare recipe that routes via bash case statement. For example:

```
test-unit-tk-linux-x86:    (implementation)
test-unit-tk-linux-arm:    test-unit-tk-linux-x86   ← alias
test-unit-tk-macos-x86:    test-unit-tk-linux-x86   ← alias
test-unit-tk-macos-arm:    test-unit-tk-linux-x86   ← alias
test-unit-tk:              ← bash case routing
```

When a parameter changes (e.g., `ZIG_GLOBAL_CACHE_DIR` or `--summary`), the implementer must either update all 5 aliases or remember to update only the base recipe and trust the `: alias` mechanism. The current pattern relies on make's implicit recipe inheritance, which works but is fragile — adding a new platform (e.g., `windows-arm`) requires updating the routing case statement AND verifying all aliases still point to the right base.

**Decision: Accept debt.** The alias pattern is intentional — it supports platform-specific override when needed (e.g., `test-unit-tk-windows-arm` has explicit build steps). Document the pattern in `doc/execution/testing-tickoni.md`. Follow-up: Add a justfile comment block at the top explaining the alias convention.

### 2.2 Reusability

**Finding R1 — PASS (GOOD)**

The `orchestrator.py` test facade is reusable: it can be called from any shell script (`python3 orchestrator.py llm-server-start`, `python3 orchestrator.py zig-test --target system-test`) or from Python code (`from infra.llama_server import start_server`). The infra modules are self-contained with no external dependencies beyond the Python standard library.

The `llama_cpp_download.py` strategy is reusable via the install orchestrator: `python3 orchestrator.py llm-server` installs both llama.cpp and the model through registered strategies.

**Finding R2 — RESOLVED**

`run_unit_tests_dynamic.sh` has been removed. `contrib/test/infra/dynamic_test_opts.py` is the sole active implementation. See T1.

**Finding R3 — PASS (GOOD)**

Deleted the entire `llama_cpp_build.py` (~257 lines of cmake/git/ninja logic) and replaced with `llama_cpp_download.py` (~117 lines). The new strategy delegates to `download.py` shared helpers (`_download_and_verify`, `_extract_archive`, `_expand_home`, `_is_windows`). This is good dependency hygiene — common patterns live in shared code, platform-specific logic is parameterized.

### 2.3 Analysability

**Finding A1 — PASS (HIGH IMPROVEMENT)**

The sequential test runner is trivially analyzable:
- Read test list file → iterate → run each binary → count pass/fail → exit 1 if any fail.
No process trees, no NUMA topology reads, no CPU slotting logic, no parallel dispatch/reap loops.

**Finding A2 — PASS (GOOD)**

The `dynamic_test_opts.py` module is self-documenting with clear constants, typed docstrings, and a single entry point. The algorithm is:
1. Detect memory (free -b or sysctl)
2. Detect cores (nproc or sysctl)
3. Apply formula: `page_cnt = safe_budget / (page_sz * max_j * overhead_mult)`
4. Output `TEST_OPTS=...` and `LDFLAGS_EXE=...`

**Finding A3 — DEBT (MEDIUM)**

The CI consolidation replaced 4 separate workflow files (`tests-short.yml`, `tests-long.yml`, `tests-xlong.yml`, `benchmark.yml`) with 8 sub-workflows (`_ci-unit.yml`, `_ci-integration.yml`, `_ci-system.yml`, `_ci-demo.yml`, `_ci-conformance.yml`, `_ci-quality.yml`, `_ci-security-deep.yml`, `_ci-security-secrets.yml`) orchestrated by `ci.yml`.

While this is a genuine improvement (shared `detect-changes`, no duplicate runner setup), the cognitive load to understand the full CI pipeline increased:
- A developer now needs to understand `ci.yml` (217 lines) as the entry point AND read each `_ci-*.yml` to understand what actually runs.
- The old model had one workflow per concern with a clear name (`Tests / Long`, `Tests / Short`), making it easy to find "where are the Firedancer unit tests?" → `tests-long.yml`.
- The new model uses `_ci-unit.yml` + a `detect-changes` job, requiring knowledge of the orchestration pattern.

**Decision: Accept debt.** The consolidation is a net improvement — fewer duplicate workflows, shared change detection, cleaner CI. Document the new orchestration model in `doc/execution/ci.md` (already done — the plan updates the CI documentation). Add a diagram to `ci.md` showing the `ci.yml` → `_ci-*.yml` dispatch tree.

### 2.4 Modifiability

**Finding MO1 — PASS (HIGH IMPROVEMENT)**

The new test infrastructure is trivially modifiable:
- Adding a new test runner script: 18 lines (see `run_live_investment_demo.sh`).
- Changing the llama.cpp server startup parameters: edit one Python function in `infra/llama_server.py`.
- Changing the dynamic memory formula: edit one file (`infra/dynamic_test_opts.py`).

Compare to the old:
- Changing the NUMA scheduler required understanding the `sow()` / `reap()` / `dispatch()` / `runner()` interaction across 470+ lines of bash with 12+ associative arrays and dynamic nameref (`declare -n`).
- Changing the llama.cpp build required editing `ensure_llama_cpp.sh` (146 lines of CUDA detection, cmake configuration, platform branching).

**Finding MO2 — RESOLVED**

All `contrib/readme/run-badged-command.py` references in the justfile have been updated to `contrib/tool/readme/run-badged-command.py`. See T3.

- `zig_build.py` — only deals with zig build execution.

### 2.7 Separation of Concerns

**Finding S1 — PASS (EXCELLENT)**

The story establishes a clear boundary between setup and test:

```
contrib/setup/orchestrator.py  ← setup: install llama.cpp + model
contrib/test/orchestrator.py   ← test: start/stop server, run zig test
contrib/test/run_live_investment_demo.sh  ← orchestration: setup → start → test → cleanup
```

This matches the separation rule in `doc/execution/contribution/tickoni.md`:
> `contrib/setup/` — build llama.cpp, download model, start/stop server
> `contrib/test/` — orchestrate setup → start server → run Zig system-test → kill server

**Finding S2 — PASS (GOOD)**

The test runner (`run_unit_tests.sh`) no longer handles coverage setup, process management, or NUMA topology. It only runs tests sequentially and reports pass/fail. Coverage is handled externally (the `test-cov-*` justfile recipes configure LLVM profiling separately).

### 2.10 Unnecessary Complexity

**Finding X2 — DEBT (LOW)**

**Decision: Accept debt.** The 14 strategies cover distinct categories (apt, pip, download, zig, build, none, llama_cpp_download, hf_cli, hf_model, openssl_build, qt_installer, npm, nodejs, python_script). Each is small and focused. The `__init__.py` import is a minor overhead that ensures all strategies register their `@register` decorator on import.
