## 1. Executive Summary

This story introduces three distinct workstreams:

1. **Badge automation** (primary story scope): `badge_updater.py`, `badge-update.yml`, coverage CI job
2. **Justfile split** (V2.10.S2-3): Monolithic `justfile` → `just/*.just` import tree
3. **Windows platform support** (V2.10.S8-5): `fd_tile_threads_platform_windows.c`, `fd_cpu_topo_platform_windows.c`, `fd_log_windows.c`, shmem/NUMA platform shims, tests

Total changes: **59 files, +6,130 / -1,464 lines**.

The codebase passes pytest (97 passed, 1 skipped) for contrib/test. The `just quality-check-all` command fails due to missing upstream Firedancer tooling (`contrib/quality/quality.sh` references paths that resolve via submodule setup, `src/disco/events` is submodule-only). This is an **infrastructure gap**, not a code quality issue within this story's scope.

## 2. ISO/IEC 25010 Maintainability Assessment

### 2.1 Modularity

**Rating: GOOD**

The justfile split is the strongest modularity win. The monolithic 1,000+ line `justfile` is decomposed into 13 focused files:

| File | Responsibility |
|------|---------------|
| `just/common.just` | Shared variables, platform detection, setup recipes, memory management |
| `just/build/all.just` | Build dispatchers, aggregate recipes |
| `just/build/linux.just` | Linux-specific build/test |
| `just/build/macos.just` | macOS-specific build/test |
| `just/build/windows.just` | Windows-specific build/test |
| `just/test/unit.just` | Unit test orchestration |
| `just/test/integration.just` | Integration test orchestration |
| `just/test/demo.just` | Demo conformance recipes |
| `just/test/system.just` | System/E2E test recipes |
| `just/test/coverage.just` | Coverage recipes |
| `just/quality.just` | Format, lint, proto checks |
| `just/security.just` | Security checks (CodeQL, gitleaks, seccomp, proof, sanitize, engine) |
| `justfile` | Import declarations + CI-specific entry points |

The badge updater is also well-modularized into logical sections (documented via comment headers):
- `badge_updater.py` sections: constants → GitHub API helpers → parent-commit walk → badge resolution → README update → git commit & push → main

**Finding M-1 (Minor — Accepted debt):** `just/common.just` is 410 lines — the largest new file. While responsibilities are logically grouped (variables, platform, setup, quality setup, secrets setup, coverage setup, security setup, Qt setup, dispatchers, memory, kill-test), it could benefit from splitting `setup-*` recipes (lines 91-276, ~180 lines) into `just/setup/linux.just`, `just/setup/macos.just`, `just/setup/windows.just` for future growth. *Debt accepted — no action required in this story.*

**Finding M-2 (Good):** `scripts/dispatch` and `dispatch-map.json` cleanly separate the dispatch *logic* from the dispatch *data*. The JSON map is the single source of truth; the Python script is a thin runner. This is a textbook factory pattern.

### 2.2 Reusability

**Rating: GOOD**

Reusable workflow design:
- `_ci-coverage.yml` — `workflow_call` only, reusable as a DAG node
- `tests-coverage.yml` — `workflow_call` + `schedule` + `workflow_dispatch`, invocable standalone

Both share nearly identical step sequences (checkout, setup toolchain, build, run coverage, generate JSON). The duplication (~15 lines) is acceptable because the standalone workflow needs `build-tk` (full build) while the reusable one downloads the artifact.

**Finding R-1 (Low — Accepted debt):** `_ci-coverage.yml` and `tests-coverage.yml` share 13 of 15 lines. The duplication is bounded (2 workflows) and the workflows have genuinely different requirements (artifact download vs full build). *Debt accepted.*

**Finding R-2 (Good):** `badge_updater.py` functions are all independently testable: `_coverage_color()`, `badge_url()`, `replace_badge_block()`, `resolve_badges()`. No global state mutability except for constants. The `--dry-run` flag makes it safe to run locally without side effects.

### 2.3 Analysability

**Rating: GOOD (improved from MIXED)**

**Strengths:**
- `badge_updater.py` has clear section headers and inline docstrings
- Commit messages are conventional and descriptive (`fix: ci.yml — ...`, `feat: add ...`)
- Each CI job has a single clear responsibility in the aggregated pattern

**Finding A-1 (Medium — DONE):** `find_last_successful_sha()` walk now logs `[walk]` prefixed print statements for each skipped SHA, iteration count, and termination reason (see `0fd497376`).

**Finding A-2 (Minor — DONE):** Added `contrib/test/test_badge_updater.py` with 25 tests covering `_coverage_color()`, `badge_url()`, `_resolve_simple_badge()`, `resolve_badges()` (with mocked API), `replace_badge_block()`, and `update_readme()`. All 25 pass. Tests run under `contrib/test/` via existing pytest config. (see `57f645cd9`).

**Finding A-3 (Minor — DONE):** `resolve_badges()` refactored to data-driven loop using `_BADGE_DEFS` table and `_resolve_simple_badge()` helper (see `0fd497376`). Reduced from 60 lines of copy-paste to a 6-line loop over structured config.

### 2.4 Modifiability

**Rating: GOOD**

The dispatch-map approach makes platform additions straightforward:
1. Add entry to `dispatch-map.json`
2. Add platform alias in the relevant `just/<category>.just`
3. The bare dispatcher's `case` statement in `justfile` auto-extends via make's target inheritance

**Finding Mo-1 (Minor — Platform alias maintenance burden):** The comment in `just/common.just` (lines 8-25) correctly documents the alias convention but doesn't prevent forgetfulness. When adding a new platform (e.g., `windows-arm`), every existing category must be updated. A script to validate dispatch-map coverage vs justfile aliases would help, but this is an enhancement, not a defect. *Debt accepted.*

**Finding Mo-2 (Good):** The justfile import structure means changes to one category (e.g., adding a new security check) don't require touching unrelated files. The `justfile` root only needs `import "just/security.just"` — no recipe duplication.

### 2.5 Testability

**Rating: GOOD (improved from NEEDS IMPROVEMENT)**

**What's Good:**

  - `test_badge_updater.py`: 25 tests — `_coverage_color()`, `badge_url()`, `_resolve_simple_badge()`, `resolve_badges()` (mocked API), `replace_badge_block()`, `update_readme()`

**Finding T-1 (Medium — DONE):** Resolved alongside A-2. `test_badge_updater.py` lives in `contrib/test/` and is collected by the existing `pyproject.toml` pytest config (`python_files = ["test_*.py"]`). 25 tests, all passing. (see `57f645cd9`).

**Finding T-2 (Low — DONE):** `contrib/test/test_dispatch_map.py` (6 tests) validates dispatch-map.json: valid platform keys, no duplicates, no orphans, platform.sh parity, JSON structure. All 6 pass. (see `57f645cd9`).

There's no dry-run or mock path for the badge-update workflow itself. The `--dry-run` flag in `badge_updater.py` helps, but there's no automated test exercising the full pipeline. *Debt accepted — the workflow_run trigger is inherently a merge-to-main event.*

## 3. Detailed Findings by Category

### 3.1 Cohesion and Coupling

**High Cohesion (Good):**
- Each `just/*.just` file has a single responsibility (build, test, quality, security)
- `badge_updater.py` functions are cohesive: API helpers are grouped, badge resolution is grouped
- `scripts/dispatch` has one responsibility: route to the correct just recipe

**Coupling Assessment:**
- Low coupling between justfile categories (imports, no cross-references)
- `badge_updater.py` depends on GitHub API, git, JSON — all external, well-isolated
- C platform files (`fd_tile_threads_platform_windows.c` etc.) are properly isolated behind `FD_HAS_WINDOWS` guards

### 3.2 Separation of Concerns

**GOOD.** The story maintains clear boundaries:
- CI workflows: `ci.yml` (orchestrator), `_ci-coverage.yml` (coverage DAG node), `badge-update.yml` (post-merge updater), `tests-coverage.yml` (standalone invoker)
- Dispatch: `dispatch-map.json` (data) vs `scripts/dispatch` (logic)
- Platform code: Windows impls in `*_platform_windows.c`, Linux in `*_linux.c`, shared in headers

### 3.3 API and Ownership Boundaries

**GOOD.**
- `badge_updater.py` follows the documented badge-to-job mapping from the story spec
- The parent-commit walk respects the "last successful merge" semantics
- CI aggregated jobs (`project-build`, `project-tests`, `project-security`) serve as clear ownership gates
- Windows platform code is properly bounded: `FD_HAS_WINDOWS` guards, `fd_log_windows.c` replaces only what's needed

**Finding B-1 (Low — DONE):** `AGGREGATED_JOBS` is a module-level constant list — adding a new aggregated job is a one-line addition. This is a simple, explicit list that's easy to maintain. *Debt accepted.*

### 3.4 Naming and Documentation

**GOOD.**
- Commit messages are conventional and descriptive
- `badge_updater.py` has a module-level docstring and per-function docstrings
- Comment headers in `badge_updater.py` clearly separate sections
- `dispatch-map.json` keys follow consistent `{os}-{arch}` convention

**Finding N-1 (Minor — DONE):** `update_readme()` now uses `badge_key` as alt text consistently for all badges. Removed the inconsistent `readme_key.title() + " Tests"` and per-badged overrides. (see `0fd497376`).

### 3.5 Duplication

**Finding D-1 (Medium — DONE):** Resolved alongside A-3. `resolve_badges()` uses `_BADGE_DEFS` data table and `_resolve_simple_badge()` helper. 60 lines of copy-paste reduced to a 6-line loop. (see `0fd497376`).

**Finding D-2 (Low — CI workflow duplication):** `_ci-integration.yml` and `_ci-system.yml` each have a 2-line diff from the old version. Check if there's a reusable workflow pattern that both should share.

### 3.6 Unnecessary Complexity

**LOW.** The story's complexity is appropriate:
- The parent-commit walk is complex but well-documented in the story plan
- The justfile import structure is more complex than a single file but pays for itself with modularity
- The dispatch-map approach replaces 5 inline dispatchers with one script — net simplification

**Finding C-1 (Informational — Windows CPU ID parsing):** `fd_tile_threads_platform_windows.c` has a 60+ line CPU string parser (lines 436-510) that handles ranges, strides, and floating tiles. This is complex but justified — it mirrors the Linux parser's capabilities. Consider adding a unit test for edge cases.

### 3.7 Dead Code

**LOW.**
- The old `justfile` (1,084 lines) is replaced, not deleted — but the git diff shows it's entirely removed from the working tree
- No obvious dead functions or unreachable code paths detected
- `refresh-badges.py` was minimally changed (6 lines) — it's still referenced by CI workflows and the old badge system

**Finding DC-1 (Informational — Badge marker format in README.md):** The README badge markers (`<!-- badge:build:start/end -->`, etc.) are not audited. If they drift from the expected format, `replace_badge_block()` will fail with `ValueError`. Consider adding a validation step.

### 3.8 Dependency Hygiene

**GOOD.**
- `badge_updater.py` uses only stdlib: `argparse`, `json`, `subprocess`, `sys`, `pathlib`, `os`, `urllib.request`, `base64`
- No third-party dependencies introduced
- `dispatch-map.json` is pure JSON, no runtime dependencies
- CI workflows use pinned action versions (`@v7`, `@v5`)

**Finding DH-1 (Low — DONE):** Added `_api_request()` helper with 10s per-call timeout (down from 30s), retry-on-failure (up to 3 retries with exponential backoff), and targeted exception handling for 403/404/502/503/504. Worst case: 10s × 3 retries = 30s max per call. (see `0fd497376`).

### 3.9 Regression Test Coverage

**What exists:**
- `contrib/test/` pytest suite: 97 tests, 1 skipped (all passing)
  - `test_badge_updater.py`: 25 tests — `_coverage_color()`, `badge_url()`, `_resolve_simple_badge()`, `resolve_badges()` (mocked), `replace_badge_block()`, `update_readme()`
  - `test_dispatch_map.py`: 6 tests — platform key validation, no duplicates, no orphans, platform.sh parity, JSON structure
  - Remaining 66 tests: setup scripts (asset resolution, install methods, MSVC detection, shell routing, UUID linking)
- `test_fd_shmem_getrandom.c`: compile-time test for EINTR/short-read retry
- `test_fd_shmem_macros.c`: compile-time test for feature-test macro ordering
- `test_cpu_topo_platform_windows.c`: Windows CPU topology tests
- `test_tile_threads_platform_windows.c`: Windows tile thread tests

**Gaps:**
