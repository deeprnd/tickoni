## 3. Diagnostic Signal Audit

### `PollResult` union — existing, extended Windows path

```zig
pub const PollResult = union(enum) {
    running,
    reaped: std.process.Child.Term,
    detached,
    failed,
};
```

**Before this story:** On Windows, `tryReapNoHang` always returned `.running`. The supervisor never learned that a Windows tile had exited. The `.reaped` and `.failed` arms were dead code on Windows.

**After this story:** On Windows, `tryReapNoHang` calls `os_api.processPoll()` (backed by `tk_process_poll` in C), which uses `WaitForSingleObject` to check exit status. Returns:
- `.running` — process still alive (`WAIT_TIMEOUT`)
- `.reaped` with `.signal = SIGKILL` — exit code 255 (force kill via `TerminateProcess`)
- `.reaped` with `.exited = code` — normal or error exit
- `.failed` — process PID resolution failed
- `.detached` — PID null (already cleaned up)

This is an **observability improvement**, not a new signal. The `.reaped` and `.failed` arms existed but were unreachable on Windows.

**Verdict:** PASS — Diagnostic signals follow existing patterns. No new signal shapes introduced.

### `ProcessOutcome` — no changes

`ProcessOutcome` (`.exited_ok`, `.exited_code`, `.crashed`, `.force_terminated`, `.stopped`, `.unknown`) is unchanged. The `outcomeFromTerm` function uses the same logic.

**Verdict:** PASS — No changes to outcome schema.

### Exit code 255 mapping (Windows `TerminateProcess`)

The story changes `tk_kill_process` on Windows from exit code 1 to 255. This enables `tryReapNoHang` to recognize force-killed processes as `.signal = SIGKILL` (9) instead of an arbitrary exit code 1.

```zig
if (status == 255) return .{ .reaped = .{ .signal = @fromBackingInt(@intCast(9)) } };
```

This improves failure visibility: the supervisor can distinguish "force killed" from "exited with code 1" (which might indicate a successful exit or a different failure).

**Verdict:** PASS — This is a diagnostic accuracy improvement, not a signal addition.

## 4. Failure Visibility Audit

### Per-tile visibility

From `observability.md`:

| Tile | Signal focus |
| --- | --- |
| `tkings` / `ingest_tile` | produced events, ingress backpressure, sandbox failure simulation |
| `tkdedu` / `dedupe_tile` | duplicate detection |
| `tkpoly` / `policy_tile` | allow, deny, duplicate-drop |
| `tkaudt` / `audit_tile` | append-only audit ordering |
| `tkrepl` / `replay_tile` | deterministic replay comparison |
| `tkmetr` / `metric_tile` | metric snapshots |
| `tkdiag` / `diag_tile` | crash, sandbox, audit, replay diagnostics |

**Before this story:** On Windows, the supervisor could not detect when a tile process had exited (`.running` always). Tile crash detection relied on the supervisor's own crash-detection loop, which may not have been exercised on Windows.

**After this story:** The supervisor's `reapExitedChildrenNoHang()`, `refreshProcessHealth()`, and `stopProcess()` paths now correctly observe Windows tile exits via `tryReapNoHang`. Crashed tile detection works on Windows.

**Failure categories from observability.md to preserve:**
- tile exit or sandbox failure — **PASS** (now observable on Windows)
- audited malformed event rejection — not affected
- policy evaluation failure — not affected
- audit append failure — not affected
- replay divergence — not affected
- queue saturation and backpressure — not affected

**Verdict:** PASS — Failure visibility preserved and improved on Windows.

### Crash-only model

From `observability.md`: "The target model is crash-only: if a tile process exits unexpectedly, the supervisor tears down the topology instead of hiding partial degraded state."

The supervisor's `stopProcess()` path calls `reapExitedChildrenNoHang()` and `refreshProcessHealth()` on every child. With this story, the `.reaped` arm (previously dead on Windows) now fires correctly, clearing the child from `self.children` and allowing the supervisor to track tile lifecycle accurately.

**Verdict:** PASS — Crash-only teardown path works on Windows.

### Snapshot diagnostics

From `telemetry.md`, `PaymentPipelineState.snapshotDiag()` returns:
- `crashed_tile` — tile index marked crashed, or -1
- `sandbox_failures` — simulated failures
- `audit_records` — current count
- `replay_checked` / `replay_match` — boolean gauges

This story does not change `snapshotDiag()`. The `crashed_tile` gauge continues to be set by the supervisor when `refreshProcessHealth()` detects a non-running child that was previously healthy. The story makes this work on Windows.

**Verdict:** PASS — Existing diagnostic snapshot preserved, Windows path enabled.

### Supervisor output

From `observability.md`, the `start` command prints:
```
tickoni-supervisor: Phase 0 pipeline completed
tiles: [0] ingest_tile state=stopped ...
metrics: produced=10000 audited=10000 duplicates=1 denied=1 backpressure_waits=...
diag: sandbox_failures=0 replay_checked=true replay_match=true
tickoni-supervisor: stopped
```

This story does not change the supervisor's final output format. The tile states (`.running`, `.stopped`, `.crashed`) are now observable on Windows.

**Verdict:** PASS — Output format unchanged, visibility improved.

The story's T8 (integration verification) should validate this on macOS and Windows.

**Verdict:** PASS (with note) — Tests verify the metric tile works on Linux. Cross-platform `/metrics` validation is deferred to T8 integration verification.
