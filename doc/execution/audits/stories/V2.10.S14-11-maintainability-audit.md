This audit covers the code changes between `origin/main` and the `story/process-fn-removal` branch. The story removes the `process-fn` concept (per-tile callback dispatch) and consolidates the tile bootstrap onto a single `fd_stem` path.

## 1. Modularity

**Finding 1.1 — PASS.** Deletion of `tile_process.zig` (300 lines) was correct and complete. This file embodied the "process mode" abstraction that is now redundant. Its removal eliminates an entire layer of indirection between `tile_main.zig` and the tile's own fd_stem run loop.

**Finding 1.2 — PASS.** The `tile_main.zig` module now has a clear, single responsibility: bootstrap the fd_stem tile from a spec file. The `runPipelineStage` function (80 lines of per-tile callback dispatch) has been fully removed, reducing `tile_main.zig` to ~165 lines focused on the stem-tile path only.

**Finding 1.3 — PASS.** The C shim `tile_run.c` reduction (deletion of `__tile_run` function and its test stubs) properly removes the two-path bootstrap (process-mode vs stem-mode) at the C ABI boundary. The remaining functions (`tile_init`, `tile_run`) serve the unified stem path.

**Finding 1.3a — PASS.** Supporting files updated consistently:
- `build-lib/lib/tile_run.zig`: comment cleaned (removed reference to deleted `tile_process.zig`).
- `src/tickoni/runtime/mod.zig`: `pub const tile_process = @import("tile_process.zig")` removed.
- `src/tickoni/c_abi/topo_run.zig`: comments updated to remove references to `tile_process.zig` and `T4` story milestones.
- `src/tickoni/c_abi/shim/tango.c`: comments updated to remove reference to `tile_process.zig`.
All supporting file changes are consistent with the main deletion and introduce no drift.

**Finding 1.4 — PASS.** `tile_registry.zig` no longer carries the `process_fn: ?ProcessFn` field on `TileEntry`. This was the last Zig-side reference to the removed abstraction. The registry now purely maps `TileId → TileEntry` with capability metadata.

**Finding 1.5 — PASS.** The `LaunchMode` enum (`.process`, `.stem`) and `ProcessFn` type alias have been fully removed from all changed files. No orphaned references remain.

### Assessment: Strong modularity improvement

The story successfully collapses two parallel bootstrap paths into one. This reduces the cognitive load for understanding tile lifecycle by one full abstraction layer. The remaining files are more focused.

## 2. Reusability

**Finding 2.1 — PASS.** The `stemRun` function in `tile_main.zig` is now the single reusable entry point for all stem tiles. It is called by the supervisor for stem tiles and by `main.zig` for the initial bootstrap. No per-tile callbacks are needed.

**Finding 2.2 — PASS.** The C shim functions `tile_init` and `tile_run` remain reusable across all tile types. The removed `__tile_run` was the only non-reusable artifact.

**Finding 2.3 — NOTE (Low severity).** The `tile_main.zig` module doc comment is now minimal: "Internal `__stem-run <spec-file>` child entry point." It could briefly note what a "stem tile" is for newcomers, but this is documentation, not code quality.

### Assessment: Good reusability

With the process-fn abstraction gone, the remaining entry points are cleaner and more reusable. The `stemRun` path is the canonical one for all tiles.

## 3. Analysability

**Finding 3.1 — PASS.** The elimination of `process_fn` callbacks removes a source of indirection that made it hard to trace tile behavior. Previously, reading `tile_registry.zig` showed a `process_fn` field, but the actual callback implementation lived in `tiles/payment_pipeline/process.zig` or similar. Now the tile's own `stemRun` path is directly visible.

**Finding 3.2 — PASS.** The supervisor (`supervisor.zig`) no longer conditionally launches tiles via process-fn dispatch. The tile spawn loop (`spawnPaymentPipelineProcess` → `spawnStemTiles`) now follows a single code path. This makes it easier to reason about tile lifecycle.

**Finding 3.3 — PASS.** The `topologies.zig` file references to `stemRun` are now the only references (previously there were also `runPipelineStage` references). The topology-to-implementation mapping is now 1:1.

### Assessment: Good analysability

The code is now easier to trace from supervisor → tile → tile's own run loop. One fewer indirection layer.

---

## 4. Modifiability

**Finding 4.1 — PASS.** Adding or removing tiles now requires only changes to `tile_registry.zig`, `topologies.zig`, and the tile's own source file. The old pattern required updates in three places: registry entry, `tiles/payment_pipeline/process.zig`, and `tile_main.zig`. Now only the registry entry is needed.

**Finding 4.2 — PASS.** The `supervisor.zig` tile spawn logic is now simpler: it iterates tiles and launches them uniformly. There's no per-tile mode branching. This makes future modifications (e.g., adding new tile lifecycle hooks) straightforward.

**Finding 4.3 — PASS.** The C shim layer (`tile_run.c`) is now minimal. Future changes to tile bootstrapping need only touch one path.

### Assessment: Good modifiability

Reducing the codebase by ~400 lines (300 from `tile_process.zig` + ~100 from `tile_main.zig` deletions) while removing a full abstraction layer directly improves modifiability.

## 6. Cohesion and Coupling

**Finding 6.1 — PASS.** Cohesion improved: `tile_main.zig` is now tightly focused on stem-tile bootstrap. The old `runPipelineStage` function had low cohesion — it looked up a tile in the registry and dispatched to a callback that lived in an entirely different module.

**Finding 6.2 — PASS.** Coupling reduced between `tile_main.zig` and the per-tile implementation modules (`tiles/payment_pipeline/process.zig`, etc.). Those modules no longer need to conform to a `ProcessFn` signature.

**Finding 6.3 — PASS.** The supervisor no longer needs to understand tile modes. The `topologies.zig` `StemTopo` builder no longer references `process_fn` or `LaunchMode`.

### Assessment: Improved cohesion, reduced coupling

The removal of `process_fn` breaks an unnecessary dependency chain between tile registry, tile main, and per-tile implementation modules.

## 7. Separation of Concerns

**Finding 7.1 — PASS.** The separation is now cleaner:
- `supervisor.zig`: orchestrates tile lifecycle (spawn, monitor, halt)
- `tile_main.zig`: bootstraps a single tile from spec file
- Tile source files: implement the tile's own run logic
- `tile_registry.zig`: maps tile IDs to metadata (no behavioral callbacks)

**Finding 7.2 — PASS.** The old `process_fn` pattern blurred the boundary between tile metadata (registry) and tile behavior (implementation module). Removing it restores clear separation.

### Assessment: Strong separation of concerns

## 8. API and Ownership Boundaries

**Finding 8.1 — PASS.** `tile_registry.zig` now owns only metadata (tile IDs, capability envelopes, instance counts). The `process_fn` field was the only behavioral field, and it's gone.

**Finding 8.2 — PASS.** `tile_main.zig` owns the stem-tile bootstrap contract: takes a spec file path, rebuilds topology, calls `c_abi.topo_run.runTileSimple`.

**Finding 8.3 — PASS.** `supervisor.zig` owns the orchestration contract: spawn tiles, monitor state, handle halts. No process-fn dispatch logic remains.

**Finding 8.4 — NOTE (Low severity).** The `tile_main.zig` module now has two public functions: `stemRun` (the only entry point) and the `test` block. The old `run` function (for process-mode tiles) is gone, which is correct.

### Assessment: Clear API and ownership boundaries
