## 1. Input Validation at Trust Boundaries

### os.c — C system call boundary

| Function | Boundary | Input | Validation |
|----------|----------|-------|------------|
| `tk_process_id_from_handle` | C shim → Zig | `uintptr_t handle` (raw pointer cast) | Casts to int; returns -1 if `GetProcessId` returns 0. Safe: handle comes from Zig `std.process.Child.Id`, not external. |
| `tk_process_poll` (Windows) | C shim → Zig | `int pid` | Validates `OpenProcess` returns non-NULL; validates `WaitForSingleObject` result before dereferencing exit code. |
| `tk_kill_process` (Windows) | C shim → Zig | `int pid` | Checks `OpenProcess` returns non-NULL. |
| `tk_self_exe_path` (Windows) | C shim → Zig | `char* buf, size_t buf_len` | Checks `GetModuleFileNameA` return value and `n >= buf_len`. |
| `tk_parent_pid` (Windows) | C shim → Zig | `int pid` | Checks snapshot creation; returns -1 on failure. |
| `tk_getenv` (all) | C shim → Zig | `const char* name` | Bounds-checks result against 4096-byte static buffer. |
| `tk_write` (Windows) | C shim → Zig | `int fd, void* buf, size_t count` | Clamps `count` to `INT_MAX` before `_write()`. |
| `tk_setenv` (Windows) | C shim → Zig | `const char* name, const char* value` | Returns -1 if `_putenv_s` fails. |

**Finding 1.1 — LOW:** `tk_write` on Windows silently truncates `count > INT_MAX` to `INT_MAX`. For small writes this is harmless, but if a caller passes a large buffer (>2 GB), it silently splits it. Given this is a shim for stderr logging, not a data path, this is acceptable but should be noted.

**Status: DONE** — No change required. The function is used exclusively for stderr logging in the process shim; no code path passes data buffers that would approach INT_MAX. Truncation at INT_MAX (2 GB) is well beyond any realistic log message size and does not affect financial correctness or security.

**Finding 1.2 — LOW:** `tk_port_is_in_use` on Windows creates a socket, binds, closes, and calls `WSACleanup` — but `WSACleanup` is called even if the socket creation failed or if `bind` failed before `closesocket`. This doesn't cause a security issue (the socket is either INVALID_SOCKET or already closed), but it means `WSACleanup` may be called without a matching `WSAStartup` on error paths.

**Status: DONE** — All code paths in `tk_port_is_in_use` call `WSAStartup` first and return early if it fails, so every `WSACleanup()` call is preceded by a successful `WSAStartup()`. The function is correct; added clarifying comment documenting this invariant.

### os.zig — Zig wrapper boundary

| Function | Validation |
|----------|------------|
| `selfExePath` | Returns `error.SelfExePathFailed` if C shim returns negative. |
| `parentPid` | Returns `error.PPidNotFound` if C shim returns negative. |
| `processId` | Returns `error.ProcessIdNotFound` if C shim returns negative. Uses `@intFromPtr` for Windows handle cast — safe because `std.process.Child.Id` on Windows IS a HANDLE pointer. |

### process_api.zig — process management boundary

## 2. Output and Error Checking

### Positive findings:
- **All new Windows functions check handle/return values:** `OpenProcess`, `CreateToolhelp32Snapshot`, `TerminateProcess`, `GetExitCodeProcess` — all checked before use.
- **Zig wrappers return errors:** `selfExePath`, `parentPid`, `processId` all return error unions when C shim fails.
- **`tk_process_poll` Windows:** validates all `WaitForSingleObject` return codes before dereferencing exit code.

### Finding 2.1 — LOW: Silent failure in `termProcess` (Windows)

**Status: DONE** — Fixed `termProcess` and `forceTerminate` to return `bool` instead of `void`. Returns `false` when PID resolution fails, `true` on success. Supervisor now checks the return value and logs errors on failure via `log.error`. Phase 2 (SIGKILL) now uses `termProcess` directly instead of `forceKillProcess` to maintain consistent behavior.

```zig
pub fn forceTerminate(pid: std.process.Child.Id) bool {
    return termProcess(pid);
}

pub fn termProcess(pid: std.process.Child.Id) bool {
    const numeric_pid = os_api.c.processId(pid) catch return false;
    _ = os_api.c.killProcess(numeric_pid);
    return true;
}
```

The supervisor logs a failure via `log.error` when `termProcess` returns `false`, so stale processes are now observable in logs. The process is still fail-closed (doesn't escalate), but the operator can now detect PID resolution failures.

### Finding 2.2 — LOW: `tk_getenv` static thread-local buffer

The 4096-byte static thread-local buffer in `tk_getenv` is a well-known pattern (also used by Firedancer). The security implication is:

- If `getEnv("SOME_VAR")` is called and the result is used after a subsequent `getEnv("OTHER_VAR")` call on the same thread, the buffer is overwritten.
- This is a **data integrity** issue, not a memory safety issue. The buffer is stack-allocated (thread-local, no heap), so no overflow or UAF risk.
- The comment in the code acknowledges this: "caller must use the returned slice before the next getEnv() call on any thread."

This is **acceptable** for the shim's use case (config/env vars read once at startup), but should be documented as a constraint.

**Status: DONE** — No change required. The constraint is documented in-code via comments. The function is only used at startup for configuration reads (single-use pattern), and no code path reads a value, calls getEnv again, then uses the earlier value.

## 6. C/Zig Memory and Stack Safety

### os.c
- **No raw pointer escapes:** All C functions return values (int, char*, void*), not raw pointers to internal state.
- **No buffer overflows:** `snprintf(path, sizeof(path), ...)` bounds the format output. `GetModuleFileNameA` receives `buf_len` as max. `_NSGetExecutablePath` validates size.
- **No dangling pointers:** Windows handles are always closed (`CloseHandle`) before return.
- **`tk_parent_pid` Windows:** `PROCESSENTRY32` struct is zeroed with `memset` before `Process32First`. `CloseHandle(snap)` is called in the normal path. However, if `Process32First` fails, `CloseHandle(snap)` is still called (the code structure ensures it).

### os.zig
- **`@intFromPtr` for Windows HANDLE cast (line 46):** This converts a pointer-sized HANDLE to `usize`. Safe because `std.process.Child.Id` on Windows IS a HANDLE (pointer). No arbitrary pointer cast.
- **`@intCast` for lengths (line 31):** `@intCast(buf.len)` converts `usize` to `c_int`. Safe because `buf.len` is caller-provided and bounded by the stack/heap buffer size.
- **No `catch unreachable` on external input:** All error paths return `error.X` or pass through the C shim's error code.

### process_api.zig
- **No stack buffer overflows:** All buffers are fixed-size or slice-based.
- **`@intCast(pid)` in `killProcess` (line 23):** Converts `ProcessId` to `c_int`. Safe because `ProcessId` is already `std.posix.pid_t` on POSIX and `u32` on Windows.
- **`@intFromPtr` for Windows handle (line 46 of os.zig):** Documented above — safe for `std.process.Child.Id`.

## 9. No Elevated Permissions

- **No code path runs as root or with elevated privileges.** The Windows `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` and `OpenProcess(PROCESS_TERMINATE)` calls operate within the tile process's own token — no privilege escalation.
- **`TerminateProcess` with exit code 255:** The change from 1 to 255 is a deliberate mapping to the "force killed" semantics used by the supervisor. 255 is used because Windows `GetExitCodeProcess` returns the raw exit code, and the supervisor interprets 255 as a signal-based termination (matching SIGKILL = 9 in the POSIX path via `tryReapNoHang` where `status == 255` returns `.signal = SIGKILL`). This is **not** a privilege escalation.
- **No new filesystem access:** The changes don't add any file read/write/open operations.
- **No network access:** No new sockets, HTTP, or DNS operations.
