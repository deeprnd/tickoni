## ISO/IEC 25010 Maintainability Characteristics

### 1. Modularity — GOOD

Each file has a single, clearly declared responsibility:

| Module | Responsibility |
|--------|---------------|
| `tk_audit_stem.c` | DURING_FRAG/AFTER_FRAG for tkaudt: build hash-chained AuditEvents |
| `tk_model_stem.c` | DURING_FRAG/AFTER_FRAG for tkmodl: govern request, resolve fixture, publish audit+result |
| `tk_agent_sink_stem.c` | Bounded result-sink: observe tkmodl result link, count committed results |
| `tk_policy_stem.c` | DURING_FRAG/AFTER_FRAG for tkpoly: increment hops, apply decision chain, publish |
| `tile_run.c` | Tile dispatcher: match tile name → fd_topo_run_tile_t descriptor |
| `audit.zig` / `tkmodl.zig` / `tkpoly.zig` / `tkagnt.zig` | Thin Zig FFI wrappers over C stem symbols |
| `tile_registry.zig` | Single source of truth for tile identity, launch mode, counter schema, link cardinality |
| `validator_parity.zig` | C/Zig governance parity tests (20 cases) |
| `tkpoly_bounded.zig` | Bounded tkpoly tile context for Phase 5 stem migration |

**F-001 [MOD] `tile_main.zig` mixes entry/dispatch with config I/O — RESOLVED (config handoff extracted)**
- Original claim: 22,236 chars / ~1,471 lines mixing process entry, config loading and dispatch.
- Verified measurement: the file was 456 lines / 19,781 bytes, not ~1,471, but the concern was real: `loadPolicyLimit` / `loadModelConfig` and their 10 fail-closed tests (~290 lines) sat beside `stemRun` and `runPipelineStage`.
- Fix: moved the config handoff (`loadPolicyLimit`, `loadModelConfig`, their helpers and all 10 tests, unchanged apart from the test-name prefix `tile_main:` → `tile_main_config:`) into `src/app/tickoni/tile_main_config.zig`. `tile_main.zig` is now 174 lines: `run`, `stemRun` (calls `config.loadPolicyLimit` / `config.loadModelConfig`), and `runPipelineStage` registry dispatch. The now-unused `tiles` and `util` imports were removed. No behavior, error set, or fail-closed ordering changed.
- Not split into three files: the proposed `tile_main_dispatch.zig` would hold a ~20-line registry lookup, and the process entry point is `run` plus `stemRun`, which share one boot path. A two-way split removes the actual mixing without scattering the entry point.
- Test wiring: no `build-lib` change. The `test-tile-main` lane reaches the moved tests through `test { _ = config; }` in `tile_main.zig` (same module imports and linkage).
- Evidence: `zig fmt --check src/app/tickoni/` clean; `test-tile-main` lane 11/11 (10 config tests + the import test); `just quality-check-all` PASS.

### 2. Reusability — EXCELLENT

The stem tile pattern is reused consistently across all four C stem files:

```
ctx struct → scratch footprint/align → privileged_init → unprivileged_init →
DURING_FRAG (stage) → AFTER_FRAG (commit + publish + gate) → SHOULD_SHUTDOWN
```

All stem tiles use:
- `stem_helpers.h` macros (`STK_GET_CTX`, `STK_UNPRIV_INIT`, `STK_EVENT_EXHAUSTED`)
- `stk_validate_frag()`, `stk_chunk_to_gaddr()`, `stk_publish_counter()`
- `fd_stem.c` include pattern with `STEM_CALLBACK_*` defines
- `STK_DEFINE_RUN_TILE_ACCESSORS()` macro

The Zig FFI wrappers follow an identical thin-wrapper pattern:
`extern fn → pub fn wrapper() → inline for (name, path, scope)`.

The `tkmodl_validate()` / `policyOutcome()` functions are pure helpers used both in C stem and Zig parity tests.

### 3. Analysability — EXCELLENT

- Every C stem file has a top-level block comment explaining its scope, fd_stem contract, and output links.
- The Zig FFI modules have block comments for each extern group and each wrapper group.
- The tile registry is documented at the top with its single-source-of-truth purpose.
- The parity test file `validator_parity.zig` documents branch order and has 20 named cases.
- No empty `catch {}` block exists under `src/` (`rg -n 'catch\s*\{\s*\}' src --glob '*.zig'` returns no matches); errors are propagated or reported.
- Scratch layout comments explain why accessors recompute offsets from scratch base.

### 4. Modifiability — GOOD

**Pattern consistency is strong**: adding a new stem tile follows the established template:
1. Define context struct → 2. Define scratch footprint/align → 3. Define privileged/unprivileged init → 4. Implement DURING_FRAG → 5. Implement AFTER_FRAG → 6. Define `fd_topo_run_tile_t` → 7. Add `STK_DEFINE_RUN_TILE_ACCESSORS` → 8. Register in `tile_registry.zig` → 9. Add predicate in `tile_run.c` → 10. Add Zig FFI module → 11. Add parity tests.

**F-002 [MOD] C/Zig stem boilerplate duplication — RESOLVED (shared `RunDescriptor` comptime template)**
- Original claim: the Zig FFI wrappers are 1:1 identical across `audit.zig`, `tkmodl.zig`, `tkpoly.zig`, `tkagnt.zig`; add a comptime template.
- Verified scope: the modules are not identical overall (317 / 307 / 384 / 122 lines; per-tile accessors differ), but the `tk_get_<stem>_run_{name,tile,run,scratch_align,scratch_footprint,privileged_init,unprivileged_init}` set is the same seven externs and wrappers in each. That shared part is what the template covers. On the C side the pattern is already shared via `stem_helpers.h`.
- Fix: added `src/tickoni/c_abi/stem_run.zig` with `RunDescriptor(comptime sym, comptime Tile)`, which resolves the seven C exports via `@extern` from a closed, comptime-built name (`"tk_get_" ++ sym ++ "_run_" ++ field`). `tkmodl.zig` (`"model"`), `tkpoly.zig` (`"policy"`) and `tkagnt.zig` (`"agent_sink"`) drop their 7 hand-written `extern fn` lines each and delegate their existing public wrappers (`getModelRun*`, `getPolicyRun*`, `getRunName`, `getRunTile`) to it; their identity tests use the same descriptor. Public API is unchanged and no caller was touched. A missing C export remains a link error, and tile-specific accessors (scratch footprint, counters, setters) stay explicit `extern fn`s.
- Limits, stated plainly: `audit.zig` is not converted. It is a separate build module (`c_abi_audit`, see `build-lib/mod/modules.zig`) and cannot share a file with the `c_abi` module; `tknorm.zig`/`tkdedu.zig` were outside this story's scope. The saving is ~21 declaration lines plus the repeated symbol strings, not the ~80% the audit estimated. The template builds C symbol names from strings, which AGENTS.md treats with caution ("prefer explicit ... over stringly-typed registries"); it is acceptable here because the set is closed, comptime-checked at link time, and confined to one 48-line file, but reviewers may reasonably prefer to revert it.
- Evidence: unit lanes unchanged (tkmodl 12/12, tkagnt 2/2, tkpoly 35/35); `just quality-check-all` and `just test-integration-tk` pass.

**F-003 [MOD] `tile_registry.zig` test mass — RESOLVED (tests moved to `tile_registry_test.zig`)**
- Original claim: 713 lines, ~89% tests (measured: 33 tests, ~62%).
- Fix: moved the test section (banner, `phase0_tile_cnt`, topology helpers, all 33 tests) verbatim into `src/app/tickoni/tile_registry_test.zig` (463 lines). The tests only used the registry's public API (`entries`, `findById`, `validate`, `TileEntry`, `CounterField`, ...), so no visibility changes were needed; the test file aliases them from `@import("tile_registry.zig")`. `tile_registry.zig` is now 265 lines of production code plus a 3-line `test { _ = @import("tile_registry_test.zig"); }` so the tests keep running in the same lane (supervisor + registry lane: 38/38, i.e. 4 supervisor + 33 registry + 1 import test). No `build-lib` change.
- Correction to the finding: `build-lib/lanes/unit.zig` does not use a parallel `tests/` directory; the file follows the sibling-file `*_test.zig`/`test_*.zig` approach already used under `src/app/tickoni/` (`test_metric_watchdog.zig`).

**F-004 [MOD] No dedicated integration test for tkpoly stem tile — RESOLVED (`test_tile_tkpoly_integration.zig` added)**
- Original claim: there is no `test_tile_tkpoly.zig` exercising the full tkpoly stem lifecycle.
- Verified: `test_tile_tkpoly.zig` already exists (819 lines, 17 tests) and covers decision branches, precedence, audit-chain evidence per run, self-exit, HALT and counters. What it did not assert is cross-run replay stability of the audit chain.
- Fix: added `src/tickoni/test/integration/test_tile_tkpoly_integration.zig` and registered it in `build-lib/lanes/integration.zig` beside the other tile tests. It runs the full pipeline twice with identical input and signed limit (N=8, covering allow, deny, duplicate and malformed branches), asserts the chain is well-formed (seq, `prev_hash` linkage, expected outcomes at offsets 3/5/7), and requires every record (seq, source offset, outcome, source-event hash, prev hash, hash) to be identical across runs. Helpers are local because each integration file is its own test root.
- Evidence: the new test passes in `just test-integration-tk` ("All 1 tests passed"); the 17 existing tkpoly tests still pass.

### 6. Cohesion — EXCELLENT

Every module has a single, well-defined purpose:

- `tk_audit_stem.c`: audit event building and hash-chain advancement. No policy, no model logic.
- `tk_model_stem.c`: model request governance and fixture resolution. No policy, no audit record building (only publishes).
- `tk_agent_sink_stem.c`: bounded observation. No decisions, no external calls.
- `tk_policy_stem.c`: payment decision chain (malformed > duplicate > high-amount). No audit, no model.
- `tile_run.c`: name-based tile dispatch. No business logic.
- `tile_registry.zig`: tile identity and link cardinality validation.
- `validator_parity.zig`: C/Zig governance parity testing.
- `tkpoly_bounded.zig`: bounded tile context initialization.

### 7. Coupling — GOOD

**Low coupling areas:**
- FFI modules (`audit.zig`, `tkmodl.zig`, etc.) are thin wrappers with no business logic.
- Registry (`tile_registry.zig`) is the single source of truth — no duplicate tile mappings.
- Process-mode pipeline stages (`process.zig`) read config by value, no dependency on LaunchSpec shape.
- Orchestration is tile-agnostic: registry-based dispatch, no hardcoded tile indices for logic decisions.

**Higher coupling (acceptable):**
- C stem files directly include Firedancer headers (`fd_topo.h`, `fd_stem.c`, `fd_wksp.h`). This is intentional for FD stem integration — the C code *is* the Firedancer tile.
- `tile_run.c` includes `stem_helpers.h` and all stem tile headers. This is a dispatcher — it must know about all tiles.

### 8. Naming and Documentation — EXCELLENT

- Tile IDs are consistent: `TILE_ID_TKAUDT`, `TILE_ID_TKMODL`, `TILE_ID_TKAGNT`, `TILE_ID_TKPOLY`.
- FFI function names follow `tk_<stem>_<action>` pattern.
- Zig wrapper names follow `<stem><Action>` pattern.
- All C stem files have comprehensive block comments explaining their fd_stem contract.
- The `stem_helpers.h` macros have clear names (`STK_GET_CTX`, `STK_UNPRIV_INIT`, `STK_EVENT_EXHAUSTED`).

### 9. Duplication — MODERATE

**Significant duplication (addressed above in F-002):**
- C stem boilerplate across 4 files (~400+ lines of repeated pattern)
- Zig FFI boilerplate across 4 modules (~200 lines of repeated pattern)

**Minor duplication (acceptable):**
- The `fd_topo_run_tile_t` initializer structs are nearly identical across stem files, but each has tile-specific fields (name, scratch callbacks). This is acceptable.
- The `privileged_init` pattern is repeated, but each tile has different state initialization.

### 10. Unnecessary Complexity — NONE DETECTED

Code is straightforward: C stem files follow a single well-documented pattern, Zig wrappers are thin, the registry is a simple lookup table. No speculative abstractions, no over-engineered error handling.

### 11. Dead Code — NONE

All changed files are active: the git diff shows 0 removed files and 0 removed functions. The `R090` rename (`test_model_tile_http.zig` → `test_model_http_backend.zig`) and `R060` rename (`tkpoly-fd-stem-migration.md` → `tkpoly-fd-stem-migration-done.md`) are clean renames.

### 12. Dependency Hygiene — GOOD

- C files include only necessary Firedancer headers. No circular dependencies.
- Zig modules use explicit `@import()` — no global namespace pollution.
- The `audit_schema.h` translate-c types are imported consistently.
- `tkmodl.zig` and `tkpoly.zig` share `audit_mod` for schema types — single source of truth for wire types.

### 13. Empty `catch {}` Blocks — NONE

`rg -n 'catch\s*\{\s*\}' src --glob '*.zig'` returns no matches. The previous revision of this audit listed 7 instances in `logger.zig`, `audit_stage.zig`, `tile_process.zig` and `checks.zig`; none exist in the current tree, so the table was removed rather than carried forward.
