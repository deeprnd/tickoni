## 1. Modularity

**Assessment: GOOD**

Each concern lives in its own file with clear ownership boundaries:

- `wksp.c` owns the C-level workspace create/join/delete wrappers. It has two platform blocks (Linux/macOS, Windows), each self-contained — no cross-contamination.
- `topo_run_platform_*.c` owns platform-specific tile pre-boot. Linux has `prctl(PR_SET_NAME)` and no explicit workspace join (upstream handles it); macOS and Windows have explicit workspace join loops. The separation is correct.
- `os.c` owns all cross-platform OS primitives (monotonic clock, sleep, exe path, parent PID, process poll, kill, write, isatty, fflush, setenv, getenv, affinity). The three platform blocks plus fallback are well-gated.
- `os_api.zig` owns the Zig-side re-export of os.c. Thin — one line per function.
- `process_api.zig` owns cross-platform process kill/reap logic. It correctly routes to the os shim on Windows and to std.posix on POSIX.
- `cpu.zig` owns CPU affinity bit manipulation.
- `test_process_api.zig` owns unit tests for process management.

The c_abi layer (`wksp.zig`, `topo_run.zig`, `os.zig`) is thin and mechanical — extern declarations and small wrapper functions that pass arguments through. This matches the "narrow membrane" rule from tickoni.md.

**Finding M-1: os.c is large at 694 lines.**

os.c contains 14 exported functions × 4 platform blocks (Linux, macOS, Windows, fallback) = 56 implementation blocks. The function count has grown from the original 11 in the story plan to 14 (three affinity functions added: `tk_get_affinity`, `tk_set_affinity`, `tk_port_is_in_use`).

**Decision: ACCEPT DEBT.** The pattern is deliberate and follows the tickoni.md "Platform And Operating-System Boundaries" section: each platform gets its own block in the shim file. Extracting shared helpers would add abstraction without reducing actual code, because implementations genuinely differ (e.g., `tk_self_exe_path` uses `readlink` on Linux, `_NSGetExecutablePath` on macOS, `GetModuleFileNameA` on Windows). The size is acceptable for the current function count but should be revisited if the function count reaches 18+.

## 2. Reusability

**Assessment: GOOD**

The architecture promotes reuse correctly:

- `os_api.zig` is reused by `process_api.zig`, `cpu.zig`, `tile_process.zig`, and any module needing cross-platform primitives.
- `process_api.zig` is reused by `supervisor.zig` for child management.
- `wksp.zig` is reused by `topo_build.zig` and `tile_process.zig`.
- `topo_run.zig` is reused by `tile_process.zig`.
- `cpu.zig` is reused by `cpu_placement.zig` and any module needing CPU affinity bit manipulation.
- `test_process_api.zig` is reusable as a reference for testing process-management patterns in new tiles.

**Finding R-1: os_api.zig is not imported via a consistent namespace.**

`process_api.zig` line 2: `const os_api = @import("os_api.zig");` — this is a relative import, not the `util.os_api` pattern used elsewhere. This is a minor inconsistency: the `util` module is the public namespace for Tickoni utilities.

**Decision: ACCEPT DEBT.** Low impact — `process_api.zig` only imports `os_api.zig` and `builtin`, both of which are available via either path. The inconsistency doesn't affect API surface or maintainability.

## 3. Analysability

**Assessment: GOOD**

- Every platform path is clearly marked with `FD_HAS_*` guards.
- `topo_run_platform.h` defines the exact two-entry public interface (`tk_topo_platform_pre_boot`, `tk_topo_platform_join_tile_workspaces`).
- `os.c` uses `tk_*` prefixed symbols throughout, consistent with the shim naming convention.
- `topo_run.zig` has a comprehensive module doc explaining the Linux vs non-Linux dispatch decision.
- `tile_process.zig` has a thorough module doc explaining the single-tile lifecycle and global context pattern.

**Finding A-1: os.c has 694 lines but lacks section comment headers between function groups.**

os.c has 14 functions spanning 694 lines with no blank-line section headers to help readers navigate between "process management" functions (`tk_process_reap_nohang`, `tk_process_force_terminate`, `tk_process_release`) and "utility" functions (`tk_monotonic_nanos`, `tk_self_exe_path`, `tk_parent_pid`, etc.). The Linux/macOS shared block and Windows block each contain these functions interleaved.

**Decision: ACCEPT DEBT.** The function order within each platform block is identical, which aids comparison between platforms. Adding section headers would improve navigation but is not urgent.

**Finding A-2: topo_run_platform_common.h uses #error guards that catch missing macro definitions at compile time.**

This is a good safety mechanism. If a platform file forgets to define `TK_PRE_BOOT_THREAD_NAME` or `TK_STACK_DIAGNOSTICS`, compilation fails with a clear error.

**Decision: RESOLVED — good pattern, no action needed.**

## 4. Modifiability

**Assessment: GOOD**

The three-platform structure is easy to modify:

- Adding a new OS primitive means adding it to all three platform blocks in `os.c` (and the fallback block).
- The `FD_HAS_*` guards are the single source of truth for platform detection.
- `wksp.c` has a clean two-path structure: Linux/macOS shares one path, Windows has a separate path.
- `topo_run_platform_common.h` uses macro-based platform hooks (`TK_PRE_BOOT_THREAD_NAME`, `TK_STACK_DIAGNOSTICS`) that are easy to extend.

**Finding Mf-1: os.c fallback block is incomplete.**

The fallback block (lines 593-693) is compiled when none of `FD_HAS_LINUX`, `FD_HAS_MACOS`, or `FD_HAS_WINDOWS` is true. It has stub implementations for 14 functions, including `tk_setenv` (always returns -1) and `tk_getenv` (always returns NULL). These are not currently used by any Tickoni code outside test contexts.

**Decision: ACCEPT DEBT.** The fallback block is not compiled on any supported platform (Linux, macOS, Windows are all covered). The stub functions are only reachable in test contexts where callers handle null/error returns gracefully.

**Finding Mf-2: topo_run_platform_linux.c has no explicit workspace join logic.**

Linux delegates workspace joining to upstream `fd_topo_join_tile_workspaces()` (line 48: just a pass-through). macOS and Windows have explicit join loops (lines 44-62 in macos, lines 33-52 in windows). This is correct because Linux's upstream path handles it, but a new contributor unfamiliar with the story might wonder why Linux is missing the join loop.

**Decision: ACCEPT DEBT (not a defect).** The omission is intentional — upstream Firedancer handles Linux workspace joining. However, a comment explaining this would help future contributors.

## 5. Testability

**Assessment: GOOD**

**Finding T-1: Resolved — `test-os-shim` unit test now covers the C shim layer.**

A dedicated unit test binary `test-os-shim` was added to `build-lib/lanes/unit.zig` (lines 98–123). It compiles `os.zig` with `os.c` (including `TK_PROCESS_TEST` macro) and runs 16 test cases covering all major platform shim functions: `monotonic_nanos`, `self_exe_path` (normal, truncation, overflow, idempotent), `getenv`/`setenv` round-trip, `getenv_len`, `process` ABI layout verification, `getenv_len` for PATH, `parent_pid` (valid and nonexistent), `port_is_in_use` (various ports, crash safety), `writeFd`, `isatty`, and `getenv` truncation for long values.

The test is registered as a standalone `zig build test-os-shim` step and also participates in the full `run-tests` suite. It exercises the C shim layer in isolation — not through integration tests — providing direct coverage of the cross-platform OS primitives that were the audit's primary concern.

Remaining coverage (wksp.c, topo_run_platform_*.c) is verified by integration tests (`test_process_pipeline.zig`, `test_link_bounds.zig`) and by `test-wksp` (requires Firedancer libs). This is acceptable — the audit finding is resolved for os.c, and wksp.c/topo_run_platform_*.c remain thin wrappers.

**Finding T-2: os_api.zig has no dedicated unit tests.**

`os_api.zig` is a thin re-export (70 lines), so the lack of unit tests is acceptable. However, `c_abi/os.zig` (245 lines) has its own test blocks that exercise the C shim linkage, and `test_process_api.zig` (174 lines) tests the higher-level process management. Together, these provide good coverage.

**Decision: ACCEPT DEBT.** The indirect test coverage through `c_abi/os.zig` tests and `test_process_api.zig` is sufficient for a thin re-export layer.

## 6. Cohesion and Coupling

**Assessment: GOOD**

- `os.c` is highly cohesive: every function provides a cross-platform OS primitive. No mixed concerns.
- `wksp.c` is highly cohesive: every function is a workspace create/join/delete wrapper.
- `topo_run_platform_*.c` files are cohesive per-platform: they share the same pre-boot logic pattern.
- `topo_run_platform_common.h` is cohesive: it provides shared initialization that each platform file includes with platform-specific macro hooks.

**Finding C-1: Code duplication in topo_run_platform_macos.c and topo_run_platform_windows.c.**

The `tk_topo_platform_join_tile_workspaces` function is identical between macOS (lines 43-62) and Windows (lines 33-52). The only difference is the pre-boot thread naming (handled via macros in the shared header).

**Decision: ACCEPT DEBT.** The join logic is platform-invariant in its current form (it iterates `topo->workspaces` and calls `fd_wksp_attach` for each). If the join logic diverges per-platform in the future (e.g., platform-specific workspace naming), the duplication would become a maintenance burden. For now, the shared header approach with macro hooks is the right tradeoff.

**Finding C-2: Code duplication in os.c — Linux and macOS share implementations for many functions.**

The Linux/macOS block (lines 93-338) has shared implementations for `tk_monotonic_nanos`, `tk_sleep_nanos`, `tk_write`, `tk_isatty`, `tk_fflush`, `tk_port_is_in_use`. Platform-specific differences (`tk_self_exe_path`, `tk_parent_pid`) use nested `#if FD_HAS_LINUX` / `#else` inside the shared block.

**Assessment: GOOD — the shared Linux/macOS block is correct and intentional.** Both platforms use POSIX `clock_gettime`/`nanosleep` with identical signatures, so sharing is appropriate.

## 7. Separation of Concerns

**Assessment: GOOD**

The architecture follows the tickoni.md separation diagram correctly:

- `src/tickoni/c_abi/shim/` owns C-level wrappers.
- `src/tickoni/util/os_api.zig` owns the Zig re-export layer.
- `src/app/tickoni/supervisor.zig` owns tile lifecycle orchestration (unchanged, consumes the new shims).
- No Tickoni product logic leaks into the shim layer.
- The `topo_run_platform_*.c` files operate on `fd_topo_t` and `fd_topo_tile_t` — Firedancer types — without adding Tickoni-specific fields.

**Finding S-1: wksp.c has no clear boundary between "existing Linux/macOS code" and "new Windows code."**

`wksp.c` uses `#if FD_HAS_LINUX || FD_HAS_MACOS` / `#elif FD_HAS_WINDOWS` to separate the two paths. Both paths contain nearly identical wrapper code (same function signatures, same `FD_LOG_INFO` logging, same pass-through to Firedancer functions). The Windows path is a copy of the Linux/macOS path with different includes.

**Decision: RESOLVED — correct separation.** The duplication is acceptable because both paths call the same Firedancer API; the shmem differences are handled upstream. The story's intent is to make Windows work identically to Linux/macOS through Firedancer's existing shmem abstraction.

**Finding B-2: wksp.c exports tk_* prefixed functions that wrap fd_wksp_* functions.**

This is correct — the `tk_*` prefix marks them as Tickoni-owned wrappers around Firedancer's `fd_wksp_*` API, consistent with the shim naming convention.

**Decision: RESOLVED — correct boundary.**

## 11. Unnecessary Complexity

**Assessment: LOW**

- No hidden abstractions or service-locator patterns.
- No dynamic dispatch or stringly-typed registries.
- No recursion in runtime code.
- Tagged unions used correctly for backend selection (no vtable-heavy interface structs).
- Global context (`g_ctx` in `tile_process.zig`) is justified by Firedancer's fixed callback signature and one-tile-per-process invariant.

**Finding X-1: tile_process.zig uses a module-level global g_ctx (line 51) to pass state between tk_tile_privileged_init and tk_tile_run.**

This is the only global mutable state in the story's scope. It is explicitly documented and justified:
1. Firedancer's `fd_topo_run_tile_t` callback signature takes `(*anyopaque, *anyopaque)` — no room for Zig closure state.
2. Tickoni runs exactly one tile per process, so a single global is safe.
3. It is set once at the bottom of `run()` before calling into the harness.

**Decision: RESOLVED — correct pattern.** This mirrors Firedancer's own pattern for callback state.
