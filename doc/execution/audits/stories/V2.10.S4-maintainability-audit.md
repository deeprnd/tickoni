# V2.10.S4 Maintainability Audit

**Story:** V2.10.S4 — `justfile` fully-qualified recipe names and dispatcher cleanup
**Audit date:** 2026-08-28
**Auditor:** Repository maintainability review
**Scope:** `justfile`, the qualified-recipe checker, platform detection used by
`just`, and the build/test scripts directly invoked by the S4 recipe surface.

## Verdict

**Acceptable with explicitly recorded follow-up debt.** No blocking
maintainability finding remains in the S4 implementation. The qualified recipe
grid is present, bare recipes are routers, aggregate recipes retain the required
bare-dispatcher boundary, native FD unit-test recipes do not fall back to
Tickoni tests, and the requested Linux-host validation passed.

The story remains `Backlog`; this audit does not change roadmap status or
acceptance checkboxes. macOS and Windows execution evidence requires those
hosts and is therefore handed to the platform CI/documentation follow-up.

## ISO/IEC 25010 assessment

### Modularity

**Pass.** Platform/compiler variants are independently addressable recipes.
Dispatch logic is isolated in the five bare router recipes rather than mixed
with build bodies. Quality and security aliases are separate from their
existing Linux/x86-only implementations. The repository-local grid checker
also tests the aggregate/qualified boundary.

### Reusability

**Pass with accepted duplication debt.** Existing shell build helpers remain
the reusable implementation units, and legacy recipe names delegate to
canonical names instead of duplicating command bodies. The five native FD unit
recipes repeat the final `run-unit-test` invocation because the platform build
step and Linux-only linker flag must remain visible in each qualified recipe.
This is readable and mechanically auditable, but not maximally DRY.

### Analysability

**Pass for the S4 surface.** Recipe comments identify canonical recipes,
compatibility aliases, Linux/x86-only quality/security scope, and the native FD
unit-test rule. `contrib/test/check-just-recipe-grid.sh` reports missing names,
aggregate direct-qualified calls, CET-flag placement, and accidental FD-to-TK
fallbacks.

### Modifiability

**Pass with documented follow-up debt.** Adding or changing a canonical recipe
has a single named target, and compatibility aliases point at it. The remaining
cross-cutting maintenance risks are the pre-existing duplicate setup detector
and callers/docs that still use legacy names. Both are assigned below rather
than silently changed in S4, because S1/S5 and S6/S7 own those boundaries.

### Testability

**Pass for available execution paths.** The recipe-grid checker provides a
fast deterministic contract test; Linux qualified Tickoni unit and integration
lanes execute successfully; the Linux native Firedancer C unit lane executes
successfully. Non-Linux recipes were statically/dry-run checked but not claimed
as executed from this Linux/x86 host.

## Findings and decisions

### MAINT-01 — Qualified Tickoni aliases share one portable implementation

- **Severity:** Low
- **Characteristics:** Modularity, reusability, analysability
- **Affected paths:** `justfile:161-172`, `justfile:313-321`,
  `justfile:358-365`
- **Finding:** The Linux ARM, macOS, and (for build/integration) Windows
  qualified targets delegate to the Linux/x86 Tickoni target. This is an
  intentional reuse of the platform-neutral Zig command, but the dependency
  shape can make a platform-specific recipe look less explicit when debugging
  or extending platform behavior.
- **Decision:** Accepted debt. No S4 behavior change is justified: the story
  requires equivalent Tickoni commands and reserves CI/documentation migration
  for later work. The existing Windows unit/integration targets remain explicit
  where their build preparation differs.
- **Owner:** S6 CI/platform lane owner
- **Follow-up:** During V2.10.S6, verify each qualified Tickoni target on its
  native runner and split only the targets whose native setup actually differs;
  retain shared dependencies where the command is genuinely portable.

### MAINT-02 — Native FD unit-test command repetition

- **Severity:** Low
- **Characteristics:** Reusability, modifiability
- **Affected paths:** `justfile:276-296`
- **Finding:** The five `test-unit-fd-*` recipes repeat the final GNU Make
  `run-unit-test` command. The repetition keeps the native C test contract
  visible and makes the Linux-only CET flag auditable, but changes to common
  test options require multiple edits.
- **Decision:** Accepted debt. Extracting a parameterized just recipe would
  add indirection to a small, platform-sensitive build boundary and could hide
  the exact non-Linux flag difference. The grid checker currently protects the
  important invariant.
- **Owner:** S7 build-tooling/documentation owner
- **Follow-up:** If a sixth native FD platform or another shared option is
  added, introduce one narrowly parameterized helper and extend the grid test
  in the same change; do not abstract this before that trigger.

### MAINT-03 — Duplicate setup platform detector - DONE, deleted contrib/setup/platform.sh.

- **Severity:** Medium, pre-existing/out of S4 scope
- **Characteristics:** Modifiability, analysability, dependency hygiene
- **Affected paths:** `contrib/platform.sh`, `contrib/setup/platform.sh`
- **Finding:** The setup path contains a second platform detector with different
  fallback behavior. This is a source-of-truth discrepancy documented in the
  S4 implementation plan, not introduced by the S4 `justfile` changes.
- **Decision:** Accepted debt for S4; no duplicate detector was added and the
  `justfile` uses the repository-root detector.
- **Owner:** S1/S5 setup owner
- **Follow-up:** Reconcile setup scripts to source or invoke
  `contrib/platform.sh`, then add a setup-lane regression test covering Linux,
  macOS, and native Windows architecture detection.

### MAINT-04 — Legacy recipe callers and documentation remain during handoff

- **Severity:** Low, intentional compatibility debt
- **Characteristics:** Analysability, modifiability, testability
- **Affected paths:** `.github/workflows/**`, `doc/execution/ci.md`,
  `doc/execution/development.md`, `doc/execution/testing-tickoni.md`, and
  compatibility aliases in `justfile:243-250`
- **Finding:** Some callers still use bare or legacy names. Removing them in S4
  would break the stated compatibility window and violate the story's explicit
  S6/S7 scope split.
- **Decision:** Accepted debt with explicit handoff. Compatibility aliases are
  thin delegations, not duplicate implementations, and the S4 checker verifies
  the canonical grid.
- **Owner:** S6 CI owner for workflows; S7 documentation owner for docs
- **Follow-up:** Migrate CI to qualified names in S6, update command examples in
  S7, then remove aliases only after repository-wide caller search and a
  deprecation decision.

### MAINT-05 — Non-Linux runtime coverage is unavailable on this host

- **Severity:** Low, environment-limited coverage gap
- **Characteristics:** Testability
- **Affected paths:** `justfile:282-296`,
  `justfile:319-321`, `justfile:363-365`,
  `justfile:383-411`
- **Finding:** The Linux/x86 host cannot execute native macOS or Windows
  recipes. Static checks and dry-runs validate recipe presence and command
  shape, but they cannot prove native build/link behavior.
- **Decision:** Accepted environment debt, not an S4 code defect. No platform
  pass is claimed below.
- **Owner:** S6 CI/platform lane owner
- **Follow-up:** Execute the qualified macOS and Windows lanes on their native
  runners and attach results to the S6/S7 evidence bundle. Preserve the
  documented macOS x86 vendor blocker if encountered.

## Negative checks and dead-code review

- No S4 recipe invokes `test-unit-tk` from a `test-unit-fd-*` target.
- `-Wl,-z,shstk` appears only in the Linux qualified FD unit recipe.
- The portable `cpu_count` value comes from `contrib/platform.sh`; the
  remaining `nproc` uses are in `build-fd-dev` and `test-e2e-fd`, outside the
  S4 qualified FD-unit contract.
- Compatibility aliases are intentional and reachable during the S6 migration
  window; they are not dead code.
- No new TODO/FIXME, dependency, public API, tile ownership, or storage-boundary
  issue was introduced by S4.
