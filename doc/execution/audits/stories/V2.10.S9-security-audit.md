### 2.2 Demo Env Fallback — STILL FALLS BACK, NOT FAIL-CLOSED

**File: `src/tickoni/test/demo/investment/mod.zig:190-198`**


**Analysis:** This function still falls back to a default value on env miss. This is intentional for **demo/test code** (not production runtime). ### 2.3 Test `getEnv` Helper — SAFE NULL-ON-MISS

**File: `src/tickoni/test/system/test_investment_demo_live.zig:6-17`**

```zig
fn getEnv(name: []const u8) ?[]const u8 {
    const env = std.c.environ;
    var count: usize = 0;
    while (env[count] != null) : (count += 1) {}
    for (env[0..count]) |entry| {
        const kv = std.mem.span(entry);
        if (std.mem.startsWith(u8, kv, name) and kv.len > name.len and kv[name.len] == '=') {
            return kv[name.len + 1 ..];
        }
    }
    return null;  // <-- returns null, not default
}
```

**Analysis:** Returns `?[]const u8` (optional). Callers use `orelse` to choose their behavior:

```zig
const model_id = (getEnv("TK_LLM_MODEL_ID") orelse demo.default_model_id);
```

This is the same pattern as the old code which used `envOrDefault` internally. The `orelse` gives the caller explicit control. No silent defaults.

**Verdict:** Safe. Return type is optional, caller controls fallback.

### 2.4 `TK_LIVE_TEST` Handling — SECURITY IMPROVEMENT

**Before (0.16):**
```zig
if (std.process.EnvInfo.init().get("TK_LIVE_TEST")) |v| {
    if (!std.mem.eql(u8, v, "1")) {
        if (v.len > 0) {
            std.debug.print("=== WARNING: TK_LIVE_TEST has unexpected value '{s}', staying in fixture mode ===\n", .{v});
        }
    } else {
        live_config.use_fixture = false;
    }
}
```

**After (0.17):**
```zig
if (getEnv("TK_LIVE_TEST")) |v| {
    if (std.mem.eql(u8, v, "1")) {
        live_config.use_fixture = false;
    }
}
```

**Analysis:** The old code had a **security concern**: if `TK_LIVE_TEST` was set to any non-"1" value (e.g., "0", "no", "false"), it would print a warning but **still stay in fixture mode** — which is fail-safe. The new code is simpler and more correct: it only enables live mode when the value is exactly "1". Anything else (including unset, empty, or wrong value) stays in fixture mode.

**Verdict:** **Improved** fail-closed behavior. The old code's warning path was dead-code (always safe), but the new code is cleaner and unambiguously fails safe.

## 3. New Unsafe Patterns Detected

### 3.1 REGRESSION: `fixture_events.zig:328` — Broken API Call

```zig
const file = try std.Io.Dir.createFileAbsolute(std.testing.io, path, .{ .truncate = true });
...
try file.writeAll(\\\\\ // Auto-generated...
```

**Problem:** In Zig 0.17, `std.Io.File` (the new I/O system) does not have a `writeAll` method. The old `std.fs.File` API had `writeAll(data)` as a direct method. The new `std.Io.File` requires using `std.Io.Writer.fixed(file)` or the writer pattern.

**Impact:** This is a **compile error**, not a security vulnerability. However, it means the fixture generation test (`gen audit fixture values`) cannot compile, which blocks the entire test suite from building under ReleaseSafe. This prevents the sanitize check from running its safety assertions.

**Root cause:** The Zig 0.17 stdlib I/O was completely rewritten from `std.fs` to `std.Io`. The `writeAll` method exists on `std.Io.Writer`, not on `std.Io.File` directly.

**Fix required:** Replace `file.writeAll(...)` with the writer pattern. See the fix applied in the companion file `test_investment_demo_live.zig:301-304` which uses `std.Io.Writer.fixed(&line_buf)` and `try file.writeAll(w.buffered())`.

### 3.2 POTENTIAL: `std.c.environ` Access — Global State

Multiple new helper functions (`getEnv`, `hasEnv`, `getEnvSlice`) access `std.c.environ` directly — the global C environment pointer array. This is necessary because Zig 0.17 removed `std.process.EnvInfo` and `getEnvVarOwned`, making `std.c.environ` the primary way to access the environment outside of `std.process.Init`.

**Analysis:** This is not a new pattern — the old code used `std.process.EnvInfo.init().get()` which also reads the same global state. The new helpers are more careful:
- They properly handle `?:null` terminator
- They check the '=' separator at the correct offset
- They handle `?[*:0]u8` entries (some entries in the C env array can be null on some systems)

**Verdict:** No regression in unsafe behavior. The new helpers are at least as correct as the old `EnvInfo` approach.

## 7. Conclusion

The Zig 0.17 migration **does not introduce any new security regressions in fail-closed behavior**. All environment variable access paths remain correctly null-on-miss, with callers controlling fallbacks. The `TK_LIVE_TEST` switch was actually improved (simpler, less error-prone). Audit hash chains, replay safety, and demo behavior are all preserved.

The only migration-regression finding is a **compile error** in `fixture_events.zig` caused by the Zig 0.17 stdlib I/O rewrite (`writeAll` removed from `std.Io.File`). This blocks the sanitize check but is not a security vulnerability — it is a straightforward API migration that needs the `writeAll` call to be rewritten using the new `std.Io.Writer` pattern.

The sanitize check cannot produce a safety-runtime verification result because of compile failures. This is a **pre-existing blocker** (fd_version) plus a **fixable regression** (writeAll). Neither is a security concern in the fail-closed behavior domain.
