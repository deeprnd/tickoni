The badge updater (`contrib/tool/readme/badge_updater.py`) reads GitHub Actions check-run status via REST API. This is a CI status probe, not a Tickoni runtime telemetry signal. It does not add or modify any metric, diagnostic, or operator signal in the Tickoni runtime.

The only Zig change in the branch is `src/app/tickoni_cli/cli.zig`, which modifies CLI argument parsing (`pos_start` assignment logic) and has no telemetry/diagnostic output.

No new diagnostic signal bypasses the Phase 0 snapshot pattern.

### TEL-02 — Low-cardinality label policy

**Status: PASS.**

S10 adds no metric labels, telemetry attributes, or operator dimensions. The ci.yml change introduces new **GitHub Actions job names** (`Project Build`, `Project Tests`, `Project Security`) as aggregated job names in the DAG. These are bounded, named job identifiers — not metric labels — and they are used exclusively for CI routing and badge resolution.

The badge_updater.py `AGGREGATED_JOBS` constant (`contrib/tool/readme/badge_updater.py:29-34`) is a whitelist of job names: `["Project Build", "Project Tests", "Project Security", "Tests / Coverage"]`. These are static string constants, not high-cardinality runtime labels. No S10-scoped path adds source event IDs, payment IDs, account IDs, case IDs, wallet or processor addresses, prompt text, raw model output, raw error messages, or stack traces to any telemetry surface.

The low-cardinality label policy in `doc/execution/telemetry.md:131-158` is therefore preserved.

### OBS-02 — Smoke-check coverage

**Status: PASS — unchanged.**

S10 does not modify the smoke-check command surface (`just test-unit-tk`, `zig build run -- start`, `just test-unit-fd`, `just test-all`). The new `tests-coverage.yml` workflow adds a standalone coverage validation path (weekly Monday + dispatch), but does not change or replace existing smoke checks. The coverage sub-workflow (`_ci-coverage.yml`) is gated behind the `unit` job, so unit-test smoke checks still run before coverage.

### OBS-03 — Failure propagation and visibility

**Status: PASS — improved.**

S10 improves failure visibility across the aggregated gate layer:

- The new `project-build`, `project-tests`, and `project-security` aggregate jobs all appear in `ci-required` with `always()` guards, so their pass/fail/skip status is always visible in the final `ci-required` output.
- The `ci-required` check iterates all 5 aggregates (`plan`, `quality`, `security-secrets`, `project-build`, `project-tests`, `project-security`) and reports `FAIL: <job>=<status>` for any failure. This is an improvement over the previous pattern where individual platform job names were listed.
- The `ci-required` job correctly handles the `core=false` (docs-only PR) case: it expects all 5 non-plan aggregates to be `skipped` and passes silently rather than failing.
- The new `coverage` lane runs in parallel with `integration`/`system`/`demo` and its result feeds into `project-tests`, so a coverage failure blocks the `project-tests` aggregate and is visible at that level.
- All new workflow files use bounded timeouts (`timeout-minutes: 10` for badge-update, `45` for standalone coverage, `30` for reusable coverage) to prevent hung workflows from blocking visibility.
- No new workflow adds `continue-on-error`.
- All sub-workflows use `strategy.fail-fast: false` (inherited from `_ci-build.yml` / `_ci-unit.yml` / `_ci-integration.yml` / `_ci-system.yml` / `_ci-demo.yml`), so a single platform failure does not hide failures on other platforms.

The existing Phase 0 crash-only behavior and `snapshotDiag()` reporting are outside the changed S10 scope and remain unchanged.
