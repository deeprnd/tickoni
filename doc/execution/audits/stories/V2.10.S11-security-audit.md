## Audit Findings by Category

### 1. Input Validation at Trust Boundaries

#### 1.1 `llama_cpp_download.py` — URL Resolution (FIXED)
**File:** `contrib/setup/install/strategies/llama_cpp_download.py`
**Fixed:** 2025-09-05 — `base_url` validation added in `story/qt-poc`

The `_resolve_from_config` method now validates `base_url` via `_validate_base_url()` which rejects empty/whitespace strings with `sys.exit(1)`. SHA256 enforcement added in `execute()` method (see Finding 7.3 below). Platform key format validation remains as future enhancement (no known risk vector).

**Status:** FIXED — base_url empty rejection now fail-closed. SHA256 enforcement moved to separate finding (7.3).

#### 1.2 `dynamic_test_opts.py` — Subprocess Output Parsing (FIXED — LOW)
**File:** `contrib/test/infra/dynamic_test_opts.py`
**Fixed:** 2025-09-05 — Minimum bounds added to `_detect_memory_bytes()`

Memory detection via `free -b` parses column 6 of `free` output. CPU detection via `nproc`/`sysctl`. No validation that parsed integers are reasonable (e.g., negative memory, zero cores).

**Risk:** Unlikely in practice since `free` and `nproc` output is well-defined, but no bounds check on parsed values.

**Recommendation:** Add minimum bounds (memory >= 1GB, cores >= 1) after parsing.

**Status:** FIXED — `MIN_MEMORY = 1_073_741_824` (1 GB) constant added; both `free -b` and `sysctl` return paths now reject values below 1 GB and fall through to the next method.

#### 1.3 `llama_server.py` — Server Binary and Model Path (FIXED — MEDIUM)
**File:** `contrib/test/infra/llama_server.py`
**Fixed:** 2025-09-05 — Path canonicalization with traversal guard added

The `start_server` function constructs `server_bin` and `model_path` from directory + filename, checks `os.path.isfile()`, then passes them to `subprocess.Popen`. No path traversal validation, no validation that the model file has expected size or format.

**Risk:** If `LLAMA_DIR` or `MODEL_DIR` env vars point to attacker-controlled paths (e.g., via a compromised CI config), an arbitrary binary could be executed. The model path is particularly sensitive — a symlink or crafted file could expose sensitive data.

**Recommendation:** Add path canonicalization and check that resolved paths are under the expected root. Consider validating model file size and extension.

**Status:** FIXED — `os.path.realpath()` used to resolve symlinks on both `server_bin` and `model_path`, then validated that resolved paths start with their respective root directories. Rejects symlinks that escape the expected directory.

#### 1.4 `llama_cpp_download.py` — Direct URL Override (MEDIUM CONCERN)
**File:** `contrib/setup/install/strategies/llama_cpp_download.py`
**Lines:** 73-76

```python
if params.get('download_url'):
    url = params['download_url']
    sha256 = params.get('sha256', sha256)
```

A `download_url` parameter bypasses all artifact resolution and config validation. Any caller can pass an arbitrary URL.

**Risk:** CI or local config could be manipulated to download from a malicious URL. SHA256 from params is used as fallback but is also unvalidated.

**Recommendation:** Add URL scheme validation (reject `file://`, validate `https://`). Require explicit opt-in for non-standard URLs.

#### 1.5 `run_unit_tests.sh` — Test Binary Path (LOW CONCERN)
**File:** `contrib/test/run_unit_tests.sh`
**Lines:** 24-30

The script reads test binaries from a file. Each line becomes `$test_bin` and is passed directly to `"$test_bin" --page-sz $PAGE_SZ -j $JOBS`. No validation of the test list file format beyond line reading.

**Risk:** A crafted test list could include unexpected paths. However, the test list is generated by the build system, not user input.

**Recommendation:** Add path prefix validation — all entries must resolve to a known build directory.

### 2. Output/Error Checking and Fail-Closed Behavior

#### 2.1 `llama_cpp_download.py` — Download Error Handling (PASS)
**Lines:** 62-69

Download uses `_download_and_verify` which checks for download failure, empty file, and SHA256 mismatch. All three cases call `sys.exit(1)` — fail-closed.

#### 2.2 `llama_cpp_download.py` — Extraction Verification (PASS)
**Lines:** 78-80

After extraction, verifies the server binary exists. Fails with `sys.exit(1)` if missing.

#### 2.3 `llama_server.py` — Health Check Timeout (PASS)
**Lines:** 68-92

Health check loop has a 60-iteration, 2-second-poll timeout (120s max). If the server dies prematurely, it's detected via `proc.poll()` and the function returns 1. If health never responds, the process is terminated. Fail-closed.

#### 2.4 `llama_server.py` — stop_server Error Handling (PASS)
**Lines:** 102-135

Handles missing PID file, `ProcessLookupError`, and general exceptions. All return 1 with stderr message.

#### 2.5 `dynamic_test_opts.py` — Subprocess Failure (MEDIUM CONCERN)
**Lines:** 22-50

Subprocess calls use `try/except` to catch `FileNotFoundError`, `ValueError`, `TimeoutExpired`. On failure, they fall through to the next detection method. The final fallback is `sys.exit(1)`.

**Issue:** The `FileNotFoundError` catch silently suppresses the error. If `free -b` is missing (not just the command but the data source), it falls through without logging. The `ValueError` catch on `int(parts[6])` similarly suppresses malformed output.

**Recommendation:** Add a `_debug` flag or log the failure reason at debug level before falling through.

#### 2.6 `run_unit_tests.sh` — Missing Test File (PASS)
**Lines:** 20-24

```bash
if [[ ! -f "$TESTS_FILE" ]]; then
  echo "No test list file..."
  echo "All 0 tests passed."
  exit 0
fi
```

Missing test list exits 0 with "0 tests passed." This is debatable — failing closed would suggest exit 1. However, this handles the case where no unit tests are registered (legitimate empty build), so exit 0 is acceptable.

#### 2.7 `run_unit_tests_dynamic.sh` — Resource Detection Failure (PASS)
**Lines:** 17-22

Memory detection: if all methods fail, exits 1 with error. Below 4 GB, exits 1 with error. This is fail-closed.

#### 3.4 `run_cli_demo_tests.sh` — Version Check Case Change (FIXED — LOW)
**File:** `contrib/test/run_cli_demo_tests.sh`
**Fixed:** 2025-09-05 — Reverted to case-sensitive comparison
**Line:** ~28

```diff
-assert text.lower().startswith('tickoni '), text
+assert text.startswith('Tickoni '), text
```

This changes from case-sensitive to case-insensitive version checking. If the version string is crafted to contain mixed case (e.g., `TiCkOnI`), the old code would reject it and the new code would accept it. The version comes from the binary itself, not external input, so this is low risk — but it does slightly weaken a validation check.

**Recommendation:** Document why this change is needed. If it's for a legitimate toolchain change, add a comment.

**Status:** FIXED — reverted to original case-sensitive check `text.startswith('Tickoni ')`.

### 4. Static and Preallocated Memory Discipline

#### 4.1 `run_unit_tests.sh` — Removed NUMA Scheduler (PASS)
The old runner had complex NUMA-aware scheduling with associative arrays, PID tracking, and page budgeting across NUMA nodes. The new version is a simple sequential loop. This eliminates the risk of NUMA page exhaustion bugs and simplifies reasoning about memory usage.

#### 4.2 `dynamic_test_opts.py` — Memory Calculation (PASS)
The dynamic calculation uses fixed constants:
- `page_sz_normal = 4096` (compile-time constant)
- `os_reserve_gb = 16` (compile-time constant)
- `overhead_mult = 8` (compile-time constant)
- `max_jobs = 6` (compile-time constant)
- `min_page_cnt = 65536` (compile-time constant)

The formula `page_cnt = safe_budget // (page_sz * max_j * overhead_mult)` is integer division — no floating-point drift. Result is clamped to `min_page_cnt` and rounded down to 1024-page boundary. No runtime-grown buffers.

#### 4.3 C Test Changes (PASS)
`test_wksp.c`: Default `--page-cnt` changed from 1 to 262144. This is a config-time constant in the test source. No runtime allocation changes.

`test_store.c`: Default `--page-cnt` changed from 1 to 10000. Same pattern.

## Overall Assessment

**RISK: LOW-MEDIUM**

This story is fundamentally a build/test infrastructure refactor with positive security implications:
- Removal of unreliable CI hacks (`prlimit`, `drop_caches`) that masked real failures
- Removal of 608-line Windows build script that was a large attack surface for build-time injection
- SHA256 verification for pre-built artifacts (where configured)
- Simplified test runner eliminates NUMA scheduling complexity and associated edge cases

The main concerns are configuration-driven: the download strategy trusts its config input without sufficient validation, and the direct URL override is an unbounded trust boundary. These are mitigated in practice because:
1. The tool-versions.json is a repo-internal file, not external input
2. CI pipelines don't use the `download_url` override parameter
3. The download happens in a temporary directory, not in a sensitive location
