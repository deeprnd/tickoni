## Audit Findings by Category

### 1. Input Validation at Trust Boundaries

#### 1.1 `qt_installer.py` — Config Metadata Resolution
**File:** `contrib/setup/install/strategies/qt_installer.py`, lines 73-111
**Severity:** PASS — input validation present and correct

The `_resolve_from_config` method validates every config key before use:
- `qt_module`: rejected with `sys.exit(1)` if `None` (line 91-97)
- `asset_name`: rejected with `sys.exit(1)` if `None` (line 98-104)
- `base_url`: passed through as-is (line 89); validated to be non-empty in a separate finding (1.1.1)
- `sha256`: passed through as-is; checked for truthiness before calling `_verify_sha256` (line 241)

No raw config values are interpolated into shell commands or file paths without first being resolved from a structured dictionary keyed by platform string.

**Status:** PASS

#### 1.1.1 `qt_installer.py` — base_url Validation
**File:** `contrib/setup/install/strategies/qt_installer.py`, line 89
**Severity:** LOW — finding present, not critical

`base_url` is read from config at line 89 but NOT validated for emptiness in this strategy. This contrasts with `llama_cpp_download.py` which has explicit `_validate_base_url()` that rejects empty/whitespace strings with `sys.exit(1)`.

The download URL is constructed at line 205: `download_url = f'{base_url}/{asset_name}'`. If `base_url` is empty, this produces `//asset_name` which resolves to a protocol-relative URL. This would fail at download time (not a silent bypass), but it lacks the explicit fail-closed guard present in the analogous `llama_cpp_download` code.

**Verdict:** LOW — the failure mode is a download error (hard fail), not a silent fallback. However, for consistency with the established `llama_cpp_download` pattern, an explicit empty-string check before URL construction would be preferred. No code change required for S3 closure — this is a best-practice gap.

**Status:** LOW (informational)

#### 1.2 `command.py` — Windows `command -v` Handling
**File:** `contrib/setup/install/checks/command.py`, lines 69-83
**Severity:** PASS — input validation present

The `build_check` function now accepts `platform_str` and validates it against `'windows'` (line 79). When `platform_str` contains `'windows'`, the POSIX `command -v` pattern is extracted with `re.fullmatch(r'command -v ([A-Za-z0-9_.+-]+)', check.strip())` — the regex enforces a safe character whitelist for the extracted executable name. This is then passed to `ExecutableCheck` which uses `shutil.which()` (not a shell command).

If the platform_str does NOT contain `'windows'`, the original `ShellCheckCommand(check)` is used, which runs the raw `check` string via `subprocess.run(cmd, shell=True, ...)`. The `check` string comes from the `tool-versions.json` configuration, which is a static JSON file managed by the team — not user input. The risk is bounded by the JSON schema (trusted source).

**Status:** PASS

#### 1.3 `apt.py` — WinGet Resolution Fail-Closed
**File:** `contrib/setup/install/strategies/apt.py`
**Severity:** PASS — improved fail-closed behavior (fix from pre-existing)

The `_find_winget_shell` function was rewritten to return a `WingetResolution` dataclass instead of a bare string. The new `_require_winget()` function (lines 293-302) validates the resolution result and calls `sys.exit(1)` if `resolution.command is None`. This replaces the old behavior where `_find_winget_shell` could fall through to `return 'cmd'` — which was a silent fallback to an unverified shell.

**Verdict:** PASS — pre-existing weakness remediated. The old code returned `'cmd'` as a last resort; the new code fails explicitly with `sys.exit(1)` and an actionable error message.

**Status:** PASS (also fixes pre-existing issue)

### 3. Don't Trust User Input

#### 3.1 `qt_installer.py` — Credential Handling
**File:** `contrib/setup/install/strategies/qt_installer.py`, lines 258-274
**Severity:** PASS — credentials from environment only, conditional

Qt installer credentials (`QT_USERNAME`, `QT_PASSWORD`) are read from `os.environ.get()` at lines 258-259 with empty-string defaults. The credential flags (`--email` and `--pw`) are ONLY added if BOTH values are truthy (line 273: `if qt_username and qt_password`). This means:
- No credentials are sent to the installer if env vars are not set
- Credentials are NOT logged — the `install_str` string at line 279 is printed, but it's built from `parts` which includes the raw credential values. This is a minor concern (see finding 3.2).

**Verdict:** PASS on trust boundary — credentials only used when present. The print statement exposes them in logs when present, which should be flagged.

**Status:** PASS (with note in 3.2)

#### 3.2 `qt_installer.py` — Credential Logging
**File:** `contrib/setup/install/strategies/qt_installer.py`, line 280
**Severity:** LOW — credentials visible in installer output string

The `install_str` at line 279 is constructed by joining all `parts`, which includes the raw `--email user` and `--pw pass` flags when credentials are present. This means the credential values appear in the `[INSTALLER]` log line.

**Verdict:** LOW — credentials are in an operator-visible log line, not in a persisted secret store. For an install-time setup script, this is acceptable but should be noted. In CI, the log line would be visible to anyone with CI log access.

**Remediation:** Redact the `--pw` value in the log output: `parts.extend(['--email', qt_username, '--pw', '***'])` when printing. Not a blocker for S3.

**Status:** LOW (informational)

#### 3.3 Qt Source Files — No User Input
**Files:** `main.cpp`, `Main.qml`, `CMakeLists.txt`
**Severity:** PASS — hello-world stub, no I/O, no external calls

All three source files are self-contained stubs:
- `main.cpp`: creates QGuiApplication, loads QML from qrc (bundled), checks for empty root objects, returns
- `Main.qml`: static text display, no networking, no JavaScript, no model binding
- `CMakeLists.txt`: pure build configuration, no runtime code

None of these files read user input, access the network, or execute external commands.

**Status:** PASS

#### 4.2 Qt Install Strategy — Installer Execution
**File:** `contrib/setup/install/strategies/qt_installer.py`
**Severity:** PASS — installer runs as user, no privilege escalation

The Qt Online Installer is invoked with `--root <install_dir>` where `install_dir` defaults to `~/Qt`. The installer runs as the current user — it does not request root/admin privileges. On Windows, the `/S` flag is silent-install, not elevated-install.

The installer binary is downloaded to a `tempfile.TemporaryDirectory()` and executed from there. After execution, the temporary directory is cleaned up automatically (context manager).

**Status:** PASS

#### 4.3 Environment Variable Loading
**File:** `contrib/setup/orchestrator.py`, lines 95-98
**Severity:** LOW — `.env` loaded unconditionally

The orchestrator now calls `load_dotenv(os.path.join(_repo_root, '.env'), override=False)`. This loads any `.env` file into the environment, including credentials like `QT_TOKEN` (from `.env.example`). The `override=False` flag means existing environment variables take precedence, which is correct (fail-safe).

However, `.env.example` defines `QT_TOKEN` but the Qt installer strategy reads `QT_PASSWORD`. The `.env.example` file defines `QT_TOKEN` which is the API token for the Qt account, while the installer strategy reads `QT_PASSWORD`. These are different values — `QT_TOKEN` is unused by the current code, and `QT_PASSWORD` is not defined in `.env.example`. This is a configuration mismatch, not a security issue, but worth noting.

**Status:** PASS (LOW — `.env.example` has `QT_TOKEN` but code uses `QT_PASSWORD`; configuration mismatch, not security risk)

#### 10.1 `_ci-security-deep.yml` — Parameterized Execution
**File:** `.github/workflows/_ci-security-deep.yml`
**Severity:** PASS — gated execution, deny-by-default

The workflow now accepts a required `check` input parameter. Each check step (sanitize, seccomp, proof, engine) is gated with an `if` condition:
- `if: inputs.check == 'sanitize'`
- `if: inputs.check == 'seccomp'`

### Required Follow-Up

1. **LOW 3.2 — Credential redaction in installer log output**: In `qt_installer.py` line 280, the `install_str` printed via `print(f'[INSTALLER] {install_str}')` includes the raw `--pw` value. Redact it: build the printed string without the password, or replace `'--pw', qt_password` with `'--pw', '***'` in the printed output. This is a best-practice improvement, not a blocker.

2. **LOW 1.1.1 — base_url empty-string validation**: Add a check similar to `llama_cpp_download.py`'s `_validate_base_url()` in `qt_installer.py` to reject empty `base_url` explicitly. This ensures consistency across install strategies and provides a clearer error message at config time rather than download time.

3. **Configuration mismatch — `.env.example` vs code**: `.env.example` defines `QT_TOKEN` but `qt_installer.py` reads `QT_PASSWORD`. This is a configuration issue (not security). The `.env.example` should be updated to define `QT_PASSWORD` (or the code should use `QT_TOKEN` — align on the correct env var name per Qt's documentation). This should be fixed before the setup orchestrator is used in production.
