# V2.10.S8 Maintainability Audit

**Story:** CI pipeline consolidation and cascading gate design
**Auditor:** V2.10.S8.T10 — Maintainability audit

## Executive Summary

This story consolidates 10 scattered GitHub Actions workflow files into a single `ci.yml` with a 6-stage cascading gate pipeline, replaces the entire contrib build/test/setup/toolchain directory tree with data-driven Python orchestrators and platform strategy modules, and restructures the `justfile` around fully-qualified recipe names. The consolidation is architecturally sound and the maintainability profile is generally strong: clear module boundaries, explicit strategy pattern usage, and data-driven configuration eliminate the prior shell-script duplication.

**Overall rating: PASS with 7 accepted debts (all low-severity).**

## 1. Modularity

### Assessment: STRONG

The story introduces a clean separation of concerns across new directories:

| Directory | Responsibility |
|---|---|
| `.github/workflows/` | Orchestration DAG (no build logic) |
| `.github/actions/` | Thin GitHub composite actions |
| `contrib/build/` | Build orchestration (Python + data-driven) |
| `contrib/build/strategies/` | Platform-specific build logic (Strategy pattern) |
| `contrib/setup/` | CI tool installation (Python + data-driven) |
| `contrib/test/` | Test orchestration and infra utilities |
| `contrib/quality/` | Quality/security linting scripts |
| `contrib/security/` | Security scanning scripts |

Each directory has a single entry point (`orchestrator.py`) with clear sub-modules. The Strategy pattern in `contrib/build/strategies/` is well-implemented: `linux.py`, `macos.py`, and `windows.py` each define the same interface (`resolve_make`, `resolve_cc`, `nproc`) with platform-appropriate implementations. The registry in `__init__.py` uses `importlib` — no stringly-typed dispatch.

**Finding:** HIGH — The `build/orchestrator.py` file is 444 lines. While functionally coherent, it handles config loading, make command construction, mode-specific cleanup, Windows-specific post-build steps, and dry-run logic. A future refactor to split `cmd_build_fd` into a separate `BuildExecutor` class would improve this, but the current size is acceptable for a build orchestrator.

**Finding:** MEDIUM — The `justfile` is now the primary interface surface (752 lines changed). It serves as both documentation and dispatch layer. This is intentional and documented in the story scope. No finding at this level.

**Finding:** LOW — Deleted files (221 deletions) included `contrib/zigw.sh`, `contrib/build.sh`, `contrib/fd-build-lib.sh`, `contrib/fd-build-windows.sh`, `contrib/fd-tk-libs.sh`, and `contrib/ci-run-build-tk.sh`. The audit confirms all callers were updated. No orphan references detected.

## 2. Reusability

### Assessment: STRONG

Key reuse patterns:

1. **Workflow sub-workflows:** `_ci-build.yml`, `_ci-unit.yml`, `_ci-integration.yml`, `_ci-system.yml`, `_ci-demo.yml`, `_ci-quality.yml`, `_ci-security-deep.yml`, `_ci-conformance.yml` are reusable via `workflow_call`. Each is a self-contained matrix that downloads artifacts from upstream stages rather than rebuilding. This eliminates the prior duplication where each workflow re-instantiated setup, deps, and build steps.

2. **Build strategy interface:** The `contrib/build/strategies/` modules expose a unified interface per platform. Adding a new platform requires only a new module implementing `resolve_make`, `resolve_cc`, `resolve_ar`, and `nproc`.

3. **Setup orchestrator:** `contrib/setup/orchestrator.py` resolves category dependencies from JSON data, then dispatches to strategy modules. Adding a new install method requires only a new module in `contrib/setup/install/strategies/` — no changes to the orchestrator.

4. **Test orchestrator:** `contrib/test/orchestrator.py` uses the same facade pattern, routing to `llama_server.py`, `zig_build.py`, and `dynamic_test_opts.py`.

5. **Matrix data in YAML:** Platform configurations are encoded as matrix entries in YAML rather than duplicated `run:` blocks. Each entry is ~5-7 lines of declarative data. The `_ci-build.yml` sub-workflow has 9 matrix entries (98 lines total) versus the prior pattern of ~200 lines per platform in separate workflow files.

**Finding:** LOW — The `_ci-unit.yml`, `_ci-integration.yml`, `_ci-system.yml`, and `_ci-demo.yml` sub-workflows share identical step structure (checkout → install just → setup toolchain → setup fd deps → build fd libs → run tests). The only variance is `test-recipe` and `build-recipe`. This could be further unified by passing these as inputs to a generic `test-stage.yml`, but the current duplication is bounded (4 files × 7 steps = 28 steps) and the recipe names are explicit — a future optimization, not a current debt.

**Finding:** LOW — `contrib/test/infra/` has an `__init__.py` with only `contrib = 1 +` (a single blank line and stray text). This is harmless but should be cleaned up.

## 3. Analysability

### Assessment: STRONG

1. **Change detection action:** `plan-ci/action.yml` uses a fail-open policy — any unknown file triggers `core=true`, preventing silent CI skips. The safe-skip set (README.md, LICENSE, docs/*, book/*) is explicit and auditable. The action is self-contained with no external dependencies.

2. **Required aggregation job:** The `ci-required` job in `ci.yml` explicitly iterates over all 11 jobs and checks their results. This makes the pipeline status machine-readable and human-readable. The `docs-only PR` branch correctly calculates expected skipped count.

3. **Build orchestrator logging:** The orchestrator prints `[+]` prefixed status lines at each phase boundary (config loaded, strategy loaded, tool resolved, make command built, build started, build complete). This makes CI logs traceable to specific phases.

4. **Setup orchestrator logging:** Similarly prints `[INSTALL]`, `[DRY-RUN]`, `[COMPLETE]` prefixed lines.

5. **Strategy module isolation:** Platform-specific logic is isolated. If Linux builds fail, you inspect `contrib/build/strategies/linux.py` and `contrib/build/strategies/__init__.py` — you don't need to scan macOS or Windows code.

**Finding:** LOW — The `ci.yml` `ci-required` job uses a `case` statement with 11 `needs.<job>.result` expressions. This is verbose but explicit. No finding — it's the correct tradeoff for CI aggregation.

## 4. Modifiability

### Assessment: STRONG

1. **Adding a platform:** Requires changes to exactly 4 files:
   - `contrib/build/strategies/<platform>.py` (new module)
   - `contrib/build/strategies/__init__.py` (add case branch)
   - `contrib/build/build-config.json` (add platform entry)
   - Each sub-workflow YAML file (add matrix entry)

2. **Adding a tool to setup:** Requires changes to exactly 1 file:
   - `contrib/setup/tool-versions.json` (add tool entry + category membership)
   - Optionally: `contrib/setup/install/strategies/<method>.py` (new install method)

3. **Adding a test stage:** Requires changes to exactly 2 files:
   - `contrib/test/orchestrator.py` (add command + parser entry)
   - `contrib/test/infra/<stage>.py` (implement stage logic)
   - Plus: a new `_ci-<stage>.yml` sub-workflow + `ci.yml` job definition

4. **Deleting a tool:** Simply remove from JSON. The orchestrator won't attempt install. No shell function to update.

**Finding:** MEDIUM — The `justfile` has many platform-qualified aliases (e.g., `quality-format-check-fd-linux-x86`, `security-gitleaks-check-fd-linux-x86`). These are explicitly requested in the story scope ("fully-qualified recipe names") and serve as the interface for CI sub-workflows. The pattern is consistent but adds lines. No remediation needed — this is intentional design.

**Finding:** LOW — The sub-workflow YAML files have `# Reusable <X> workflow:` header comments but no cross-reference to their consumer jobs. The `ci.yml` comments reference `doc/execution/plans/v2.10-s8-5.md` for build/unit/quality. Other sub-workflows lack these references. Add `# Reference: doc/execution/plans/v2.10-s8-5.md` (or appropriate plan file) to each sub-workflow header.

## 6. Cohesion and Coupling

### Assessment: STRONG

**High cohesion:**
- `contrib/build/orchestrator.py`: single responsibility (build orchestration)
- `contrib/build/strategies/linux.py`: single responsibility (Linux build tool resolution)
- `contrib/setup/orchestrator.py`: single responsibility (tool installation orchestration)
- `contrib/setup/install/strategies/apt.py`: single responsibility (apt install method)
- Sub-workflow YAML files: single responsibility (one test/build stage each)

**Low coupling:**
- Sub-workflows communicate only via `workflow_call` inputs/outputs and GitHub artifacts
- Python orchestrators communicate only via CLI args and exit codes
- Strategy modules communicate only through the `load()` factory function
- No cross-imports between platform strategies
- No circular dependencies in the setup orchestrator (dependency graph is acyclic)

**Finding: LOW — The `contrib/build/orchestrator.py` uses `importlib.import_module(".strategies.windows", "contrib.build")` inside `cmd_build_fd` and `_write_manifests`. The `__import__("contrib.build.strategies", fromlist=["load"])` call in `main()` and `cmd_build_fd` is a different import pattern. For consistency, use `importlib.import_module` or `from contrib.build.strategies import load` everywhere. This is a style finding, not a functional issue.**

## 8. API and Ownership Boundaries

### Assessment: STRONG

1. **just recipe names are the public API:** All CI workflows invoke `just <fully-qualified-recipe>`. The recipes are the contract between CI and local development. The story scope explicitly requires this.

2. **orchestrator.py CLI is the public API:** `contrib/build/orchestrator.py` exposes `build-fd`, `build-tk`, `nproc`, and `make` subcommands. Each has documented args. No internal functions are referenced from CI.

3. **Strategy modules are internal:** `contrib/build/strategies/linux.py` functions are called only via the `load()` factory in `__init__.py`. No CI workflow or justfile references them directly.

4. **Build config JSON is the data contract:** `contrib/build/build-config.json` defines targets, source sets, exclude patterns, and libs. The orchestrator reads it at runtime. Adding a source dir requires editing exactly one file.

**Finding: LOW — The `contrib/build/orchestrator.py` has `sys.path.insert(0, ROOT_DIR)` which adds the repo root to the import path. This is necessary for `import contrib.build.strategies` to work from any working directory, but it means relative imports could accidentally pick up non-contrib modules if the repo root contains a conflicting package. This is a minor risk and not actionable without broader restructuring.**
