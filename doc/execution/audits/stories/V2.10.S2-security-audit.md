## 2. Code Review Findings

### 2.1 Input Validation at Trust Boundaries

**CRITICAL FINDING: `build.zig:21` — unvalidated `fd_lib_dir` option**
```zig
const fd_lib_dir = b.option([]const u8, "fd-lib-dir", "Firedancer lib dir (default: build/fd-tickoni-fd/lib)") orelse "build/fd-tickoni-fd/lib";
```
- The `fd_lib_dir` is used directly in string formatting for file paths without any validation
- Paths are passed to `b.path()`, `b.fmt()`, and `cwd_relative` without checking for path traversal (`..`), empty strings, or excessively long paths
- A malicious value like `../../../../../../etc` would be passed through to `addObjectFile` and `addLibraryPath` calls
- **Risk:** Path traversal leading to linking arbitrary archives
- **Severity:** LOW-MEDIUM (build-time only, not runtime; requires build system access to exploit)
- **Remediation:** Add a validation function that rejects `..` components, empty strings, and paths exceeding a reasonable length (e.g., 1024 chars)

**MINOR FINDING: `modules.zig:107-125` — unvalidated `version` option**
```zig
const build_version_option = b.option([]const u8, "version", "Build version string") orelse "0.1.0";
```
- Version string is parsed with `catch 0` fallback — silently accepts malformed versions
- No length validation on `bv_pre` (pre-release tag)
- **Risk:** Information disclosure via embedded version strings, potential injection in downstream consumers
- **Severity:** LOW (cosmetic, but `catch 0` masks parse failures silently)

**MINOR FINDING: `lane.zig:17-18` — `catch unreachable` on path construction**
```zig
const build_root_str = b.root.toString(b.allocator) catch unreachable;
const full_script_path = std.fmt.bufPrint(...) catch unreachable;
```
- `catch unreachable` discards path construction errors
- Per security.md: "Do not discard a Zig error union with `catch unreachable` unless the unreachable state is actually provable"
- **Risk:** A panic on unusual build configurations masks root cause
- **Severity:** LOW (build-time panic, not exploitable)

### 2.2 Output and Error Checking

**MINOR FINDING: `factory.zig:55` — `catch unreachable` on allocator**
```zig
const imports = b.allocator.alloc(std.Build.Module.Import, 15) catch unreachable;
```
- Per security.md: allocator calls should be checked; `catch unreachable` is only acceptable for provably unreachable states
- Memory exhaustion in build-time is possible (though unlikely with 15 slots)
- **Severity:** LOW

**MINOR FINDING: `codec.zig:120` — `@panic` on missing manifest**
```zig
) catch @panic("missing Windows FD Zig link manifest; run just build-fd first");
```
- Uses `@panic` instead of returning an error — build-time crash with opaque message
- **Severity:** LOW (build-time only)

### 2.3 Fail-Closed Behavior

**PASS — Build system uses explicit linkage flags (`TestLinkage`)**
- `TestLinkage` is a `packed struct(u8)` with all bools defaulting to `false` — deny-by-default linkage
- Tests must explicitly declare which libraries they need (codec, firedancer, topo_run, tile_run, libc)
- No test can accidentally pull in dependencies through implicit transitive imports in the spec layer

**PASS — Module factory is explicit**
- `ModuleFactory.createIntModules()` creates modules in strict dependency order
- Each module's imports are explicitly listed — no wildcard or catch-all imports
- Missing a required import in the spec means the build fails (compile error), not a silent runtime failure

### 2.4 No-Bypass Paths

**PASS — No direct agent/tool/adapter access**
- The build system only compiles test binaries and the supervisor executable
- No network access, no filesystem writes beyond build artifacts, no privilege escalation
- `addPlainTestRun` uses `run_test_series.sh` which is a pre-existing, reviewed script

**MINOR FINDING: `helpers.zig:136-145` — shell command construction**
```zig
const c_check = b.addSystemCommand(&.{
    "sh", "-c",
    b.fmt("zig cc -target {s} -c -I src -std=c17 -UBMI2 -ULZCNT -DFD_HAS_HOSTED=1 {s} -o {s}/{s}.o {s} 2>&1 || true", .{
        shims.buildTriple(b, target),
        shims.shimCFlagsFor(target.result)[0],
        cache_o_dir,
        shim_file,
        b.fmt("src/tickoni/c_abi/shim/{s}", .{shim_file}),
    }),
});
```
- Shell command construction uses `b.fmt()` interpolation — values are comptime constants or derived from `target`, not user input
- `shim_file` comes from the trusted `shims.shim_c_files` array
- **Severity:** LOW (trusted inputs, but pattern is worth noting for future contributors)

### 2.5 Static, Preallocated Memory (Critical-Systems Discipline)

**PASS — Build-time only, no hot-path concerns**
- `build-lib/` code runs exclusively during `zig build` (compile time), not during tile execution
- No runtime event processing, no per-event allocations, no hot-path memory concerns
- Scratch/workspace/stack discipline from security.md applies to tile runtime code, not build scripts

**MINOR FINDING: `integration.zig:55` — runtime allocator in build step**
```zig
const imports = b.allocator.alloc(std.Build.Module.Import, 15) catch unreachable;
defer b.allocator.free(imports);
```
- Uses heap allocator during build time (acceptable for build scripts)
- Pattern is correct: allocated → used → freed with defer
- **Severity:** LOW (build-time only, pattern is sound)

### 2.6 C/Zig Memory and Stack Safety

**PASS — No unsafe casts or pointer operations**
- No `@ptrCast`, `@alignCast`, `@intCast`, or `@truncate` on external inputs in `build-lib/`
- `std.Build.Module.Import` pointers are created by Zig's build system and type-checked
- C shim compilation uses `b.addCSourceFiles()` which handles the ABI correctly

**PASS — `TestLinkage` uses `packed struct` with padding**
```zig
pub const TestLinkage = packed struct(u8) {
    needs_codec: bool = false,
    needs_firedancer: bool = false,
    needs_topo_run: bool = false,
    needs_tile_run: bool = false,
    needs_libc: bool = false,
    _pad: u3 = 0,
};
```
- Explicit padding field, no undefined bits
- All fields default to `false` (deny-by-default)

### 2.7 Agent Capability Boundaries

**N/A — Build system does not implement agent capabilities**
- `build-lib/` is a build configuration system, not a runtime agent harness
- No agent identity, capability enforcement, or policy decisions in build code
- The compiled test binaries are runtime artifacts — their security properties are assessed separately

### 2.8 Deny-By-Default Policy

**PASS — Explicit capability declarations**
- `TestLinkage` defaults all flags to `false`
- `TestSpec` defaults `imports` to `&.{}` and `action` to `.cov` (explicit defaults)
- Module imports are explicit per-module lists — no wildcard matching

### 2.9 No Elevated Permissions

**PASS — Build scripts run as the invoking user**
- No privilege escalation, no root access, no seccomp changes
- `addPlainTestRun` delegates to a pre-existing bash script
- File writes are limited to `zig-out/`, `build/`, and `.zig-cache/` (standard Zig output locations)

### Findings Requiring Remediation

1. **`fd_lib_dir` path validation** (LOW-MEDIUM): Add validation before use in path construction
2. **`catch unreachable` on allocator** (LOW): Replace with proper error handling or document why exhaustion is impossible

### Overall Assessment

**PASS — No blocking security issues.** The build.zig modularization is a build-time refactor with no runtime security impact. The extracted code does not introduce new attack surfaces: no network access, no privilege escalation, no agent capability changes. The only meaningful finding is the unvalidated `fd_lib_dir` CLI option, which is a build-time concern that could allow path traversal if a malicious actor has access to the build environment. All scanner checks (gitleaks, CodeQL, seccomp, proof, sanitize) pass.
