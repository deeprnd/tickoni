**SEC-03 (Medium):** `badge_updater.py` accepts a raw SHA string from the CLI (`argparse sha`) with no format validation. In CI, this comes from `github.event.workflow_run.head_sha` which is always a valid 40-char hex SHA. However, the `--reset` flag and the `args.sha` parameter are available from local CLI without validation. An attacker who can run the script locally with a crafted SHA (e.g., containing shell metacharacters) could inject into the API URL or git commands.

**Remediation:** Add SHA format validation (`if not re.match(r'^[0-9a-f]{40}$', sha): raise ValueError(...)`). **DONE — 2026-09-07.** Added `re.match(r'^[0-9a-f]{40}$')` validation in `main()` that rejects non-40-char-hex SHAs with a clear error message and `sys.exit(1)`.

## S10-Specific Security Findings

### SEC-01 (Medium) — `badge_updater.py` git push without pre-check

**Location:** `badge_updater.py` lines 343-363

**Issue:** `git_commit_and_push()` performs an unconditional `git push origin main` after modifying `README.md`. If the script encounters a merge conflict on push (another workflow or bot also pushing to main), `subprocess.run(..., check=True)` raises `CalledProcessError` and the workflow fails. However, there is no pre-push check (e.g., `git fetch origin main` + compare) to detect if the remote is ahead of local before attempting the push.

**Risk:** Low in CI context (GitHub Actions checkout is fresh), but the error message from `git push` could leak to CI logs. The push is authenticated with the same `GITHUB_TOKEN` used for API reads, so a compromised token could rewrite README history.

**Remediation:** Add `git fetch origin main` before the push and verify the local branch is not behind. If behind, skip the push and log a warning.

**DONE — 2026-09-07.** `git_commit_and_push()` now runs `git fetch origin main` before push, then `git rev-list --left-right --count HEAD...origin/main` to compare. If remote is behind, the push is skipped with a warning.

### SEC-02 (Medium) — `badge_updater.py` path traversal risk in `get_blob_content`

**Location:** `badge_updater.py` lines 77-92

**Issue:** The `get_blob_content()` function accepts a `path` parameter that is used directly in the GitHub API URL (`f"{url}?ref={sha}"`). While the path is not interpolated into the URL (it's used as a query parameter), the GitHub API's `contents/{path}` endpoint could theoretically be used to read arbitrary files from the repository if an attacker controls the `path` argument.

**Risk:** Low — the path argument comes from internal function calls (parent-commit walk uses fixed paths) or from CLI (not used for file reading). No user-controlled path reaches this function. However, the function signature doesn't restrict the path to the README, which is a latent risk.

**Remediation:** Add path validation to restrict reads to `README.md` only (or add an allowlist of valid paths).

**DONE — 2026-09-07.** `get_blob_content()` now validates path against `ALLOWED_PATHS = {"README.md"}` and raises `ValueError` for any disallowed path.

### SEC-03 (Medium) — No SHA format validation (see Trust-Boundary Review above)

**Remediation:** Add `re.match(r'^[0-9a-f]{40}$', sha)` validation at the entry point in `main()`.

**DONE — 2026-09-07.** See Trust-Boundary Review above.

### SEC-04 (Low) — Broad exception swallowing in API helpers

**Remediation:** Replace `except Exception` with `except (urllib.error.URLError, json.JSONDecodeError, OSError, ValueError):` to let `KeyboardInterrupt` and `SystemExit` propagate.

**DONE — 2026-09-07.** See Output and Error Checking table above.

### SEC-05 (Low) — No rate-limit handling for GitHub API

**Location:** `badge_updater.py` lines 48-92

**Issue:** The parent-commit walk can make up to 100 API calls (50 parents × 2 calls per parent: check-runs + commit info). At 60 requests/minute (unauthenticated) or 5,000 requests/minute (authenticated with `GITHUB_TOKEN`), this is well within limits. However, there is no retry logic for HTTP 429 (rate limit) or 5xx responses. A transient rate limit would silently skip that parent commit, potentially causing the walk to miss the last successful merge and default to unknown badges.

**Risk:** Low — the walk limit is 50 parents, and with 5,000 requests/minute auth, rate limiting is unlikely. But a transient 429 would cause silent degradation.

**Remediation:** Add retry-with-backoff for transient HTTP errors (429, 500, 502, 503, 504).

**DONE — 2026-09-07.** `_api_request` now includes HTTP 429 in its retry list, reads the `Retry-After` header when present, and prints rate-limit warnings.
